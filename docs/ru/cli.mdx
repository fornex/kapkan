# Справочник CLI

Kapkan — это единый бинарник. Всё, что он делает, выбирается флагами командной строки при запуске,
плюс есть небольшое число **команд**, которые осматривают работающую систему и завершаются. Все
логи идут в **stderr**; REST API и метрики Prometheus отдаются по HTTP на `api.listen` (по
умолчанию `127.0.0.1:8080`), а служебные флаги (`-version`, `-dump-schema`, `-dump-zones-schema`) и
команды печатают свой вывод в **stdout**.

```sh
kapkan [flags]                     # run the daemon
kapkan [flags] <command> [args]    # run a command and exit
```

Глобальные флаги идут **до** команды; собственные флаги команды — после неё. Так,
`kapkan -config /etc/kapkan/config.yaml dataplane status -json` берёт путь к конфигурации из
глобального `-config` и передаёт `-json` команде `dataplane status`. Флаг, который сам по себе
завершает работу (`-version`, `-check-config`, `-dump-schema`, `-dump-zones-schema`, `-check-update`,
`-s`), нельзя сочетать с командой — Kapkan отвергает такое сочетание, а не выполняет молча что-то
одно.

## Флаги

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `-config <path>` | `configs/dev.yaml` | Путь к YAML-[файлу конфигурации](/docs/configuration). |
| `-log-format <fmt>` | `json` | Формат вывода логов: `json` (структурированный, для сборщиков логов) или `text` (читаемый, для локальных запусков). Любое значение, кроме `text`, трактуется как `json`. |
| `-log-level <lvl>` | `info` | Минимальный уровень логов: `debug`, `info`, `warn`, `error`. Нераспознанное значение откатывается к `info`. |
| `-check-config <path>` | — | Проверить файл конфигурации по пути `<path>` и завершиться — демон **не** запускается. См. [ниже](#проверка-конфигурации). |
| `-dump-schema` | `false` | Напечатать JSON-схему конфигурации в stdout и завершиться. См. [ниже](#вывод-схемы). |
| `-dump-zones-schema` | `false` | Напечатать JSON-схему [файла зон](/docs/zones), который мозг отдаёт граничным узлам (`edge.zones_file`), в stdout и завершиться. |
| `-version` | `false` | Напечатать версию сборки и завершиться. Та же версия доступна во время работы через `/api/v1/status` и [метрику](/docs/metrics) `kapkan_build_info`. |
| `-check-update` | `false` | Однократно выполнить опциональную [проверку обновлений](/docs/configuration) и завершиться — `0`, если версия актуальна, `10`, если доступно обновление, `1` при ошибке. Опрашивает GitHub Releases API; отправляет только сам запрос, никогда — идентичность узла или конфигурацию. |
| `-pid-file <path>` | `/run/kapkan/kapkan.pid` | Куда демон записывает свой идентификатор процесса при запуске (удаляется при корректном завершении); читается `-s`, чтобы найти работающий демон. Сбой записи не фатален — демон всё равно работает, недоступен только `-s`. |
| `-s <signal>` | — | Послать сигнал работающему демону и завершиться, прочитав `-pid-file`: `reload`, `stop` или `quit`. Демон при этом **не** запускается. См. [ниже](#управление-работающим-демоном). |

<Callout type="info" title="json или text?">
Используйте `-log-format text` для локальной разработки — это формат, который применяет
[Быстрый старт](/docs/quickstart). В промышленной среде оставляйте `json` по умолчанию, чтобы сборщик логов
мог разбирать структурированные поля; [systemd-юнит](/docs/deployment) поставляется с
`-log-format json -log-level info`.
</Callout>

## Запуск демона

Без служебного флага Kapkan открывает свои приёмники потоков, REST API и (когда не в режиме dry-run) BGP-спикер,
затем работает, пока не получит `SIGINT` или `SIGTERM`, после чего корректно завершается. Он завершается с
ненулевым кодом только при фатальной ошибке запуска или выполнения.

```sh
# Local, human-readable logs against the bundled dev config:
kapkan -config configs/dev.yaml -log-format text

# Production-style: structured logs at info level:
kapkan -config /etc/kapkan/config.yaml -log-format json -log-level info
```

Файл конфигурации можно перечитывать во время работы без перезапуска — выполните [`kapkan -s reload`](#управление-работающим-демоном),
отправьте `SIGHUP` напрямую (`systemctl reload kapkan`) или сделайте `POST /api/v1/config/reload`. См.
[справочник конфигурации](/docs/configuration), чтобы узнать, что перечитывается, а что фиксируется при запуске.

## Управление работающим демоном

```sh
kapkan -s reload    # re-read the config file (SIGHUP)
kapkan -s stop      # graceful shutdown (SIGTERM)
kapkan -s quit      # alias of stop
```

`-s` читает идентификатор процесса из `-pid-file` (по умолчанию `/run/kapkan/kapkan.pid`, записывается
демоном при запуске) и доставляет соответствующий сигнал этому процессу — то же локальное управление в стиле
nginx, что и `nginx -s reload`. Ему не нужны ни сетевое соединение, ни API-токен, поэтому он работает даже
если REST API недоступен; ему нужно право слать сигнал демону, так что запускайте его от `root` или
пользователя `kapkan`.

| Значение `-s` | Сигнал | Эффект |
| --- | --- | --- |
| `reload` | `SIGHUP` | Горячая перезагрузка файла конфигурации. То же, что `systemctl reload kapkan` или `POST /api/v1/config/reload`. |
| `stop` / `quit` | `SIGTERM` | Корректное завершение. То же, что `systemctl stop kapkan`. Эти два — псевдонимы: завершение Kapkan всегда корректное (он просит BGP-пиров сохранить маршруты подавления атак через [Graceful Restart](/docs/mitigation)). |

Если pid-файл отсутствует или устарел (нет такого процесса) либо у вас нет прав послать сигнал, `-s`
печатает причину в stderr и завершается с кодом `1`.

<Callout type="info" title="Где находится pid-файл">
Поставляемый [systemd-юнит](/docs/deployment) задаёт `RuntimeDirectory=kapkan`, так что `/run/kapkan`
существует и доступен для записи пользователю `kapkan`; демон записывает туда `/run/kapkan/kapkan.pid` и
удаляет его при корректной остановке. В локальном dev-запуске этого каталога может не быть — демон печатает
предупреждение и продолжает работу, а `-s` сообщит «no pid file». Передайте `-pid-file /tmp/kapkan.pid` и
демону, и `-s`, если хотите воспользоваться этим сокращением локально.
</Callout>

## Служебные флаги

Эти флаги завершаются до запуска демона — они никогда не открывают приёмник и не отправляют
анонс маршрута, поэтому их безопасно запускать на промышленном хосте. (`-check-update` делает один
исходящий запрос к releases API; остальные полностью офлайн.)

### Проверка конфигурации

```sh
kapkan -check-config /etc/kapkan/config.yaml
```

Выполняет ровно тот же разбор и проверку, что и движок, — включая кросс-полевые правила, которые
статическая схема выразить не может, — затем печатает разрешённую конфигурацию (режим, защищаемые сети,
настроенные приёмники потоков, число групп и эффективное подавление атак по каждой
[hostgroup](/docs/hostgroups)) и завершается:

| Код выхода | Значение |
| --- | --- |
| `0` | Конфигурация корректна. |
| `1` | Конфигурация некорректна; точная ошибка печатается в stderr. |

Чёткое разделение 0/1 без проблем встраивается в CI или предрелизную проверку. См.
[Проверку конфигурации](/docs/configuration#проверка-конфигурации).

Корректная конфигурация всё же может напечатать блок `WARNING` после строки `OK` — это допустимая
конфигурация, которую демон выполнит, но почти наверняка не то, что вы имели в виду. Сегодня такой
случай один: [статическое правило, которое никогда не
сработает](/docs/dataplane-tuning#правила-которые-никогда-не-сработают), с именем правила и тем, что
забирает его пакеты. Код выхода остаётся `0`, поэтому существующая проверка не затрагивается; если
вы хотите, чтобы предупреждения тоже роняли сборку, проверяйте вывод на `WARNING` вдобавок к коду.

### Вывод схемы

```sh
kapkan -dump-schema
```

Печатает JSON-схему конфигурации в stdout и завершается с кодом `0` (или `1` при внутренней ошибке).
[Конструктор конфигурации](/config) использует эту схему, чтобы проверять поля прямо в вашем браузере.

```sh
kapkan -dump-zones-schema
```

То же для [файла зон](/docs/zones), который мозг отдаёт граничным узлам (`edge.zones_file`): его
JSON-схема, с перечислениями и границами словаря зон, для вашего редактора или инструментов
арендатора.

### Вывод версии

```sh
kapkan -version
```

Печатает версию сборки (тег релиза плюс короткую VCS-ревизию, когда она известна) в stdout и завершается.
Та же строка отдаётся во время работы на `/api/v1/status` и переносится [метрикой](/docs/metrics) `kapkan_build_info` —
так что вы можете подтвердить версию бинарника локально без какого-либо исходящего трафика.

### Проверка обновлений

```sh
kapkan -check-update
```

Однократно по требованию выполняет [`update_check`](/docs/configuration) и завершается: `0`, если версия актуальна, `10`,
если доступен более новый релиз, `1` при ошибке. Запрашивает GitHub Releases API и отправляет только сам
запрос (ваш IP и обобщённый User-Agent) — никогда идентичность узла, конфигурацию или данные об
атаках. Периодическая проверка внутри процесса **выключена по умолчанию**; этот флаг работает независимо от
этой настройки.

## Команды

### `dataplane status`

```sh
kapkan dataplane status              # human-readable report
kapkan dataplane status -json        # the same inspection as JSON
```

Сообщает, действительно ли плоскость данных XDP фильтрует трафик, а если нет — почему. Два
свойства делают эту команду пригодной прямо во время инцидента:

- **Она строго только для чтения.** Она открывает закреплённые программу и карты в режиме только
  для чтения — файловые дескрипторы карт несут `BPF_F_RDONLY`, поэтому запись через них отвергает
  само *ядро*, — и она никогда не загружает программу, не создаёт карту, не пишет значение в карту,
  не подключается, не отключается и не удаляет закрепление. Запуск демона перенимает или
  пересобирает набор закреплений; эта команда так не умеет, поэтому она никогда не будет стоить вам
  тех правил подавления, которые вы пытаетесь диагностировать.
- **Она работает при остановленном демоне.** Это основной случай, а не приятный бонус: при значении
  по умолчанию `dataplane.on_exit: keep` ядро продолжает применять статическую политику вообще без
  процесса Kapkan, и эта команда читает закрепления напрямую, чтобы вам об этом сообщить.

Отчёт начинается с вердикта и способа исправления, а затем даёт подробности: подключённые
интерфейсы с реально действующим режимом, версии ядра и схемы карт, текущее поколение, счётчики
статических и динамических правил, размер / заполненность / память по каждой карте, флаг dry-run и
счётчики вердиктов.

Про две вещи в этом выводе стоит знать заранее:

- **Режим подключения `GENERIC` выносится в первую строку.** `xdp_mode: auto` без ошибки
  откатывается с драйверного пути на обобщённый (skb), а это стоит примерно порядка величины
  пропускной способности, поэтому это заголовок, а не одно поле из двадцати.
- **Счётчики вердиктов печатаются двумя блоками.** *Терминальные* счётчики делят трафик без
  пересечений — на каждый пакет увеличивается ровно один, — поэтому они суммируются.
  *Наблюдательные* счётчики увеличиваются *вместе* с терминальным для того же пакета
  (`dryrun_would_drop`, `pass_rule_expired`, `pass_frag_noports`, `err_policy_missing`); прибавление
  их к итогу дало бы число пакетов больше, чем самих пакетов, поэтому они перечислены отдельно и
  никогда не входят в сумму.

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `-json` | `false` | Напечатать весь результат осмотра в виде JSON, включая поле `state`, из которого выводятся коды выхода. |
| `-pin-path <dir>` | из `-config` | Каталог bpffs, который нужно осмотреть. По умолчанию берётся `dataplane.pin_path` из конфигурации, названной глобальным `-config`, с откатом на `/sys/fs/bpf/kapkan`, если этот файл прочитать не удалось. Отчёт всегда сообщает, на какой путь он смотрел и откуда этот путь взялся. |

#### Коды выхода

| Код выхода | Сообщаемое состояние | Значение и что делать |
| --- | --- | --- |
| `0` | `enforcing` | Хотя бы на одном интерфейсе есть живое подключение XDP. Делать нечего. |
| `10` | `no_pin_path`, `no_program`, `detached` | Плоскость данных **не фильтрует**, и при этом ничего не сломано — она здесь ни разу не запускалась, либо остановлена, либо её подключений больше нет. Запустите Kapkan или проверьте, что настроенные интерфейсы существуют. |
| `11` | `not_bpffs`, `torn`, `schema_skew` | Что-то нужно **починить**, прежде чем это заработает: bpffs не смонтирована, набор закреплений разорван либо у закреплённых карт версия схемы отличается от версии этого бинарника. Напечатанная причина называет исправление (смонтировать bpffs; перезапустить Kapkan). |
| `1` | `attach_unknown` или любая ошибка чтения | Команда **не смогла ответить** — чаще всего из-за прав (см. ниже). Намеренно не сообщается как «не фильтрует», потому что фильтрация вполне может идти. |
| `2` | — | Ошибка использования: неизвестный флаг, команда или лишний аргумент. |

Кодом `0` завершается только `enforcing`, поэтому `kapkan dataplane status >/dev/null` без проблем
встраивается в проверку мониторинга. Соглашение «`10` — для осмысленного состояния» то же самое,
что и у [`-check-update`](#проверка-обновлений).

#### Права доступа

Читать закрепления гораздо дешевле, чем создавать их: на ядре с
`kernel.unprivileged_bpf_disabled=0` не требуется **вообще никаких привилегий** — ни
`CAP_NET_ADMIN`, ни `CAP_PERFMON`, которые нужны демону, чтобы *загрузить и подключить* программу,
здесь не участвуют. А ограничивает доступ вот что:

- Каталог закреплений имеет режим `0700` и принадлежит пользователю, от имени которого работает
  демон, так что на практике вам понадобится `sudo kapkan dataplane status`.
- На ядре с установленным `kernel.unprivileged_bpf_disabled` — по умолчанию в Debian и Ubuntu —
  `bpf(2)` дополнительно требует `CAP_BPF`, даже чтобы открыть уже существующее закрепление.
- **Закреплениям link нужно право на запись, а не только на чтение:** ядро отказывает в
  `BPF_OBJ_GET` для `bpf_link`, если дескриптор открыт не с `O_RDWR`. Поэтому читатель без прав
  root видит все карты и ни одного подключения, и это сообщается как `attach_unknown` (код выхода
  `1`), а не как «отключено».

<Callout type="info" title="Она никогда не меняет то, что диагностирует">
Именно поэтому `dataplane status` — отдельный путь только для чтения, а не переиспользование
стартового кода самого демона. Запуск плоскости данных перенимает существующий набор закреплений —
или, когда схема не совпадает, сносит его и пересобирает, стирая все динамические правила
подавления в ядре. Диагностика, способная сделать такое посреди атаки, была бы хуже, чем полное
отсутствие диагностики.
</Callout>

### `scrub`

```sh
kapkan scrub -config /etc/kapkan/scrub.yaml
```

Запускает роль [узла очистки](/docs/scrubbing#управляемые-узлы-очистки): тот же бинарник, другая
работа. Нет ни обнаружения, ни BGP, ни слушателя телеметрии — машина принимает трафик, который
отвёл на неё мозг, длинными опросами (long-poll) читает таблицу правил мозга и держит свою
локальную XDP-[плоскость данных](/docs/dataplane) применяющей ровно то, что мозг велит отбрасывать.
Опрос заодно служит сигналом живости узла.

Всё специфичное для роли живёт в собственном `scrub.yaml`; `config.yaml` демона **не** читается
(`-config` здесь по умолчанию равен `/etc/kapkan/scrub.yaml`). У него три части: контроллер, к
которому подключаться, идентичность узла и тот же блок `dataplane:`, что несёт демон.

```yaml
dry_run: true                     # the remote-role default — counts, drops nothing
controller:
  url: "https://kapkan.example.net:8443"   # the brain's API base (no path)
  token_env: KAPKAN_AGENT_TOKEN            # env var holding the agent token (required)
  name: scrub-fra1                         # must equal a scrubbing.nodes[] name on the brain
dataplane:
  interfaces: [eth0]              # the dirty side (diverted traffic arrives here)
  xdp_mode: auto
  pin_path: /sys/fs/bpf/kapkan
```

<Callout type="warning" title="Узел очистки по умолчанию в режиме dry-run">
`dry_run` по умолчанию равен **true** для удалённой роли — узел устанавливает правила и считает,
что они *отбросили бы*, но ничего не отбрасывает, пока вы явно не зададите `dry_run: false`. Он
никогда не применяет правило, которое мозг пометил как dry-run, пока то действует в боевом режиме,
и требует действительного токена agent: без него его опросы не несут идентичности, и мозг счёл бы
его мёртвым. Используйте `https` вне лаборатории — открытый `controller.url` отправляет токен в
незашифрованном виде.
</Callout>

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `-config <path>` | `/etc/kapkan/scrub.yaml` | Конфигурация узла очистки. |
| `-log-format <fmt>` | `json` | `json` или `text`. |
| `-log-level <lvl>` | `info` | `debug`, `info`, `warn` или `error`. |

Убедитесь, что узел работает, командой `kapkan dataplane status` на самом узле — она сообщает
`ENFORCING` и число установленных правил, — а [представление Nodes](/docs/dashboard) со стороны
мозга показывает его живым. Доставка отведённого трафика до узла — это
[руководство по сетевой интеграции](/docs/network-integration).

### `edge`

```sh
kapkan edge -config /etc/kapkan/edge.yaml
```

Запускает роль [граничного узла](/docs/edge): nginx или Angie на этой машине становится управляемым
HTTPS-фронтом для зон, которые обслуживает мозг. Роль длинными опросами (long-poll) читает документ
зон мозга, отрисовывает конфигурацию терминатора и устанавливает её под защитой `nginx -t`, отвечает
на `auth_request` nginx из локальной службы решений, читает лог доступа в сводки по источникам,
выпускает и продлевает сертификаты зон на самой машине и отчитывается о себе. Опрос заодно служит
сигналом живости узла. Пошаговое описание — в [руководстве по установке](/docs/edge-install).

Всё специфичное для роли живёт в собственном `edge.yaml`; `config.yaml` демона **не** читается
(`-config` здесь по умолчанию равен `/etc/kapkan/edge.yaml`).

```yaml
dry_run: true                          # the remote-role default — marks, refuses nothing
controller:
  url: https://kapkan.example.net:8443 # the brain's API base (no path); https outside a lab
  token_env: KAPKAN_EDGE_TOKEN         # env var holding the agent token (required)
  name: edge-1                         # must equal an edge.nodes[] name on the brain
  report_interval_seconds: 10          # self-report cadence
state_dir: /var/lib/kapkan-edge        # document cache, generations, ACME keys and certificates
sockets_dir: /run/kapkan-edge          # edge-decide.sock, edge-challenge.sock, edge-log.sock
socket_group: nginx                    # the terminator's worker group (nginx | www-data | angie)
terminator:
  binary: nginx                        # nginx (default) | angie
  main_conf: /etc/nginx/nginx.conf     # -c for `nginx -t` and `nginx -s reload`; empty = compiled default
  reload: exec                         # exec (default) | signal | command
  pid_file: /run/nginx.pid             # liveness check; required for reload: signal
  # command: [systemctl, reload, nginx]
acme:
  directory: ""                        # default CA; empty = Let's Encrypt production
  fallback: ""                         # optional second CA after three consecutive failures
  contact: ["mailto:ops@example.net"]
  # eab:                               # External Account Binding for CAs that require one
  #   - directory: https://acme.zerossl.com/v2/DV90
  #     kid: your-kid
  #     hmac_key_env: KAPKAN_EDGE_ZEROSSL_HMAC
  # disabled: true                     # issue nothing (zones stay on :80 answering 503)
status_listen: 127.0.0.1:9102          # /healthz + /metrics; unauthenticated, keep it private
omit_catch_all: false                  # true when nginx.conf has its own default_server
disable_ipv6: false                    # true on hosts without an IPv6 stack
```

| Ключ | Значение |
| --- | --- |
| `dry_run` | Отсутствует или `true`: решения подсчитываются и помечаются (`X-Kapkan-Mark: would-deny:<reason>` доходит до исходного сервера), но ни одно не применяется. Задайте `false`, чтобы отказывать. |
| `controller.url` / `token_env` / `name` | Базовый адрес API мозга (без пути, без учётных данных в URL), переменная окружения с токеном **agent** и имя этого узла — оно должно совпадать с записью `edge.nodes[]` на мозге, иначе каждый опрос — это громкий `404`. |
| `state_dir` / `sockets_dir` | Собственные каталоги роли (по умолчанию `/var/lib/kapkan-edge`, `/run/kapkan-edge`) — никогда не `/var/lib/kapkan` и `/run/kapkan` мозга: на общем хосте systemd сменил бы им владельца и удалил бы их прямо из-под роли. Абсолютные, без символов, которые nginx мог бы истолковать неверно. |
| `socket_group` | Группа обработчиков терминатора. Сокеты решений и лога имеют для неё режим `0660`; сокет challenge — `0666` (он отвечает на публичные токены). Пустое значение оставляет два ограниченных по группе сокета доступными только владельцу. |
| `terminator.binary` / `main_conf` | Что запускать для `-t` и перезагрузок, и основная конфигурация, передаваемая как `-c`. Этот файл должен один раз содержать `include /var/lib/kapkan-edge/conf/live/*.conf;` внутри `http {}`. |
| `terminator.reload` | `exec` запускает `<binary> -s reload` (нужно послать сигнал master-процессу nginx — юнит работает от root); `signal` посылает `HUP` процессу с pid из `pid_file`; `command` запускает `terminator.command`, например `[systemctl, reload, nginx]`. |
| `terminator.pid_file` | Если задан, читается на каждом такте отчёта и проверяется сигналом `0`: `/healthz` отвечает `503`, а отчёт говорит `alive: false`, пока ни у одного процесса нет этого pid. |
| `acme.directory` / `fallback` / `contact` | CA узла по умолчанию (собственный блок `acme` зоны переопределяет directory и fallback), запасной CA, который пробуется после трёх неудач подряд (должен отличаться от разрешённого основного), и контакт учётной записи — каждая запись в нём — это URL `mailto:` (`mailto:ops@example.net`), иначе файл отклоняется. |
| `acme.eab[]` | External Account Binding для каждого URL directory (`directory`, `kid`, `hmac_key_env`) для CA, которые его требуют — ZeroSSL, Google Trust Services. Ключ HMAC — это секрет, и он читается из названной переменной окружения. |
| `acme.disabled` | Ничего не выпускать: зоны остаются на `:80` и отвечают `503` (лаборатория, где отрабатывается всё, кроме выпуска). Сертификаты, предоставленные оператором, пока не поддерживаются. |
| `status_listen` | Если задан, обслуживает `/healthz` и `/metrics`. Без аутентификации — loopback или приватный адрес. |
| `omit_catch_all` / `disable_ipv6` | Убрать общий `default_server` Kapkan (ваш `nginx.conf` объявляет свой) / убрать слушатели `[::]` (нет стека IPv6). |

<Callout type="warning" title="Граничный узел по умолчанию в режиме dry-run">
`dry_run` по умолчанию равен **true** для удалённой роли — узел считает и помечает то, в чём
*отказал бы*, но ни в чём не отказывает, пока вы явно не зададите `dry_run: false`. Он требует
действительного токена agent: без него его опросы не несут идентичности, и мозг счёл бы его
мёртвым. Используйте `https` вне лаборатории — открытый `controller.url` отправляет токен в
незашифрованном виде.
</Callout>

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `-config <path>` | `/etc/kapkan/edge.yaml` | Конфигурация граничного узла. |
| `-check` | выключен | Проверить файл и то, что он называет на этой машине — группа сокетов должна существовать, а любой ключ EAB быть корректно сформирован (проблемы); отсутствующий токен, бинарник терминатора или `main_conf` — предупреждение, — и выйти. |
| `-log-format <fmt>` | `json` | `json` или `text`. |
| `-log-level <lvl>` | `info` | `debug`, `info`, `warn` или `error`. |

Убедитесь, что узел работает, командой `curl 127.0.0.1:9102/healthz` — `200` с `"converged":true`,
как только документ отрисован и введён в работу, — а инвентарь мозга (`GET /api/v1/edge/nodes`)
показывает его живым. Схема файла зон со стороны мозга — `kapkan -dump-zones-schema`.

### `nginx-exporter`

```sh
KAPKAN_API_TOKEN=... kapkan nginx-exporter -log /var/log/nginx/kapkan.json.log -api http://127.0.0.1:8080
```

Следит за хвостом JSON-лога доступа nginx, измеряет частоту запросов каждого источника за окно и
отправляет вердикты в [канал блокировки источников](/docs/api#канал-блокировки-источников) мозга.
Обязательный `log_format`, пороги и эксплуатационные границы описаны рядом с самой возможностью:
[эталонный экспортёр](/docs/dataplane#эталонный-экспортёр-kapkan-nginx-exporter). Глобальные флаги
демона не читаются; всё у него своё:

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `-log <path>` | — (обязателен) | Лог доступа nginx в документированном JSON-`log_format`. |
| `-api <url>` | `http://127.0.0.1:8080` | Базовый URL API мозга. |
| `-token-env <name>` | `KAPKAN_API_TOKEN` | Переменная окружения с токеном **operator**. |
| `-victim <ip>` | — | Фиксированная жертва; переопределяет поле `dst` из лога. |
| `-window <dur>` | `10s` | Окно измерения. |
| `-rps <n>` | `50` | Запросов в секунду с одного источника, при которых взводится блокировка. |
| `-min-requests <n>` | `100` | Минимум запросов за окно, прежде чем применяется арифметика скоростей. |
| `-error-ratio <r>` | `0` | Дополнительно требовать такую долю 4xx/5xx (`0` отключает эту ось). |
| `-ttl <dur>` | `5m` | TTL блокировки; всё ещё горячий источник обновляется до её истечения. Должен быть не меньше `2×-window`. |
| `-observe` | выключен | Записывать вердикты в лог, не отправляя их. |
| `-log-format` / `-log-level` | `json` / `info` | Собственные логи экспортёра. |
