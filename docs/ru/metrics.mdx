# Метрики

Kapkan экспортирует метрики Prometheus в пространстве имён `kapkan_` по адресу `GET /metrics` на
слушателе API (`api.listen`, по соглашению `127.0.0.1:8080` — значение из примера конфигурации; поле обязательное, поэтому задайте его). Они охватывают весь конвейер —
приём потоков, движок обнаружения, подавление атак через RTBH, уведомления и, там где она включена,
плоскость данных XDP в ядре — поэтому вы можете собирать
данные о пропускной способности, задержке, активных атаках и анонсированных маршрутах в свою
существующую систему мониторинга.

<Callout type="info" title="/metrics остаётся открытым">
Конечная точка `/metrics` всегда доступна без аутентификации, даже когда вы задаёте токен API через
`api.token_env`. Только конечные точки данных `/api/v1` требуют `Authorization: Bearer <token>`.
Привязывайте слушатель соответствующим образом — см. [Аутентификация](/docs/authentication).
</Callout>

## Доступные метрики

| Метрика | Метки | Значение |
| --- | --- | --- |
| `kapkan_ingest_flows_total` | `proto` | Общее число принятых потоков, с разбивкой по протоколу потоков. |
| `kapkan_ingest_packets_total` | `exporter`, `proto` | Общее число полученных телеметрических датаграмм, с разбивкой по исходному экспортёру (с ограниченной кардинальностью; см. [`flow_sources`](/docs/configuration)) и протоколу. |
| `kapkan_ingest_decode_errors_total` | `proto` | Телеметрические датаграммы, которые не удалось декодировать, с разбивкой по протоколу. |
| `kapkan_ingest_dropped_flows_total` | — | Потоки, отброшенные из-за того, что входная очередь движка была заполнена. |
| `kapkan_engine_active_attacks` | — | Gauge атак, находящихся в процессе в данный момент. |
| `kapkan_engine_attacks_total` | — | Счётчик атак, обнаруженных с момента запуска. |
| `kapkan_engine_process_latency_seconds` | — | Гистограмма задержки обработки на горячем пути, измеряемой один раз на каждую партию приёма (а не на каждый поток). |
| `kapkan_engine_tracked_hosts` | — | Gauge хостов, отслеживаемых движком в данный момент. |
| `kapkan_engine_boundary_debug_bytes_total` | `exporter`, `iface`, `dir` | Скорректированные на частоту выборки байты к защищаемым хостам (`dir=in`) или от них (`dir=out`), с разбивкой по `exporter` и интерфейсу (`iface` = ifIndex). Появляется только при [`sampling.boundary_debug: true`](/docs/configuration) — временное подспорье для поиска ваших граничных интерфейсов. Кардинальность НЕ ограничена; отключите метрику снова после того, как изучите разбивку. |
| `kapkan_engine_events_dropped_total` | `kind` | События жизненного цикла движка, отброшенные из-за переполнения канала событий, с разбивкой по `kind` (`attack_started`, `attack_ongoing`, `attack_ended`). Отброшенное `attack_started` или `attack_ended` — реальная потеря: подавление или уведомление этого эпизода пропускается; отброшенный heartbeat `attack_ongoing` самовосстанавливается в следующем окне обнаружения. В норме держится на нуле; рост счётчика означает, что потребитель событий не успевает. |
| `kapkan_mitigate_announced_routes` | `mode` | Gauge blackhole-маршрутов, анонсированных в данный момент, с разбивкой по режиму `real` / `dry_run`. Учитывает только те ступени, которые просят пира что-то применить (`blackhole`, `divert`, `flowspec`); блокировки на локальной ступени `dataplane` — в `kapkan_mitigate_dataplane_bans`. |
| `kapkan_mitigate_flowspec_rules` | `mode` | Gauge правил [FlowSpec](/docs/flowspec), анонсированных в данный момент, с разбивкой по режиму `real` / `dry_run`. Следите за этим значением относительно лимита маршрутов FlowSpec на ваших маршрутизаторах. |
| `kapkan_mitigate_dataplane_bans` | `mode` | Gauge блокировок, которые в данный момент применяет плоскость данных XDP на этом узле, а не вышестоящий маршрутизатор, с разбивкой по режиму `real` / `dry_run`. Они ничего не анонсируют пирам и продолжают фильтровать даже при обрыве BGP. |
| `kapkan_mitigate_dataplane_rules` | `mode` | Gauge правил, установленных этими блокировками в ядре, с разбивкой по режиму `real` / `dry_run`. Блокировка даёт 1 правило, если атака чисто определена как одновекторная, и до 8, если она смешанная или неопознанная, поэтому значение лежит между `kapkan_mitigate_dataplane_bans` и восьмикратным от него. Следите за ним относительно `dataplane.limits.max_dynamic_rules` так же, как за `kapkan_mitigate_flowspec_rules` относительно лимита маршрутов вышестоящего маршрутизатора. |
| `kapkan_mitigate_bans_rejected_total` | `reason` | Блокировки, отклонённые предохранителем безопасности, с разбивкой по `reason`: `max_active_bans`, `blast_radius_fraction`, `blast_radius_rate` или `max_active_prefix_bans` (ковровая бомбардировка). |
| `kapkan_mitigate_source_blocks` | `mode` | Датчик живых [блокировок источников](/docs/dataplane#блокировки-источников-из-вашего-стека) — пар источник→жертва, установленных через `POST /api/v1/dataplane/sources`, — с разбивкой на `real` / `dry_run`. Семантика режима та же, что у датчиков выше: `dry_run` значит «записано и показано, в карте ядра ничего нет». Эти пары берут те же слоты политики, что и блокировки, поэтому следите за суммой относительно `dataplane.limits.max_dynamic_rules`. |
| `kapkan_mitigate_source_blocks_rejected_total` | `reason` | Запросы на блокировку источника, отклонённые **политикой**, с разбивкой по `reason`: `no_dataplane`, `victim_protected`, `source_allowlisted`, `source_in_networks`, `victims_full` (у этого источника уже 8 жертв), `slots_full` (не осталось слотов после брони каждой блокировки), `install_failed` или `other`. Ошибки во входных данных (неверный адрес, TTL вне диапазона) — это дефект вызывающей стороны, и здесь они намеренно **не** учитываются: растущие `source_allowlisted` или `slots_full` — вот сигнал, достойный оповещения, потому что он означает, что интеграция просит блокировки, которые никогда не подействуют. |
| `kapkan_mitigate_fallback_total` | `from`, `to` | Анонсы подавления, понизившиеся до запасного метода из-за того, что пир отклонил основной, с разбивкой по `from`/`to`. Ненулевая серия `from="flowspec"` указывает на аплинки, которые не поддерживают FlowSpec. |
| `kapkan_notify_notifications_total` | `channel`, `result` | Попытки отправки уведомлений, с разбивкой по каналу (telegram, slack, email, webhook, exec) и `result` (`ok`, `error` или `dropped`, когда слоты доставки были переполнены). |
| `kapkan_storage_rows_total` | `table`, `result` | Строки, переданные в опциональное [хранилище ClickHouse](/docs/storage), с разбивкой по таблице и значениям `written` / `dropped` / `error`. `dropped` = очередь хранилища была заполнена (хранилище никогда не блокирует обнаружение, поэтому потоки всё равно обрабатываются и атаки подавляются). |
| `kapkan_build_info` | `version`, `revision`, `goversion`, `goos`, `goarch` | Постоянный info-gauge со значением `1`, несущий данные о работающей сборке в своих метках (идиома `node_exporter`). Отслеживайте расхождение версий по парку с помощью `count by (version)(kapkan_build_info)` — без какого-либо phone-home. |
| `kapkan_update_available` | `latest_version`, `security` | `1`, когда включаемая опционально проверка [`update_check`](/docs/configuration) обнаруживает более новый релиз (иначе метрика отсутствует); `security="true"` отмечает релиз, связанный с безопасностью. |

Метка `mode` у `kapkan_mitigate_announced_routes` — самый быстрый способ подтвердить состояние
dry-run с одного взгляда: пока `dry_run: true`, каждый потенциальный маршрут учитывается под
`mode="dry_run"` и ничего под `mode="real"`. См. [Подавление атак](/docs/mitigation) и
[Модель безопасности](/docs/safety).

Две метрики `kapkan_mitigate_dataplane_*` — это учёт со стороны подавления: что именно оно
установило, с привязкой к блокировкам, которым эти правила принадлежат, и с раскладкой по
замороженному признаку dry-run каждой блокировки. `kapkan_dataplane_rules` измеряет ту же величину
с другого конца: все правила, которые ядро действительно выполняет, — статические из вашей
конфигурации плюс те же самые динамические, — с раскладкой по признаку самой плоскости данных.
То есть при `mode="real"` метрика `kapkan_mitigate_dataplane_rules` должна повторять динамическую
часть `kapkan_dataplane_rules`.

Стройте графики по обеим и сравнивайте их, а не складывайте. Это два независимых пути к одному и
тому же числу, и устойчивое расхождение между ними **в режиме `real`** — настоящая неисправность
(несработавший отзыв или правила, которые ядро завершило по сроку под блокировкой, всё ещё
считающей себя активной), которую единая сумма как раз и скрыла бы.

Не настраивайте оповещения на корзины `dry_run`. Блокировка в режиме dry-run никогда не доходит до
установщика, поэтому в ядро ничего не попадает: `kapkan_mitigate_dataplane_rules{mode="dry_run"}`
показывает правила, которые *были бы* установлены, а динамическая часть `kapkan_dataplane_rules`
остаётся нулевой. Это расхождение — задуманная разница между намерением и измерением, и, поскольку
`dry_run` включён по умолчанию, именно его покажет любое новое развёртывание.

Метка `proto` — это протокол передачи, по которому пришёл поток: `sflow5`, `netflow5`,
`netflow9` или `ipfix` (например, `kapkan_ingest_flows_total{proto="sflow5"}`).

## Плоскость данных (XDP)

Семейство `kapkan_dataplane_*` описывает плоскость данных XDP в ядре
([`dataplane.enabled: true`](/docs/dataplane)). Большинство этих серий создаётся по мере того,
как плоскость данных в них записывает, поэтому на узле, который подавляет атаки исключительно
средствами BGP, они отсутствуют, а не показывают нули.

Значительная часть семейства описывает жизненный цикл, и это сделано намеренно. Программа XDP,
которая не подключена, выглядит ровно так же, как подключённая: демон работает, API отвечает,
блокировки записываются — и единственное видимое отличие в том, что пакеты, которые вы просили
отбрасывать, не отбрасываются. Поэтому «подключена ли она» — это метрика, а не то, что нужно
выводить из строки журнала при запуске.

<Callout type="warning" title="Пять серий есть и без плоскости данных">
`kapkan_dataplane_degraded`, `kapkan_dataplane_pins_rebuilt`,
`kapkan_dataplane_shadowed_static_rules`, `kapkan_dataplane_policy_generation` и
`kapkan_dataplane_policy_apply_seconds` не имеют меток,
поэтому они регистрируются при запуске и экспортируются любой сборкой — со значением `0` на узле,
который никогда не загружал программу BPF. Не читайте `kapkan_dataplane_degraded == 0` как
«плоскость данных исправна»: на узле, работающем только через BGP, это означает, что деградировать
попросту нечему. Ставьте оповещения о плоскости данных в зависимость от того, работает ли она
вообще, — самая дешёвая такая проверка — наличие `kapkan_dataplane_xdp_mode`.
</Callout>

| Метрика | Метки | Значение |
| --- | --- | --- |
| `kapkan_dataplane_degraded` | — | `1`, когда хотя бы у одного настроенного интерфейса нет живого подключения XDP. Это единственная серия, по которой стоит настраивать оповещение. `/healthz` сообщает о том же состоянии строкой `dataplane: DEGRADED (n/m interfaces attached)` и всё равно возвращает 200 — перезапуск не создаст отсутствующую сетевую карту. |
| `kapkan_dataplane_xdp_mode` | `interface`, `mode` | `1`, когда программа подключена к этому интерфейсу в этом режиме (`native` или `generic`), и `0` для другого режима — так что переход на запасной режим, переживший перезапуск, никогда не оставит устаревшую серию, утверждающую сразу оба. ОБЕ серии равны `0` для интерфейса, который вообще не фильтрует, — именно в этом разница между «на обобщённом пути» и «без защиты». `generic` обходится примерно в 10 раз дороже по процессорному времени на пакет, чем `native`. |
| `kapkan_dataplane_attach_errors_total` | `interface` | Неудачные попытки подключения, включая повторные попытки наблюдателя. Рост *вместе с* `kapkan_dataplane_degraded` — это сетевая карта, которая не принимает программу; рост *без* него — нестабильная линия связи, которая восстанавливается. |
| `kapkan_dataplane_reattach_total` | `interface` | Сколько раз программа была подключена к интерфейсу заново после потери подключения. Именно это делает заметной сетевую карту с перебоями: каждый отдельный сбор метрик сообщает, что всё в порядке, а этот счётчик говорит, что это было не так. |
| `kapkan_dataplane_pins_rebuilt` | — | `1`, когда при запуске была найдена существующая закреплённая программа, отвергнута и пересоздана — ожидаемо после обновления, которое меняет объект BPF, раскладку его карт или `dataplane.limits`. Цена в том, что динамические правила предыдущего процесса потеряны; активные атаки подавляются заново на следующем интервале обнаружения. |
| `kapkan_dataplane_shadowed_static_rules` | — | Статические правила конфигурации, которые никогда не сработают, потому что список разрешённых источников или более раннее статическое правило уже забирает каждый пакет, который они выбирают. `0` — единственное здоровое значение, и любое другое стоит оповещения: у этого дефекта нет других числовых признаков, ведь собственный счётчик мёртвого правила тоже стоит на нуле — ровно так же выглядит корректное правило, трафик которого не пришёл. Публикуется заново при каждом применении политики, поэтому сбрасывается на той перезагрузке, которая исправит конфигурацию. См. [Правила, которые никогда не сработают](/docs/dataplane-tuning#правила-которые-никогда-не-сработают). |
| `kapkan_dataplane_packets_total` | `verdict` | Пакеты по окончательному вердикту XDP (`pass_default`, `pass_allow_src`, `drop_static`, `drop_rl`, …). На каждый пакет учитывается ровно один окончательный вердикт — прочитайте [Окончательные вердикты и наблюдения](#окончательные-вердикты-и-наблюдения), прежде чем суммировать эту метрику. |
| `kapkan_dataplane_bytes_total` | `verdict` | Байты, по тем же окончательным вердиктам. График «пакетов в секунду» сам по себе не отличит SYN-флуд с пакетами по 64 байта от отражённого усиления с пакетами по 1500 байт, а реагировать на них нужно по-разному. |
| `kapkan_dataplane_observations_total` | `kind` | Наблюдения на пути обработки пакетов, которые сопровождают окончательный вердикт, а не заменяют его: `dryrun_would_drop`, `pass_rule_expired`, `pass_frag_noports`, `err_policy_missing`, а также копирующий сэмплер [плоскости отпечатков](/docs/fingerprinting) — `fp_emitted` / `fp_throttled` / `fp_ring_full`. Это намеренно отдельная метрика — см. ниже. |
| `kapkan_dataplane_filter_bypass_packets_total` | `reason` | **Тревога, а не статистика.** Пакеты, пересланные дальше без проверки хотя бы одного правила, потому что они сначала натолкнулись на предел разбора в пути обработки пакетов. Сегодня существует одна причина `reason` — `ipv6_exthdr_cap`. Настраивайте оповещение на любую ненулевую скорость — см. [Тревога об обходе фильтра](#тревога-об-обходе-фильтра). |
| `kapkan_dataplane_filter_bypass_bytes_total` | `reason` | Байты того же самого, по той же метке `reason`. Они отличают разведку от потока: горстка сконструированных пакетов в час — это кто-то измеряет ваш разборщик, а устойчивый битрейт — та атака, ради которой это измерение и делалось. |
| `kapkan_dataplane_rules` | `mode` | Правила, которые ядро применяет прямо сейчас, — статическая политика плюс динамические правила подсистемы подавления — с разбивкой на `real` / `dry_run` ровно так же, как у `kapkan_mitigate_flowspec_rules`. Режим — это собственный флаг пути обработки пакетов, вычитанный обратно из ядра, а не флаг из файла конфигурации: перенятый набор закреплённых объектов может всё ещё работать с флагом предыдущего процесса. |
| `kapkan_dataplane_map_entries` | `map` | `max_entries` каждой карты BPF в том виде, в каком она фактически создана, после применения `dataplane.limits`. |
| `kapkan_dataplane_map_bytes` | `map` | Оценка ядром объёма памяти на каждую карту BPF, в байтах (поле `memlock` из `fdinfo` карты). |
| `kapkan_dataplane_policy_generation` | — | Поколение статической политики с двойной буферизацией, активное в ядре в данный момент. Само значение неинтересно; тревожен наклон — каждое переключение обходит карту политик под тем же мьютексом, который упорядочивает установку правил, поэтому поколение, растущее раз в секунду, означает, что что-то переопубликовывает политику в цикле. |
| `kapkan_dataplane_policy_apply_seconds` | — | Гистограмма времени сборки и публикации одного поколения статической политики. На этом промежутке удерживается тот самый мьютекс, которого ждёт установка правила, — поэтому именно эта метрика отвечает на вопрос «мог ли перечитанный конфиг задержать подавление атаки?». |

### Окончательные вердикты и наблюдения

<Callout type="warning" title="Никогда не складывайте эти два семейства">
`kapkan_dataplane_packets_total` и `kapkan_dataplane_observations_total` — намеренно две разные
метрики. Счётчики наблюдений увеличиваются *вместе с* окончательным вердиктом для того же самого
пакета: переписывание в режиме dry-run увеличивает и `dryrun_would_drop`, и тот `pass`, в который
вердикт был переписан. Поэтому одна метрика, несущая и то и другое, заставила бы самый очевидный
запрос завышать счёт ровно на тех пакетах, которые вам важнее всего сосчитать правильно.
</Callout>

Поскольку эти два семейства разделены, на каждый пакет учитывается ровно один окончательный
вердикт, а значит

```
sum(rate(kapkan_dataplane_packets_total[1m]))
```

— это пакеты, прошедшие через путь обработки, а

```
sum(rate(kapkan_dataplane_packets_total{verdict=~"drop_.*"}[1m]))
  / sum(rate(kapkan_dataplane_packets_total[1m]))
```

— доля отброшенных. Ни один из этих двух запросов не должен включать
`kapkan_dataplane_observations_total`.

Во время dry-run стоит следить за наблюдением `dryrun_would_drop`: оно считает пакеты, которые
*были бы* отброшены, и это единственный весомый довод в пользу того, чтобы выключить `dry_run`.

```
sum(rate(kapkan_dataplane_observations_total{kind="dryrun_would_drop"}[1m]))
```

### Тревога об обходе фильтра

`kapkan_dataplane_filter_bypass_packets_total{reason="ipv6_exthdr_cap"}` считает пакеты, которые
плоскость данных **переслала дальше, не проверив ни одного правила**. Любой другой вердикт
`pass_*` означает, что правила были перебраны и ни одно не сказало отбросить; этот означает, что
правила не перебирались вовсе — ни списки разрешений, ни правила отбрасывания, ни ограничения
скорости. Для таких пакетов фильтр фактически был выключен.

Причина — бюджет разбора: путь обработки пакетов проходит не более восьми расширенных заголовков
IPv6, и пакет, несущий больше, пересылается дальше непроверенным. То, что он пропускается, а не
отбрасывается, сделано намеренно — предел разбора никогда не должен превращаться в запрет по
умолчанию, — а значит этот счётчик и есть всё имеющееся средство защиты.
[Единственное, что он не проверяет](/docs/dataplane-operate) описывает
механизм и что с этим делать.

Легитимный трафик никогда не выстраивает восемь расширенных заголовков, поэтому порог оповещения —
ноль, а не какая-то скорость, которую вы подбираете:

```
sum(rate(kapkan_dataplane_filter_bypass_packets_total[5m])) > 0
```

Обе серии публикуются и пока обхода не было, поэтому исправная плоскость данных показывает явный
`0`, а не «нет данных» — именно так вы вообще можете понять, что оповещение подключено.

<Callout type="warning" title="Второй взгляд, а не лишний трафик">
Эти пакеты учитываются и в `kapkan_dataplane_packets_total{verdict="pass_exthdr_cap"}`.
Дублирование намеренно: `packets_total` по-прежнему разбивает трафик ровно один раз, а это
семейство выносит один из его элементов под именем, которое правило оповещения может назвать прямо.
Никогда не складывайте эти две метрики.
</Callout>

### Счётчики при перезапуске

`kapkan_dataplane_packets_total` и `kapkan_dataplane_bytes_total` начинаются с нуля вместе с
процессом, а вот карты в ядре, из которых они читаются, — нет: процесс, перенявший существующий
набор закреплённых объектов, наследует суммы предыдущего. Сборщик берёт базовую отметку из первого
чтения и публикует только то, что наблюдал *этот* процесс, поэтому `rate()` остаётся верным при
запуске вместо всплеска шириной во всё время жизни предыдущего процесса. Абсолютные суммы из ядра
доступны на `/api/v1/status`, если они вам нужны.

Та же переустановка базовой отметки происходит, когда счётчики идут назад, а это может означать
только их сброс под процессом (закреплённые объекты пересозданы, карта создана заново). Поэтому
пересоздание выглядит как пропуск в скорости, а не как отрицательный всплеск.

### Размер карт и память

`kapkan_dataplane_map_entries` и `kapkan_dataplane_map_bytes` — это обратная связь для
`dataplane.limits`. Память карт BPF списывается на memory-cgroup юнита одним шагом при загрузке,
поэтому значение `MemoryMax=`, которого хватало до появления плоскости данных, может привести к
OOM-завершению юнита при запуске. Основной объём занимают две карты — `kapkan_rl_src4` и
`kapkan_rl_src6`, размер которых задаётся через `dataplane.limits.max_ratelimit_sources`, — и,
будучи LRU-хешами, они выделяются целиком заранее независимо от того, будет ли хоть один источник
ограничен по скорости. Понизьте лимит и считайте результат с этих gauge, а не додумывайте его:

```
sum(kapkan_dataplane_map_bytes)
```

### Счётчики отбрасывания по блокировкам

Сколько ядро отбросило **для одной жертвы** — сознательно не здесь. `/metrics` доступен без
аутентификации, и адрес жертвы в метке раскрыл бы, кто находится под атакой, любому, кто может
достучаться до слушателя. Эти счётчики по каждой блокировке и по каждому правилу находятся в
защищённом аутентификацией [`/api/v1/bans`](/docs/api), в объекте `dataplane` каждой блокировки.

## Плоскость отпечатков

[Плоскость отпечатков](/docs/fingerprinting) ([`dataplane.fingerprint.enabled: true`](/docs/fingerprinting))
сообщает здесь о своём читателе в пространстве пользователя; её копирующий сэмплер в ядре — на
`kapkan_dataplane_observations_total{kind="fp_emitted"|"fp_throttled"|"fp_ring_full"}` выше.

| Метрика | Метки | Значение |
| --- | --- | --- |
| `kapkan_fingerprint_events_total` | `result` | События кольцевого буфера по исходу у читателя: `classified` (вычислен JA4), `blocked`, `would_block` (совпадение в режиме dry-run), `suppressed` (повтор в пределах периода охлаждения блокировки), `block_error` (отклонено политикой — в белом списке / под защитой / бюджет исчерпан), `unparsed` (усечённый пакет, не рукопожатие или недешифруемый пакет QUIC), `malformed`, `unknown_axis`, `panic`. Растущий `block_error` — вот сигнал, достойный оповещения; растущий `unparsed` под нагрузкой — обычно просто усечённые снимки, и это безвредно. |

Рост `fp_throttled` при выходе `fp_emitted` на плато — это сэмплер делает свою работу под флудом
рукопожатий; устойчивый `fp_ring_full` означает, что читатель не успевает опустошать кольцевой буфер.

## Сбор метрик

Добавьте Kapkan как цель сбора (scrape target) в конфигурацию Prometheus:

```yaml
scrape_configs:
  - job_name: kapkan
    metrics_path: /metrics
    static_configs:
      - targets: ["127.0.0.1:8080"]
```

Используйте хост и порт из значения `api.listen` (по соглашению `127.0.0.1:8080`). Если вы открываете слушатель за пределами
localhost, задайте токен API — `/metrics` остаётся доступным без него, поэтому вашему сборщику
не нужны учётные данные.

Чтобы посмотреть сырой вывод напрямую:

```sh
curl -s localhost:8080/metrics | grep kapkan_
```

## Панель Grafana

Официальную панель управления Grafana для набора `kapkan_*` можно скачать напрямую по ссылке
[`kapkan-overview.json`](/kapkan-overview.json) (его исходник лежит в репозитории в каталоге
[`engine/deploy/grafana/`](https://github.com/fornex/kapkan/tree/main/engine/deploy/grafana)).
Он охватывает весь конвейер — скорости приёма потоков/датаграмм/декодирования и отброшенные потоки,
активные и начавшиеся атаки, отслеживаемые хосты, квантили задержки горячего пути, анонсированные
маршруты и правила FlowSpec по `mode`, блокировки, отклонённые по `reason`, запасные переключения
подавления, а также результаты уведомлений и хранилища. Ряд **Data plane** охватывает метрики XDP,
описанные выше: пакеты в секунду по вердикту, правила в ядре по режиму, подключение по интерфейсу и
режиму, ошибки подключения, поколение политики и квантили времени применения, а также записи
карт BPF.

В Grafana перейдите в **Dashboards → New → Import**, загрузите JSON и выберите ваш источник данных
Prometheus при запросе (он шаблонизирован как `DS_PROMETHEUS`). Панель управления рассчитана на
Grafana 10+ и проверен на импорт в Grafana 11. См.
[README](https://github.com/fornex/kapkan/blob/main/engine/deploy/grafana/README.md) рядом с
ним для информации о provisioning.
