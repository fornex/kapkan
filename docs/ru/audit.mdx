# Журнал аудита

Каждое изменяющее состояние действие API записывается в **аудиторский след** — это ответ на вопрос «кто
заблокировал `203.0.113.66` в 03:14 и кто перезагрузил конфигурацию». В каждой записи указаны оператор
(API-токен, выполнивший вызов), действие, цель и результат — включая
**отклонённые** действия, поскольку отказ в блокировке сам по себе является решением, подлежащим аудиту.

След пишется из обработчиков мутаций [API](/docs/api) и доступен через единственную
конечную точку чтения, `GET /api/v1/audit`. Он сохраняется в [ClickHouse](/docs/storage) рядом с
историей атак и трафика и **ограничен областью tenant** на стороне сервера — так же, как и любое другое чтение.

Если вы не используете [мультиарендность](/docs/multi-tenancy) (одно развёртывание обслуживает одного
клиента или вашу собственную сеть), поле `tenant` пустое, и токен администратора видит каждую
запись — приведённые ниже замечания об ограничении областью tenant можно пропустить.

<Callout type="info" title="Всегда логируется, доступно для запросов при включённом хранилище">
Каждая мутация логируется на уровне `INFO` независимо от хранилища. Для истории, доступной по запросу, нужен
[ClickHouse](/docs/storage): при отключённом хранилище конечная точка возвращает `available: false`
(она никогда не выдаёт ошибку), и у вас по-прежнему есть строки аудита в логе процесса.
</Callout>

## Что записывается

Аудиту подвергаются шесть действий. `ban`, `config_reload` и `source_block` записываются как при
успехе, так и при ошибке; `edge_challenge` — на каждый `200`: снятие рычага, которого не было,
всё равно записывает `cleared`, и только отклонённый рычаг (`404`, `400`, `409`) не попадает в
след; `unban` и `source_unblock` записываются только при успехе — неудачное или
холостое удаление возвращает ошибку и не заносится в след, хотя по-прежнему логируется (неудачный
unban — это `404 "no active ban"`, а не решение политики, поэтому привязывать нечего):

| Действие | Когда | Записываемые результаты (`result`) |
| --- | --- | --- |
| `ban` | `POST /api/v1/ban` | `active` при успехе; `rejected`, когда защитный механизм отказывает. Блокировка в режиме dry-run всё равно записывает `active` — симуляция обозначается отдельным полем `dry_run`. |
| `unban` | `POST /api/v1/unban` | `withdrawn` при успехе. |
| `config_reload` | `POST /api/v1/config/reload` | `ok` при успехе; `error`, когда новую конфигурацию не удаётся разобрать или проверить. |
| `source_block` | `POST /api/v1/dataplane/sources` | `blocked` при успехе; `rejected`, когда политика отказывает. Отклонённая блокировка источника сама является действием оператора, поэтому привязывается так же, как отклонённая блокировка. [Плоскость отпечатков](/docs/fingerprinting) также пишет записи `source_block` — `source: "auto"`, только при успехе — когда блокирует JA4. |
| `source_unblock` | `POST /api/v1/dataplane/sources/unblock` | `removed` при успехе. |
| `edge_challenge` | `POST`/`DELETE /api/v1/edge/zones/{name}/challenge` | `set`, когда [рычаг](/docs/edge#рычаг) повёрнут, `cleared`, когда он отпущен (`DELETE` или `mode: off`, независимо от того, действовал ли рычаг); `reason` — это `<mode> until <RFC 3339>; <operator's reason>` при `set` и причина оператора (`mode: off`) или пусто (`DELETE`) при `cleared`. Отклонённый рычаг — неизвестная зона или зона за пределами арендатора, неверный TTL, зона в `mode: none` — не записывается. |

`config_reload` доступен только токенам без ограничения области (admin). Оператору с областью tenant
отказывают с `403` *до* того, как перезагрузка запустится, и **запись аудита не пишется** — этот отказ
виден только в логе процесса. Так что если ограниченная перезагрузка как будто пропала из следа, дело именно в этом.

**Отклонённое** действие аудируется намеренно: блокировка, отклонённая белым списком, заданными
`networks` или [защитой по радиусу поражения (blast-radius)](/docs/safety), оставляет запись аудита с `result:
"rejected"` и причиной отказа в `reason`. Поэтому аудиторский след показывает как попытки изменений, так и
применённые изменения.

## Идентичность оператора

Поле `operator` — это **имя** сопоставленного [API-токена](/docs/authentication) — то самое
`name`, которое вы задаёте каждой записи в списке `api.tokens`. Именно так след привязывает
действие к человеку или системе:

```yaml
api:
  tokens:
    - { name: alice,      token_env: KAPKAN_ALICE, role: operator }
    - { name: automation, token_env: KAPKAN_AUTO,  role: operator }
```

Блокировка, выданная с токеном `alice`, записывает `operator: "alice"`. На открытом (без токенов) API
нет субъекта для привязки, поэтому `operator` пустой — ещё одна причина
[задать токены](/docs/authentication) перед тем, как выставлять listener наружу.

## GET /api/v1/audit

Возвращает записи аудита в порядке от новых к старым. Требует роль **viewer**, как и остальные операции чтения.

| Параметр запроса | По умолчанию | Примечания |
| --- | --- | --- |
| `from` | now − 1h | Начало окна в формате RFC 3339. |
| `to` | now | Конец окна в формате RFC 3339. Должен быть позже `from`; окно не может превышать **31 days**. |
| `action` | (все) | Фильтр по одному из `ban`, `unban`, `config_reload`, `source_block`, `source_unblock`, `edge_challenge`. |
| `target` | (все) | Фильтр по одному IP. Должен быть виден tenant вызывающей стороны, иначе запрос — `403`. |

Конечная точка возвращает не более ~1000 записей на запрос, от новых к старым. Если на загруженном окне
вы упираетесь в этот предел, более старые события молча отбрасываются из ответа — сузьте окно или
воспользуйтесь фильтрами `target`/`action`.

```http
GET /api/v1/audit?from=2026-06-22T00:00:00Z&action=ban HTTP/1.1
Authorization: Bearer <token>
```

```json
{
  "available": true,
  "events": [
    {
      "event_time": "2026-06-22 03:14:09",
      "action": "ban",
      "result": "rejected",
      "operator": "alice",
      "role": "operator",
      "tenant": "customerA",
      "target": "203.0.113.66",
      "target_type": "host",
      "reason": "whitelisted",
      "source": "api",
      "ban_state": "rejected",
      "dry_run": 0
    }
  ]
}
```

Каждая запись содержит следующие поля:

| Поле | Примечания |
| --- | --- |
| `event_time` | UTC, `YYYY-MM-DD HH:MM:SS`. |
| `action` | `ban`, `unban`, `config_reload`, `source_block`, `source_unblock` или `edge_challenge`. |
| `result` | `active`, `rejected`, `withdrawn`, `ok`, `error`, `blocked`, `removed`, `set` или `cleared`. |
| `operator` | Имя сопоставленного API-токена; пустое в открытом (без токенов) режиме. |
| `role` | Роль вызывающей стороны (`viewer` / `operator`). |
| `tenant` | Область tenant вызывающей стороны; пустая для неограниченного (admin) вызова. |
| `target` | IP для `ban`/`unban`; `source->victim` для `source_block`/`source_unblock`; зона для `edge_challenge`; пустой для `config_reload`. |
| `target_type` | `host` для `ban`/`unban`; `source` для `source_block`/`source_unblock`; `zone` для `edge_challenge`; `global` для `config_reload`. |
| `reason` | Детали отказа или ошибки; пустое при успехе — кроме `edge_challenge`: при `set` это режим, время его окончания и причина оператора, при `cleared` — причина оператора или пусто. |
| `source` | `api` для действия оператора или `auto` для действия, инициированного движком. Сегодня [плоскость отпечатков](/docs/fingerprinting) пишет записи `source_block` с `source: "auto"` — без оператора, роли и tenant — когда JA4 клиента находится в списке блокировки. |
| `ban_state` | Итоговое состояние блокировки для `ban`/`unban`; пустое для `config_reload`, действий с блокировкой источников и `edge_challenge`. |
| `dry_run` | `1`, когда действие выполнялось в режиме [dry-run](/docs/safety) (`ban`/`unban`, действия с блокировкой источников); всегда `0` для `config_reload` и `edge_challenge`, которые dry-run не ограничивает. |

Запрос с окном вне допустимого диапазона возвращает `400`; неизвестное значение `action` возвращает `400`;
некорректный `target` возвращает `400`. При отключённом хранилище ответ —
`{"available": false, "events": []}` со статусом `200`. Поле `events` — всегда массив: окно, в
котором нет ни одной видимой вызывающей стороне записи (первый день tenant, фильтр, под который
ничего не подошло), — это `[]`, а не `null`.

## Ограничение областью tenant

Конечная точка аудита **ограничена областью tenant на стороне сервера**, точно как `/attacks` и `/bans`.
[Токен, ограниченный областью tenant](/docs/multi-tenancy), видит только те записи, чей `tenant` совпадает с его
собственной областью; область привязывается во время аутентификации и не может быть расширена никаким параметром
запроса. Неограниченный (admin) токен видит записи всех tenant. Фильтр `target`, который
называет адрес вне tenant вызывающей стороны, отклоняется с `403`, поэтому журнал аудита не является
оракулом существования между tenant.

## Хранение

Записи аудита живут в таблице ClickHouse `audit_events` и наследуют тот же построчный TTL `ttl_days`,
что и остальное [хранилище](/docs/storage) — срок хранения ограничен без вмешательства
оператора. Сохранение работает по принципу best-effort через ту же ограниченную очередь: медленный или недоступный ClickHouse
отбрасывает строки, а не задерживает блокировку, при этом строка лога уровня `INFO` выводится всегда.
