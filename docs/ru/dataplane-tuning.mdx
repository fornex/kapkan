# Настройка и справка

Точный справочник по плоскости данных: как проверяется пакет, чем отличается политика, которую вы
пишете, от правил, которые генерирует детектор, единственная возможность, которую FlowSpec выразить
не может, и как лимиты превращаются в память ядра. Если вы ещё только разворачиваете её, начните с
[Установки плоскости данных](/docs/dataplane-install).

## Что ядро проверяет и в каком порядке

Для каждого пакета программа проходит **фиксированный, ненастраиваемый** порядок и останавливается на
первом вердикте:

1. **Разрешённые источники** — `dataplane.allowlist`. Совпадение сразу пропускается.
2. **Защищённые назначения** — ваш `protected_whitelist`, зеркалируемый в ядро. Совпадение сразу
   пропускается.
3. **Статические правила** — ваша постоянно действующая политика, побеждает первое совпадение.
4. **Динамические правила по источникам** — записи для каждого атакующего, которые установил детектор.
5. **Динамические правила по жертвам** — правила сопоставления атаки, не более восьми на атаку,
   побеждает первое совпадение.
6. **По умолчанию: пропустить.**

<Callout type="info" title="Два списка разрешений, две разные оси">
`dataplane.allowlist` — это список **источников**, которым всегда разрешено отправлять трафик.
`protected_whitelist` — это список **назначений**, которые никогда не банятся. Они не взаимозаменяемы,
и оба применяются в ядре — если хранить гарантию по назначениям только в пространстве пользователя,
останется окно, в котором правило, установленное мгновением раньше, могло бы всё ещё отбрасывать
трафик к защищённому узлу.
</Callout>

Вердикт по умолчанию всегда — **пропустить**. Нигде в программе нет запрета по умолчанию, нет режима,
в котором добавление правила меняет судьбу несовпавшего трафика, и нет автоматического отбрасывания
фрагментов или необычных протоколов. Пакет, который не удалось разобрать, пропускается и учитывается,
если только вы явно не включите `drop_malformed: true`. Это исполнитель подавления, а не межсетевой
экран: он отбрасывает то, что ему велели отбросить, и пересылает всё остальное.

## Статическая политика против сгенерированных правил

**Статические правила** — это то, что вы пишете. Они всегда включены, не зависят от каких-либо атак
и полезны для трафика, который вам никогда не нужен (`drop_chargen`), и для постоянных потолков
(`cap_icmp`). Имена обязательны и должны быть уникальными, чтобы два правила никогда не могли
незаметно ссылаться на одну и ту же запись.

```yaml
static_rules:
  - name: drop_chargen
    match: { proto: udp, src_port: 19 }
    action: drop
  - name: cap_icmp
    match: { proto: icmp }
    action: ratelimit
    profile: icmp_cap
```

Любое `name` здесь — и у правила, и у профиля — это метка, которую вы придумываете сами, а не ключевое слово; так правило называется в счётчиках, логах и консоли. Фиксированный словарь — только у перечислимых полей: `action` это `pass`, `drop` или `ratelimit`; `match.proto` это `tcp`, `udp`, `icmp` или `icmp6` (пусто — любой, а для `icmp`/`icmp6` порты отклоняются); в `match` есть ещё `src`, `src_port`, `dst_port` и `payload`. [Справочник конфигурации](/docs/configuration) перечисляет каждое поле и его допустимые значения в одной таблице.

### Сопоставление TLS- и QUIC-рукопожатий

`match.payload` сужает правило по тому, с чего **начинается** полезная нагрузка. У него два
значения, по одному на транспорт: `tls_client_hello` сопоставляется с TCP-сегментом, открывающим
TLS ClientHello, а `quic_initial` — с UDP-датаграммой, открывающей QUIC v1 Initial. Каждое — та
форма, из которой на своём транспорте состоит **флуд рукопожатий**, и именно это сообщение обычное
соединение отправляет ровно один раз:

```yaml
ratelimit_profiles:
  - { name: handshake_cap, pps: 20 }   # each source: 20 new handshakes/s

static_rules:
  - name: cap_tls_handshakes
    match: { proto: tcp, dst_port: 443, payload: tls_client_hello }
    action: ratelimit
    profile: handshake_cap
```

За этим правилом стоит идти, когда флуд состоит из *установленных соединений*, каждое из которых
начинает рукопожатие и дальше не идёт: для сервера это самая дорогая часть, а правило по флагам SYN
такой вектор не видит, потому что эти соединения уже установлены. Оно естественно сочетается с
корзинами по источникам: ClientHello может прийти только по завершённому TCP-рукопожатию, поэтому
источники — настоящие адреса, а не подменённые, и каждый получает свой бюджет.

Поскольку правило сопоставляется только с рукопожатием, данные и ACK уже установленного соединения
не затрагиваются — клиент посреди скачивания не конкурирует за тот же потолок.

<Callout type="warning" title="Ставьте его выше более широкого правила для порта 443">
Среди статических правил **побеждает первое совпадение**. Если вы держите ещё и общий потолок на
`{proto: tcp, dst_port: 443}`, он сопоставляется и с ClientHello — поэтому правило для рукопожатий,
написанное *ниже* него, не сработает никогда: молча, без ошибки и без единого признака в счётчиках.
Ставьте более узкое правило первым:

```yaml
static_rules:
  - name: cap_tls_handshakes        # narrower — must come first
    match: { proto: tcp, dst_port: 443, payload: tls_client_hello }
    action: ratelimit
    profile: handshake_cap
  - name: cap_https_per_source      # broader ceiling on everything else
    match: { proto: tcp, dst_port: 443 }
    action: ratelimit
    profile: https_cap
```

Если порядок перепутан, Kapkan вам об этом скажет: правило для рукопожатий будет названо в строке
`WARN` при каждом применении политики и в `WARNING` от `kapkan -check-config`. См. [Правила, которые
никогда не сработают](#правила-которые-никогда-не-сработают) — анализ понимает `payload`, поэтому
правильный порядок выше не вызывает предупреждений, а сообщается только перевёрнутый.
</Callout>

<Callout type="warning" title="Чего он намеренно не делает">
ClientHello читается с фиксированного смещения, и плоскость данных **никогда не собирает поток
заново**. ClientHello, разбитый на несколько TCP-сегментов, не сопоставляется и пропускается — как и
всё остальное, о чём разбор не может вынести решение: фильтр скорее недосопоставит, чем
пересопоставит, и так везде.

Оно также работает только для TCP — поэтому `proto: tcp` обязателен, а не опционален. **Рукопожатие
HTTP/3 — не дело этого фильтра**: оно находится внутри QUIC поверх UDP/443 и зашифровано ещё до
того, как этот фильтр увидит хоть байт, — этот транспорт берёт на себя `quic_initial`, о котором
ниже.

И граница шифрования реальна в обе стороны: Kapkan сопоставляет *форму* рукопожатия, но не его
содержимое, и ничто в плоскости данных не читает HTTP внутри установленной сессии TLS.
</Callout>

### Сопоставление QUIC-рукопожатий

`quic_initial` — UDP-близнец: оно сопоставляется с датаграммой, открывающей **QUIC v1 Initial**, —
пакет, с которого начинается каждое рукопожатие QUIC/HTTP-3 и который сервер обязан разобрать и
ответить на него собственной криптографией рукопожатия. Флуд таких пакетов — QUIC-аналог флуда
ClientHello, и инструмент тот же — потолок по каждому источнику:

```yaml
ratelimit_profiles:
  - { name: quic_handshake_cap, pps: 20 }

static_rules:
  - name: cap_quic_handshakes
    match: { proto: udp, dst_port: 443, payload: quic_initial }
    action: ratelimit
    profile: quic_handshake_cap
```

Учитывается только рукопожатие: каждый пакет уже установленного QUIC-соединения использует форму
короткого заголовка и не сопоставляется, поэтому клиент посреди скачивания не конкурирует с новыми
рукопожатиями за этот потолок. `proto: udp` обязателен по той же причине «говорите, что имеете в
виду», по которой `tls_client_hello` требует `tcp`.

<Callout type="warning" title="Ставьте его выше более широкого правила для UDP/443">
Та же ловушка «побеждает первое совпадение», что и у его TLS-близнеца, — и здесь более широкое
правило у вас, скорее всего, уже есть: прошлые выпуски этой страницы рекомендовали как инструмент
против QUIC именно простой потолок по каждому источнику на `{proto: udp, dst_port: 443}`. Это
правило сопоставляется и с Initial, поэтому правило с `quic_initial`, написанное *ниже* него, не
сработает никогда. Ставьте более узкое правило для рукопожатий первым; если порядок перепутан,
Kapkan назовёт мёртвое правило в строке `WARN` при каждом применении политики и в
`kapkan -check-config` — см. [Правила, которые никогда не
сработают](#правила-которые-никогда-не-сработают).
</Callout>

<Callout type="warning" title="Чего оно намеренно не делает">
Initial распознаётся по пяти байтам на фиксированном смещении: форма длинного заголовка с типом
пакета Initial и версия 1. **Согласование версий (version negotiation) и QUIC v2 не
сопоставляются** (v2 перенумеровывает типы пакетов под другой константой версии; его
распространённость сейчас пренебрежимо мала), а полезная нагрузка, слишком короткая для решения,
пропускается — недосопоставить и переслать, как и всё остальное в плоскости данных.

Проверки **минимального размера намеренно нет**, хотя RFC требует, чтобы клиентский Initial
приходил в датаграмме размером ≥1200 байт: правило на этом предикате должно учитывать всё, что
стеку QUIC сервера приходится разбирать, а укороченные «Initial» — ровно то, что смастерит
атакующий, чтобы проскользнуть под проверкой размера.

Одна особенность именно QUIC, о которой стоит знать: в отличие от TCP, где подменённый источник не
может завершить рукопожатие, поверх которого едет ClientHello, QUIC Initial — *первый* пакет
соединения, так что источники могут быть подменены. `ratelimit` по каждому источнику всё равно
ограничивает каждый подменённый адрес, но атакующий, перебирающий источники, переносит нагрузку на
LRU-таблицу источников, а не на криптографический стек. Рассчитывайте `limits.max_ratelimit_sources`
с учётом этого — или на время атаки сочетайте правило с простым `drop`.
</Callout>

Вектора `tls_handshake_flood` на стороне обнаружения нет, и это намеренно: обнаружение работает на
выборочной телеметрии потоков, которая не несёт байтов полезной нагрузки. Это правило пишет
оператор, и оно всегда включено, а не включается блокировкой во время атаки.

**Динамические правила** генерируются для каждой атаки на основе той же классификации, что управляет
FlowSpec: протокол, отражённый порт-источник вектора усиления, флаги TCP SYN, фрагментация и
доминирующие источники атаки в выборке трафика. Вы их не пишете и не можете редактировать; они
появляются в `/api/v1/bans` у бана, которому принадлежат, и истекают вместе с ним.

Эти два вида никогда не сталкиваются: статические правила занимают собственную карту (шаг 3 выше),
динамические — другую (шаги 4–5), и размер каждой задаётся своим лимитом.

## Правила, которые никогда не сработают

Среди статических правил **побеждает первое совпадение**: программа останавливается на первом
правиле, условию которого пакет удовлетворяет. Поэтому правило, чьё множество совпадений
*содержится* во множестве более раннего правила, — мёртвая политика: перебор каждый раз
останавливается выше, и такое правило не может взять ни одного пакета.

```yaml
static_rules:
  - name: drop_https_flood
    match: { proto: tcp, dst_port: 443 }
    action: drop
  - name: pass_partner_https          # never fires: drop_https_flood takes these packets first
    match: { src: 198.51.100.0/24, proto: tcp, dst_port: 443 }
    action: pass
```

[Список разрешённых источников](#что-ядро-проверяет-и-в-каком-порядке) делает то же самое с
приоритета 1: совпадение пропускает пакет и прекращает проверку до того, как будет рассмотрено хоть
одно статическое правило, — поэтому добавление префикса в `dataplane.allowlist` отключает каждое
статическое отбрасывание, нацеленное на источник внутри него.

Kapkan проверяет обе оси при **каждом применении политики** — при запуске и при каждой перезагрузке
конфигурации — и называет найденные правила в пяти местах:

- строка журнала уровня `WARN` со списком таких правил;
- `shadowed_statics` в отчёте о перезагрузке;
- условие `policy_shadowed` на `/healthz` и `/api/v1/status`, которое сохраняется, пока перезагрузка
  не исправит конфигурацию;
- [метрика](/docs/metrics) `kapkan_dataplane_shadowed_static_rules`, у которой единственное
  здоровое значение — `0`;
- `WARNING` от `kapkan -check-config` — единственное место, где такой дефект можно поймать *до* того,
  как придёт трафик, который правило должно было отфильтровать.

<Callout type="warning" title="Сообщается, а не отвергается">
Недостижимое правило — это предупреждение, а никогда не ошибка запуска. Мёртвое правило ничего не
применяет, поэтому отказ принять конфигурацию обменял бы дефект, который сегодня не стоит ни одного
пакета, на демон подавления атак, который не запустится, — на машине, вся работа которой в том, чтобы
фильтровать, когда придёт атака. Kapkan выполнит такую конфигурацию; он просто не перестанет вам о
ней сообщать.
</Callout>

Покрытие определяется только по `match`, поэтому правило, которое лишь повторяет вердикт более
раннего, тоже попадает в отчёт. `payload` считается частью этого `match` — именно поэтому
рекомендованная расстановка правил для рукопожатий не вызывает предупреждений: правило, которое
требует `payload: tls_client_hello`, строго *уже* правила без него, так что покрыть широкий потолок
для порта 443, написанный ниже, оно не может. Поменяйте их местами — и правило для рукопожатий
мертво, а это ровно тот случай, о котором здесь и сообщается. Вердикт выносится отдельно для каждого
семейства адресов, потому что
программа строга к семейству: правило без `match.src` покрывает оба семейства и мертво только тогда,
когда заняты оба — возможно, двумя разными более ранними правилами, о чём сообщение говорит прямо. По
оси списка разрешённых источников сообщается только о правилах `drop` и `ratelimit`: правило `pass`,
которое этот список и так сделал избыточным, пропускает те же пакеты в любом случае. По оси «побеждает
первое совпадение» сообщается о любом действии, потому что там самая опасная форма — как раз `pass`:
широкое отбрасывание, за которым идёт узкое исключение, которое кто-то собирался предоставить, — и
оно не предоставляется.

Исправляется переносом частного правила **выше** общего, сужением общего правила или записи в списке
разрешённых источников, либо удалением правила, если оно и так было избыточным.

## Ограничение скорости для каждого источника

Действие `ratelimit` применяется **к каждому адресу-источнику**, а не ко всему трафику жертвы в целом.
Каждый источник получает собственную корзину токенов, поэтому лимит в *N* пакетов в секунду удерживает
каждый отдельный источник на уровне *N* — распределённый флуд ограничивается по каждому участнику, а не
позволяет тысяче источников делить (и исчерпывать) один совокупный потолок.

**Профиль — часть ключа корзины** (`{victim, source, profile}`), и это работает в обе стороны: два
правила, называющие *один и тот же* профиль, расходуют **один общий бюджет** на каждый источник — их
совпавшие пакеты конкурируют между собой, — а правила с разными профилями учитываются независимо.
Заводите отдельный профиль под каждую независимо учитываемую вещь — именно поэтому примеры правил
для TLS- и QUIC-рукопожатий на этой странице используют два профиля, а не делят один.

```yaml
ratelimit_profiles:
  - { name: icmp_cap, mbps: 10 }      # each source: 10 Mbps
  - { name: dns_reply, pps: 50000 }   # each source: 50k pps
```

`icmp_cap` и `dns_reply` — это имена, которые вы выбрали, а не ключевые слова: профиль — просто именованный потолок, а статическое правило вызывает его через поле `profile:` (`cap_icmp` выше использует `icmp_cap`). Профилю нужно хотя бы одно из `pps` или `mbps`; задайте оба — и что будет достигнуто первым, то и перестанет пропускать пакеты источника. Профиль, на который не ссылается ни одно правило, удаляется при следующей перезагрузке.

<Callout type="info" title="Это единственное, что FlowSpec выразить не может">
FlowSpec `traffic-rate` применяется к потоку, который сопоставляет правило, поэтому правило,
покрывающее жертву, ограничивает весь совпадающий трафик этой жертвы совокупно — и легитимные клиенты
конкурируют с атакующими за один и тот же лимит. Корзины по каждому источнику — это не более быстрая
версия того, что анонсер уже делал; это то, что он структурно вообще не мог сделать.
</Callout>

`max_ratelimit_sources` ограничивает, сколько корзин источников существует одновременно. Это таблица с
вытеснением наименее недавно использованных (LRU): за пределами лимита наименее активные источники
вытесняются, что при очень широком флуде означает, что некоторые источники ненадолго снова допускаются,
прежде чем их снова ограничат.

## Режимы подключения

Есть два места в пути приёма, где ядро может запустить программу:

- **native** — драйвер вызывает её, как только пакеты приходят с NIC, до выделения `sk_buff`. Требует
  поддержки со стороны драйвера и делает наименьший объём работы на пакет.
- **generic** — ядро вызывает её после выделения `sk_buff`. Работает на любом интерфейсе, включая
  virtio, и делает больше работы на пакет, чтобы до этого дойти.

`xdp_mode: auto` (по умолчанию) использует native там, где драйвер это поддерживает, и generic там, где
нет. `native` отказывается запускаться, а не откатывается — это то, что вам нужно, когда вы рассчитывали
на драйверный хук и предпочли бы узнать об этом при загрузке. `generic` принудительно включает второй
режим; он предназначен в основном для virtio и тестовых окружений.

<Callout type="warning" title="В режиме auto откат происходит молча">
Смена драйвера, обновление ядра или новый NIC могут перевести вас с native на generic без ошибки, а
generic делает гораздо меньше на ядро процессора. Какой режим на самом деле получил каждый интерфейс,
сообщает `kapkan dataplane status`, и он экспортируется как метрика — если вы рассчитывали на native,
настройте оповещение об этом. См. [оповещение в разделе «Эксплуатация»](/docs/dataplane-operate).
</Callout>

## Истечение правил и завершение работы

Каждое сгенерированное правило несёт собственную отметку времени истечения, и программа в ядре считает
истёкшее правило отсутствующим. Это критично: если процесс Kapkan падает, его убивают или он зависает,
установленные им правила всё равно перестают действовать по расписанию — мёртвая плоскость управления не
может бесконечно оставлять легитимный трафик жертвы отброшенным.

При штатном завершении работы `on_exit` определяет, что останется. Значение по умолчанию, `keep`,
оставляет программу подключённой, чтобы статическая политика продолжала действовать при перезапуске или
обновлении, а динамические правила отмирали сами. `detach` полностью удаляет программу, что пропускает
весь трафик.

## Лимиты и память

`limits` задаёт размер карт ядра, которые выделяются **один раз**, при подключении программы:

| Ключ | По умолчанию | Что ограничивает |
| --- | --- | --- |
| `max_dynamic_rules` | 4096 | Правила, которые может установить детектор. Каждый бан добавляет до 8. |
| `max_static_rules` | 256 | Ваши собственные постоянно действующие правила. |
| `max_ratelimit_sources` | 1048576 | Корзины токенов для каждого источника. |

`max_dynamic_rules` должно быть **не меньше** `ban.max_active_bans × 8`; Kapkan отклоняет меньшую
конфигурацию, потому что альтернатива — это установки, начинающие сбоить в разгар атаки и незаметно
вырождающиеся в чёрную дыру. Значения по умолчанию лежат ровно на этой границе при 512 активных банах.

Поскольку карты выделяются заранее, память резервируется независимо от того, идёт атака или нет, и
таблица корзин по источникам доминирует в общем объёме. Память карт относится на memory cgroup сервиса
(ядро 5.11+), поэтому если вы задаёте `MemoryMax=` для юнита, рассчитывайте его с учётом карт.

Карты — не весь бюджет. Очередь приёма каждого слушателя телеметрии вмещает до
[`listen.queue`](/docs/configuration) датаграмм примерно по 10 КБ — до ~160 МБ на слушатель при
значении по умолчанию, — и заполняется она ровно тогда, когда телеметрия приходит быстрее, чем её
успевают декодировать, то есть во время атаки. При лимите, в котором для очередей не осталось места,
OOM-killer завершит демон раньше, чем слушатель отбросит хоть одну датаграмму.
