# Один адрес, много узлов (anycast)

<Callout type="info" title="Адрес объявляет ваша сеть; Kapkan ведёт машины за ним">
У Kapkan нет мнения о маршрутизации, и он к ней никогда не притрагивается. **Ваш** маршрутизатор,
ваш speaker или балансировщик вашего облака ставит один адрес перед несколькими
[граничными узлами](/docs/edge); Kapkan даёт каждой из этих машин её сертификаты, её конфигурацию
и её собственную службу решений и говорит вам, какая из них годна обслуживать. Ничто в Kapkan не
объявляет, не снимает и не направляет адрес зоны — BGP-speaker мозга существует для жертв под
атакой, а не для служебной маршрутизации.
</Callout>

Всё на этой странице было выполнено на настоящем ядре с настоящим маршрутным переходом, настоящим
nginx, настоящим HTTP/3 и настоящим удостоверяющим центром ACME, прежде чем было записано:
приёмочный стенд — `engine/scripts/labnet/edge-e6-anycast.sh`, два узла за одним
`198.51.100.7/32`, проложенным как ECMP-маршрут через два линка «точка-точка», с переключением
политики хеширования в ядре от плеча к плечу. Числа ниже приводятся вместе с условиями, которые их
породили, потому что большинство из них меняется вместе с этими условиями.

## Что даёт общий адрес, а что нет

Он даёт одно имя, одну историю с сертификатами и одну политику на N машин, а машину выбирает сеть.
Он **не** объединяет ничего из того, что узлы считают или кешируют. Строчка, которую стоит держать
в голове: **мозг раздаёт политику, но никогда не вердикты.**

- **Любой потолок частоты — на узел.** `policy.rate.rps` — это ведро с токенами на той машине,
  которая обслуживает запрос. Два узла за одним адресом — это два ведра, и источник, который сеть
  размазывает по обоим, встречает каждое из них отдельно. См.
  [потолки на узел](#потолки-на-узел-и-выбранное-вами-хеширование) — это тот единственный факт,
  который чаще всего застаёт врасплох оператора, переходящего с одного узла на три.
- **Любая таблица вердиктов — на узел.** Свёртки, которые переводят источник флуда в запрет, — это
  собственные десятисекундные окна узла. Источник, заблокированный на одном узле, не заблокирован
  у его соседа.
- **Любой кеш TLS-сессий — на узел**, и сессия, выданная на одном узле, никогда не возобновляема
  на другом — [что не переходит между узлами](#что-переходит-между-узлами-а-что-нет).
- **Любой сертификат — собственный сертификат узла.** Два узла, обслуживающих одно имя,
  обслуживают два разных конечных сертификата, выпущенных по двум ACME-заказам с двух ключей
  учётных записей, которые никогда не покидают свои машины. Стенд прочитал оба отпечатка — они
  различаются.
- **Допуск — общий для парка.** Посетитель, прошедший
  [ступень доказательства работы](/docs/edge#ступень-доказательства-работы) на одном узле, имеет
  допуск на всех: ключи подписи приходят в документе.
- **Рычаг и файл зон — общие для парка.** Изменение частоты, ступень, рычаг доходят до каждого узла
  на его следующем опросе и ничего не перезагружают —
  [разделение на быстрый и медленный пути](/docs/edge#разделение-на-быстрый-и-медленный-пути)
  не зависит от того, сколько узлов в парке.

## Топология

```
                     ┌── линк A (10.0.1.0/30) ──▶ edge-1   198.51.100.7/32 на lo
 клиент ──▶ маршр. ──┤                                      kapkan edge · nginx · токен a1
   198.51.100.7      └── линк B (10.0.2.0/30) ──▶ edge-2   198.51.100.7/32 на lo
   (один ECMP-маршрут,                                      kapkan edge · nginx · токен a2
    два nexthop)                                                 │
                                                                 └── unicast ──▶ мозг (API)
```

Четыре правила, и стенд построен ровно по ним:

1. **VIP живёт на loopback каждого узла**, как `/32`:

   ```sh
   # на каждом узле за этим адресом
   ip addr add 198.51.100.7/32 dev lo
   ```

   Kapkan отрисовывает директивы `listen` без адреса, поэтому nginx отвечает на том адресе,
   которым воспользовался клиент, а отрисовка вообще не упоминает VIP. Ни `edge.yaml`, ни файл зон
   его не называют.

2. **Маршрутизатор несёт один маршрут с одним nexthop на узел**, а не по маршруту на узел:

   ```sh
   # на маршрутизаторе перед ними
   ip route replace 198.51.100.7/32 \
     nexthop via 10.0.1.2 dev leg-a weight 1 \
     nexthop via 10.0.2.2 dev leg-b weight 1
   ip route flush cache
   ```

   Маршрут с двумя nexthop — это ECMP-маршрут; проверка — `ip route show 198.51.100.7/32`, который
   печатает две строки `nexthop`. Speaker (bird, FRR), принимающий объявления обоих узлов и
   сливающий их, даёт то же самое — см. [вариант с BGP](#вариант-с-bgp).

3. **Каждый узел доходит до мозга по unicast, со своего адреса, со своим привязанным токеном.**
   Один токен `agent` на узел, привязанный через `api.tokens[].node`, здесь не роскошь: мозг
   отмечает присутствие и отдаёт документ каждого узла по имени, а общий токен за общим адресом
   обесценивает и то и другое.

   ```yaml
   # kapkan.yaml на мозге
   api:
     tokens:
       - { name: edge-1, token_env: KAPKAN_EDGE_1_TOKEN, role: agent, node: edge-1 }
       - { name: edge-2, token_env: KAPKAN_EDGE_2_TOKEN, role: agent, node: edge-2 }
   edge:
     nodes:
       - { name: edge-1 }
       - { name: edge-2 }
     stale_after_seconds: 15
   ```

   Стенд проверяет обе половины: мозг отдаёт `GET /api/v1/edge/zones?node=edge-1` по токену edge-1
   и отвечает `403`, когда тот же токен спрашивает про имя edge-2. См.
   [привязку агентского токена к его узлу](/docs/authentication#привязка-агентского-токена-к-его-узлу).

4. **Конфигурации узлов одинаковы всюду, кроме `controller.name`** — и токена, который каждый узел
   читает из своего окружения. Ничто другое в общем адресе не требует значения на узел. Два файла
   `edge.yaml` на стенде различаются ещё и в `state_dir`/`sockets_dir`/`terminator.pid_file`,
   `status_listen` и `terminator.main_conf`, но только потому, что два его «узла» делят один хост и
   не могут делить эти пути и порты; на отдельных машинах это один и тот же файл с одним
   изменённым именем. Оба проходят `kapkan edge -check`.

### Обратный путь

Ответ клиенту несёт тот адрес, на который пришёл запрос, поэтому на узле с одним аплинком VIP
уходит обратно единственным возможным путём и настраивать нечего. Две вещи всё же требуют
внимания:

- **Трафик, который порождает сам узел, должен использовать его unicast-адрес.** Опрос мозга,
  отчёт и ACME-заказ уходят по маршруту по умолчанию с собственным адресом источника узла — именно
  это и делает узел опознаваемым. Не давайте VIP маршрут, который сделает его предпочтительным
  источником; `/32` на `lo` этого не делает.
- **Узел, чей маршрут по умолчанию ведёт в управляющий или «мозговой» аплинк, обязан отправлять
  ответы с VIP через служебный линк.** Дайте трафику с общего адреса собственный маршрутный
  контекст, сначала переносимая форма:

  ```sh
  # отдельная таблица для трафика, исходящего с общего адреса
  ip route add default via 10.0.1.1 dev leg-a table 100
  ip rule  add from 198.51.100.7 lookup 100
  ```

  Скажем прямо, что это делает: в таблице 100 **один** маршрут по умолчанию, поэтому она
  *прибивает* каждый ответ с VIP к leg-a, на какой бы линк ни пришёл запрос. С одним служебным
  линком это ровно то, что нужно. С двумя служебными линками задайте в таблице 100 многопутевой
  маршрут по умолчанию —
  `ip route add default table 100 nexthop via 10.0.1.1 dev leg-a nexthop via 10.0.2.1 dev leg-b` —
  и примите, что ответ уйдёт по хешу ядра, а не по линку входа; возврат ровно по тому линку, на
  который пришёл пакет, — это работа отслеживания соединений (`CONNMARK`, восстанавливаемая в
  fwmark, с правилом на каждый линк), а не правила по адресу источника. В любом случае ответ уходит
  служебным линком, а это и нужно вышестоящему узлу с `rp_filter` или межсетевым экраном с
  состоянием.

  **Устройство VRF** (`ip link add vrf-edge type vrf table 100`, затем подчинить линк) — та же
  таблица, до которой добираются через устройство, а не через правило, на ядрах, собранных с
  `CONFIG_NET_VRF`. Форма с утечкой маршрутов выше — та, что проверена в лаборатории сетевой
  интеграции, и работает на любом ядре с `CONFIG_IP_MULTIPLE_TABLES`; у узлов anycast-стенда по
  одному линку, поэтому считайте рецепт для двух аплинков
  [рецептом обратного пути](/docs/network-integration#обратный-путь), применённым здесь, а не
  плечом этого стенда. Асимметричные пути приносят с собой и
  [ловушку `rp_filter`](/docs/network-integration#rp_filter-и-асимметричный-ответ).

### Размещение, если у парка есть точки присутствия

Узлы за одним адресом обязаны все обслуживать зоны на этом адресе: дайте каждому из них хост-группу
зоны в `edge.nodes[].hostgroups` или оставьте зону глобальной на узлах без области размещения.
Зона, размещённая в стороне от узла, там вообще не отрисовывается — размещённая зона стенда никогда
не появляется на узле, который не перечисляет её группу, и этот узел ничего не отвечает по её
имени. Правило и его последствия — в разделе
[Размещение зон по узлам](/docs/edge#размещение-зон-по-узлам).

## На какой узел попадает клиент: хеш

Ядро выбирает nexthop, хешируя пакет, и **какие поля оно хеширует — это sysctl, который задаёте
вы**, а не свойство anycast:

```sh
sysctl -w net.ipv4.fib_multipath_hash_policy=0   # уровень 3: адрес источника и назначения
sysctl -w net.ipv4.fib_multipath_hash_policy=1   # уровень 4: 4-кортеж, порты включительно
ip route flush cache                             # работающий кеш хранит прежнее решение
```

| Политика | Что хеширует | Что получает один клиент | Когда её брать |
| --- | --- | --- | --- |
| `0` (уровень 3) | адрес источника и назначения | **Один узел** на каждое соединение, пока не изменится топология | Стабильное, отлаживаемое размещение: один клиент держится одного узла, его кеш сессий остаётся тёплым, а QUIC остаётся на месте. Рекомендуемое значение по умолчанию — с оговоркой про потолок ниже |
| `1` (уровень 4) | 4-кортеж, порты включительно | **Оба узла**, соединение за соединением | Ровное распределение по узлам ценой того, что соединения одного клиента, а с ними и учёт его частоты, разлетаются по всем |

На стенде 40 свежих соединений от одного клиента при политике `0` все несли имя одного и того же
узла; при политике `1` те же 40 достигли обоих узлов, и точно так же — 40 запросов
`--http3-only`: та же политика хеширует UDP-4-кортеж, так что **QUIC распределяется ровно как
TCP**, и оба узла посчитали свою долю в `kapkan_edge_requests_total{protocol="h3"}` и в
`h3_requests` отчёта за окно.

Ни одна из форм не «липкая» ни в каком смысле, на который могло бы положиться соединение. Смена
адреса клиента (Wi-Fi на LTE, перепривязка NAT) — это новый вход хеша при любой политике, а при
уровне 4 каждое новое соединение — новый жребий: оно попадает не на тот узел, где было прошлое,
примерно в (N−1)/N случаев — при двух узлах каждое второе соединение. Эта доля и есть частота, с
которой клиент платит полное TLS-рукопожатие, ведь сессия живёт только на том узле, который её
выдал. QUIC-соединение, попавшее на узел, который его никогда не видел, просто переподключается:
nginx маршрутизирует QUIC по сокету, на который тот пришёл, а не по идентификатору соединения, и
миграция соединения **между** узлами не поддерживается — см.
[чего не умеет nginx](/docs/edge#http3-quic).

## Потолки на узел и выбранное вами хеширование

`policy.rate.rps` применяется на том узле, который обслуживает запрос, поэтому источник,
размазанный по N узлам, может быть пропущен в N раз выше потолка. Это общеизвестная половина. Та
половина, которая стоит операторам инцидента, — что **две формы хеширования различаются по роду, а
не только по степени.**

Стенд задал `policy.rate.rps: 5` и выпустил 40 соединений от одного источника по двум узлам:

| Политика хеша | Обслужено | Отказано (`429`) | `deny_rate` edge-1 / edge-2 | Пачка |
| --- | --- | --- | --- | --- |
| `0` (уровень 3) | 6 | 34 | 0 / 34 | 0,3 с |
| `1` (уровень 4) | 12 | 28 | 10 / 18 | 0,2 с |

Читайте две строки одну против другой, а не по отдельности. Какой именно узел отказывает и точное
разделение по узлам — дело хеша, и оно меняется от прогона к прогону: повторный прогон разделил
отказы уровня 4 как 14/14 вместо 10/18, — тогда как число обслуженных и соотношение не изменились.

- **При уровне 4 источник получил в 2,0 раза больше пропущенных запросов.** Эта цифра — *диапазон*,
  а не константа: ведро узла держит `rps` токенов и пополняется на `rps` в секунду, поэтому за
  пачку длительностью `T` секунд на узел пропускается `rps + rps·T`, а множитель приближается к
  числу узлов, только пока доля всплеска на каждом узле всё ещё превышает его собственную норму.
  Стенд проверяет диапазон 1,5×–2,5×, записывая длительность пачки рядом со счётчиками — потому в
  таблице и есть колонка *пачка*. **Задавайте `rps` на узел примерно как задуманный потолок для
  всего парка, делённый на число узлов**, и ожидайте, что реальная пропущенная частота окажется
  между этим значением и самим потолком.
- **При уровне 3 весь всплеск приходится на один узел** — и 34 отказа в десятисекундном окне одного
  узла пересекают правило флуда в свёртках (не менее 20 отказов и не менее 30 % решённых запросов
  этого источника). В зоне, где `challenge` равен `off` или `manual` — у зоны стенда он `off`, —
  это переводит источник там в **запрет в таблице вердиктов** на `DenyTTL`: минута для начала, при
  повторе удваивающаяся до десяти. Стенд потом щупает этот источник и требует `403`. В зоне
  `challenge: auto` первое пересечение забирает себе [лестница](/docs/edge#лестница): источник
  отправляется на ступень доказательства работы и получает запрет, только если продолжает флудить
  после прохождения ступени или под вызовом, — браузер проходит, бот нет. При уровне 4 те же 40
  соединений разделились 10/18, ни один узел вообще не переступил порог, и оба узла по-прежнему
  сообщают источник как `allow` в своих `top_sources`.

<Callout type="warning" title="Низкий rps на узел при хешировании по уровню 3 блокирует занятого клиента">
При уровне 4 источник сверх своего потолка *притормаживают*: он собирает `429` с `Retry-After` и
остаётся `allow`. При уровне 3 тот же самый всплеск *блокируют*: он сосредоточен на одном узле и
пересекает правило флуда там. В зоне с `challenge: off` или `manual` это сразу `403` на `DenyTTL` —
перевод, о котором не объявляет ни один `429` и о котором не знает ни один другой узел. В зоне
`challenge: auto` это сначала [ступень](/docs/edge#лестница) и запрет только если источник флудит
дальше — посадка мягче, но это всё равно решение одного узла о клиенте, которого остальные узлы
считают нормальным. Если вы используете рекомендуемое хеширование по уровню 3, задавайте потолок на
узел по самому занятому законному клиенту, какой у вас есть, и понаблюдайте за
`kapkan_edge_decisions_total{result="deny_rate"}` по узлам, прежде чем его затягивать.
</Callout>

Запрос, которому отказали по частоте, **не** несёт заголовка с атрибуцией узла — location
`@kapkan_denied` в отрисовке объявляет собственный `add_header`, а nginx отбрасывает
унаследованный набор везде, где location объявляет свой, — так что считайте отказы по `/metrics`
каждого узла, а не по ответу.

## Сертификаты: раздача детерминирована

Каждый узел заказывает собственный сертификат на общее имя, а проверка HTTP-01 от CA приходит на
VIP — то есть попадает на тот узел, который выберет хеш, а это обычно **не** тот узел, который
заказывал. Работает это потому, что заказывающий узел публикует свой ответ на вызов в мозг, а мозг
раздаёт его в документе каждого узла, обслуживающего зону.

Стенд доказывает это единственным некруговым способом: он прибивает маршрут к одному только
edge-2 на всё время выпуска, так что сертификат edge-1 мог быть проверен только по токену вызова,
розданному на edge-2. Оба узла в итоге держали собственные сертификаты на общее имя, с разными
отпечатками конечных сертификатов.

Ещё две вещи, которые стенд прибивает гвоздями и которые обе важны на общем адресе:

- **Выпуск сериализуется по зоне — то есть заказы разносятся во времени, а не уменьшаются в
  числе.** Просьба о слоте зоны, пока его держит другой узел, получает `granted: false` с именем
  держателя и `retry_after_seconds`, так что узлы заказывают друг за другом, а не разом. Заказывают
  они по-прежнему N сертификатов: у каждого узла собственный конечный сертификат, поэтому один
  выпуск имени, размещённого на N узлах, стоит N против
  [потолка дубликатов](/docs/edge#ограничения-о-которых-стоит-знать) у CA — около пяти в неделю у
  Let's Encrypt, и считается он по размещению. **Парку больше этого потолка на одном имени нужен
  `acme.fallback` или отдельные учётные записи CA**; никакая сериализация не купит вам шестой
  сертификат. Слот к тому же рекомендательный: узел, прождавший его 15 минут, всё равно
  заказывает, — так что это разносчик во времени, но никогда не замок.
- **Перезапущенный узел ничего не заказывает.** Стенд перезапускает узел и находит его сертификаты
  вернувшимися с диска: его собственный `kapkan_edge_acme_attempts_total` остаётся `0`, и слота у
  мозга он не просит.

## Снятие с маршрута: что значит «сними меня»

Общий адрес хорош ровно настолько, насколько хороша та штука, что перестаёт слать трафик на
сломанный узел. Снимайте по предикату из двух частей — собственный сигнал Kapkan **и** проба
самого слушателя — и не обращайте внимания на два соблазнительных не-сигнала.

| Сигнал | Снимать по нему? | Что видел стенд |
| --- | --- | --- |
| **`/healthz` на `status_listen` отвечает `503`** | **Да** | nginx узла был убит; `/healthz` стал `503` через **495 мс**, при `controller.report_interval_seconds: 1` на стенде |
| **Локальная TLS-проба собственного `:443` узла с SNI зоны не проходит** | **Да** | Не плечо стенда: `/healthz` снимает pid-файл терминатора на такте отчёта, поэтому он не видит заклинивший слушатель, истёкший сертификат или отвергнутое TLS-рукопожатие. Щупайте то же, что делает клиент |
| `converged: false` в состоянии узла | **Нет** | Документ, который узел отверг: прежнее проверенное поколение продолжало обслуживать, `/healthz` оставался `200`, и 20 из 20 запросов через VIP были обслужены — в том числе edge-2 |
| Инвентарь мозга говорит `alive: false` | **Нет** | Это взгляд мозга на опрос, а не взгляд узла на себя, и он отстаёт на `stale_after_seconds` |

**Снимайте, когда отказывает любой из двух сигналов «да», и объявляйте, только пока держатся оба.**
Они отвечают на разные вопросы: `/healthz` говорит, что Kapkan считает процесс терминатора живым, а
проба — что машина действительно доводит до конца TLS-рукопожатие и обслуживает зону. На самом
узле:

```sh
# действительно ли эта машина обслуживает зону? — с узла, к его собственному слушателю
curl -sf -m2 --resolve shop.example.com:443:127.0.0.1 -o /dev/null https://shop.example.com/
```

Именно `--resolve` делает это настоящей проверкой: запрос несёт SNI и Host зоны, поэтому истёкший
сертификат, сломанная отрисовка или мёртвый источник — всё это её проваливает, а `127.0.0.1`
держит пробу в стороне от общего адреса и вне хеша.

<Callout type="warning" title="/healthz снимается на такте отчёта">
Проверка живости терминатора едет на `controller.report_interval_seconds` — **по умолчанию 10 с**,
1 с на стенде. `/healthz` не может рассказать вам о мёртвом nginx быстрее этого интервала, поэтому
**оператор, который снимает маршрут по `/healthz`, ставит этот интервал равным желаемому периоду
опроса** и опрашивает не чаще. Проверке также нужен заданный `terminator.pid_file`: без него узлу
нечего проверять и смерть невидима. И это в любом случае снятие *pid* — мастер-процесс, живой при
заклинившем слушателе, читается как `200`, и ровно поэтому локальная TLS-проба и есть вторая
половина предиката.
</Callout>

### Что будет, если никто не снимет

Маршрут продолжает указывать на мёртвый узел, а хеш продолжает слать ему долю трафика. Когда один
из двух узлов убит начисто, при хешировании по уровню 4 40 соединений стенда разделились на
**16 отказов соединения и 24 обслуженных** — отказы это `000` у клиента, никакого ответа вообще, а
не отказ в обслуживании. Какой узел отваливается и точное разделение — дело хеша и меняется от
прогона к прогону; а вот то, что доля отваливается, — нет. Установленное keepalive-соединение к
выжившему узлу ответило `200` по тому же соединению; соединение к мёртвому узлу просто исчезло.
**Общий адрес не даёт установленному соединению никакой защиты.**

Тем временем мозг замечает — медленно и только для протокола: инвентарь стал `alive: false` через
**5103 мс** после убийства, что складывается из `stale_after_seconds: 5` после последнего появления
мёртвого узла и такта, на котором мозг заметил. Ничто в этом переключении не трогает
маршрутизацию: VIP-маршрут маршрутизатора всё это время был побайтово тем же, журнал мозга ни разу
не упомянул адрес, и его список блокировок — то множество, что объявляет его speaker, — тоже ничего
из этого не нёс.

### Мёртвый nexthop не требует оператора; мёртвый узел требует

Положите **линк** вместо узла, и маршрутизатор сам пометит nexthop как `dead`: все 40 запросов были
обслужены без единого действия оператора. Это различие стоит усвоить — *напрямую подключённый
маршрутизатор замечает потерю линка, маршрутизируемый переход нет.* Узел, который мёртв, пока его
линк поднят, невидим для маршрутизации, и именно поэтому вам нужно снятие по здоровью.

Само снятие — это изменение RIB и ничего больше:

```sh
# на маршрутизаторе: перестать пользоваться сломанным узлом
ip route replace 198.51.100.7/32 via 10.0.1.2 dev leg-a
ip route flush cache
```

Первая пачка стенда, полностью из `200`, завершилась через **45 мс** после этой команды, а за ней
40 из 40 по TCP и 20 из 20 по HTTP/3. Восстановление ограничивает следующий запрос клиента, а не
какой-либо таймер Kapkan.

### Мёртвый мозг — тоже не повод снимать

Парк работает на последнем известном состоянии (fail-static), и общий адрес меняет в этом одну
вещь. С убитым начисто мозгом узлы стенда обслужили 20 из 20 запросов по TCP и 20 из 20 по HTTP/3
через VIP, с обоих узлов, с `/healthz` `200` на каждом: мозга нет в предикате здоровья, а последний
документ и сертификаты продолжают обслуживать с диска.

Единственное, что он меняет, — это **продление**, и только за общим адресом: раздача вызовов выше —
дело мозга, поэтому с упавшим мозгом ответ заказывающего узла на вызов не доходит ни до одного
другого узла, и проверка HTTP-01 удаётся, только когда хеш случайно отправит CA на заказывающий
узел, — примерно 1 попытка из N. Эти попытки повторяются ежечасно и никогда не засчитываются в
пользу запасного CA, так что ничего не сгорает; границу простоя задаёт сертификат, а не мозг.
Сигнал `kapkan_edge_cert_not_after_seconds` за T−30 д — это и есть бюджет, за который вам нужно
починить мозг. См. [что делает узел при отказах](/docs/edge#что-делает-узел-при-отказах).

Возвращает узел в строй **его собственный следующий опрос**, а границу задаёт собственная отсрочка
опроса после неудачи — секунда, удваивающаяся до потолка в 30, — и никогда не
`edge.stale_after_seconds`, который управляет лишь тем, сколько мозг ждёт, прежде чем счесть
молчащий узел потерянным. На стенде оба узла снова были `alive` через **840 мс** после возвращения
мозга, и задержка зависит только от того, сколько длился простой (как высоко успела забраться
отсрочка). Не снимайте адрес из-за того, что мозг недоступен; снимайте из-за того, что узел перед
вами не обслуживает.

### Вариант с BGP

Там, где адрес объявляется, а не прописан статически, поставьте на каждый узел speaker и пусть он
объявляет VIP `/32`, пока держится собственный предикат этого узла. У стенда есть дополнительное
плечо, которое гоняет на bird2 половину этого цикла — ту, что с `/healthz`, **вне приёмочного пути** и за `ANYCAST_BGP=1`, так что по
умолчанию оно пропускается и не несёт записанных чисел:

```sh
#!/bin/sh
# на каждом узле: объявлять, пока здоров, и снять, как только нет
# 9101 ниже — порт status_listen этого узла, подставьте свой
while :; do
  if curl -sf -m1 -o /dev/null http://127.0.0.1:9101/healthz \
     && curl -sf -m2 --resolve shop.example.com:443:127.0.0.1 \
             -o /dev/null https://shop.example.com/; then
    birdc -s /run/bird/ctl enable announce
  else
    birdc -s /run/bird/ctl disable announce
  fi
  sleep 1
done
```

Что это плечо утверждает, при пробе раз в секунду и подогнанном под неё интервале отчёта: убийство
nginx на узле убирает его из FIB маршрутизатора и уводит запросы следующей пачки на выживший узел,
тогда как отвергнутый документ маршрут **не** снимает — `/healthz` остаётся `200`, так что протокол
остаётся включённым. Это тот же контракт, что и в таблице выше, только исполняемый speaker'ом, а не
руками. Speaker ваш: bird, FRR, что угодно, что крутится в вашей сети. Kapkan не поставляет ни
одного и ни одним не управляет.

## Что переходит между узлами, а что нет

| Факт | Переходит? | Почему |
| --- | --- | --- |
| Cookie допуска | **Да** | Ключи подписи ступени общие для парка, они в документе. Посетитель, решивший задачу на одном узле, был обслужен другим по этой cookie, а источник увидел `X-Kapkan-Mark: cleared` |
| TLS-сессия | **Нет** | Сессия — это запись с состоянием в собственном разделяемом кеше узла; её не несёт ни один stateless-билет, и ни один ключ билетов не общий, поэтому на другом узле её не может быть. На предъявленную сессию edge-1 edge-2 отвечает `New` — в обе стороны, и по TLS 1.2, и по TLS 1.3 |
| Ведро частоты, таблица вердиктов, окно свёрток | **Нет** | На узел, по замыслу — [потолки на узел](#потолки-на-узел-и-выбранное-вами-хеширование) |
| QUIC-соединение | **Нет** | nginx маршрутизирует QUIC по сокету, а не по идентификатору соединения; мигрировавший клиент переподключается |

<Callout type="info" title="Сессия возобновляется на том узле, который её выдал, и ни на каком другом">
Catch-all-сервер `:443`, который отрисовывает Kapkan, — а при `omit_catch_all` и голый
QUIC-якорь — несёт собственные строки сессий из зон: `ssl_session_cache shared:kapkan_ssl:10m;
ssl_session_timeout 1d; ssl_session_tickets off;`. Они там обязаны быть, потому что OpenSSL ищет
сессию — и сохраняет её — через контекст того сервера, на котором соединение **началось**, то есть
сервера по умолчанию для адреса, даже после того как SNI перевёл соединение в зону. Поэтому
вернувшийся клиент возобновляет сессию на том узле, который её выдал, одинаково по TLS 1.2 и
TLS 1.3 (при `ssl_session_tickets off` билет 1.3 — это запись с состоянием в том же самом кеше), и
получает `New` на любом другом узле; стенд проверяет обе половины в обе стороны.

Сессию удерживает на её узле именно эта локальность — запись с состоянием в собственном кеше
этого узла, при том что её не несёт ни один stateless-билет и ни один ключ билетов не общий, — а
**не** сертификат. На nginx до 1.29.2 действующий session id context принадлежит
catch-all-серверу без сертификата, так что он ни к чему узел не привязывает (edge-spec §3).

**Используете `omit_catch_all: true`? Вашему собственному серверу по умолчанию на `:443` нужны те
же три строки** — и вашему QUIC-серверу тоже, если вы вдобавок задали `quic.omit_anchor`. Без них
каждый вернувшийся клиент на этом узле платит полное рукопожатие;
[руководство по установке](/docs/edge-install#устранение-неполадок) несёт эту строку.
</Callout>

### MTU: один плохой линк стоит HTTP/3 на всём адресе

QUIC никогда не фрагментирует и сдаётся на пути ниже 1280 байт. На общем адресе это не проблема
отдельного узла, потому что **MTU пути кешируется по назначению, а назначение — это тот самый
адрес, который делят все узлы**:

1. Стенд поставил MTU 1200 только на одном линке. Из 40 запросов `--http3-only` **38 провалились**,
   а TCP всё это время был 40 из 40, потому что TCP зажимает свой MSS на каждое соединение.
   Сколько именно пройдёт, прежде чем урок усвоится, — жребий хеша; стенд проверяет, что
   подавляющее большинство не проходит.
2. Это не доля трафика. Как только первый запрос, добравшийся до узла с малым MTU, научил клиента
   MTU пути в 1200 байт для VIP (`ip route get 198.51.100.7` показывает закешированное исключение),
   **ни один** запрос по HTTP/3 не прошёл — даже в сторону нетронутого узла.
3. Починка линка это не вылечила: 10 из 10 всё равно провалились. Закешированное клиентом
   исключение переживает неисправность. Только `ip route flush cache` на клиенте вернул HTTP/3, и
   после этого 20 из 20 прошли с обоих узлов.

Кеши ваших посетителей вам не сбросить. Считайте любой путь ниже 1280 байт на любом линке общего
адреса отказом HTTP/3 для всего этого адреса, чините MTU до того, как объявите h3, и держитесь
[порядка раскатки h3](/docs/edge#http3-quic) — сначала узлы, UDP 443 и MTU вторым шагом.

## Как проверить парк за одним адресом

Выполняйте это с клиента, который дотягивается до адреса, и с операторского токена на мозге.

```sh
# 1. Один маршрут, два nexthop — не два маршрута
ip route show 198.51.100.7/32

# 2. Какая форма хеша действует на самом деле
sysctl net.ipv4.fib_multipath_hash_policy

# 3. Оба узла обслуживают имя, каждый со СВОИМ сертификатом
openssl s_client -connect 10.0.1.2:443 -servername shop.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -fingerprint -sha256
openssl s_client -connect 10.0.2.2:443 -servername shop.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -fingerprint -sha256

# 4. Общий адрес обслуживает, и по TCP, и по HTTP/3
curl -s -o /dev/null -w '%{http_code}\n' https://shop.example.com/
curl --http3-only -s -o /dev/null -w '%{http_code} %{http_version}\n' https://shop.example.com/

# 5. Каждый узел жив, размещён и сообщает свой собственный документ
curl -s -H "Authorization: Bearer $TOKEN" https://kapkan.example.net:8443/api/v1/edge/nodes
```

В инвентаре проверьте по каждому узлу три вещи, в таком порядке:

- **`alive: true` и свежий `last_seen`** — сигнал живости это опрос.
- **`hostgroups` покрывает зону** на каждом узле за адресом — собственную хост-группу зоны или
  `global` для глобальной зоны. Узел, чья область не покрывает её, ничего для неё не отрисовывает и
  ничего не отвечает. (`zones_placed` рядом — это *счётчик*: сколько зон файла держит документ
  этого узла, — так что он скажет вам, что область узла пуста, но никогда не скажет, какие именно
  зоны в ней.) Взгляд со стороны зоны — тот же факт с другого конца:
  `GET /api/v1/edge/zones/status` несёт `placement` каждой зоны, в котором `nodes` обязан
  перечислять каждый узел за адресом, а `alive` — перечислять их всех ещё раз.
- **`report.zones_etag` равен тому ETag, который мозг отдаёт этому узлу**
  (`GET /api/v1/edge/zones?node=<имя>`).

<Callout type="info" title="ETag двух узлов и не должны совпадать">
Каждый узел сообщает ETag **своего собственного** документа. При любом размещении в парке эти
документы различаются — один узел обслуживает зону, которую другой не обслуживает, — так что общий
`zones_etag` по всему парку **не** сигнал здоровья, и гоняться за ним значит гоняться за багом,
которого нет. Держится вот что, по узлам: ETag, который сообщает узел, — это тот ETag, который мозг
отдал *ему*. Зона, общая для узлов, побайтово одинакова в обоих документах. А ключевого материала
инвентарь не несёт никакого — сертификаты в нём названы зоной, сроком и издателем, но никогда не
байтами.
</Callout>

### Как узнать, какой узел обслужил запрос

Продуктового заголовка с именем узла нет, и это намеренно. Когда он вам нужен на день отладки, его
даст лазейка из файла зон:

```nginx
# /etc/kapkan/debug-node.conf, на который ссылается extra_directives_file зоны
add_header X-Kapkan-Node $hostname always;
```

<Callout type="danger" title="Приём для отладки, а не продуктовый заголовок">
Это публикует имя обслуживающей машины каждому клиенту этой зоны. Kapkan отрисовывает файл дословно,
и `nginx -t` — его единственный сторож. Добавляйте, пока разбираетесь с хешем или размещением, и
снова убирайте. К тому же он не едет на `429` — location отказа объявляет собственный `add_header`,
и nginx отбрасывает там унаследованный набор, — так что он может сказать вам, кто *обслужил*
запрос, но никогда — кто *отказал*. Для отказов читайте `/metrics` каждого узла.
</Callout>
