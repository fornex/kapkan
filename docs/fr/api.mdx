# API REST

Kapkan expose une petite API REST JSON pour observer la détection et piloter la mitigation
manuelle. Elle est servie sur l'adresse définie dans `api.listen`, qui vaut par défaut
`127.0.0.1:8080`. Le même écouteur sert également le [tableau de bord](/docs/dashboard) intégré
et le point de terminaison Prometheus [`/metrics`](/docs/metrics).

L'API est essentiellement en lecture : le statut, les attaques actives et récentes, l'instantané
des hôtes suivis et la table des bannissements sont tous des `GET`. Trois points de terminaison
`POST` modifient l'état — ban manuel, déban manuel et rechargement de la configuration.

<Callout type="warning" title="Authentifiez avant de l'exposer">
La valeur par défaut de `api.listen` se lie à `127.0.0.1`, de sorte que l'API n'est sûre sans
authentification que sur localhost. Avant de vous lier au-delà de la boucle locale, définissez
un token bearer. Voir [Authentification](/docs/authentication).
</Callout>

Toutes les routes `/api/v1` passent par la vérification du token lorsque l'authentification est
configurée ; une fois configurée, chaque requête doit porter `Authorization: Bearer <token>`. Les
tokens portent un **rôle** : les routes `GET` nécessitent le rôle **viewer**, et les routes
mutables (`ban`, `unban`, `config/reload`) nécessitent le rôle **operator**. `config/reload` va
plus loin : il exige un token **non rattaché (admin)**, de sorte que même un token operator
rattaché à un tenant est refusé avec un `403`. Le
[canal des nœuds de scrubbing](#le-canal-des-nœuds-de-scrubbing) prend le rôle **agent** —
l'identifiant d'un nœud de scrubbing qui atteint ces routes et rien d'autre. Une lecture avec un
token viewer fonctionne ; une
mutation avec un token viewer renvoie `403` ; un token inconnu renvoie `401`. Les points de
terminaison `POST` exigent en outre un type de contenu JSON —
envoyez `Content-Type: application/json`. Un `POST` sans cet en-tête est rejeté avec un
HTTP `415 Unsupported Media Type` ; ainsi, si un ban via `curl` échoue avec un 415, cet en-tête
manquant en est presque toujours la cause. Notez que `/metrics` et l'enveloppe statique du tableau
de bord sont servis sans token ; les données chargées par le tableau de bord sont, elles,
récupérées via l'API protégée. Voir [Authentification](/docs/authentication) pour les rôles des
tokens.

Un token peut aussi être **rattaché à un tenant** : il ne voit alors que les lignes de son
tenant sur chaque point de terminaison de lecture (`/status` est reconstruit pour ses propres
hostgroups et compteurs), et ne peut effectuer `ban`/`unban` qu'au sein de son tenant — une cible
hors tenant renvoie un `403` uniforme. Un token rattaché à un tenant ne peut pas du tout recharger
la configuration : `config/reload` est réservé aux tokens non rattachés (admin) et renvoie `403`
sinon. Voir [Multi-tenant](/docs/multi-tenancy).

## Points de terminaison

| Méthode | Chemin | Description |
| --- | --- | --- |
| GET | `/api/v1/status` | Mode, durée de fonctionnement, réseaux protégés, seuils, hostgroups, nombre d'attaques/bannissements actifs. |
| GET | `/api/v1/attacks` | Attaques actives ainsi que les 100 dernières terminées, avec échantillons et classification. |
| GET | `/api/v1/hosts` | Instantané des hôtes suivis : débits par direction, baselines apprises, état d'attaque. |
| GET | `/api/v1/bans` | Tous les bannissements, actifs et historiques. |
| GET | `/api/v1/traffic` | Historique des débits par hôte persisté (viewer) ; `{available:false, points:[]}` lorsque le stockage est désactivé. |
| GET | `/api/v1/audit` | Piste d'audit des mutations attribuée aux opérateurs (qui a banni/rechargé, quand, résultat). |
| POST | `/api/v1/ban` | Bannir manuellement une adresse. |
| POST | `/api/v1/unban` | Retirer manuellement un bannissement. |
| POST | `/api/v1/config/reload` | Relire le fichier de configuration (équivalent à `SIGHUP`). |
| POST | `/api/v1/dataplane/sources` | Rejeter une source dans le [plan de données](/docs/dataplane), rattachée à une victime, avec un TTL obligatoire. |
| POST | `/api/v1/dataplane/sources/unblock` | Retirer immédiatement un blocage de source. |
| GET | `/api/v1/dataplane/rules` | Le flux de règles du [nœud de scrubbing](/docs/scrubbing#nœuds-de-nettoyage-gérés) (`agent`/`operator` non rattaché) ; long-poll par ETag, retenu jusqu'à 30 s. |
| POST | `/api/v1/dataplane/nodes/{name}/report` | Le rapport consultatif d'un nœud de scrubbing sur lui-même (`agent`/`operator` non rattaché). |
| GET | `/api/v1/dataplane/nodes` | Inventaire des nœuds gérés : vivacité, configuration, nombre de bans par nœud (`viewer` non rattaché ou plus). |
| GET | `/api/v1/edge/history` | L'[historique edge](/docs/storage#historique-edge) d'une zone, regroupé en intervalles sur une plage (`viewer` ; un token rattaché à un tenant sur ses propres zones) ; `{available:false, points:[]}` lorsque le stockage est désactivé. |
| GET | `/api/v1/edge/history/sources` | Les sources significatives de la zone sur une plage — qui a été refusé, mis au défi ou l'aurait été (`viewer` ; un token rattaché à un tenant sur ses propres zones). |
| GET | `/api/v1/edge/events` | Les transitions que le cerveau a vues dans la flotte edge, la plus récente d'abord (`viewer` non rattaché ou plus). |
| GET | `/metrics` | Métriques Prometheus. |
| GET | `/healthz` | Sonde de vivacité/disponibilité non authentifiée : `503` jusqu'au démarrage complet, puis `200`. |

Toutes les réponses sont au format JSON. Les erreurs renvoient un objet de la forme
`{"error": "..."}` accompagné d'un statut HTTP approprié.

### GET /api/v1/status

Renvoie le mode de fonctionnement actuel et un résumé de ce que Kapkan protège. Pour le lire
(omettez l'en-tête `Authorization` si aucun token n'est configuré) :

```sh
curl -fsS localhost:8080/api/v1/status \
  -H "Authorization: Bearer $TOKEN" | jq
```

```json
{
  "dry_run": true,
  "uptime_seconds": 8123,
  "version": "v1.2.0 · a1b2c3d",
  "update_available": false,
  "role": "operator",
  "unscoped": true,
  "networks": ["203.0.113.0/24", "198.51.100.0/24"],
  "active_attacks": 1,
  "active_bans": 1,
  "thresholds": {
    "pps": 80000,
    "mbps": 1000,
    "flows_per_sec": 20000
  },
  "hostgroups": [
    { "name": "web", "calculation": "per_host", "mitigation": "blackhole", "ban": true }
  ]
}
```

`dry_run` indique le mode global : lorsqu'il vaut `true`, aucun blackhole n'est annoncé à vos
routeurs. `version` est le build en cours d'exécution, toujours présent et sans aucune sortie
réseau. `update_available` vaut `false` à moins que la vérification optionnelle
[`update_check`](/docs/configuration) ne soit activée et ne détecte une version plus récente —
il vaut alors `true` et `latest_version`, `latest_is_security` et `latest_url` sont inclus à ses côtés. Voir [Mise à niveau](/docs/upgrading).
`thresholds` et `hostgroups` reflètent la configuration active ; voir
[Détection](/docs/detection) et [Hostgroups](/docs/hostgroups) pour leur forme complète.
`role` et `unscoped` sont toujours présents — ils indiquent au tableau de bord quel token il
utilise. Les champs `networks`, `thresholds`, `bgp`, `scrubbing` et `notify` relèvent de la
configuration à l'échelle du déploiement et ne sont renvoyés qu'à un token non rattaché (admin) ;
un token rattaché à un tenant reçoit un objet de statut sans eux (uniquement `dry_run`, `version`,
`uptime_seconds`, `update_available`, `role`, `unscoped`, ses propres `hostgroups` et les
compteurs). Un token admin obtient en plus des objets `bgp`, `scrubbing` et `notify` — `notify`
n'expose que les canaux activés, jamais les tokens ou les URL. Donc, si un champ semble
« manquant », vérifiez si votre token est rattaché à un tenant plutôt que de supposer que Kapkan
est en panne.

### GET /api/v1/attacks

Renvoie les attaques actuellement actives ainsi que les 100 dernières terminées (la plus récente
en premier). Les deux tableaux contiennent des objets `Attack`.

| Champ | Type | Notes |
| --- | --- | --- |
| `scope` | string | `host` ou `group`. Les attaques à portée de groupe ne portent pas de `target`. |
| `target` | string | L'adresse attaquée (portée hôte). |
| `group` | string | Nom du hostgroup (portée groupe, ou groupe de l'hôte). |
| `tenant` | string | Le tenant du groupe propriétaire, lorsqu'il est étiqueté (voir [Multi-tenant](/docs/multi-tenancy)). |
| `direction` | string | `incoming` ou `outgoing`. |
| `metric` | string | La métrique qui a déclenché, p. ex. `pps`, `mbps`, `tcp_syn_pps`. |
| `rate` | number | Le débit de la métrique déclenchante, dans son unité : la mesure courante du moteur tant que l'attaque est active, la dernière avant sa fin ensuite. |
| `threshold` | number | Le seuil franchi. |
| `rates` | object | Ventilation complète des débits par protocole (voir ci-dessous), issue de la même mesure que `rate`. |
| `active` | bool | `true` tant que l'attaque est en cours. |
| `ban_state` | string | `active`, `withdrawn` ou `rejected`. Omis lorsqu'il n'y a pas de bannissement. |
| `method` | string | Méthode de mitigation : `blackhole`, `flowspec` ou `divert`. Omis lorsqu'il n'y a pas de bannissement. |
| `route` | string | La chaîne de route (`blackhole …` / `divert …`), ou un résumé `flowspec: ...`, lorsqu'un bannissement existe. |
| `flowspec` | array | Les règles [FlowSpec](/docs/flowspec) générées, lorsque `method` vaut `flowspec`. |
| `dry_run` | bool | Indique si le bannissement était virtuel. |
| `started_at` | string | Horodatage RFC 3339. |
| `ended_at` | string | Horodatage RFC 3339 ; omis tant que l'attaque est active. |
| `sample` | object | Échantillon de flow capturé à la détection ; omis lorsque l'échantillonnage est désactivé. |
| `classification` | object | Vecteur d'attaque inféré ; omis lorsqu'il n'est pas classifié. |
| `reason` | object | Pourquoi la détection a déclenché — provenance du seuil, warm-up, parts de protocole. Attaché au démarrage. |

```json
{
  "active": [
    {
      "scope": "host",
      "target": "203.0.113.66",
      "group": "web",
      "direction": "incoming",
      "metric": "pps",
      "rate": 412000,
      "threshold": 80000,
      "rates": {
        "pps": 412000,
        "mbps": 3100,
        "flows_per_sec": 9800,
        "udp_pps": 405000,
        "udp_mbps": 3080
      },
      "active": true,
      "ban_state": "active",
      "route": "blackhole 203.0.113.66/32 next-hop 192.0.2.1 community 65000:666",
      "dry_run": false,
      "started_at": "2026-06-13T09:41:07Z",
      "sample": {
        "top_sources": [
          { "key": "198.51.100.23", "packets": 1240000, "bytes": 1612000000 }
        ],
        "top_src_ports": [
          { "key": "123", "packets": 1180000, "bytes": 1534000000 }
        ],
        "top_dst_ports": [
          { "key": "443", "packets": 1240000, "bytes": 1612000000 }
        ],
        "protocols": [
          { "key": "udp", "packets": 1240000, "bytes": 1612000000 }
        ],
        "total_packets": 1240000
      },
      "classification": {
        "type": "ntp_amplification",
        "confidence": 0.95,
        "src_port": 123
      }
    }
  ],
  "recent": []
}
```

Tant qu'une attaque est active, `rate` et `rates` sont relus depuis le moteur à chaque
requête : ils suivent donc l'attaque au lieu de rapporter l'instant de sa détection — quand
la fenêtre glissante ne contenait qu'une seconde et sous-estimait un flood soutenu d'un
facteur plusieurs. `metric` et `threshold` restent tels qu'ils ont été capturés à la
détection : ils nomment ce qui a déclenché, et le moteur juge la fin de l'attaque d'après
les seuils figés à son début.

L'objet `rates` porte le trio de base (`pps`, `mbps`, `flows_per_sec`) plus les champs
par protocole qui sont non nuls : `tcp_pps`, `tcp_mbps`, `udp_pps`, `udp_mbps`,
`icmp_pps`, `icmp_mbps`, `tcp_syn_pps`, `tcp_syn_mbps`, `frag_pps`, `frag_mbps`. L'objet
`sample` résume les flows mis en tampon à l'origine de la détection — `top_sources`,
`top_src_ports`, `top_dst_ports`, `protocols` (chacun une liste de compteurs
`{key, packets, bytes}`), une liste `flows` brute facultative et `total_packets`. Le `type`
de `classification` est l'un des vecteurs documentés dans [Détection](/docs/detection) ;
`confidence` est la part (`0..1`) du trafic d'attaque correspondant à la signature gagnante, et
`src_port` est le port de service réfléchi pour les vecteurs d'amplification.

L'objet `reason` explique **pourquoi** la détection a déclenché — capturé une seule fois au
démarrage, hors du chemin critique. `threshold_source` vaut `static` ou `baseline` : selon que la
limite franchie provient de la configuration statique ou d'une [baseline apprise](/docs/baselines)
échauffée. Lorsqu'il vaut `baseline`, un objet `baseline` porte le calcul effectif
(`min(ceiling, max(floor, normal × factor))`). `baseline_configured`, `warming_up` et
`warmup_remaining_seconds` expliquent un seuil statique qui ne s'est appliqué que parce que la
baseline n'était pas encore échauffée. `shares` est la fraction par protocole du total des PPS
qui a guidé la classification, et `dominant_share_gate` est la part qu'un protocole doit atteindre
pour remporter un vecteur (sinon l'attaque est `mixed`). Voir [Détection](/docs/detection) pour
savoir comment le lire.

```json
{
  "reason": {
    "threshold_source": "baseline",
    "baseline": { "normal": 1200, "factor": 8, "floor": 5000, "ceiling": 80000 },
    "baseline_configured": true,
    "shares": { "udp": 0.98, "syn": 0, "tcp": 0.01, "icmp": 0, "frag": 0 },
    "dominant_share_gate": 0.5
  }
}
```

### GET /api/v1/hosts

Renvoie un instantané de chaque hôte suivi — les données des principaux émetteurs. Chaque entrée
est un `HostStat`.

| Champ | Type | Notes |
| --- | --- | --- |
| `target` | string | L'adresse de l'hôte. |
| `group` | string | Le nom du hostgroup de l'hôte. |
| `rates` | object | Débits entrants courants sur la fenêtre glissante. |
| `rates_out` | object | Débits sortants ; non nuls uniquement lorsque la détection sortante est activée. |
| `in_attack` | bool | Indique si l'hôte est impliqué dans une attaque active. |
| `metric` | string | La métrique de l'attaque active ; omise lorsque l'hôte n'est pas attaqué. |
| `direction` | string | La direction de l'attaque active ; omise lorsque l'hôte n'est pas attaqué. |
| `baseline` | object | Baseline entrante apprise ; présente lorsque des baselines sont configurées. |
| `baseline_out` | object | Baseline sortante apprise ; présente lorsque des baselines sont configurées. |

```json
{
  "hosts": [
    {
      "target": "203.0.113.66",
      "group": "web",
      "rates": {
        "pps": 412000,
        "mbps": 3100,
        "flows_per_sec": 9800,
        "udp_pps": 405000
      },
      "rates_out": {
        "pps": 120,
        "mbps": 2
      },
      "in_attack": true,
      "metric": "pps",
      "direction": "incoming",
      "baseline": {
        "pps": 950,
        "mbps": 7,
        "flows_per_sec": 60
      },
      "baseline_out": {
        "pps": 110,
        "mbps": 2,
        "flows_per_sec": 14
      }
    }
  ]
}
```

Les objets `baseline` et `baseline_out` portent le trio de base de la normale apprise (`pps`,
`mbps`, `flows_per_sec`) et n'apparaissent que lorsque des baselines EWMA sont configurées pour
le groupe de l'hôte. Voir [Baselines](/docs/baselines).

### GET /api/v1/bans

Renvoie la table complète des bannissements — actifs et historiques. Chaque entrée est un `Ban`.

| Champ | Type | Notes |
| --- | --- | --- |
| `target` | string | L'adresse bannie. |
| `prefix` | string | Le préfixe de blackhole (`/32` ou `/128`). |
| `metric` | string | La métrique qui a déclenché le bannissement ; omise pour les bannissements manuels. |
| `rate` | number | Débit observé au moment du bannissement ; omis lorsqu'il est nul. |
| `threshold` | number | Seuil franchi ; omis lorsqu'il est nul. |
| `next_hop` | string | Le next-hop de rejet. |
| `community` | string | L'ensemble de communities attaché à la route — la community RTBH pour un blackhole, la community de divert (scrubbing) pour un ban divert — jointes par des espaces lorsqu'il y en a plusieurs. |
| `local_pref` | number | Le `LOCAL_PREF` attaché à la route ; omis lorsqu'il est nul. |
| `node` | string | Le [nœud de nettoyage géré](/docs/scrubbing#nœuds-de-nettoyage-gérés) auquel ce ban divert est figé ; omis lorsque le ban ne dévie pas vers un nœud géré. |
| `route` | string | La chaîne de route complète, ou un résumé `flowspec: ...` pour les bannissements FlowSpec. |
| `state` | string | `active`, `withdrawn` ou `rejected`. |
| `dry_run` | bool | Indique si le bannissement était virtuel. |
| `manual` | bool | `true` pour les bannissements demandés par l'opérateur. |
| `started_at` | string | Horodatage RFC 3339. |
| `expires_at` | string | Expiration du TTL ; les bannissements ne sont jamais permanents. |
| `withdrawn_at` | string | Moment où la route a été retirée ; omis tant que le bannissement est actif. |
| `reason` | string | Raison pour laquelle un bannissement a été rejeté ou retiré ; omise sinon. |
| `method` | string | Méthode de mitigation : `blackhole`, `flowspec` ou `divert`. |
| `flowspec` | array | Les règles [FlowSpec](/docs/flowspec) générées, lorsque `method` vaut `flowspec`. |
| `escalation` | array | L'[échelle d'escalade](/docs/escalation) configurée, lorsqu'une est définie. |
| `escalation_step` | number | Index du barreau courant de l'échelle. |

```json
{
  "bans": [
    {
      "target": "203.0.113.66",
      "prefix": "203.0.113.66/32",
      "metric": "pps",
      "rate": 412000,
      "threshold": 80000,
      "next_hop": "192.0.2.1",
      "community": "65000:666",
      "route": "blackhole 203.0.113.66/32 next-hop 192.0.2.1 community 65000:666",
      "state": "active",
      "dry_run": false,
      "manual": false,
      "started_at": "2026-06-13T09:41:07Z",
      "expires_at": "2026-06-13T10:41:07Z"
    }
  ]
}
```

Voir [Mitigation](/docs/mitigation) pour comprendre comment le TTL, l'hystérésis et le plafond de
bannissements façonnent ce cycle de vie.

### GET /api/v1/audit

Renvoie la piste d'audit attribuée aux opérateurs — qui a émis chaque `ban`, `unban`,
`config_reload`, `source_block`, `source_unblock` ou `edge_challenge`, quand, et le résultat
(y compris les actions **refusées**). Les enregistrements sont triés du plus récent au plus ancien
et le point de terminaison est rattaché au tenant côté serveur. Il accepte des paramètres de requête
optionnels `from`/`to` (RFC 3339), `action`
(`ban`/`unban`/`config_reload`/`source_block`/`source_unblock`/`edge_challenge`) et
`target` (une IP), et porte par défaut sur la dernière heure :

```json
{
  "available": true,
  "events": [
    {
      "event_time": "2026-06-22 03:14:09",
      "action": "ban",
      "result": "rejected",
      "operator": "alice",
      "role": "operator",
      "tenant": "customerA",
      "target": "203.0.113.66",
      "target_type": "host",
      "reason": "whitelisted",
      "source": "api",
      "ban_state": "rejected",
      "dry_run": 0
    }
  ]
}
```

Lorsque le stockage est désactivé, la réponse est `{"available": false, "events": []}`. `events`
est toujours un tableau — vide plutôt que `null`, y compris pour un tenant dont la fenêtre ne
contient aucun enregistrement —, si bien qu'un client peut le parcourir sans garde. Notez que
les enregistrements d'audit encodent `dry_run` sous forme d'entier (`0`/`1`), et non sous forme du
booléen JSON utilisé ailleurs sur cette page. Voir la page dédiée [Journal d'audit](/docs/audit)
pour la liste complète des champs, les règles de requête, ainsi que le modèle d'identité des
opérateurs et de rattachement aux tenants.

### POST /api/v1/ban

Place manuellement une adresse en blackhole. Le corps est une seule adresse IP :

```http
POST /api/v1/ban
Content-Type: application/json

{"ip": "203.0.113.66"}
```

Sous forme de commande exécutable (omettez l'en-tête `Authorization` si vous n'avez pas encore configuré de token) :

```sh
curl -fsS -X POST localhost:8080/api/v1/ban \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"ip":"203.0.113.66"}'
```

La réponse est l'objet `Ban` résultant. Un bannissement manuel respecte toutes les règles de
sécurité qu'un bannissement automatique respecte :

- Une cible figurant sur la **liste blanche** est refusée avec un statut HTTP `409 Conflict` et `reason: "whitelisted"` ; elle n'est jamais annoncée.
- Une cible **en dehors des `networks` configurés** est refusée avec un statut HTTP `409` et `reason: "outside configured networks"`.
- Une requête qui dépasserait **`max_active_bans`** est refusée avec un statut HTTP `409` et `reason: "max_active_bans reached"`.

Dans chaque cas de `409`, le corps reste un objet `Ban` avec `state: "rejected"` et le champ
`reason` renseigné. Une IP invalide ou non analysable renvoie un statut HTTP `400`.

<Callout type="warning" title="Le dry-run s'applique toujours">
Un bannissement manuel respecte le mode global. Tant que `dry_run` vaut `true`, le bannissement
est enregistré et renvoyé avec `dry_run: true`, mais aucune route n'est annoncée. Voir le
[modèle de sécurité](/docs/safety).
</Callout>

### POST /api/v1/unban

Retire un bannissement actif pour l'adresse donnée. Le corps a la même forme `{"ip": "..."}` et
le même type de contenu JSON est requis :

```http
POST /api/v1/unban
Content-Type: application/json

{"ip": "203.0.113.66"}
```

En cas de succès, renvoie le `Ban` retiré. S'il n'existe aucun bannissement actif pour l'adresse,
renvoie un statut HTTP `404`.

### POST /api/v1/config/reload

Relit le fichier de configuration depuis le disque et l'applique — le même effet que l'envoi d'un
`SIGHUP`. Le corps est vide ; le type de contenu JSON reste requis. Contrairement à
`ban`/`unban`, ce point de terminaison exige un token **non rattaché (admin)** : un rechargement
remplace l'intégralité de la configuration, de sorte qu'un token rattaché à un tenant est refusé
avec un `403` et `config reload is restricted to unscoped (admin) tokens`.

```json
{
  "reloaded": true,
  "dry_run": false,
  "thresholds": {
    "pps": 80000,
    "mbps": 1000,
    "flows_per_sec": 20000
  }
}
```

Si la nouvelle configuration échoue à l'analyse ou à la validation, la configuration en cours
d'exécution reste intacte et le point de terminaison renvoie un statut HTTP `400` avec l'erreur.
Voir [Configuration](/docs/configuration).

### Le canal de blocage de sources

Deux points de terminaison permettent à ce qui termine déjà le trafic d'une victime — un nginx devant
elle, un exportateur de journaux, un opérateur à 3 h du matin — de confier à Kapkan une **source** à
rejeter dans le [plan de données XDP](/docs/dataplane), rattachée à cette victime et avec un TTL
obligatoire. La décision est prise là où les requêtes sont visibles ; l'application se fait dans le
noyau. Les deux exigent un token `operator` ; le rôle `agent` est refusé.

```sh
curl -fsS -X POST localhost:8080/api/v1/dataplane/sources \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"victim":"203.0.113.10","source":"198.51.100.7","ttl_seconds":600,"reason":"login flood"}'
```

| Champ | Requis | Signification |
| --- | --- | --- |
| `victim` | oui | La destination protégée à laquelle le blocage est rattaché. C'est ce qui est vérifié pour un token de tenant, et ce qui empêche les preuves d'un seul appelant de devenir un rejet global. |
| `source` | oui | L'adresse à rejeter. Doit être de la même famille d'adresses que `victim`. |
| `ttl_seconds` | oui pour un blocage | Durée de vie du blocage, de `1` à `86400` (24 h). Il n'existe pas d'entrées permanentes. Bloquer à nouveau la même paire conserve le `created_at` d'origine et applique le nouveau TTL — le rafraîchissement dont un exportateur a besoin pour maintenir un contrevenant persistant sans va-et-vient de déblocage/reblocage. |
| `reason` | non | Une note libre reprise dans la [piste d'audit](/docs/audit). |

La réponse est le `SourceBlock` résultant :

```json
{
  "source": "198.51.100.7",
  "victim": "203.0.113.10",
  "created_at": "2026-08-17T21:04:11Z",
  "expires_at": "2026-08-17T21:14:11Z",
  "dry_run": false,
  "reason": "login flood"
}
```

`POST /api/v1/dataplane/sources/unblock` prend les mêmes `victim` et `source` (tout `ttl_seconds` est
ignoré) et retire immédiatement cette seule paire, pour que personne n'attende un TTL qu'il a lui-même
saisi. Il renvoie le `SourceBlock` retiré, ou `404` si aucune paire de ce type n'est vivante.

#### Refus

Une erreur de saisie donne `400` ; une requête bien formée refusée par la politique donne `409`.
Chaque appel — refus compris — écrit un événement d'audit attribué, car un blocage refusé est
lui-même une action d'opérateur.

| Statut | Cause |
| --- | --- |
| `400` | JSON ou adresse non analysable, `victim` et `source` de familles d'adresses différentes, ou `ttl_seconds` hors de `[1, 86400]`. |
| `403` | `victim` est hors de votre tenant. Le même refus uniforme que celui des points de terminaison de bannissement, afin que ce point ne devienne pas un oracle d'existence pour les hôtes des autres tenants. |
| `404` | Déblocage uniquement : aucun blocage vivant pour cette paire. |
| `409` | Le plan de données est absent ou désactivé ; `victim` est dans `protected_whitelist` ; `source` est dans `dataplane.allowlist` ; `source` est à l'intérieur des `networks` protégés ; cette source détient déjà 8 victimes ; ou il ne reste aucun emplacement de politique. |

Les deux refus liés aux listes d'autorisation sont les plus intéressants, et ils sont des refus
précisément parce que l'alternative est le silence : le chemin de données laisse passer une source
autorisée à la précédence 1 et le trafic vers une destination protégée à la précédence 2, les deux
**avant** qu'une seule règle ne soit évaluée — un tel blocage s'installerait puis ne correspondrait
jamais à un paquet. Une `source` à l'intérieur de vos propres `networks` est également refusée : un
hôte interne relève du [bannissement](/docs/mitigation), pas du blocage de source.

<Callout type="warning" title="Un échec d'installation retire toutes les paires de cette source">
Les paires d'une source partagent un unique bloc de politique noyau, et le rollback de l'installateur
est tout-ou-rien sur ce bloc. Si une installation échoue, toutes les paires de cette source sont
retirées au lieu de rester enregistrées-mais-non-appliquées, et l'erreur le dit — rajoutez celles
dont vous avez encore besoin. La table ne prétend jamais appliquer quelque chose que le noyau
n'applique pas.
</Callout>

<Callout type="info" title="Les mêmes garanties qu'un bannissement">
Les TTL sont obligatoires et bornés, chaque paire porte sa propre expiration dans le noyau (elle
cesse donc de s'appliquer à l'heure prévue même si Kapkan meurt), les installations sont comptées
contre `dataplane.limits.max_dynamic_rules`, les blocages survivent à un redémarrage via le fichier
d'état, et `dry_run` est respecté — la paire est enregistrée, renvoyée avec `dry_run: true`, et rien
n'atteint une map du noyau. Voir
[Blocages de sources](/docs/dataplane#blocages-de-sources-depuis-votre-propre-pile) pour les limites
et le [Modèle de sécurité](/docs/safety).
</Callout>

### Le canal des nœuds de scrubbing

Ces trois points de terminaison existent pour les [nœuds de nettoyage
gérés](/docs/scrubbing#nœuds-de-nettoyage-gérés) — des machines exécutant
[`kapkan scrub`](/docs/cli). Ils prennent le rôle `agent` (l'identifiant d'un nœud de scrubbing ;
voir [authentification](/docs/authentication)) ou un token `operator` non rattaché, jamais un
`viewer` ni un token rattaché à un tenant : les documents couvrent tous les tenants, de sorte que
les rattacher est une préoccupation de flotte, non de requête.

#### GET /api/v1/dataplane/rules

La table de règles qu'un nœud applique : chaque victime [déviée](/docs/scrubbing) active, avec les
règles [FlowSpec](/docs/flowspec) à supprimer et le TTL à répliquer. Un `GET` simple renvoie le
document courant avec un `ETag` de hachage de contenu ; un `GET` dont le `If-None-Match` nomme cet
ETag est **retenu** jusqu'à ce que la table change ou pendant 30 s au maximum, puis reçoit une
réponse `304` — un long-poll qui offre des mises à jour de règles en moins d'une seconde sur du
HTTP ordinaire. Un nœud s'identifie avec `?node=<name>`, et **cette interrogation est le signal de
vivacité du nœud** — le nom doit donc être un nœud configuré (un nom inconnu renvoie `404`) et, en
dehors du mode local sans token, la requête doit porter un vrai token. Un token lié à un nœud
(`api.tokens[].node`) ne peut interroger que sous l'identité de ce nœud : un autre nom, ou aucun
nom, est un `403` uniforme avant qu'aucune présence ne soit enregistrée. Un rechargement qui
retire le nœud, retire le token ou déplace la liaison du token met fin à une interrogation en
attente avec la réponse qu'une première interrogation obtiendrait désormais (`404`, `401`, `403`).
La présence n'est estampillée que par les tokens `agent` — le `?node=X` d'un operator est un
aperçu du document de X et ne déplace aucune vivacité.

```json
{
  "version": 1,
  "bans": [
    {
      "target": "203.0.113.10",
      "prefix": "203.0.113.10/32",
      "method": "divert",
      "expires_at": "2026-08-13T10:00:00Z",
      "flowspec": [ { "dst": "203.0.113.10/32", "proto": 17, "action": "discard" } ]
    }
  ]
}
```

#### POST /api/v1/dataplane/nodes/\{name\}/report

Le rapport consultatif d'un nœud sur lui-même — version, mode XDP, dry-run côté nœud, charge et
totaux de suppressions — stocké pour la [console](/docs/dashboard). Ce n'est **jamais** un signal
de vivacité (l'interrogation l'est) : un rapport ne peut jamais maintenir un nœud mort marqué comme
actif. Le corps est plafonné à 64 KiB (`413` au-delà) et un `{name}` inconnu renvoie `404`. Le
succès est `204 No Content`.

#### GET /api/v1/dataplane/nodes

L'inventaire des nœuds que rend la vue Nœuds de la console : chaque nœud configuré avec ce que le
cerveau sait (configuration, vivacité de l'interrogation, combien de bans dévient vers lui) joint à
son dernier rapport. Une lecture de rang `viewer`, mais tokens non rattachés uniquement —
l'inventaire nomme les next-hops et les hostgroups, ce qui relève de la topologie de déploiement.
Le nombre seul (`nodes_total`) circule sur `/api/v1/status` pour tous les rôles, de sorte qu'une
console peut décider d'afficher ou non les fonctionnalités liées aux nœuds sans cet appel.

### Le canal edge

Ces points de terminaison existent pour les [nœuds edge](/docs/edge) — des machines exécutant
[`kapkan edge`](/docs/cli#edge). Comme le canal des nœuds de scrubbing, les points de terminaison
destinés aux nœuds prennent le rôle `agent` ou un token `operator` non rattaché, jamais un `viewer`
ni un token rattaché à un tenant : le document de zones couvre tous les tenants. Ceux destinés aux
humains diffèrent : l'inventaire des nœuds et les événements de la flotte
(`GET /api/v1/edge/events`) sont des lectures de rang `viewer` pour les tokens non rattachés ;
l'état des zones, l'[historique edge](#get-apiv1edgehistory) avec ses sources significatives (rang
`viewer`) et le levier (rang `operator`) admettent un token [rattaché à un
tenant](/docs/multi-tenancy) pour ses propres zones. **Le cerveau distribue la politique, jamais les
verdicts** — il n'existe aucun appel par requête, ni ici ni ailleurs ; un nœud répond seul aux
requêtes. Le nombre de nœuds edge configurés (`edge_nodes_total`) circule sur `/api/v1/status` pour
tous les rôles, de sorte qu'une console peut décider d'afficher ou non la vue Edge sans aucun de ces
appels.

#### GET /api/v1/edge/zones

Le document de zones qu'un nœud rend et applique : les zones du [fichier de zones](/docs/zones) que
le [périmètre de placement](/docs/edge#placer-les-zones-sur-les-nœuds) du nœud couvre — toutes les
zones pour le `GET` nu d'un operator, ou pour une flotte dont les zones ne portent aucun
`hostgroup` (une zone étiquetée n'est servie que par les nœuds qui listent son groupe) — avec leurs
origines, leur version TLS minimale, leurs URL de directory ACME et leur politique, plus les
autorisations d'émission en cours, les challenges ACME diffusés, les clés de laissez-passer et les
leviers de ces zones ; l'`ETag` est celui du nœud. Un `GET` simple
renvoie le document avec un `ETag` de hachage de contenu ; un `GET` dont le `If-None-Match` nomme
cet ETag est **retenu** jusqu'à ce que le document change — un rechargement réussi du fichier de
zones, un challenge de certificat publié par un nœud — ou pendant 25 s au maximum, puis reçoit une
réponse `304`. Un rechargement qui retire le nœud, retire le token ou déplace la liaison du token
met fin à une interrogation en attente avec la réponse qu'une première interrogation obtiendrait
désormais (`404`, `401`, `403`), jamais un document. Un nœud s'identifie avec `?node=<name>`, et
**cette interrogation est le signal de
vivacité du nœud** ; le nom doit donc être une entrée `edge.nodes[]` configurée (un nom inconnu
renvoie `404`) et la requête doit porter un vrai token. Un token lié à un nœud
(`api.tokens[].node`) ne peut interroger, rapporter et coordonner l'ACME que sous l'identité de ce
nœud — le nom d'un autre nœud, ou une interrogation sans `?node=`, est un `403` uniforme qui ne
nomme jamais le nœud lié, refusé avant qu'aucune présence ne soit estampillée ni rien stocké ; seuls
les tokens `agent` estampillent la présence, de sorte que le `?node=X` d'un operator est un aperçu
du document de X, sans présence. Au plus 4 interrogations par nom de token
et `max(8, 2 × le nombre de nœuds edge)` au total peuvent être retenues à la fois ; une
interrogation supplémentaire correspondante
reçoit `429` avec `Retry-After: 1` (`too many concurrent zone holds`), ce que le nœud traite comme
un échec et qui le fait temporiser (1 s, doublant jusqu'à 30 s) — donnez à chaque nœud son propre
token agent.

```json
{
  "version": 1,
  "zones": [
    {
      "name": "shop.example.com",
      "origins": ["10.0.0.10:8080"],
      "tls": { "min_version": "1.2" },
      "policy": { "mode": "decide", "failure_mode": "open", "challenge": "auto", "rate": { "rps": 50, "concurrency": 20 } }
    }
  ],
  "acme_challenges": [],
  "issuance_grants": []
}
```

`acme_directory`, `acme_fallback`, `extra_directives_file` et `tls.h3` sont omis lorsqu'ils ne sont
pas définis ; `tls.h3_options {advertise, alt_svc_max_age_seconds}` n'apparaît que là où une zone
s'écarte des valeurs par défaut (`advertise: false`, ou un `ma` non par défaut) — absent signifie
annoncer, et `86400` — de sorte qu'un fichier de zones qui se contente d'activer `h3` laisse par
ailleurs les octets et l'ETag du document inchangés. Un `acme_directory` absent signifie que le
nœud commande auprès de sa propre CA par défaut (Let's Encrypt sauf si son `edge.yaml` en dit
autrement). La politique porte `dry_run` et les
`challenge_options` qu'une zone définit ; `clearance_keys` (non montrées) sont les clés de signature
par zone du palier (celle du jour UTC courant et celle de la veille, chacune honorée 48 h — le
document porte des secrets, et un nœud le met en cache en `0600`) ; une zone sur laquelle un
opérateur a actionné
[le levier](/docs/edge#le-levier) porte `challenge_override` `{mode, until, reason}` avec un `until`
fixe, de sorte que les octets et l'ETag du document ne bougent qu'au moment où l'opérateur agit et
une fois de plus quand il expire.

#### POST /api/v1/edge/nodes/\{name\}/report

Le rapport consultatif d'un nœud sur lui-même — version, dry-run côté nœud, l'ETag du document
qu'il a **rendu** (afin qu'un opérateur puisse repérer un nœud en retard ou qui refuse), le type,
la version et la vivacité du terminateur, sa disponibilité HTTP/3 issue de la sonde `nginx -V` du
nœud (`terminator.h3 {state, module, tls_library, early_data_capable, advisory, serving,
unsupported, listening}` — `state` vaut `ready`, `no_module`, `node_off` ou `unknown` ; `advisory`
nomme un avis de sécurité QUIC publié dont la plage contient le cœur nginx du build, à titre
d'avis : les distributions rétroportent les correctifs sans bouger la version ; `serving` liste les
zones pour lesquelles la génération active écoute en QUIC, `unsupported` les zones qui l'ont
demandé et sont servies en TCP ici ; `listening` dit si quelque chose sur la machine tient UDP 443
alors que des écouteurs QUIC sont générés — la moitié locale de « HTTP/3 est-il joignable ? »,
l'autre étant le pare-feu, et absent tant qu'aucune zone n'est servie en QUIC ici, ainsi que sur
une machine sans `/proc/net/udp`), la génération active et son résultat `nginx -t`, les
certificats qu'il détient (métadonnées publiques uniquement, jamais une clé ; une longue liste est
tronquée à la limite de 64 KiB du corps, avec un compteur `certs_truncated`), et une **section
zones** : pour chaque zone qui décide et que la génération active sert, la dernière fenêtre de dix
secondes close (`at`, `window_seconds`, `rps`, `requests`, `decided`, `denied`, `challenged`,
`cleared`, `would_deny`, `would_challenge`, `status_2xx..5xx`, `h3_requests` — les requêtes arrivées
en HTTP/3), le mode de défi de la zone tel que
le nœud l'applique, si la zone est en observation seule sur ce nœud (`dry_run`) et si son palier n'y
fait que prévisualiser (`rung_dry_run` : le `dry_run` du nœud, celui de la zone ou le
`challenge_options.dry_run` propre au palier), un défi global de zone en vigueur
(`challenge_active {reason, until, dry_run}` — `dry_run` indique que la bascule n'y est qu'un
aperçu), et les sources de la fenêtre — d'abord les candidates (un défi ou un refus prévisualisé),
puis les refusées et les mises au défi, puis les plus actives du reste — chacune avec la chose la
plus forte que le nœud lui a faite (`state` : `denied`, `challenged`, `would-deny`,
`would-challenge`, `cleared`, `marked`, `allow`). Un rapport trop gros pour la limite se déleste du
détail petit à petit — d'abord les sources qui ne disent rien (sans les compter : elles ne font pas
partie de l'ensemble des candidats), puis la liste de chaque zone réduite de moitié, puis les
certificats, puis les zones — chaque coupe étant comptée : `sources_truncated` est le nombre de
sources candidates manquantes dans la liste (celles que la borne propre au nœud de 20 par fenêtre a
laissées de côté, et celles qu'un rapport en train de rétrécir a délestées), `certs_truncated` et
`zones_truncated` les entrées supprimées. Stocké et renvoyé par `GET /api/v1/edge/nodes`. Avec le
[stockage](/docs/storage#historique-edge) activé, les fenêtres et les sources significatives du
rapport sont aussi écrites dans l'historique edge, et ce qui a changé depuis le rapport précédent du
nœud devient des événements — après que le rapport a été stocké, et sans que la réponse ne l'attende
jamais. Jamais un
signal de vivacité (l'interrogation l'est). Un `{name}` inconnu renvoie `404` ; un corps de plus de
64 KiB renvoie `413 report exceeds 64 KiB` — c'est la limite sous laquelle un nœud se déleste de
détail pour rester : un `413` ici est donc le fait d'un client qui ne l'a pas fait, et rien du
rapport n'est lu ; le succès est `204 No Content`.

#### GET /api/v1/edge/nodes

L'inventaire des nœuds : chaque nœud edge configuré avec la vivacité de son interrogation, joint à
son dernier rapport, à son périmètre de placement (`hostgroups` — le périmètre effectif, `["global"]` pour
un nœud qui n'en a pas — et `zones_placed`, les zones du fichier qu'il couvre), plus `tokens` (les
noms des tokens agent qui lui sont liés par `api.tokens[].node`) et
`last_token` (le nom du token qui a interrogé en dernier sous son identité — jamais un secret) ; le
document porte `unbound_agent_tokens` tant qu'un token agent est non lié et qu'il existe des nœuds
auxquels le lier (absent sinon) — la vue de migration de
[Lier un token agent à son nœud](/docs/authentication#lier-un-token-agent-à-son-nœud).
`hostgroups` et `zones_placed` sont toujours présents ; `tokens`, `last_token` et
`unbound_agent_tokens` sont omis quand ils sont vides. Le document porte aussi `nodes_total` et le
`stale_after_seconds` sur lequel le jugement s'appuie ; chaque nœud porte `alive`, `holding` et
`last_seen`.

**Une présence est estampillée quand une interrogation commence, puis de nouveau quand elle se
termine : tant qu'une interrogation est en attente, `last_seen` porte donc le début de celle-ci** et
peut dater de 25 s sur un nœud parfaitement sain — plus ancien que `stale_after_seconds` avec les
valeurs par défaut. `holding` dit qu'une interrogation est en attente à l'instant même, et un nœud
qui en tient une est vivant quoi que dise `last_seen` ; `alive` vaut *en attente, ou vu depuis moins
de `stale_after_seconds`*, jamais quoi que ce soit que le rapport du nœud lui-même prétend. La
conséquence à anticiper : un changement qui coupe un nœud — un token retiré, une liaison déplacée —
met fin à son interrogation en attente avec le refus qu'une première interrogation obtiendrait
désormais, ce qui estampille une présence à son tour ; `alive` ne passe donc à faux que
`stale_after_seconds` plus tard, soit jusqu'à environ 40 s après le changement avec les valeurs par
défaut. Une lecture de rang `viewer`, tokens non rattachés uniquement.

#### GET /api/v1/edge/zones/status

Les zones sur toute la flotte : les sections zones des nœuds **vivants** fusionnées — par zone, les
chiffres de fenêtre sommés (les fenêtres ne sont pas alignées ; c'est donc un débit de toute la
flotte à la fenêtre près), le mode de défi de la zone, les nœuds sur lesquels elle est en
observation seule (`watch_only`) et ceux sur lesquels son palier ne fait que prévisualiser
(`rung_watch_only` — une zone `manual` ou `auto` met réellement au défi sur les nœuds qui n'y sont
pas nommés), les nœuds où un défi global de zone est en vigueur et si chacun s'applique ou n'est
qu'un aperçu, le levier en vigueur (`override`), l'HTTP/3 de la zone sur toute la flotte
(`h3 {enabled, serving, unsupported, requests}` — `enabled` est le `tls.h3` du fichier de zones tel
que le cerveau le détient, `serving` les nœuds vivants dont la génération active écoute en QUIC
pour la zone, `unsupported` ceux où elle l'a demandé et est servie en TCP, `requests` la somme des
requêtes HTTP/3 de la dernière fenêtre des nœuds ; absent pour une zone dont personne ne parle ni
ne demande h3. `enabled` apparaît pour chaque zone du fichier à laquelle il active h3 — y compris
une zone en `mode: none` — et `serving`/`unsupported` nomment les écouteurs QUIC actifs des nœuds
vivants pour la zone, d'après leur `terminator.h3`, que la zone décide ou non ; `requests` provient
de la section zones des rapports, qui ne liste que les zones **qui décident**), et
**l'ensemble des candidats** : l'union des
sources pour lesquelles les nœuds ont prévisualisé un défi ou un refus, l'état le plus fort
conservé, les plus actives d'abord, bornée à 20 par nœud rapporteur (`would_be_truncated` compte le
reste). `partial` indique que les sources candidates d'un nœud n'ont pas toutes tenu — sa borne par
fenêtre, ou un rapport qui a dû rétrécir — de sorte que l'ensemble est ce qui a survécu, pas tout le
monde ; `zones_truncated` sur le document somme les entrées de zone que les nœuds vivants ont
coupées de leurs rapports, des zones absentes ou sous-comptées ici — un compte à l'échelle de la
flotte, pris avant le filtre de tenant, de sorte qu'un appelant rattaché peut voir un nombre qui
couvre des zones qu'il ne peut pas voir. Chaque zone du fichier de zones
a elle aussi une ligne — `mode` (son `policy.mode`) et `file_challenge` (son `policy.challenge`)
sont la parole du cerveau, `challenge` ce que les nœuds appliquent — et `certs` liste le certificat
que chaque nœud vivant détient pour la zone (`node`, `not_after`, `issuer` — le dernier omis quand
le nœud n'en rapporte aucun ; des métadonnées seulement, issues des rapports ; `certs_truncated` sur
le document somme les entrées que les nœuds ont coupées de leurs rapports pour tenir dans la limite
de taille — à l'échelle de la flotte, comme `zones_truncated` —, de sorte qu'une liste courte est
ce qui a survécu, pas ce qui est détenu). Chaque zone du
fichier porte aussi son `placement {hostgroup, nodes, alive}` — le groupe dans lequel le fichier la
range, les nœuds configurés dont le périmètre la couvre et lesquels d'entre eux sont vivants — et
`unserved: true` lorsqu'elle a des nœuds mais qu'aucun n'est vivant (une zone qu'aucun périmètre de
nœud ne couvre affiche `nodes: []` et est plutôt un avertissement de `-check-config`). Ce qu'un nœud affirme d'une zone hors de son périmètre est stocké dans son rapport, et n'est ni fusionné ici ni écrit dans l'[historique edge](#get-apiv1edgehistory) (`kapkan_edge_history_dropped_total{reason="outside_scope"}`). `placement.hostgroup` n'est présent que pour les tokens non rattachés : un tenant voit les noms des nœuds sur lesquels sa zone est servie, pas la façon dont l'operator les groupe. Une lecture de rang `viewer`. Un token non rattaché voit chaque zone,
les étiquetées avec leur `tenant` (la clé est absente sur une zone non étiquetée) ; un token
[rattaché à un tenant](/docs/multi-tenancy) exactement ses propres zones — le nom d'hôte d'aucun
autre tenant dans aucune ligne, aucun ensemble de candidats ni aucune liste HTTP/3, et pas de champ
`tenant`. Les noms des nœuds sont visibles d'un tenant ; l'inventaire non. C'est le *qui aurait été
mis au défi* de la spécification edge : lisez-le avant que le palier d'une zone ne passe en
production.

```json
{
  "nodes_alive": 2,
  "nodes_reporting": 2,
  "zones": [
    {
      "zone": "shop.example.com",
      "tenant": "shop",
      "mode": "decide",
      "file_challenge": "auto",
      "nodes": 2,
      "challenge": "auto",
      "rps": 812.4,
      "requests": 8124, "decided": 8124, "would_deny": 37, "would_challenge": 1240,
      "watch_only": ["edge-2"],
      "rung_watch_only": ["edge-2"],
      "challenge_active": [
        { "node": "edge-1", "reason": "zone-rps", "until": "2026-09-06T12:05:00Z", "dry_run": true }
      ],
      "would_be": [
        { "source": "203.0.113.7", "state": "would-deny", "requests": 1210, "nodes": ["edge-1", "edge-2"] },
        { "source": "198.51.100.23", "state": "would-challenge", "requests": 640, "nodes": ["edge-1"] }
      ],
      "certs": [
        { "node": "edge-1", "not_after": "2026-11-20T09:12:00Z", "issuer": "R11" },
        { "node": "edge-2", "not_after": "2026-11-20T09:12:00Z", "issuer": "R11" }
      ]
    }
  ]
}
```

Une zone qu'aucun nœud vivant n'a encore rapportée — une zone en `policy.mode: none`, ou une zone
dont les nœuds ne sont pas en service — a tout de même sa ligne : `nodes: 0`, `rps: 0`, son `mode`
et son `file_challenge`, et `override` lorsqu'un levier est posé. Un levier sur une zone qu'un
rechargement a depuis retirée du fichier garde lui aussi une ligne, sans `mode` (pour les appelants
non rattachés uniquement — c'est à eux de le libérer). Les compteurs de requêtes (`requests`,
`decided`, `denied`, `challenged`, `cleared`, `would_deny`, `would_challenge`) sont omis quand ils
valent zéro ; `nodes` et `rps` sont toujours présents.

#### GET /api/v1/edge/history

L'[historique edge](/docs/storage#historique-edge) d'une zone : les fenêtres de dix secondes des
nœuds sommées en intervalles de `step` secondes entre `from` et `to` (RFC 3339 ; la dernière heure
par défaut ; au plus 31 jours ; `step` vaut 60 s par défaut, est relevé pour qu'une plage ne
contienne pas plus de 5 000 intervalles, et vaut au plus 86 400 s — un jour) — `{available, zone,
node, step_seconds, points: [{ts, nodes, window_seconds, requests, decided, denied, challenged,
cleared, would_deny, would_challenge, status_2xx, status_3xx, status_4xx, status_5xx,
h3_requests}]}`. `nodes` compte les nœuds distincts qui ont rapporté dans l'intervalle ;
`step_seconds` est le pas réellement appliqué ; `zone` et `node` reprennent la requête, `node`
seulement lorsque le filtre a été donné ; déduisez le débit avec `requests / window_seconds` et la
part HTTP/3 avec `h3_requests / requests`. Ces règles de plage et de pas sont partagées avec
`/api/v1/traffic` et `/api/v1/audit` — une seule implémentation, si bien que les trois répondent à
une plage invalide par le même message. `zone` est obligatoire, rabattu en minuscules comme les
noms du fichier, et doit figurer dans le fichier de zones (`404 unknown zone` sinon) ;
`node=<name>` restreint à un seul nœud configuré (`404 unknown edge node`). Rang `viewer`. Un token
[rattaché à un tenant](/docs/multi-tenancy) lit ses propres zones ; toute autre zone — celle d'un
autre tenant, non étiquetée, disparue du fichier ou inexistante — est un unique `403` uniforme
(`zone is outside your tenant`), compté dans
`kapkan_api_zone_refused_total{route="edge_history"}` et journalisé une fois par minute et par
token, et `node=` est réservé aux tokens non rattachés (un tenant obtient `nodes` comme un compte,
jamais l'historique d'un seul nœud). Stockage désactivé : `{available: false, points: []}`, jamais
une erreur — la zone n'est pas regardée, de sorte que chaque token obtient cette réponse pour
n'importe quelle zone et que rien n'est compté ni journalisé ; une requête en échec renvoie `502`.

#### GET /api/v1/edge/history/sources

Les sources significatives de la zone sur la plage — le *qui aurait été mis au défi* de la
spécification edge, posé sur une période plutôt que sur une fenêtre de dix secondes : `{available,
zone, state, sources: [{source, state, requests, windows, nodes, first_seen, last_seen}]}`, les plus
actives d'abord, au plus 1 001 lignes. Le `state` de chaque source est la chose la plus forte qu'un
nœud lui a faite sur la plage (`denied` devant `challenged` devant `would-deny` devant
`would-challenge`) ; `state=` filtre sur l'une de ces quatre valeurs (`400` pour toute autre — les
visiteurs ne sont jamais stockés), et le `state` de premier niveau reprend ce filtre, absent sans
lui. Mêmes règles de `zone`, de plage et de périmètre que l'historique ci-dessus.

#### GET /api/v1/edge/events

Les transitions que le cerveau a vues, la plus récente d'abord, au plus 1 001 : `{available,
events: [{event_time, node, zone, kind, detail}]}`, avec les filtres optionnels `node=`, `zone=` et
`kind=` — `kind` vaut l'une des valeurs `node_alive`, `node_lost`, `version`, `dry_run`,
`document_rendered`, `generation_installed`, `generation_refused`, `terminator_alive`, `h3_state`,
`cert_issued`, `cert_renewed`, `cert_gone`, `challenge_started`, `challenge_ended`, `clock_skew`,
`report_truncated` (`400` sinon). Rang `viewer`, **tokens non rattachés uniquement** : les
événements nomment les nœuds et les changements de la flotte. Les mêmes règles de plage ; avec le
stockage désactivé, la réponse est `{available: false, events: []}`.

Chaque `kind` est une **transition** : un état que le cerveau n'a jamais vu qu'une fois ne figure
donc pas ici. Le premier rapport après un démarrage du cerveau est une référence silencieuse, et la
présence l'est aussi — un nœud prend sa référence à sa première interrogation ou, si le cerveau ne
l'entend jamais, comme perdu une fois `stale_after_seconds` écoulé depuis le démarrage du tic de
présence, sans écrire de `node_lost`. Un nœud resté à l'arrêt de part et d'autre d'un redémarrage du
cerveau n'a donc aucun événement jusqu'à son retour, et le premier est un `node_alive`. Pour savoir
ce qu'un nœud est *maintenant*, lisez l'inventaire, pas cette liste.

#### POST /api/v1/edge/nodes/\{name\}/acme/slot et …/acme/challenges

Le **coordinateur d'émission**, consultatif et en mémoire. Un nœud demande un créneau par zone
avant de commander un certificat (`{"zone": "…"}` → `{"granted": true, "expires_at": …}` ou
`{"granted": false, "holder": "…", "retry_after_seconds": …}` ; `{"release": true}` le restitue),
afin qu'une flotte n'épuise pas en un après-midi le plafond de certificats dupliqués d'une CA ; il
attend au plus 15 minutes, puis commande quand même. Un nœud qui détient le créneau publie son
challenge HTTP-01 en attente (`{"zone", "token", "key_authorization"}`) et le cerveau le diffuse
dans le document de chaque nœud qui sert la zone pendant dix minutes, afin que chacun d'eux y
réponde — la validation de la CA peut atterrir sur n'importe quel nœud derrière l'adresse partagée
de la zone. Un challenge actif n'est
jamais écrasé par une key authorization différente (`409`), un nœud peut détenir 16 challenges
actifs, et chaque appel est journalisé avec le nœud, la zone et le préfixe du token : un token
agent est un identifiant qui émet des certificats, effectuez-en la rotation dès qu'un nœud est
compromis. Les deux ne prennent que les zones que le [périmètre de
placement](/docs/edge#placer-les-zones-sur-les-nœuds) du nœud couvre : une zone que le nœud ne sert
pas est pour lui un `404 unknown zone`, octet pour octet la réponse qu'obtient une zone inexistante
(un `{"release": true}` fait exception : il ne touche que l'attribution propre à l'appelant, il est
idempotent, et il reçoit `204` pour n'importe quel nom de zone, servie ou non).

#### POST /api/v1/edge/zones/\{name\}/challenge et DELETE

[Le levier](/docs/edge#le-levier) : fixer le mode de défi d'une zone pour une durée bornée, quoi que
dise le fichier de zones. Rang `operator`. Un operator [rattaché à un
tenant](/docs/multi-tenancy) ne peut l'actionner que sur ses propres zones ; toute autre zone —
celle d'un autre tenant, non étiquetée, ou disparue du fichier — est pour lui un
`404 unknown zone`, la même réponse qu'obtient un nom inconnu, décidée avant que le corps ne soit
lu. L'appelant n'en apprend pas davantage ; l'operator, si : chacun de ces refus compte dans
`kapkan_api_zone_refused_total{route="edge_lever"}` et est journalisé une fois par minute et par
token, et aucune ligne d'audit n'est écrite.

```json
{ "mode": "manual", "ttl_seconds": 1800, "reason": "credential stuffing from residential proxies" }
```

`mode` vaut `manual`, `auto` ou `off` (`off` lève la surcharge, comme le fait `DELETE`) ;
`ttl_seconds` est dans `60..86400` et requis sauf si `mode` vaut `off` ; `reason` est destiné au
journal, à la ligne d'audit et aux réponses de l'API — `override.reason` dans
`GET /api/v1/edge/zones/status` et la propre réponse de ce point de terminaison (au plus
200 caractères). Une zone inconnue renvoie
`404` ; une zone en `policy.mode: none` renvoie `409` — rien n'y met au défi. La surcharge voyage
dans le document de zones sous `challenge_override` (les interrogations retenues sont réveillées
aussitôt) et chaque nœud qui sert la zone applique le mode effectif sur son chemin rapide, de sorte
qu'elle prend fin à `until` avec ou sans cerveau. Auditée comme `edge_challenge` `set` / `cleared`. Les deux
méthodes répondent `200` avec le palier tel qu'il est désormais et où le levier agit :

```json
{
  "zone": "shop.example.com",
  "mode": "manual",
  "until": "2026-09-06T12:30:00Z",
  "reason": "credential stuffing from residential proxies",
  "file_mode": "auto",
  "zone_watch_only": false,
  "rung_watch_only": false,
  "nodes": [
    { "name": "edge-1", "alive": true, "dry_run": false },
    { "name": "edge-2", "alive": false }
  ]
}
```

`file_mode` est le `policy.challenge` tel que le fichier le porte ; `zone_watch_only` et
`rung_watch_only` sont les `policy.dry_run` et `challenge_options.dry_run` de la zone — avec l'un
ou l'autre, le levier prévisualise au lieu d'agir, sur chaque nœud ; `nodes[]` liste les nœuds sur
lesquels la zone est [placée](/docs/edge#placer-les-zones-sur-les-nœuds) — chaque nœud configuré
pour une zone qu'un rechargement a depuis retirée du fichier — avec sa vivacité et le `dry_run`
qu'il rapporte (absent tant qu'il n'a pas rapporté) — un
nœud qui ne fait que compter doit être repéré avant de faire confiance au levier. `mode`, `until`
et `reason` sont absents quand la zone suit son fichier, et `file_mode` est vide pour une zone
qu'un rechargement a depuis retirée du fichier — un tel levier peut encore être levé, jamais posé.
Le levier est tenu dans la mémoire du cerveau, comme le coordinateur d'émission ; il n'est pas
conditionné par le `dry_run` propre au cerveau. Un nœud qui exécute une version antérieure au
levier ne connaît pas `challenge_override` et suit son fichier alors que `nodes[]` le liste tout de
même : mettez d'abord les nœuds à niveau.

### GET /metrics

Sert les métriques Prometheus au format d'exposition texte standard. Ce point de terminaison n'est
pas sous `/api/v1` et est servi sans le token bearer afin qu'un scraper puisse l'atteindre. Voir
[Métriques](/docs/metrics) pour la liste complète des métriques.

### GET /healthz

Une sonde de vivacité/disponibilité, non sous `/api/v1` et servie **sans** token bearer (elle ne
divulgue rien), afin qu'un superviseur ou le script de mise à niveau [`update.sh`](/docs/upgrading)
puisse confirmer que le démon est opérationnel après un redémarrage. Elle renvoie `503 starting`
jusqu'à ce que chaque composant ait démarré, puis `200 ok`. Comme l'écouteur de l'API ne commence à
accepter des connexions qu'une fois le démon démarré, tout `200` ici signifie que la configuration a
été analysée, que les composants sont opérationnels et que Kapkan répond.

```sh
curl -fsS localhost:8080/healthz   # exits non-zero (503) until ready, then prints "ok"
```
