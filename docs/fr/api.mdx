# API REST

Kapkan expose une petite API REST JSON pour observer la détection et piloter la mitigation
manuelle. Elle est servie sur l'adresse définie dans `api.listen`, qui vaut par défaut
`127.0.0.1:8080`. Le même écouteur sert également le [tableau de bord](/docs/dashboard) intégré
et le point de terminaison Prometheus [`/metrics`](/docs/metrics).

L'API est essentiellement en lecture : le statut, les attaques actives et récentes, l'instantané
des hôtes suivis et la table des bannissements sont tous des `GET`. Trois points de terminaison
`POST` modifient l'état — ban manuel, déban manuel et rechargement de la configuration.

<Callout type="warning" title="Authentifiez avant de l'exposer">
La valeur par défaut de `api.listen` se lie à `127.0.0.1`, de sorte que l'API n'est sûre sans
authentification que sur localhost. Avant de vous lier au-delà de la boucle locale, définissez
un jeton bearer. Voir [Authentification](/docs/authentication).
</Callout>

Toutes les routes `/api/v1` passent par la vérification du jeton lorsque l'authentification est
configurée ; une fois configurée, chaque requête doit porter `Authorization: Bearer <token>`. Les
jetons portent un **rôle** : les routes `GET` nécessitent le rôle **viewer**, et les routes
mutables (`ban`, `unban`, `config/reload`) nécessitent le rôle **operator**. `config/reload` va
plus loin : il exige un jeton **non rattaché (admin)**, de sorte que même un jeton operator
rattaché à un tenant est refusé avec un `403`. Le
[canal des nœuds de scrubbing](#le-canal-des-nœuds-de-scrubbing) prend le rôle **agent** —
l'identifiant d'un nœud de scrubbing qui atteint ces routes et rien d'autre. Une lecture avec un
jeton viewer fonctionne ; une
mutation avec un jeton viewer renvoie `403` ; un jeton inconnu renvoie `401`. Les points de
terminaison `POST` exigent en outre un type de contenu JSON —
envoyez `Content-Type: application/json`. Un `POST` sans cet en-tête est rejeté avec un
HTTP `415 Unsupported Media Type` ; ainsi, si un ban via `curl` échoue avec un 415, cet en-tête
manquant en est presque toujours la cause. Notez que `/metrics` et l'enveloppe statique du tableau
de bord sont servis sans jeton ; les données chargées par le tableau de bord sont, elles,
récupérées via l'API protégée. Voir [Authentification](/docs/authentication) pour les rôles des
jetons.

Un jeton peut aussi être **rattaché à un tenant** : il ne voit alors que les lignes de son
tenant sur chaque point de terminaison de lecture (`/status` est reconstruit pour ses propres
hostgroups et compteurs), et ne peut effectuer `ban`/`unban` qu'au sein de son tenant — une cible
hors tenant renvoie un `403` uniforme. Un jeton rattaché à un tenant ne peut pas du tout recharger
la configuration : `config/reload` est réservé aux jetons non rattachés (admin) et renvoie `403`
sinon. Voir [Multi-tenant](/docs/multi-tenancy).

## Points de terminaison

| Méthode | Chemin | Description |
| --- | --- | --- |
| GET | `/api/v1/status` | Mode, durée de fonctionnement, réseaux protégés, seuils, hostgroups, nombre d'attaques/bannissements actifs. |
| GET | `/api/v1/attacks` | Attaques actives ainsi que les 100 dernières terminées, avec échantillons et classification. |
| GET | `/api/v1/hosts` | Instantané des hôtes suivis : débits par direction, baselines apprises, état d'attaque. |
| GET | `/api/v1/bans` | Tous les bannissements, actifs et historiques. |
| GET | `/api/v1/traffic` | Historique des débits par hôte persisté (viewer) ; `{available:false, points:[]}` lorsque le stockage est désactivé. |
| GET | `/api/v1/audit` | Piste d'audit des mutations attribuée aux opérateurs (qui a banni/rechargé, quand, résultat). |
| POST | `/api/v1/ban` | Bannir manuellement une adresse. |
| POST | `/api/v1/unban` | Retirer manuellement un bannissement. |
| POST | `/api/v1/config/reload` | Relire le fichier de configuration (équivalent à `SIGHUP`). |
| POST | `/api/v1/dataplane/sources` | Rejeter une source dans le [plan de données](/docs/dataplane), rattachée à une victime, avec un TTL obligatoire. |
| POST | `/api/v1/dataplane/sources/unblock` | Retirer immédiatement un blocage de source. |
| GET | `/api/v1/dataplane/rules` | Le flux de règles du [nœud de scrubbing](/docs/scrubbing#nœuds-de-nettoyage-gérés) (`agent`/`operator` non rattaché) ; long-poll par ETag, retenu jusqu'à 30 s. |
| POST | `/api/v1/dataplane/nodes/{name}/report` | Le rapport consultatif d'un nœud de scrubbing sur lui-même (`agent`/`operator` non rattaché). |
| GET | `/api/v1/dataplane/nodes` | Inventaire des nœuds gérés : vivacité, configuration, nombre de bans par nœud (`viewer` non rattaché ou plus). |
| GET | `/metrics` | Métriques Prometheus. |
| GET | `/healthz` | Sonde de vivacité/disponibilité non authentifiée : `503` jusqu'au démarrage complet, puis `200`. |

Toutes les réponses sont au format JSON. Les erreurs renvoient un objet de la forme
`{"error": "..."}` accompagné d'un statut HTTP approprié.

### GET /api/v1/status

Renvoie le mode de fonctionnement actuel et un résumé de ce que Kapkan protège. Pour le lire
(omettez l'en-tête `Authorization` si aucun jeton n'est configuré) :

```sh
curl -fsS localhost:8080/api/v1/status \
  -H "Authorization: Bearer $TOKEN" | jq
```

```json
{
  "dry_run": true,
  "uptime_seconds": 8123,
  "version": "v1.2.0 · a1b2c3d",
  "update_available": false,
  "role": "operator",
  "unscoped": true,
  "networks": ["203.0.113.0/24", "198.51.100.0/24"],
  "active_attacks": 1,
  "active_bans": 1,
  "thresholds": {
    "pps": 80000,
    "mbps": 1000,
    "flows_per_sec": 20000
  },
  "hostgroups": [
    { "name": "web", "calculation": "per_host", "mitigation": "blackhole", "ban": true }
  ]
}
```

`dry_run` indique le mode global : lorsqu'il vaut `true`, aucun blackhole n'est annoncé à vos
routeurs. `version` est le build en cours d'exécution, toujours présent et sans aucune sortie
réseau. `update_available` vaut `false` à moins que la vérification optionnelle
[`update_check`](/docs/configuration) ne soit activée et ne détecte une version plus récente —
il vaut alors `true` et `latest_version`, `latest_is_security` et `latest_url` sont inclus à ses côtés. Voir [Mise à niveau](/docs/upgrading).
`thresholds` et `hostgroups` reflètent la configuration active ; voir
[Détection](/docs/detection) et [Hostgroups](/docs/hostgroups) pour leur forme complète.
`role` et `unscoped` sont toujours présents — ils indiquent au tableau de bord quel jeton il
utilise. Les champs `networks`, `thresholds`, `bgp`, `scrubbing` et `notify` relèvent de la
configuration à l'échelle du déploiement et ne sont renvoyés qu'à un jeton non rattaché (admin) ;
un jeton rattaché à un tenant reçoit un objet de statut sans eux (uniquement `dry_run`, `version`,
`uptime_seconds`, `update_available`, `role`, `unscoped`, ses propres `hostgroups` et les
compteurs). Un jeton admin obtient en plus des objets `bgp`, `scrubbing` et `notify` — `notify`
n'expose que les canaux activés, jamais les jetons ou les URL. Donc, si un champ semble
« manquant », vérifiez si votre jeton est rattaché à un tenant plutôt que de supposer que Kapkan
est en panne.

### GET /api/v1/attacks

Renvoie les attaques actuellement actives ainsi que les 100 dernières terminées (la plus récente
en premier). Les deux tableaux contiennent des objets `Attack`.

| Champ | Type | Notes |
| --- | --- | --- |
| `scope` | string | `host` ou `group`. Les attaques à portée de groupe ne portent pas de `target`. |
| `target` | string | L'adresse attaquée (portée hôte). |
| `group` | string | Nom du hostgroup (portée groupe, ou groupe de l'hôte). |
| `tenant` | string | Le tenant du groupe propriétaire, lorsqu'il est étiqueté (voir [Multi-tenant](/docs/multi-tenancy)). |
| `direction` | string | `incoming` ou `outgoing`. |
| `metric` | string | La métrique qui a déclenché, p. ex. `pps`, `mbps`, `tcp_syn_pps`. |
| `rate` | number | Le débit de la métrique déclenchante, dans son unité : la mesure courante du moteur tant que l'attaque est active, la dernière avant sa fin ensuite. |
| `threshold` | number | Le seuil franchi. |
| `rates` | object | Ventilation complète des débits par protocole (voir ci-dessous), issue de la même mesure que `rate`. |
| `active` | bool | `true` tant que l'attaque est en cours. |
| `ban_state` | string | `active`, `withdrawn` ou `rejected`. Omis lorsqu'il n'y a pas de bannissement. |
| `method` | string | Méthode de mitigation : `blackhole`, `flowspec` ou `divert`. Omis lorsqu'il n'y a pas de bannissement. |
| `route` | string | La chaîne de route (`blackhole …` / `divert …`), ou un résumé `flowspec: ...`, lorsqu'un bannissement existe. |
| `flowspec` | array | Les règles [FlowSpec](/docs/flowspec) générées, lorsque `method` vaut `flowspec`. |
| `dry_run` | bool | Indique si le bannissement était virtuel. |
| `started_at` | string | Horodatage RFC 3339. |
| `ended_at` | string | Horodatage RFC 3339 ; omis tant que l'attaque est active. |
| `sample` | object | Échantillon de flow capturé à la détection ; omis lorsque l'échantillonnage est désactivé. |
| `classification` | object | Vecteur d'attaque inféré ; omis lorsqu'il n'est pas classifié. |
| `reason` | object | Pourquoi la détection a déclenché — provenance du seuil, warm-up, parts de protocole. Attaché au démarrage. |

```json
{
  "active": [
    {
      "scope": "host",
      "target": "203.0.113.66",
      "group": "web",
      "direction": "incoming",
      "metric": "pps",
      "rate": 412000,
      "threshold": 80000,
      "rates": {
        "pps": 412000,
        "mbps": 3100,
        "flows_per_sec": 9800,
        "udp_pps": 405000,
        "udp_mbps": 3080
      },
      "active": true,
      "ban_state": "active",
      "route": "blackhole 203.0.113.66/32 next-hop 192.0.2.1 community 65000:666",
      "dry_run": false,
      "started_at": "2026-06-13T09:41:07Z",
      "sample": {
        "top_sources": [
          { "key": "198.51.100.23", "packets": 1240000, "bytes": 1612000000 }
        ],
        "top_src_ports": [
          { "key": "123", "packets": 1180000, "bytes": 1534000000 }
        ],
        "top_dst_ports": [
          { "key": "443", "packets": 1240000, "bytes": 1612000000 }
        ],
        "protocols": [
          { "key": "udp", "packets": 1240000, "bytes": 1612000000 }
        ],
        "total_packets": 1240000
      },
      "classification": {
        "type": "ntp_amplification",
        "confidence": 0.95,
        "src_port": 123
      }
    }
  ],
  "recent": []
}
```

Tant qu'une attaque est active, `rate` et `rates` sont relus depuis le moteur à chaque
requête : ils suivent donc l'attaque au lieu de rapporter l'instant de sa détection — quand
la fenêtre glissante ne contenait qu'une seconde et sous-estimait un flood soutenu d'un
facteur plusieurs. `metric` et `threshold` restent tels qu'ils ont été capturés à la
détection : ils nomment ce qui a déclenché, et le moteur juge la fin de l'attaque d'après
les seuils figés à son début.

L'objet `rates` porte le trio de base (`pps`, `mbps`, `flows_per_sec`) plus les champs
par protocole qui sont non nuls : `tcp_pps`, `tcp_mbps`, `udp_pps`, `udp_mbps`,
`icmp_pps`, `icmp_mbps`, `tcp_syn_pps`, `tcp_syn_mbps`, `frag_pps`, `frag_mbps`. L'objet
`sample` résume les flows mis en tampon à l'origine de la détection — `top_sources`,
`top_src_ports`, `top_dst_ports`, `protocols` (chacun une liste de compteurs
`{key, packets, bytes}`), une liste `flows` brute facultative et `total_packets`. Le `type`
de `classification` est l'un des vecteurs documentés dans [Détection](/docs/detection) ;
`confidence` est la part (`0..1`) du trafic d'attaque correspondant à la signature gagnante, et
`src_port` est le port de service réfléchi pour les vecteurs d'amplification.

L'objet `reason` explique **pourquoi** la détection a déclenché — capturé une seule fois au
démarrage, hors du chemin critique. `threshold_source` vaut `static` ou `baseline` : selon que la
limite franchie provient de la configuration statique ou d'une [baseline apprise](/docs/baselines)
échauffée. Lorsqu'il vaut `baseline`, un objet `baseline` porte le calcul effectif
(`min(ceiling, max(floor, normal × factor))`). `baseline_configured`, `warming_up` et
`warmup_remaining_seconds` expliquent un seuil statique qui ne s'est appliqué que parce que la
baseline n'était pas encore échauffée. `shares` est la fraction par protocole du total des PPS
qui a guidé la classification, et `dominant_share_gate` est la part qu'un protocole doit atteindre
pour remporter un vecteur (sinon l'attaque est `mixed`). Voir [Détection](/docs/detection) pour
savoir comment le lire.

```json
{
  "reason": {
    "threshold_source": "baseline",
    "baseline": { "normal": 1200, "factor": 8, "floor": 5000, "ceiling": 80000 },
    "baseline_configured": true,
    "shares": { "udp": 0.98, "syn": 0, "tcp": 0.01, "icmp": 0, "frag": 0 },
    "dominant_share_gate": 0.5
  }
}
```

### GET /api/v1/hosts

Renvoie un instantané de chaque hôte suivi — les données des principaux émetteurs. Chaque entrée
est un `HostStat`.

| Champ | Type | Notes |
| --- | --- | --- |
| `target` | string | L'adresse de l'hôte. |
| `group` | string | Le nom du hostgroup de l'hôte. |
| `rates` | object | Débits entrants courants sur la fenêtre glissante. |
| `rates_out` | object | Débits sortants ; non nuls uniquement lorsque la détection sortante est activée. |
| `in_attack` | bool | Indique si l'hôte est impliqué dans une attaque active. |
| `metric` | string | La métrique de l'attaque active ; omise lorsque l'hôte n'est pas attaqué. |
| `direction` | string | La direction de l'attaque active ; omise lorsque l'hôte n'est pas attaqué. |
| `baseline` | object | Baseline entrante apprise ; présente lorsque des baselines sont configurées. |
| `baseline_out` | object | Baseline sortante apprise ; présente lorsque des baselines sont configurées. |

```json
{
  "hosts": [
    {
      "target": "203.0.113.66",
      "group": "web",
      "rates": {
        "pps": 412000,
        "mbps": 3100,
        "flows_per_sec": 9800,
        "udp_pps": 405000
      },
      "rates_out": {
        "pps": 120,
        "mbps": 2
      },
      "in_attack": true,
      "metric": "pps",
      "direction": "incoming",
      "baseline": {
        "pps": 950,
        "mbps": 7,
        "flows_per_sec": 60
      },
      "baseline_out": {
        "pps": 110,
        "mbps": 2,
        "flows_per_sec": 14
      }
    }
  ]
}
```

Les objets `baseline` et `baseline_out` portent le trio de base de la normale apprise (`pps`,
`mbps`, `flows_per_sec`) et n'apparaissent que lorsque des baselines EWMA sont configurées pour
le groupe de l'hôte. Voir [Baselines](/docs/baselines).

### GET /api/v1/bans

Renvoie la table complète des bannissements — actifs et historiques. Chaque entrée est un `Ban`.

| Champ | Type | Notes |
| --- | --- | --- |
| `target` | string | L'adresse bannie. |
| `prefix` | string | Le préfixe de blackhole (`/32` ou `/128`). |
| `metric` | string | La métrique qui a déclenché le bannissement ; omise pour les bannissements manuels. |
| `rate` | number | Débit observé au moment du bannissement ; omis lorsqu'il est nul. |
| `threshold` | number | Seuil franchi ; omis lorsqu'il est nul. |
| `next_hop` | string | Le next-hop de rejet. |
| `community` | string | L'ensemble de communities attaché à la route — la community RTBH pour un blackhole, la community de divert (scrubbing) pour un ban divert — jointes par des espaces lorsqu'il y en a plusieurs. |
| `local_pref` | number | Le `LOCAL_PREF` attaché à la route ; omis lorsqu'il est nul. |
| `node` | string | Le [nœud de nettoyage géré](/docs/scrubbing#nœuds-de-nettoyage-gérés) auquel ce ban divert est figé ; omis lorsque le ban ne dévie pas vers un nœud géré. |
| `route` | string | La chaîne de route complète, ou un résumé `flowspec: ...` pour les bannissements FlowSpec. |
| `state` | string | `active`, `withdrawn` ou `rejected`. |
| `dry_run` | bool | Indique si le bannissement était virtuel. |
| `manual` | bool | `true` pour les bannissements demandés par l'opérateur. |
| `started_at` | string | Horodatage RFC 3339. |
| `expires_at` | string | Expiration du TTL ; les bannissements ne sont jamais permanents. |
| `withdrawn_at` | string | Moment où la route a été retirée ; omis tant que le bannissement est actif. |
| `reason` | string | Raison pour laquelle un bannissement a été rejeté ou retiré ; omise sinon. |
| `method` | string | Méthode de mitigation : `blackhole`, `flowspec` ou `divert`. |
| `flowspec` | array | Les règles [FlowSpec](/docs/flowspec) générées, lorsque `method` vaut `flowspec`. |
| `escalation` | array | L'[échelle d'escalade](/docs/escalation) configurée, lorsqu'une est définie. |
| `escalation_step` | number | Index du barreau courant de l'échelle. |

```json
{
  "bans": [
    {
      "target": "203.0.113.66",
      "prefix": "203.0.113.66/32",
      "metric": "pps",
      "rate": 412000,
      "threshold": 80000,
      "next_hop": "192.0.2.1",
      "community": "65000:666",
      "route": "blackhole 203.0.113.66/32 next-hop 192.0.2.1 community 65000:666",
      "state": "active",
      "dry_run": false,
      "manual": false,
      "started_at": "2026-06-13T09:41:07Z",
      "expires_at": "2026-06-13T10:41:07Z"
    }
  ]
}
```

Voir [Mitigation](/docs/mitigation) pour comprendre comment le TTL, l'hystérésis et le plafond de
bannissements façonnent ce cycle de vie.

### GET /api/v1/audit

Renvoie la piste d'audit attribuée aux opérateurs — qui a émis chaque `ban`, `unban` ou
`config_reload`, `source_block` ou `source_unblock`, quand, et le résultat (y compris les actions
**refusées**). Les enregistrements sont triés du plus récent au plus ancien et le point de
terminaison est rattaché au tenant côté serveur. Il accepte des paramètres de requête optionnels
`from`/`to` (RFC 3339), `action` (`ban`/`unban`/`config_reload`/`source_block`/`source_unblock`) et
`target` (une IP), et porte par défaut sur la dernière heure :

```json
{
  "available": true,
  "events": [
    {
      "event_time": "2026-06-22 03:14:09",
      "action": "ban",
      "result": "rejected",
      "operator": "alice",
      "role": "operator",
      "tenant": "customerA",
      "target": "203.0.113.66",
      "target_type": "host",
      "reason": "whitelisted",
      "source": "api",
      "ban_state": "rejected",
      "dry_run": 0
    }
  ]
}
```

Lorsque le stockage est désactivé, la réponse est `{"available": false, "events": []}`. Notez que
les enregistrements d'audit encodent `dry_run` sous forme d'entier (`0`/`1`), et non sous forme du
booléen JSON utilisé ailleurs sur cette page. Voir la page dédiée [Journal d'audit](/docs/audit)
pour la liste complète des champs, les règles de requête, ainsi que le modèle d'identité des
opérateurs et de rattachement aux tenants.

### POST /api/v1/ban

Place manuellement une adresse en blackhole. Le corps est une seule adresse IP :

```http
POST /api/v1/ban
Content-Type: application/json

{"ip": "203.0.113.66"}
```

Sous forme de commande exécutable (omettez l'en-tête `Authorization` si vous n'avez pas encore configuré de jeton) :

```sh
curl -fsS -X POST localhost:8080/api/v1/ban \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"ip":"203.0.113.66"}'
```

La réponse est l'objet `Ban` résultant. Un bannissement manuel respecte toutes les règles de
sécurité qu'un bannissement automatique respecte :

- Une cible figurant sur la **liste blanche** est refusée avec un statut HTTP `409 Conflict` et `reason: "whitelisted"` ; elle n'est jamais annoncée.
- Une cible **en dehors des `networks` configurés** est refusée avec un statut HTTP `409` et `reason: "outside configured networks"`.
- Une requête qui dépasserait **`max_active_bans`** est refusée avec un statut HTTP `409` et `reason: "max_active_bans reached"`.

Dans chaque cas de `409`, le corps reste un objet `Ban` avec `state: "rejected"` et le champ
`reason` renseigné. Une IP invalide ou non analysable renvoie un statut HTTP `400`.

<Callout type="warning" title="Le dry-run s'applique toujours">
Un bannissement manuel respecte le mode global. Tant que `dry_run` vaut `true`, le bannissement
est enregistré et renvoyé avec `dry_run: true`, mais aucune route n'est annoncée. Voir le
[modèle de sécurité](/docs/safety).
</Callout>

### POST /api/v1/unban

Retire un bannissement actif pour l'adresse donnée. Le corps a la même forme `{"ip": "..."}` et
le même type de contenu JSON est requis :

```http
POST /api/v1/unban
Content-Type: application/json

{"ip": "203.0.113.66"}
```

En cas de succès, renvoie le `Ban` retiré. S'il n'existe aucun bannissement actif pour l'adresse,
renvoie un statut HTTP `404`.

### POST /api/v1/config/reload

Relit le fichier de configuration depuis le disque et l'applique — le même effet que l'envoi d'un
`SIGHUP`. Le corps est vide ; le type de contenu JSON reste requis. Contrairement à
`ban`/`unban`, ce point de terminaison exige un jeton **non rattaché (admin)** : un rechargement
remplace l'intégralité de la configuration, de sorte qu'un jeton rattaché à un tenant est refusé
avec un `403` et `config reload is restricted to unscoped (admin) tokens`.

```json
{
  "reloaded": true,
  "dry_run": false,
  "thresholds": {
    "pps": 80000,
    "mbps": 1000,
    "flows_per_sec": 20000
  }
}
```

Si la nouvelle configuration échoue à l'analyse ou à la validation, la configuration en cours
d'exécution reste intacte et le point de terminaison renvoie un statut HTTP `400` avec l'erreur.
Voir [Configuration](/docs/configuration).

### Le canal de blocage de sources

Deux points de terminaison permettent à ce qui termine déjà le trafic d'une victime — un nginx devant
elle, un exportateur de journaux, un opérateur à 3 h du matin — de confier à Kapkan une **source** à
rejeter dans le [plan de données XDP](/docs/dataplane), rattachée à cette victime et avec un TTL
obligatoire. La décision est prise là où les requêtes sont visibles ; l'application se fait dans le
noyau. Les deux exigent un token `operator` ; le rôle `agent` est refusé.

```sh
curl -fsS -X POST localhost:8080/api/v1/dataplane/sources \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"victim":"203.0.113.10","source":"198.51.100.7","ttl_seconds":600,"reason":"login flood"}'
```

| Champ | Requis | Signification |
| --- | --- | --- |
| `victim` | oui | La destination protégée à laquelle le blocage est rattaché. C'est ce qui est vérifié pour un token de tenant, et ce qui empêche les preuves d'un seul appelant de devenir un rejet global. |
| `source` | oui | L'adresse à rejeter. Doit être de la même famille d'adresses que `victim`. |
| `ttl_seconds` | oui pour un blocage | Durée de vie du blocage, de `1` à `86400` (24 h). Il n'existe pas d'entrées permanentes. Bloquer à nouveau la même paire conserve le `created_at` d'origine et applique le nouveau TTL — le rafraîchissement dont un exportateur a besoin pour maintenir un contrevenant persistant sans va-et-vient de déblocage/reblocage. |
| `reason` | non | Une note libre reprise dans la [piste d'audit](/docs/audit). |

La réponse est le `SourceBlock` résultant :

```json
{
  "source": "198.51.100.7",
  "victim": "203.0.113.10",
  "created_at": "2026-08-17T21:04:11Z",
  "expires_at": "2026-08-17T21:14:11Z",
  "dry_run": false,
  "reason": "login flood"
}
```

`POST /api/v1/dataplane/sources/unblock` prend les mêmes `victim` et `source` (tout `ttl_seconds` est
ignoré) et retire immédiatement cette seule paire, pour que personne n'attende un TTL qu'il a lui-même
saisi. Il renvoie le `SourceBlock` retiré, ou `404` si aucune paire de ce type n'est vivante.

#### Refus

Une erreur de saisie donne `400` ; une requête bien formée refusée par la politique donne `409`.
Chaque appel — refus compris — écrit un événement d'audit attribué, car un blocage refusé est
lui-même une action d'opérateur.

| Statut | Cause |
| --- | --- |
| `400` | JSON ou adresse non analysable, `victim` et `source` de familles d'adresses différentes, ou `ttl_seconds` hors de `[1, 86400]`. |
| `403` | `victim` est hors de votre tenant. Le même refus uniforme que celui des points de terminaison de bannissement, afin que ce point ne devienne pas un oracle d'existence pour les hôtes des autres tenants. |
| `404` | Déblocage uniquement : aucun blocage vivant pour cette paire. |
| `409` | Le plan de données est absent ou désactivé ; `victim` est dans `protected_whitelist` ; `source` est dans `dataplane.allowlist` ; `source` est à l'intérieur des `networks` protégés ; cette source détient déjà 8 victimes ; ou il ne reste aucun emplacement de politique. |

Les deux refus liés aux listes d'autorisation sont les plus intéressants, et ils sont des refus
précisément parce que l'alternative est le silence : le chemin de données laisse passer une source
autorisée à la précédence 1 et le trafic vers une destination protégée à la précédence 2, les deux
**avant** qu'une seule règle ne soit évaluée — un tel blocage s'installerait puis ne correspondrait
jamais à un paquet. Une `source` à l'intérieur de vos propres `networks` est également refusée : un
hôte interne relève du [bannissement](/docs/mitigation), pas du blocage de source.

<Callout type="warning" title="Un échec d'installation retire toutes les paires de cette source">
Les paires d'une source partagent un unique bloc de politique noyau, et le rollback de l'installateur
est tout-ou-rien sur ce bloc. Si une installation échoue, toutes les paires de cette source sont
retirées au lieu de rester enregistrées-mais-non-appliquées, et l'erreur le dit — rajoutez celles
dont vous avez encore besoin. La table ne prétend jamais appliquer quelque chose que le noyau
n'applique pas.
</Callout>

<Callout type="info" title="Les mêmes garanties qu'un bannissement">
Les TTL sont obligatoires et bornés, chaque paire porte sa propre expiration dans le noyau (elle
cesse donc de s'appliquer à l'heure prévue même si Kapkan meurt), les installations sont comptées
contre `dataplane.limits.max_dynamic_rules`, les blocages survivent à un redémarrage via le fichier
d'état, et `dry_run` est respecté — la paire est enregistrée, renvoyée avec `dry_run: true`, et rien
n'atteint une map du noyau. Voir
[Blocages de sources](/docs/dataplane#blocages-de-sources-depuis-votre-propre-pile) pour les limites
et le [Modèle de sécurité](/docs/safety).
</Callout>

### Le canal des nœuds de scrubbing

Ces trois points de terminaison existent pour les [nœuds de nettoyage
gérés](/docs/scrubbing#nœuds-de-nettoyage-gérés) — des machines exécutant
[`kapkan scrub`](/docs/cli). Ils prennent le rôle `agent` (l'identifiant d'un nœud de scrubbing ;
voir [authentification](/docs/authentication)) ou un jeton `operator` non rattaché, jamais un
`viewer` ni un jeton rattaché à un tenant : les documents couvrent tous les tenants, de sorte que
les rattacher est une préoccupation de flotte, non de requête.

#### GET /api/v1/dataplane/rules

La table de règles qu'un nœud applique : chaque victime [déviée](/docs/scrubbing) active, avec les
règles [FlowSpec](/docs/flowspec) à supprimer et le TTL à répliquer. Un `GET` simple renvoie le
document courant avec un `ETag` de hachage de contenu ; un `GET` dont le `If-None-Match` nomme cet
ETag est **retenu** jusqu'à ce que la table change ou pendant 30 s au maximum, puis reçoit une
réponse `304` — un long-poll qui offre des mises à jour de règles en moins d'une seconde sur du
HTTP ordinaire. Un nœud s'identifie avec `?node=<name>`, et **cette interrogation est le signal de
vivacité du nœud** — le nom doit donc être un nœud configuré (un nom inconnu renvoie `404`) et, en
dehors du mode local sans jeton, la requête doit porter un vrai jeton.

```json
{
  "version": 1,
  "bans": [
    {
      "target": "203.0.113.10",
      "prefix": "203.0.113.10/32",
      "method": "divert",
      "expires_at": "2026-08-13T10:00:00Z",
      "flowspec": [ { "dst": "203.0.113.10/32", "proto": 17, "action": "discard" } ]
    }
  ]
}
```

#### POST /api/v1/dataplane/nodes/\{name\}/report

Le rapport consultatif d'un nœud sur lui-même — version, mode XDP, dry-run côté nœud, charge et
totaux de suppressions — stocké pour la [console](/docs/dashboard). Ce n'est **jamais** un signal
de vivacité (l'interrogation l'est) : un rapport ne peut jamais maintenir un nœud mort marqué comme
actif. Le corps est plafonné à 64 KiB (`413` au-delà) et un `{name}` inconnu renvoie `404`. Le
succès est `204 No Content`.

#### GET /api/v1/dataplane/nodes

L'inventaire des nœuds que rend la vue Nœuds de la console : chaque nœud configuré avec ce que le
cerveau sait (configuration, vivacité de l'interrogation, combien de bans dévient vers lui) joint à
son dernier rapport. Une lecture de rang `viewer`, mais jetons non rattachés uniquement —
l'inventaire nomme les next-hops et les hostgroups, ce qui relève de la topologie de déploiement.
Le nombre seul (`nodes_total`) circule sur `/api/v1/status` pour tous les rôles, de sorte qu'une
console peut décider d'afficher ou non les fonctionnalités liées aux nœuds sans cet appel.

### Le canal edge

Ces points de terminaison existent pour les [nœuds edge](/docs/edge) — des machines exécutant
[`kapkan edge`](/docs/cli#edge). Comme le canal des nœuds de scrubbing, ils prennent le rôle
`agent` ou un jeton `operator` non rattaché, jamais un `viewer` ni un jeton rattaché à un tenant :
le document de zones couvre tous les tenants. **Le cerveau distribue la politique, jamais les
verdicts** — il n'existe aucun appel par requête, ni ici ni ailleurs ; un nœud répond seul aux
requêtes.

#### GET /api/v1/edge/zones

Le document de zones qu'un nœud rend et applique : chaque zone du [fichier de zones](/docs/zones)
avec ses origines, sa version TLS minimale, ses URL de directory ACME et sa politique, plus les
autorisations d'émission en cours et les challenges ACME diffusés à la flotte. Un `GET` simple
renvoie le document avec un `ETag` de hachage de contenu ; un `GET` dont le `If-None-Match` nomme
cet ETag est **retenu** jusqu'à ce que le document change — un rechargement réussi du fichier de
zones, un challenge de certificat publié par un nœud — ou pendant 25 s au maximum, puis reçoit une
réponse `304`. Un nœud s'identifie avec `?node=<name>`, et **cette interrogation est le signal de
vivacité du nœud** ; le nom doit donc être une entrée `edge.nodes[]` configurée (un nom inconnu
renvoie `404`) et la requête doit porter un vrai jeton. Au plus 4 interrogations par nom de jeton
et 8 au total peuvent être retenues à la fois ; une interrogation supplémentaire correspondante
reçoit `429` avec `Retry-After: 1` (`too many concurrent zone holds`), ce que le nœud traite comme
un échec et qui le fait temporiser (1 s, doublant jusqu'à 30 s) — donnez à chaque nœud son propre
jeton agent.

```json
{
  "version": 1,
  "zones": [
    {
      "name": "shop.example.com",
      "origins": ["10.0.0.10:8080"],
      "tls": { "min_version": "1.2" },
      "policy": { "mode": "decide", "failure_mode": "open", "challenge": "off", "rate": { "rps": 50, "concurrency": 20 } }
    }
  ],
  "acme_challenges": [],
  "issuance_grants": []
}
```

`acme_directory`, `acme_fallback`, `extra_directives_file` et `tls.h3` sont omis lorsqu'ils ne sont
pas définis ; un `acme_directory` absent signifie que le nœud commande auprès de sa propre CA par
défaut (Let's Encrypt sauf si son `edge.yaml` en dit autrement).

#### POST /api/v1/edge/nodes/\{name\}/report

Le rapport consultatif d'un nœud sur lui-même — version, dry-run côté nœud, l'ETag du document
qu'il a **rendu** (afin qu'un opérateur puisse repérer un nœud en retard ou qui refuse), le type,
la version et la vivacité du terminateur, la génération active et son résultat `nginx -t`, et les
certificats qu'il détient (métadonnées publiques uniquement, jamais une clé ; une longue liste est
tronquée à la limite de 64 KiB du corps, avec un compteur `certs_truncated`) — stocké et renvoyé
par `GET /api/v1/edge/nodes`. Jamais un signal de vivacité (l'interrogation l'est). Un `{name}`
inconnu renvoie `404` ; le succès est `204 No Content`.

#### GET /api/v1/edge/nodes

L'inventaire des nœuds : chaque nœud edge configuré avec la vivacité de son interrogation, joint à
son dernier rapport. Une lecture de rang `viewer`, jetons non rattachés uniquement.

#### POST /api/v1/edge/nodes/\{name\}/acme/slot et …/acme/challenges

Le **coordinateur d'émission**, consultatif et en mémoire. Un nœud demande un créneau par zone
avant de commander un certificat (`{"zone": "…"}` → `{"granted": true, "expires_at": …}` ou
`{"granted": false, "holder": "…", "retry_after_seconds": …}` ; `{"release": true}` le restitue),
afin qu'une flotte n'épuise pas en un après-midi le plafond de certificats dupliqués d'une CA ; il
attend au plus 15 minutes, puis commande quand même. Un nœud qui détient le créneau publie son
challenge HTTP-01 en attente (`{"zone", "token", "key_authorization"}`) et le cerveau le diffuse
dans le document de zones pendant dix minutes afin que chaque nœud y réponde — la validation de la
CA peut atterrir sur n'importe quel nœud derrière une adresse partagée. Un challenge actif n'est
jamais écrasé par une key authorization différente (`409`), un nœud peut détenir 16 challenges
actifs, et chaque appel est journalisé avec le nœud, la zone et le préfixe du token : un jeton
agent est un identifiant qui émet des certificats, effectuez-en la rotation dès qu'un nœud est
compromis.

### GET /metrics

Sert les métriques Prometheus au format d'exposition texte standard. Ce point de terminaison n'est
pas sous `/api/v1` et est servi sans le jeton bearer afin qu'un scraper puisse l'atteindre. Voir
[Métriques](/docs/metrics) pour la liste complète des métriques.

### GET /healthz

Une sonde de vivacité/disponibilité, non sous `/api/v1` et servie **sans** jeton bearer (elle ne
divulgue rien), afin qu'un superviseur ou le script de mise à niveau [`update.sh`](/docs/upgrading)
puisse confirmer que le démon est opérationnel après un redémarrage. Elle renvoie `503 starting`
jusqu'à ce que chaque composant ait démarré, puis `200 ok`. Comme l'écouteur de l'API ne commence à
accepter des connexions qu'une fois le démon démarré, tout `200` ici signifie que la configuration a
été analysée, que les composants sont opérationnels et que Kapkan répond.

```sh
curl -fsS localhost:8080/healthz   # exits non-zero (503) until ready, then prints "ok"
```
