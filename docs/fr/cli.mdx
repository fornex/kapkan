# Référence CLI

Kapkan est un binaire unique. Ce qu'il fait est sélectionné par des options de ligne de commande au
démarrage, auxquelles s'ajoutent un petit nombre de **commandes** qui inspectent le système en cours
d'exécution puis se terminent. Tous les journaux vont vers **stderr** ; l'API REST et les métriques
Prometheus sont servies via HTTP sur `api.listen` (par défaut `127.0.0.1:8080`), tandis que les
options utilitaires (`-version`, `-dump-schema`) et les commandes écrivent leur sortie sur
**stdout**.

```sh
kapkan [flags]                     # run the daemon
kapkan [flags] <command> [args]    # run a command and exit
```

Les options globales se placent **avant** la commande ; les options propres à la commande viennent
après elle. Ainsi, `kapkan -config /etc/kapkan/config.yaml dataplane status -json` lit le chemin de
configuration depuis le `-config` global et passe `-json` à `dataplane status`. Une option qui se
termine déjà d'elle-même (`-version`, `-check-config`, `-dump-schema`, `-check-update`, `-s`) ne peut
pas être combinée avec une commande — Kapkan refuse la combinaison plutôt que d'en honorer
silencieusement une seule.

## Options

| Option | Valeur par défaut | Description |
| --- | --- | --- |
| `-config <path>` | `configs/dev.yaml` | Chemin du [fichier de configuration](/docs/configuration) YAML. |
| `-log-format <fmt>` | `json` | Format de sortie des journaux : `json` (structuré, pour les collecteurs de journaux) ou `text` (lisible par un humain, pour les exécutions locales). Toute valeur autre que `text` est traitée comme `json`. |
| `-log-level <lvl>` | `info` | Niveau de journalisation minimal : `debug`, `info`, `warn`, `error`. Une valeur non reconnue retombe sur `info`. |
| `-check-config <path>` | — | Valide le fichier de configuration situé à `<path>` puis se termine — ne démarre **pas** le démon. Voir [ci-dessous](#valider-une-configuration). |
| `-dump-schema` | `false` | Affiche le schéma JSON de la configuration sur stdout puis se termine. Voir [ci-dessous](#exporter-le-schéma). |
| `-version` | `false` | Affiche la version de build puis se termine. La même version est exposée à l'exécution via `/api/v1/status` et la [métrique](/docs/metrics) `kapkan_build_info`. |
| `-check-update` | `false` | Exécute une fois la [vérification de mise à jour](/docs/configuration) optionnelle puis se termine — `0` à jour, `10` une mise à jour est disponible, `1` en cas d'erreur. Interroge l'API GitHub Releases ; n'envoie que la requête elle-même, jamais l'identité du nœud ni la configuration. |
| `-pid-file <path>` | `/run/kapkan/kapkan.pid` | Emplacement où le démon écrit son identifiant de processus au démarrage (supprimé lors d'un arrêt propre) ; lu par `-s` pour localiser le démon en cours d'exécution. Un échec d'écriture n'est pas fatal — le démon tourne quand même, seul `-s` devient indisponible. |
| `-s <signal>` | — | Envoie un signal à un démon en cours d'exécution puis se termine, en lisant `-pid-file` : `reload`, `stop` ou `quit`. Ne démarre **pas** de démon. Voir [ci-dessous](#contrôler-un-démon-en-cours-dexécution). |

<Callout type="info" title="json ou text ?">
Utilisez `-log-format text` pour le développement local — c'est le format utilisé par le
[Démarrage rapide](/docs/quickstart). Conservez la valeur par défaut `json` en
production afin qu'un collecteur de journaux puisse analyser les champs structurés ; l'[unité
systemd](/docs/deployment) est livrée avec `-log-format json -log-level info`.
</Callout>

## Exécuter le démon

Sans option utilitaire, Kapkan ouvre ses écouteurs de flow, son API REST et (hors dry-run) son
locuteur BGP, puis tourne jusqu'à ce qu'il reçoive `SIGINT` ou `SIGTERM`, moment auquel il s'arrête
proprement. Il ne se termine avec un code non nul qu'en cas d'erreur fatale au démarrage ou à
l'exécution.

```sh
# Local, human-readable logs against the bundled dev config:
kapkan -config configs/dev.yaml -log-format text

# Production-style: structured logs at info level:
kapkan -config /etc/kapkan/config.yaml -log-format json -log-level info
```

Le fichier de configuration est rechargeable à l'exécution sans redémarrage — exécutez
[`kapkan -s reload`](#contrôler-un-démon-en-cours-dexécution), envoyez directement `SIGHUP`
(`systemctl reload kapkan`) ou `POST /api/v1/config/reload`. Voir la
[référence de configuration](/docs/configuration) pour ce qui se recharge et ce qui est figé au
démarrage.

## Contrôler un démon en cours d'exécution

```sh
kapkan -s reload    # re-read the config file (SIGHUP)
kapkan -s stop      # graceful shutdown (SIGTERM)
kapkan -s quit      # alias of stop
```

`-s` lit l'identifiant de processus depuis `-pid-file` (par défaut `/run/kapkan/kapkan.pid`, écrit
par le démon au démarrage) et délivre le signal correspondant à ce processus — le même contrôle
local à la manière de nginx que `nginx -s reload`. Il ne nécessite ni connexion réseau ni jeton
d'API, il fonctionne donc même si l'API REST est indisponible ; il a besoin de la permission de
signaler le démon, exécutez-le donc en tant que `root` ou avec l'utilisateur `kapkan`.

| Valeur de `-s` | Signal | Effet |
| --- | --- | --- |
| `reload` | `SIGHUP` | Recharge à chaud le fichier de configuration. Équivaut à `systemctl reload kapkan` ou `POST /api/v1/config/reload`. |
| `stop` / `quit` | `SIGTERM` | Arrêt gracieux. Équivaut à `systemctl stop kapkan`. Les deux sont des alias — l'arrêt de Kapkan est toujours gracieux (il demande aux pairs BGP de conserver les routes d'atténuation via [Graceful Restart](/docs/mitigation)). |

Si le pid file est absent ou périmé (aucun processus de ce type), ou si vous n'avez pas la
permission de le signaler, `-s` affiche la raison sur stderr et se termine avec le code `1`.

<Callout type="info" title="Où se trouve le pid file">
L'[unité systemd](/docs/deployment) fournie définit `RuntimeDirectory=kapkan`, de sorte que
`/run/kapkan` existe et est accessible en écriture par l'utilisateur `kapkan` ; le démon y écrit
`/run/kapkan/kapkan.pid` et le supprime lors d'un arrêt propre. Dans une exécution de développement
locale, ce répertoire peut ne pas exister — le démon émet un avertissement et continue, et `-s`
signalera « no pid file ». Passez `-pid-file /tmp/kapkan.pid` à la fois au démon et à `-s` si vous
voulez ce raccourci en local.
</Callout>

## Options utilitaires

Ces options se terminent avant le démarrage du démon — elles n'ouvrent jamais d'écouteur ni
n'envoient d'annonce de route, elles sont donc sûres à exécuter sur un hôte de production.
(`-check-update` effectue une seule requête sortante vers l'API des releases ; les autres sont
entièrement hors ligne.)

### Valider une configuration

```sh
kapkan -check-config /etc/kapkan/config.yaml
```

Effectue exactement la même analyse et la même validation que le moteur — y compris les règles
inter-champs qu'un schéma statique ne peut pas exprimer — puis affiche la configuration résolue (mode,
réseaux protégés, les écouteurs de flow configurés, le nombre de groupes, et l'atténuation effective
par [hostgroup](/docs/hostgroups)) et se termine :

| Code de sortie | Signification |
| --- | --- |
| `0` | La configuration est valide. |
| `1` | La configuration est invalide ; l'erreur exacte est affichée sur stderr. |

Cette séparation nette 0/1 s'intègre directement dans une CI ou une vérification de pré-déploiement.
Voir [Valider la configuration](/docs/configuration#valider-la-configuration).

Une configuration valide peut tout de même afficher un bloc `WARNING` après la ligne `OK` — une
configuration légale que le démon exécutera, mais presque certainement pas ce que vous vouliez dire.
Il en existe un aujourd'hui : une [règle statique qui ne peut jamais
s'appliquer](/docs/dataplane-tuning#règles-qui-ne-peuvent-jamais-sappliquer), avec le nom de la règle
et ce qui prend ses paquets. Le code de sortie reste `0`, une vérification existante n'est donc pas
affectée ; si vous voulez que les avertissements fassent aussi échouer le build, cherchez `WARNING`
dans la sortie en plus du code.

### Exporter le schéma

```sh
kapkan -dump-schema
```

Affiche le schéma JSON de la configuration sur stdout et se termine avec le code `0` (ou `1` en cas
d'erreur interne). Le [générateur de configuration](/config) utilise ce schéma pour valider les champs
dans votre navigateur.

### Afficher la version

```sh
kapkan -version
```

Affiche la version de build (le tag de release plus la révision VCS courte lorsqu'elle est connue) sur
stdout puis se termine. La même chaîne est servie à l'exécution sur `/api/v1/status` et portée par la
[métrique](/docs/metrics) `kapkan_build_info` — vous pouvez ainsi confirmer la version d'un binaire
localement sans aucune sortie réseau.

### Vérifier les mises à jour

```sh
kapkan -check-update
```

Exécute une fois à la demande la [`update_check`](/docs/configuration) puis se termine : `0` si à jour,
`10` si une release plus récente est disponible, `1` en cas d'erreur. Elle interroge l'API GitHub
Releases et n'envoie que la requête elle-même (votre adresse IP et un User-Agent générique) — jamais
l'identité du nœud, la configuration ni les données d'attaque. La vérification périodique en cours de
processus est **désactivée par défaut** ; cette option fonctionne indépendamment de ce réglage.

## Commandes

### `dataplane status`

```sh
kapkan dataplane status              # human-readable report
kapkan dataplane status -json        # the same inspection as JSON
```

Indique si le plan de données XDP filtre réellement, et pourquoi il ne le fait pas le cas échéant.
Deux propriétés la rendent utilisable en plein incident :

- **Elle est strictement en lecture seule.** Elle ouvre le programme et les maps épinglés en lecture
  seule — les descripteurs de fichier des maps portent `BPF_F_RDONLY`, de sorte que le *noyau*
  lui-même refuse toute écriture au travers — et elle ne charge jamais de programme, ne crée aucune
  map, n'écrit aucune valeur de map, n'attache ni ne détache rien et ne supprime aucun épinglage. Le
  démarrage du démon reprend un jeu d'objets épinglés existant ou le reconstruit ; cette commande ne
  le peut pas, elle ne peut donc jamais vous coûter les règles d'atténuation que vous cherchez
  justement à diagnostiquer.
- **Elle fonctionne alors que le démon est arrêté.** C'est le cas principal, pas un bonus : avec la
  valeur par défaut `dataplane.on_exit: keep`, le noyau continue d'appliquer la politique statique
  sans aucun processus Kapkan, et cette commande lit directement les objets épinglés pour vous le
  dire.

Le rapport commence par le verdict et le remède, puis donne le détail : les interfaces attachées avec
le mode réellement en vigueur, les versions du noyau et du schéma des maps, la génération active, le
nombre de règles statiques et dynamiques, la taille / l'occupation / la mémoire de chaque map,
l'indicateur dry-run et les compteurs de verdicts.

Deux points de cette sortie méritent d'être connus à l'avance :

- **Le mode d'attachement `GENERIC` est signalé dès la première ligne.** `xdp_mode: auto` retombe du
  chemin pilote vers le chemin générique (skb) sans échouer, et cela coûte environ un ordre de
  grandeur de capacité ; c'est donc une information mise en avant, et non un champ parmi vingt.
- **Les compteurs de verdicts sont affichés en deux blocs.** Les compteurs *terminaux* partitionnent
  le trafic — exactement un est incrémenté par paquet — ils sont donc totalisés. Les compteurs
  d'*observation* sont incrémentés *en plus* d'un compteur terminal pour le même paquet
  (`dryrun_would_drop`, `pass_rule_expired`, `pass_frag_noports`, `err_policy_missing`) ; les ajouter
  au total produirait un nombre de paquets supérieur au nombre de paquets réels, ils sont donc listés
  séparément et jamais inclus dans la somme.

| Option | Valeur par défaut | Description |
| --- | --- | --- |
| `-json` | `false` | Affiche l'inspection complète au format JSON, y compris le champ `state` dont sont dérivés les codes de sortie. |
| `-pin-path <dir>` | depuis `-config` | Le répertoire bpffs à inspecter. Par défaut `dataplane.pin_path` issu de la configuration désignée par le `-config` global, avec repli sur `/sys/fs/bpf/kapkan` lorsque ce fichier ne peut pas être lu. Le rapport indique toujours quel chemin il a examiné et d'où vient ce chemin. |

#### Codes de sortie

| Code de sortie | État signalé | Signification et ce qu'il faut faire |
| --- | --- | --- |
| `0` | `enforcing` | Au moins une interface possède un attachement XDP actif. Rien à faire. |
| `10` | `no_pin_path`, `no_program`, `detached` | Le plan de données **ne filtre pas**, et rien n'est cassé pour autant — soit il n'a jamais tourné ici, soit il est arrêté, soit ses attachements ont disparu. Démarrez Kapkan, ou vérifiez que les interfaces configurées existent. |
| `11` | `not_bpffs`, `torn`, `schema_skew` | Quelque chose doit être **corrigé** avant qu'il puisse fonctionner : bpffs n'est pas monté, le jeu d'objets épinglés est incomplet, ou les maps épinglées ont une version de schéma différente de celle de ce binaire. La raison affichée nomme le correctif (monter bpffs ; redémarrer Kapkan). |
| `1` | `attach_unknown`, ou toute erreur de lecture | La commande **n'a pas pu répondre** — le plus souvent un problème de permission (voir ci-dessous). Délibérément pas signalé comme « ne filtre pas », car il se peut très bien qu'il filtre. |
| `2` | — | Erreur d'invocation : une option, une commande inconnue ou un argument superflu. |

Seul `enforcing` se termine avec le code `0` : `kapkan dataplane status >/dev/null` s'intègre donc
directement dans un contrôle de supervision. La convention du `10` pour un état porteur de sens est
la même que celle utilisée par [`-check-update`](#vérifier-les-mises-à-jour).

#### Permissions

Lire des objets épinglés coûte bien moins cher que d'en créer : sur un noyau où
`kernel.unprivileged_bpf_disabled=0`, **aucune capability n'est requise** — ni `CAP_NET_ADMIN` ni
`CAP_PERFMON`, dont le démon a besoin pour *charger et attacher*, n'entrent en jeu. Ce qui
conditionne réellement l'accès :

- Le répertoire d'épinglage est en mode `0700` et appartient à l'utilisateur sous lequel tourne le
  démon ; en pratique, vous voudrez donc `sudo kapkan dataplane status`.
- Sur un noyau où `kernel.unprivileged_bpf_disabled` est activé — la valeur par défaut sur Debian et
  Ubuntu — `bpf(2)` exige en plus `CAP_BPF`, même pour ouvrir un épinglage existant.
- **Les épinglages de link exigent un droit d'écriture, pas seulement de lecture :** le noyau refuse
  `BPF_OBJ_GET` sur un `bpf_link` à moins que le descripteur ne soit ouvert en `O_RDWR`. Un lecteur
  non-root voit donc toutes les maps et aucun attachement, ce qui est signalé comme `attach_unknown`
  (code de sortie `1`) plutôt que comme « détaché ».

<Callout type="info" title="Elle ne modifie jamais ce qu'elle diagnostique">
C'est pourquoi `dataplane status` est un chemin de code séparé, en lecture seule, plutôt qu'une
réutilisation du code de démarrage du démon. Le démarrage du plan de données reprend un jeu d'objets
épinglés existant — ou, lorsque le schéma ne correspond pas, le détruit et le reconstruit, en jetant
toutes les règles d'atténuation dynamiques présentes dans le noyau. Un diagnostic capable de faire
cela en pleine attaque serait pire que pas de diagnostic du tout.
</Callout>

### `scrub`

```sh
kapkan scrub -config /etc/kapkan/scrub.yaml
```

Exécute le rôle [nœud de scrubbing](/docs/scrubbing#nœuds-de-nettoyage-gérés) : le même binaire,
un travail différent. Il n'y a ni détection, ni BGP, ni écouteur de télémétrie — la machine reçoit
le trafic que le cerveau lui a dévié, interroge en long-poll la table de règles du cerveau, et
maintient son [plan de données](/docs/dataplane) XDP local en train d'appliquer exactement ce que
le cerveau lui dit de supprimer. L'interrogation fait aussi office de signal de vivacité du nœud.

Tout ce qui est spécifique au rôle vit dans son propre `scrub.yaml` ; le `config.yaml` du démon
n'est **pas** lu (`-config` a ici pour valeur par défaut `/etc/kapkan/scrub.yaml`). Il comporte
trois parties : le contrôleur à joindre, l'identité du nœud, et le même bloc `dataplane:` qu'un
démon embarque.

```yaml
dry_run: true                     # the remote-role default — counts, drops nothing
controller:
  url: "https://kapkan.example.net:8443"   # the brain's API base (no path)
  token_env: KAPKAN_AGENT_TOKEN            # env var holding the agent token (required)
  name: scrub-fra1                         # must equal a scrubbing.nodes[] name on the brain
dataplane:
  interfaces: [eth0]              # the dirty side (diverted traffic arrives here)
  xdp_mode: auto
  pin_path: /sys/fs/bpf/kapkan
```

<Callout type="warning" title="Un nœud de scrubbing démarre en dry-run par défaut">
`dry_run` vaut **true** par défaut pour un rôle distant — le nœud installe les règles et compte ce
qu'elles *supprimeraient*, mais ne supprime rien, jusqu'à ce que vous définissiez explicitement
`dry_run: false`. Il n'applique jamais une règle que le cerveau a marquée dry-run tant qu'elle est
active, et il exige un vrai token agent : sans lui, ses interrogations ne portent aucune identité et
le cerveau le compterait comme mort. Utilisez `https` en dehors d'un laboratoire — une
`controller.url` en clair envoie le token en clair.
</Callout>

| Option | Défaut | Description |
| --- | --- | --- |
| `-config <path>` | `/etc/kapkan/scrub.yaml` | La configuration du nœud de scrubbing. |
| `-log-format <fmt>` | `json` | `json` ou `text`. |
| `-log-level <lvl>` | `info` | `debug`, `info`, `warn` ou `error`. |

Confirmez qu'un nœud tourne avec `kapkan dataplane status` sur le nœud lui-même — il rapporte
`ENFORCING` et le nombre de règles installées — et la [vue Nœuds](/docs/dashboard) du cerveau
l'affiche vivant. Acheminer le trafic dévié jusqu'au nœud est le
[guide d'intégration réseau](/docs/network-integration).

### `edge`

```sh
kapkan edge -config /etc/kapkan/edge.yaml
```

Exécute le rôle [nœud edge](/docs/edge) : le nginx ou l'Angie de la machine devient un frontal
HTTPS géré pour les zones que le cerveau sert. Le rôle interroge en long-poll le document de zones
du cerveau, rend la configuration du terminateur et l'installe derrière `nginx -t`, répond à
l'`auth_request` de nginx depuis un service de décision local, lit le journal d'accès pour en tirer
des agrégats par source, émet et renouvelle les certificats des zones sur la machine, et rend
compte de lui-même. L'interrogation fait aussi office de signal de vivacité du nœud. Le pas à pas
est le [guide d'installation](/docs/edge-install).

Tout ce qui est spécifique au rôle vit dans son propre `edge.yaml` ; le `config.yaml` du démon
n'est **pas** lu (`-config` a ici pour valeur par défaut `/etc/kapkan/edge.yaml`).

```yaml
dry_run: true                          # the remote-role default — marks, refuses nothing
controller:
  url: https://kapkan.example.net:8443 # the brain's API base (no path); https outside a lab
  token_env: KAPKAN_EDGE_TOKEN         # env var holding the agent token (required)
  name: edge-1                         # must equal an edge.nodes[] name on the brain
  report_interval_seconds: 10          # self-report cadence
state_dir: /var/lib/kapkan-edge        # document cache, generations, ACME keys and certificates
sockets_dir: /run/kapkan-edge          # edge-decide.sock, edge-challenge.sock, edge-log.sock
socket_group: nginx                    # the terminator's worker group (nginx | www-data | angie)
terminator:
  binary: nginx                        # nginx (default) | angie
  main_conf: /etc/nginx/nginx.conf     # -c for `nginx -t` and `nginx -s reload`; empty = compiled default
  reload: exec                         # exec (default) | signal | command
  pid_file: /run/nginx.pid             # liveness check; required for reload: signal
  # command: [systemctl, reload, nginx]
acme:
  directory: ""                        # default CA; empty = Let's Encrypt production
  fallback: ""                         # optional second CA after three consecutive failures
  contact: ["mailto:ops@example.net"]
  # eab:                               # External Account Binding for CAs that require one
  #   - directory: https://acme.zerossl.com/v2/DV90
  #     kid: your-kid
  #     hmac_key_env: KAPKAN_EDGE_ZEROSSL_HMAC
  # disabled: true                     # issue nothing (zones stay on :80 answering 503)
status_listen: 127.0.0.1:9102          # /healthz + /metrics; unauthenticated, keep it private
omit_catch_all: false                  # true when nginx.conf has its own default_server
disable_ipv6: false                    # true on hosts without an IPv6 stack
```

| Clé | Signification |
| --- | --- |
| `dry_run` | Absent ou `true` : les décisions sont comptées et marquées (`X-Kapkan-Mark: would-deny:<reason>` atteint l'origine), aucune n'est appliquée. Mettez `false` pour refuser. |
| `controller.url` / `token_env` / `name` | L'URL de base de l'API du cerveau (sans chemin, sans identifiants dans l'URL), la variable d'environnement contenant le token **agent**, et le nom de ce nœud — il doit être égal à une entrée `edge.nodes[]` sur le cerveau, sinon chaque interrogation renvoie un `404` retentissant. |
| `state_dir` / `sockets_dir` | Les répertoires propres au rôle (par défaut `/var/lib/kapkan-edge`, `/run/kapkan-edge`) — jamais les `/var/lib/kapkan` et `/run/kapkan` du cerveau, dont systemd changerait le propriétaire et qu'il supprimerait sous ses pieds sur un hôte partagé. Absolus, sans caractères que nginx pourrait mal interpréter. |
| `socket_group` | Le groupe des workers du terminateur. Les sockets de décision et de journal sont en `0660` pour lui ; le socket de challenge est en `0666` (il répond à des tokens publics). Vide, les deux sockets restreints au groupe restent accessibles au seul propriétaire. |
| `terminator.binary` / `main_conf` | Ce qu'il faut exécuter pour `-t` et les rechargements, et la configuration principale à passer en `-c`. Ce fichier doit contenir `include /var/lib/kapkan-edge/conf/live/*.conf;` une seule fois, à l'intérieur de `http {}`. |
| `terminator.reload` | `exec` exécute `<binary> -s reload` (il doit pouvoir signaler le master de nginx — l'unité tourne en root) ; `signal` envoie `HUP` au pid de `pid_file` ; `command` exécute `terminator.command`, par exemple `[systemctl, reload, nginx]`. |
| `terminator.pid_file` | Lorsqu'il est défini, lu à chaque tick de rapport et signalé avec `0` : `/healthz` répond `503` et le rapport indique `alive: false` tant qu'aucun processus ne porte ce pid. |
| `acme.directory` / `fallback` / `contact` | La CA par défaut du nœud (le bloc `acme` propre à une zone l'emporte pour la directory et le repli), la CA de repli essayée après trois échecs consécutifs (elle doit différer de la CA principale résolue), et le contact du compte. |
| `acme.eab[]` | External Account Binding par URL de directory (`directory`, `kid`, `hmac_key_env`) pour les CA qui l'exigent — ZeroSSL, Google Trust Services. La clé HMAC est un secret et est lue depuis la variable d'environnement nommée. |
| `acme.disabled` | N'émettre aucun certificat : les zones restent sur `:80` en répondant `503` (un laboratoire qui exerce tout sauf l'émission). Les certificats fournis par l'opérateur ne sont pas encore une fonctionnalité. |
| `status_listen` | Sert `/healthz` et `/metrics` lorsqu'il est défini. Non authentifié — loopback ou une adresse privée. |
| `omit_catch_all` / `disable_ipv6` | Supprimer le `default_server` fourre-tout de Kapkan (votre `nginx.conf` en déclare un) / supprimer les écouteurs `[::]` (pas de pile IPv6). |

<Callout type="warning" title="Un nœud edge démarre en dry-run par défaut">
`dry_run` vaut **true** par défaut pour un rôle distant — le nœud compte et marque ce qu'il
*refuserait* mais ne refuse rien, jusqu'à ce que vous définissiez explicitement `dry_run: false`.
Il exige un vrai token agent : sans lui, ses interrogations ne portent aucune identité et le
cerveau le compterait comme mort. Utilisez `https` en dehors d'un laboratoire — une
`controller.url` en clair envoie le token en clair.
</Callout>

| Option | Défaut | Description |
| --- | --- | --- |
| `-config <path>` | `/etc/kapkan/edge.yaml` | La configuration du nœud edge. |
| `-check` | désactivé | Valide le fichier et ce qu'il nomme sur cette machine — le groupe du socket doit exister et toute clé EAB être bien formée (problèmes) ; un token, un binaire de terminateur ou un `main_conf` absent n'est qu'un avertissement — puis se termine. |
| `-log-format <fmt>` | `json` | `json` ou `text`. |
| `-log-level <lvl>` | `info` | `debug`, `info`, `warn` ou `error`. |

Confirmez qu'un nœud tourne avec `curl 127.0.0.1:9102/healthz` — `200` avec `"converged":true`
une fois le document rendu et actif — et l'inventaire du cerveau (`GET /api/v1/edge/nodes`, la
vue Nœuds de la console) l'affiche vivant. Le schéma côté cerveau du fichier de zones s'obtient
avec `kapkan -dump-zones-schema`.

### `nginx-exporter`

```sh
KAPKAN_API_TOKEN=... kapkan nginx-exporter -log /var/log/nginx/kapkan.json.log -api http://127.0.0.1:8080
```

Suit un journal d'accès JSON de nginx, mesure les débits de requêtes par source et par fenêtre,
et poste les verdicts sur le
[canal de blocage de sources](/docs/api#le-canal-de-blocage-de-sources) du cerveau. Le
`log_format` requis, les seuils et les bornes opérationnelles vivent avec la fonctionnalité :
[l'exportateur de référence](/docs/dataplane#lexportateur-de-référence--kapkan-nginx-exporter).
Les options globales du démon ne sont pas lues ; tout lui est propre :

| Option | Défaut | Description |
| --- | --- | --- |
| `-log <path>` | — (requis) | Le journal d'accès nginx, dans le `log_format` JSON documenté. |
| `-api <url>` | `http://127.0.0.1:8080` | L'URL de base de l'API du cerveau. |
| `-token-env <name>` | `KAPKAN_API_TOKEN` | Variable d'environnement contenant un token **operator**. |
| `-victim <ip>` | — | Victime fixe ; remplace le champ `dst` du journal. |
| `-window <dur>` | `10s` | Fenêtre de mesure. |
| `-rps <n>` | `50` | Requêtes/seconde par source qui arment un blocage. |
| `-min-requests <n>` | `100` | Plancher par fenêtre avant que l'arithmétique de débit ne s'applique. |
| `-error-ratio <r>` | `0` | Exige en plus cette part de 4xx/5xx (`0` désactive cet axe). |
| `-ttl <dur>` | `5m` | TTL du blocage ; une source encore chaude est rafraîchie avant qu'il n'expire. Doit valoir au moins `2×-window`. |
| `-observe` | désactivé | Journalise les verdicts sans les poster. |
| `-log-format` / `-log-level` | `json` / `info` | La journalisation propre à l'exportateur. |
