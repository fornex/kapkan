# Authentification

Par défaut, l'API et le tableau de bord de Kapkan sont **non authentifiés**. Cela n'est sûr que
parce que la valeur par défaut de `api.listen` se lie à `127.0.0.1` — l'écouteur n'est accessible
que depuis l'hôte lui-même, de sorte qu'aucun token n'est requis pour lire l'état, lister les
attaques ou émettre des bannissements manuels. Dès que vous liez l'écouteur à une adresse
routable, cette protection disparaît.

<Callout type="danger" title="Définissez un token avant d'exposer l'écouteur">
Si vous remplacez `api.listen` par autre chose que localhost — par exemple `0.0.0.0:8080`
ou une interface spécifique — configurez d'abord un token. Un écouteur non authentifié sur une
adresse routable permet à n'importe qui d'atteindre l'[API](/docs/api), y compris les endpoints
de bannissement et de débannissement manuels.
</Callout>

## Définir un token

La forme abrégée est un unique token operator. Ajoutez `token_env` au bloc `api` — il nomme la
variable d'environnement qui contient le token ; le secret lui-même est lu depuis l'environnement
du processus à chaque requête, jamais depuis le fichier de configuration :

```yaml
api:
  listen: "0.0.0.0:8080"
  token_env: "KAPKAN_API_TOKEN"   # token read from this env var, never the file
```

Fournissez ensuite la valeur hors bande, par exemple via l'environnement de votre gestionnaire de
services ou un fichier de secrets :

```sh
export KAPKAN_API_TOKEN="$(openssl rand -hex 32)"
./kapkan -config /etc/kapkan/config.yaml
```

Conserver le token dans une variable d'environnement plutôt que dans le YAML signifie que la
configuration reste sûre à valider dans git et à comparer avec le reste de votre [configuration](/docs/configuration).

Ce token unique est tout ce dont la plupart des déploiements ont besoin — le reste de cette page
(rôles, tenants) est optionnel et peut attendre.

## Rôles

Pour un contrôle d'accès basé sur les rôles, utilisez `tokens` au lieu de `token_env` — une liste où
chaque entrée nomme la variable d'environnement contenant son secret ainsi qu'un rôle :

```yaml
api:
  listen: "0.0.0.0:8080"
  tokens:
    - { name: dashboard,  token_env: "KAPKAN_API_RO", role: viewer }
    - { name: automation, token_env: "KAPKAN_API_RW", role: operator }
```

`name`, `token_env` et `role` sont tous requis pour chaque entrée ; `role` doit valoir exactement
`viewer`, `operator` ou `agent`. Une valeur manquante ou mal orthographiée est une erreur de
validation bloquante au démarrage, et non une valeur par défaut silencieuse.

| Rôle | Autorisations |
| --- | --- |
| `viewer` | Lecture seule : état, attaques, hôtes, bannissements, métriques. |
| `operator` | Tout ce qu'un viewer peut faire, plus le bannissement/débannissement manuel, les [blocages de sources](/docs/api#le-canal-de-blocage-de-sources) et le rechargement de la configuration (le rechargement est réservé aux admins — voir ci-dessous). |
| `agent` | L'identifiant d'un nœud — celui d'un [nœud de scrubbing](/docs/scrubbing#nœuds-de-nettoyage-gérés) ou d'un [nœud edge](/docs/edge) : les interrogations de règles et de zones, son propre rapport et la coordination ACME edge, et **rien d'autre**. Liez-le à son nœud avec `node` (ci-dessous). |

Il n'existe pas de rôle `admin` distinct à attribuer — un *admin* est simplement un token operator
sans `tenant` défini. Les valeurs de rôle que le moteur accepte sont `viewer`, `operator` et
`agent` ; la distinction admin/limité relève de l'axe [Multi-tenant](/docs/multi-tenancy), abordé
ci-dessous.

<Callout type="info" title="Le rôle agent n'est pas un viewer amoindri">
`agent` se situe **hors** de l'échelle de privilèges, en dessous de `viewer` : il accorde
exactement les routes de nœud (les interrogations de règles et de zones, les deux rapports sur soi,
le créneau ACME edge et la publication des défis) et se voit refuser tout autre point de
terminaison, y compris le canal de blocage de sources, qui installe des règles noyau et reste donc
réservé au rôle operator —
un token agent compromis, qui réside sur une machine distante, ne doit pas devenir une
clé de lecture universelle. Il ne peut pas non plus être rattaché à un tenant : le flux de règles
concerne l'ensemble du déploiement, de sorte qu'un `tenant` sur un token agent est une erreur de
validation bloquante. Donnez à chaque nœud son propre token agent, jamais un token
operator, et **liez-le au nœud** (ci-dessous).
</Callout>

### Lier un token agent à son nœud

Un token agent porte `node` : le nom d'exactement une entrée `edge.nodes[]` ou `scrubbing.nodes[]`.
Le cerveau refuse alors ce token sur chaque route où un nœud se nomme lui-même — les interrogations
(`?node=<name>`), les rapports sur soi, le créneau ACME et la publication des défis — lorsque le nom
présenté est celui d'un autre nœud, et il refuse **avant** de faire quoi que ce soit de ce nom :
aucune présence n'est estampillée, aucun rapport stocké, aucun créneau accordé, aucune autorisation
de clé publiée. Le refus est un `403` uniforme qui ne nomme pas le nœud lié, un avertissement par
minute et par token dans le journal du cerveau, et un compte dans
`kapkan_api_node_binding_refused_total{route}`. Aucune ligne d'[audit](/docs/audit) n'est écrite :
la piste d'audit attribue ce qu'un opérateur a changé, et une machine refusée n'a rien changé — la
ligne de journal et le compteur sont là où se révèle un token de nœud mal configuré ou volé. Un
token lié qui interroge sans `?node=` est refusé lui aussi : sa liaison dit quel nœud il est.

```yaml
api:
  tokens:
    - { name: edge-fra1, token_env: KAPKAN_EDGE_FRA1, role: agent, node: edge-fra1 }
    - { name: edge-nyc1, token_env: KAPKAN_EDGE_NYC1, role: agent, node: edge-nyc1 }
    - { name: scrub-1,   token_env: KAPKAN_SCRUB_1,   role: agent, node: fra1 }
```

Les règles : `node` n'est autorisé que sur les tokens `agent` ; le nom doit exister dans exactement
une des deux listes de nœuds (un nom présent dans les deux est refusé comme ambigu — les deux canaux
sont des domaines de confiance différents) ; plusieurs tokens peuvent lier le même nœud, et c'est
ainsi qu'un token se renouvelle sans interruption.

Sans `node`, un token agent est un **identifiant valable pour toute la flotte** : il peut interroger
sous l'identité de n'importe quel nœud et rapporter sous l'identité de n'importe quel nœud — la
raison pour laquelle un token volé imposait naguère de le renouveler pour toute la flotte. Ce que
`node` change, c'est l'usurpation d'identité et le rayon de rotation ; ce qui limite l'ensemble des
zones pour lesquelles un token lié volé peut émettre, c'est le [périmètre de
placement](/docs/edge#placer-les-zones-sur-les-nœuds) du nœud : agissant sous l'identité de son
propre nœud, il ne peut prendre le créneau d'émission et publier une autorisation de clé ACME que
pour les zones que ce périmètre couvre — toutes les zones sur une flotte sans périmètres. Traitez la
compromission d'un nœud comme une exposition de certificat pour les zones de ce nœud, et renouvelez
le token de ce nœud. Un token non lié continue de fonctionner exactement comme avant : une flotte
migre donc un nœud à la fois — sauf si un nœud a un [périmètre de
placement](/docs/edge#placer-les-zones-sur-les-nœuds) (`edge.nodes[].hostgroups`), auquel cas chaque
token `agent` doit porter `node`, sous peine d'erreur de validation bloquante, car un périmètre
appliqué face à un token partagé est une promesse que rien ne tient — et il est nommé tant qu'il
n'est pas lié : par `kapkan -check-config` (un WARNING), dans le journal du démon au démarrage et à
chaque rechargement, et dans l'inventaire edge (`unbound_agent_tokens` ; par nœud, `tokens` liste
les noms des tokens liés et `last_token` le token qui a interrogé en dernier sous son identité —
regardez-le basculer pendant une migration). Faire aussi d'un token agent non lié une erreur sur les
flottes sans périmètres est prévu pour une version MAJEURE.

La présence n'est estampillée que par les tokens agent : un operator qui interroge avec `?node=X`
reçoit le document de X en **aperçu** et ne fait pas paraître X vivant.

**Laissez à une étape de migration le temps de se voir.** Un changement de token atteint une
interrogation déjà en attente : le rechargement y met fin avec la réponse qu'une première
interrogation obtiendrait désormais (`401` pour un token disparu, `403` pour un token dont la
liaison a été déplacée), et le nœud se reconnecte avec ce qu'il a maintenant. L'*inventaire*, lui,
est plus lent, parce qu'une présence est estampillée quand une interrogation commence puis de
nouveau quand elle se termine — le refus compris : un nœud que vous venez de couper affiche donc
`alive` pendant tout le reste de son attente (jusqu'à 25 s), puis `edge.stale_after_seconds`
par-dessus, soit environ 40 s avec les valeurs par défaut. Attendez ce délai avant de lire la
bascule de `last_token`, sans quoi vous regarderez l'état d'avant votre changement.

`token_env` et `tokens` sont **mutuellement exclusifs** — `token_env` correspond à exactement un
token operator. Une requête est comparée à chaque token configuré (en temps constant) ; le rôle le
plus élevé qui correspond s'applique. Une lecture avec un token viewer fonctionne ; une mutation
avec un token viewer est refusée par un `403 Forbidden` ; une requête sans token valide reçoit un
`401 Unauthorized`. Une variable d'environnement vide ou non définie ne correspond jamais, de sorte
qu'un secret mal configuré échoue en mode fermé.

Donnez à chaque token un secret distinct — si une même valeur de secret est configurée pour deux
tokens ayant des rôles, des tenants ou des liaisons de nœud différents (une entrée non liée et une
entrée liée comprises), la requête est refusée (`401 Unauthorized`) plutôt que de deviner lequel
vous vouliez. Le démon journalise `ambiguous API token` lorsque cela se produit.

La *valeur* secrète d'un token est lue depuis l'environnement à chaque requête, de sorte que sa
rotation prend effet à la requête suivante. Ajouter ou supprimer des *entrées* de token dans le YAML
modifie l'ensemble des tokens, ce qui prend effet au prochain [rechargement de
configuration](/docs/api). Ni l'un ni l'autre ne nécessite de redémarrage.

Un token peut également porter un `tenant` optionnel, le limitant aux données d'un seul client. C'est
la fonctionnalité [Multi-tenant](/docs/multi-tenancy), superposée aux rôles décrits ici.

Le bannissement/débannissement manuel ne requiert qu'un token operator, mais `POST /api/v1/config/reload`
est en plus [réservé aux admins](/docs/multi-tenancy) : le token doit être sans périmètre (ne porter aucun
`tenant`), car un rechargement réécrit la politique de chaque tenant ainsi que l'ensemble des tokens
lui-même. Un token operator limité à un tenant est refusé par un `403 Forbidden` — `config reload is restricted
to unscoped (admin) tokens`.

<Callout type="info" title="Le nom du token est l'identité de l'operator">
Le `name` de chaque token est ce que le [journal d'audit](/docs/audit) enregistre comme `operator`
pour chaque bannissement, débannissement et rechargement de configuration qu'il émet — donnez donc
des noms significatifs aux tokens. Sur une API ouverte (sans token), il n'y a aucun principal à
attribuer, et le champ `operator` de l'audit est vide.
</Callout>

## Ce qu'il protège

Une fois un token défini, chaque requête `/api/v1` doit le transporter dans un en-tête
`Authorization` en utilisant le schéma bearer :

```http
GET /api/v1/status HTTP/1.1
Host: kapkan.internal:8080
Authorization: Bearer <token>
```

Le token fourni est comparé à celui configuré en **temps constant**, de sorte que la comparaison
elle-même ne divulgue pas le secret par effet de timing.

Ce qui reste ouvert et ce qui devient protégé :

| Chemin | Avec un token configuré |
| --- | --- |
| `GET /api/v1/*` | Requiert un token **viewer** (ou operator) |
| `POST /api/v1/*` | Requiert un token **operator** **et** un type de contenu JSON |
| `GET /metrics` | Ouvert — le scrape Prometheus reste non authentifié |
| Coque statique de l'UI (`/`) | Ouverte — mais pas les données qui se trouvent derrière |

La coque statique de l'UI du tableau de bord reste accessible afin qu'un navigateur puisse la
charger, mais elle ne possède aucune donnée propre : elle interroge `/api/v1`, demande donc le
token et le conserve dans `sessionStorage`. De même, `/metrics` reste ouvert pour votre scraper
Prometheus. Consultez la page [tableau de bord](/docs/dashboard) pour savoir comment l'UI gère la
demande de token.

## CSRF

Les endpoints POST requièrent `Content-Type: application/json` en plus du token. Un navigateur
effectuant une requête cross-site ne peut pas définir un en-tête `Authorization` personnalisé sans
un preflight CORS, et un simple envoi de formulaire ne peut pas transmettre le type de contenu
JSON. Exiger les deux — le token dans un en-tête de requête et le type de contenu JSON — bloque la
falsification de requête cross-site (CSRF) contre les endpoints de bannissement manuel, de
débannissement et de rechargement de configuration.

<Callout type="info" title="Rôles et tenants sont des axes différents">
Un rôle délimite ce qu'un token peut *faire* (lecture ou mutation). Le `tenant` optionnel d'un token
délimite quelles données il peut *voir et toucher*. Ils se composent : un viewer peut être sans
périmètre (tous les tenants) ou limité à un seul. Voir [Multi-tenant](/docs/multi-tenancy).
</Callout>
