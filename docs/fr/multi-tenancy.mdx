# Multi-tenant

Une seule instance Kapkan peut servir de nombreux clients (cas d'usage fournisseur de services
managés (MSP) ou centre de données internet (IDC)) et donner à chacun un token qui ne voit et ne
touche **que les siens** : attaques, bannissements et hôtes. Un tenant n'est qu'une étiquette
optionnelle sur un [hostgroup](/docs/hostgroups) — ou, sur un cerveau edge, sur une
[zone](/docs/zones) — il n'y a pas de nouvel objet de premier niveau,
pas de registre de tenants distinct, et le chemin critique de détection reste intact.

```yaml
tenant: "house"                 # optional: label the global/fallback group

hostgroups:
  - name: custA-web
    tenant: "customerA"         # this group belongs to customerA
    networks: ["203.0.113.0/26"]
  - name: custA-dns
    tenant: "customerA"         # a tenant can span several groups
    networks: ["203.0.113.64/26"]
  - name: custB
    tenant: "customerB"
    networks: ["198.51.100.0/24"]
  - name: shared-infra          # no tenant → visible only to admin tokens
    networks: ["192.0.2.0/24"]

api:
  tokens:
    - { name: admin,    token_env: KAPKAN_ADMIN, role: operator }
    - { name: a-portal, token_env: KAPKAN_A,     role: viewer,   tenant: "customerA" }
    - { name: b-ops,    token_env: KAPKAN_B,     role: operator, tenant: "customerB" }
```

## Comment le mettre en place

Trois étapes correspondent directement au YAML ci-dessus :

1. **Étiquetez le ou les hostgroups de chaque client** avec `tenant: "customerA"` (la même étiquette peut se répéter sur plusieurs groupes — par exemple les groupes web et DNS d'un client), ou ses [zones edge](/docs/zones) avec `zones[].tenant` pour un client qui a des noms d'hôtes et aucun préfixe.
2. **Ajoutez un token API** sous `api.tokens` portant ce même `tenant:` plus un `role:` — `viewer` est en lecture seule, `operator` peut aussi bannir/débannir.
3. **Remettez ce token au client.** Il ne voit et ne touche alors que ses propres préfixes ; tout le reste (les autres tenants, les groupes non étiquetés) lui est invisible.

C'est tout le workflow. Le reste de cette page explique comment la propriété est résolue et précisément ce qu'un token cadré peut et ne peut pas faire.

## Le modèle

« Quel tenant possède cette IP » est résolu par **la même** recherche de hostgroup par préfixe le
plus long que le moteur et le mitigateur utilisent déjà pour attribuer le trafic — quand des
préfixes se chevauchent, le hostgroup correspondant le plus spécifique l'emporte
([longest-prefix match](/docs/glossary)). Un tenant peut s'étendre sur plusieurs hostgroups (un
client avec des groupes web et DNS séparés). Une [zone edge](/docs/zones) porte la même étiquette
(`zones[].tenant`), si bien qu'un client peut ne posséder que des noms d'hôtes et aucun préfixe.

Toute IP qui tombe en dehors de tout hostgroup nommé est gérée par le **groupe global/de repli**
implicite (le fourre-tout). Ce groupe global peut porter un `tenant` de premier niveau afin que ce
trafic fourre-tout soit attribué à un tenant « house » ; un hostgroup nommé **sans** `tenant` est
non étiqueté et visible uniquement par les tokens admin.

Une étiquette de tenant n'est **pas** une unité de politique de mitigation — les seuils, les
attributs BGP et l'escalade restent par hostgroup. C'est purement une étiquette de propriété
utilisée pour cadrer l'API.

**La propriété et le placement sont deux axes, et ils n'ont pas le droit de se contredire.** Une
zone porte aussi un `hostgroup` — [l'endroit où elle est
servie](/docs/edge#placer-les-zones-sur-les-nœuds) —, et ce groupe peut lui-même porter un `tenant`.
Rien n'est hérité dans un sens ni dans l'autre : une zone dans un groupe étiqueté est une zone
« house » tant qu'elle ne dit pas le contraire, et l'étiquette d'une zone ne change jamais l'endroit
où elle tourne. Ce qui est refusé, c'est un *désaccord* : quand la zone et le hostgroup qu'elle nomme
portent tous deux un tenant et que les deux diffèrent, le rechargement échoue dans son ensemble et
les zones précédentes restent en service, parce qu'une même zone ne peut pas appartenir à deux
clients. Le groupe global fait exception, et délibérément : c'est le fourre-tout de la flotte, pas le
PoP d'un client, si bien qu'une zone étiquetée peut y résider quoi que dise le `tenant` de premier
niveau de `kapkan.yaml`.

## Périmètre du token

Un [token API](/docs/authentication) gagne un `tenant` optionnel, qui s'appuie sur son rôle : un
`viewer` peut lire mais ne rien modifier ; un `operator` peut aussi bannir/débannir.

| Token | Voit | Peut modifier |
| --- | --- | --- |
| sans périmètre (pas de `tenant`) | tous les tenants (admin) | tout ce que son rôle autorise (un viewer lit tous les tenants ; un operator peut bannir/débannir dans tous les tenants) |
| `tenant: customerA`, `role: viewer` | uniquement customerA | rien |
| `tenant: customerA`, `role: operator` | uniquement customerA | uniquement customerA |

Un token sans périmètre est un admin — le comportement par défaut, entièrement rétrocompatible. Un
token cadré sur un tenant qu'aucun hostgroup — et, avec un bloc `edge`, aucune
[zone](/docs/zones) — n'utilise est rejeté au chargement de la config (une faute de frappe ne
verrait sinon silencieusement rien). Avec un bloc edge, cette vérification a besoin des deux
fichiers : elle tourne donc quand le démon les charge ; le validateur côté navigateur ne voit que
`kapkan.yaml`, et `kapkan -check-config` sur l'hôte est la vraie vérification.

<Callout type="info" title="Le rôle agent se situe hors de cet axe">
Le token `agent` d'un [nœud de scrubbing](/docs/scrubbing#nœuds-de-nettoyage-gérés) n'est **pas**
un viewer amoindri doté d'un tenant — il est entièrement hors de l'échelle des rôles, et il **ne
peut pas** être cadré sur un tenant (la combinaison est une erreur de configuration). Le [flux de
règles et l'inventaire des nœuds](/docs/api) couvrent tous les tenants par conception : un nœud de
scrubbing filtre pour l'ensemble du déploiement, de sorte que le cadrage par tenant au niveau du
nœud est une préoccupation de [flotte](/docs/scrubbing), non de token. Traitez un token agent comme
concernant tout le déploiement, et gardez-le hors des machines qui détiennent des données clients.

Ce qui restreint un token agent, c'est la topologie, jamais la propriété.
[`node`](/docs/authentication#lier-un-token-agent-à-son-nœud) le lie à une seule machine, et le
[périmètre de placement](/docs/edge#placer-les-zones-sur-les-nœuds) d'un nœud edge décide quelles
zones son document porte — quel qu'en soit le propriétaire. Ainsi, un token lié sur un PoP qui sert
les zones d'un seul client détient bien les zones d'un seul client, mais il les détient à cause de
l'endroit où se trouve la machine, non parce que le token serait cadré : rien en lui n'est vérifié
face à un tenant.
</Callout>

## Application

Le cadrage est **par défaut en refus : un token cadré ne voit jamais que son propre tenant.** Le
tenant est dérivé une seule fois lors de l'authentification et appliqué à chaque ligne, de sorte
qu'un token cadré ne peut jamais retomber sur les données d'un autre tenant.

- **Lectures** — `/api/v1/status`, `/attacks`, `/hosts`, `/bans` et `/audit` ne renvoient que les
  lignes dont le groupe propriétaire porte le tenant de l'appelant. `/status` est reconstruit par
  périmètre : un token cadré n'obtient que ses propres hostgroups et compteurs, jamais les réseaux
  protégés globaux, les seuils globaux ni la ligne de config du groupe de repli à l'échelle du
  déploiement — ainsi un tenant n'apprend jamais les préfixes ou la posture BGP d'un autre. Un
  tenant house (le groupe de repli étiqueté d'un `tenant`) voit toujours ses attaques, bannissements
  et hôtes fourre-tout ; seule la ligne de config de ce groupe est masquée. Le [journal d'audit](/docs/audit)
  est lié au tenant de l'appelant côté serveur, et un filtre `target` nommant une adresse hors du
  tenant est refusé — pas d'oracle d'existence inter-tenant.
- **Mutations** — un operator cadré ne peut `ban`/`unban` que dans ses propres préfixes. Une cible
  hors du tenant renvoie un `403` uniforme, qu'un bannissement existe ou non, de sorte qu'un
  tenant ne peut pas sonder l'état de bannissement d'un autre. Le
  [canal de blocage de sources](/docs/api#le-canal-de-blocage-de-sources) se rattache au même axe via
  son champ `victim` : un token cadré ne peut bloquer une source que *pour ses propres* victimes, et
  une victime hors du tenant reçoit le même `403` uniforme au blocage comme au déblocage.
  `POST /api/v1/config/reload` est
  **réservé aux admins** — un reload réécrit la politique de chaque tenant ainsi que l'ensemble
  des tokens lui-même.
- **Zones edge** — une zone du [fichier de zones](/docs/zones) porte elle aussi un `tenant`
  optionnel. `GET /api/v1/edge/zones/status` ne renvoie à un token cadré que ses propres zones — le
  nom d'hôte d'un autre tenant n'apparaît dans aucune ligne, aucun ensemble de candidats et aucune
  liste HTTP/3, et le champ `tenant` est omis — et un operator cadré ne tire le
  [levier](/docs/edge#le-levier) que sur ses propres zones : toute autre zone, celle d'un autre
  tenant, non étiquetée ou disparue du fichier, renvoie le même `404 unknown zone` qu'un nom
  inconnu. L'[historique edge](/docs/api#get-apiv1edgehistory) suit la même ligne : un token cadré
  lit l'historique et les sources significatives de ses propres zones, toute autre zone est un
  unique `403` uniforme, et le filtre par nœud comme les événements de la flotte restent sans
  périmètre. Les noms des nœuds sur lesquels une zone est servie sont visibles de son tenant ; le
  document de zones, les rapports des nœuds, la coordination ACME, l'inventaire des nœuds et
  `config/reload` restent sans périmètre.
- **L'ambiguïté échoue de façon sûre** — si un même secret bearer correspond à des tokens de rôle
  ou de tenant différents (un secret réutilisé), la requête est refusée plutôt que résolue vers le
  périmètre le plus large.

<Callout type="warning" title="Une ressource est partagée entre tenants : les 8 emplacements de victimes d'une source">
Le contrôle d'accès est par tenant, mais une structure du noyau ne l'est pas. Un blocage de source
ancre un unique bloc de politique noyau sur la **source**, et ce bloc contient au plus 8 victimes,
quel qu'en soit le propriétaire. Si le même attaquant frappe des victimes dans deux tenants, ces
victimes se disputent les mêmes 8 emplacements, et le neuvième blocage est refusé quel que soit le
tenant qui le demande. Les sources bloquées distinctes puisent en outre dans le pool de politique de
tout le déploiement. Aucune de ces deux limites ne peut être partitionnée par tenant — cela découle
de l'agencement « un bloc de politique par source » — donc sur un déploiement partagé, traitez le
canal de blocage de sources comme une ressource partagée et réservez son usage au tenant qui a
observé le trafic. Voir
[Blocages de sources](/docs/dataplane#blocages-de-sources-depuis-votre-propre-pile).
</Callout>

### Vérifier l'isolation

Remettez le token cadré à `curl` et confirmez qu'il ne voit que son propre tenant. `/api/v1/status`
ne renvoie que les hostgroups de ce tenant :

```bash
curl -H "Authorization: Bearer $KAPKAN_A" http://127.0.0.1:8080/api/v1/status
# → only customerA's hostgroups and counts; no other tenant, no global config
```

Confirmez ensuite qu'un bannissement inter-tenant est refusé — bannir une adresse hors du tenant du
token renvoie `403` :

```bash
curl -X POST -H "Authorization: Bearer $KAPKAN_A" \
  -d '{"ip":"198.51.100.5"}' http://127.0.0.1:8080/api/v1/ban
# → 403 {"error":"target is outside your tenant"}
```

<Callout type="info" title="/metrics et le tableau de bord">
`/metrics` n'est pas cadré par tenant — il reste ouvert au scraping Prometheus et ne requiert aucun token,
même lorsque l'authentification de l'API est configurée. La coquille
du tableau de bord est partagée (elle ne détient aucune donnée propre) ; chaque appel de données
qu'elle effectue est filtré par le token qui y est collé, de sorte que le token viewer d'un tenant
n'affiche que les données de ce tenant.
</Callout>

<Callout type="warning" title="La propriété suit la config courante">
La visibilité d'un token cadré est calculée par rapport à la config en direct : re-tenanter un
préfixe (un reload réservé aux admins) transfère immédiatement ses attaques et bannissements en
cours au **nouveau** propriétaire. C'est délibéré — le contrôle suit la propriété courante — mais
cela signifie qu'un reload erroné peut brièvement déplacer des lignes entre tenants.
</Callout>

## Rétrocompatibilité

Aucun tenant configuré nulle part = comportement mono-tenant, à l'octet près : chaque groupe est
non étiqueté, chaque token est un admin sans périmètre, et l'API renvoie tout comme avant. La
multi-tenancy est opt-in et vous ne pouvez pas obtenir d'isolation sur une API ouverte (sans
token) — il n'y a aucun principal à cadrer.
