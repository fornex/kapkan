# CLI-Referenz

Kapkan ist ein einzelnes Binary. Was es tut, wird beim Start über Kommandozeilen-Flags
ausgewählt, dazu kommt eine kleine Zahl von **Befehlen**, die das laufende System inspizieren und
sich dann beenden. Alle Logs gehen nach **stderr**; die REST-API und die Prometheus-Metriken
werden über HTTP auf `api.listen` (Standard `127.0.0.1:8080`) bereitgestellt, während die
Hilfs-Flags (`-version`, `-dump-schema`, `-dump-zones-schema`) und die Befehle ihre Ausgabe nach
**stdout** schreiben.

```sh
kapkan [flags]                     # run the daemon
kapkan [flags] <command> [args]    # run a command and exit
```

Globale Flags stehen **vor** dem Befehl; die eigenen Flags des Befehls folgen ihm.
`kapkan -config /etc/kapkan/config.yaml dataplane status -json` liest den Konfigurationspfad also
aus dem globalen `-config` und übergibt `-json` an `dataplane status`. Ein Flag, das sich ohnehin
selbst beendet (`-version`, `-check-config`, `-dump-schema`, `-dump-zones-schema`, `-check-update`,
`-s`), lässt sich nicht mit einem Befehl kombinieren — Kapkan verweigert die Kombination, statt
stillschweigend nur eines von beiden zu befolgen.

## Flags

| Flag | Standard | Beschreibung |
| --- | --- | --- |
| `-config <path>` | `configs/dev.yaml` | Pfad zur YAML-[Konfigurationsdatei](/docs/configuration). |
| `-log-format <fmt>` | `json` | Log-Ausgabeformat: `json` (strukturiert, für Log-Collectors) oder `text` (menschenlesbar, für lokale Läufe). Jeder andere Wert als `text` wird als `json` behandelt. |
| `-log-level <lvl>` | `info` | Minimales Log-Level: `debug`, `info`, `warn`, `error`. Ein unbekannter Wert fällt auf `info` zurück. |
| `-check-config <path>` | — | Validiert die Konfigurationsdatei unter `<path>` und beendet sich — startet den Daemon **nicht**. Siehe [unten](#eine-konfiguration-validieren). |
| `-dump-schema` | `false` | Gibt das JSON-Schema der Konfiguration auf stdout aus und beendet sich. Siehe [unten](#das-schema-ausgeben). |
| `-dump-zones-schema` | `false` | Gibt das JSON-Schema der [Zonendatei](/docs/zones), die ein Edge-Gehirn ausliefert (`edge.zones_file`), auf stdout aus und beendet sich. |
| `-version` | `false` | Gibt die Build-Version aus und beendet sich. Dieselbe Version wird zur Laufzeit über `/api/v1/status` und die `kapkan_build_info`-[Metrik](/docs/metrics) bereitgestellt. |
| `-check-update` | `false` | Führt die optionale [Update-Prüfung](/docs/configuration) einmalig aus und beendet sich — `0` aktuell, `10` ein Update ist verfügbar, `1` bei einem Fehler. Fragt die GitHub-Releases-API ab; sendet nur die Anfrage selbst, niemals Knotenidentität oder Konfiguration. |
| `-pid-file <path>` | `/run/kapkan/kapkan.pid` | Wohin der Daemon beim Start seine Prozess-ID schreibt (bei sauberem Herunterfahren entfernt); wird von `-s` gelesen, um den laufenden Daemon zu finden. Ein Schreibfehler ist nicht fatal — der Daemon läuft trotzdem, nur `-s` ist nicht verfügbar. |
| `-s <signal>` | — | Signalisiert einen laufenden Daemon und beendet sich, indem `-pid-file` gelesen wird: `reload`, `stop` oder `quit`. Startet **keinen** Daemon. Siehe [unten](#einen-laufenden-daemon-steuern). |

<Callout type="info" title="json oder text?">
Verwenden Sie `-log-format text` für die lokale Entwicklung — es ist das Format, das der
[Schnellstart](/docs/quickstart) nutzt. Behalten Sie im
Produktivbetrieb den Standard `json` bei, damit ein Log-Collector die strukturierten Felder
parsen kann; die [systemd-Unit](/docs/deployment) wird mit `-log-format json -log-level info`
ausgeliefert.
</Callout>

## Den Daemon betreiben

Ohne Hilfs-Flag öffnet Kapkan seine Flow-Listener, die REST-API und (sofern nicht im Dry-Run) den
BGP-Speaker und läuft dann, bis es `SIGINT` oder `SIGTERM` empfängt, woraufhin es sich sauber
herunterfährt. Es endet nur bei einem fatalen Start- oder Laufzeitfehler mit einem Wert ungleich
null.

```sh
# Local, human-readable logs against the bundled dev config:
kapkan -config configs/dev.yaml -log-format text

# Production-style: structured logs at info level:
kapkan -config /etc/kapkan/config.yaml -log-format json -log-level info
```

Die Konfigurationsdatei ist zur Laufzeit ohne Neustart neu ladbar — führen Sie
[`kapkan -s reload`](#einen-laufenden-daemon-steuern) aus, senden Sie `SIGHUP` direkt
(`systemctl reload kapkan`) oder `POST /api/v1/config/reload`. Siehe die
[Konfigurationsreferenz](/docs/configuration) dazu, was neu geladen wird und was beim Start
fixiert ist.

## Einen laufenden Daemon steuern

```sh
kapkan -s reload    # re-read the config file (SIGHUP)
kapkan -s stop      # graceful shutdown (SIGTERM)
kapkan -s quit      # alias of stop
```

`-s` liest die Prozess-ID aus `-pid-file` (Standard `/run/kapkan/kapkan.pid`, beim Start vom
Daemon geschrieben) und stellt das passende Signal an diesen Prozess zu — dieselbe nginx-artige
lokale Steuerung wie `nginx -s reload`. Es benötigt keine Netzwerkverbindung und kein API-Token,
funktioniert also auch, wenn die REST-API nicht erreichbar ist; es benötigt jedoch die Berechtigung,
den Daemon zu signalisieren, führen Sie es daher als `root` oder als `kapkan`-Benutzer aus.

| `-s`-Wert | Signal | Wirkung |
| --- | --- | --- |
| `reload` | `SIGHUP` | Lädt die Konfigurationsdatei im laufenden Betrieb neu. Wie `systemctl reload kapkan` oder `POST /api/v1/config/reload`. |
| `stop` / `quit` | `SIGTERM` | Sauberes Herunterfahren. Wie `systemctl stop kapkan`. Die beiden sind Aliase — Kapkans Herunterfahren ist immer graceful (es bittet BGP-Peers, Mitigation-Routen via [Graceful Restart](/docs/mitigation) beizubehalten). |

Wenn die pid-Datei fehlt oder veraltet ist (kein solcher Prozess) oder Ihnen die Berechtigung zum
Signalisieren fehlt, gibt `-s` den Grund auf stderr aus und beendet sich mit `1`.

<Callout type="info" title="Wo die pid-Datei liegt">
Die mitgelieferte [systemd-Unit](/docs/deployment) setzt `RuntimeDirectory=kapkan`, sodass
`/run/kapkan` existiert und für den `kapkan`-Benutzer beschreibbar ist; der Daemon schreibt dort
`/run/kapkan/kapkan.pid` und entfernt es bei einem sauberen Stopp. In einem lokalen Dev-Lauf
existiert dieses Verzeichnis möglicherweise nicht — der Daemon protokolliert eine Warnung und fährt
fort, und `-s` meldet „no pid file". Übergeben Sie `-pid-file /tmp/kapkan.pid` sowohl an den Daemon
als auch an `-s`, wenn Sie die Abkürzung lokal nutzen möchten.
</Callout>

## Hilfs-Flags

Diese Flags beenden sich, bevor der Daemon startet — sie öffnen niemals einen Listener und
senden keine Route-Ankündigung, sodass sie sich gefahrlos auf einem Produktivhost ausführen
lassen. (`-check-update` stellt eine einzelne ausgehende Anfrage an die Releases-API; die
übrigen sind vollständig offline.)

### Eine Konfiguration validieren

```sh
kapkan -check-config /etc/kapkan/config.yaml
```

Führt exakt dasselbe Parsen und dieselbe Validierung der Engine aus — einschließlich der
feldübergreifenden Regeln, die ein statisches Schema nicht ausdrücken kann — gibt dann die
aufgelöste Konfiguration aus (Modus, geschützte Netze, die konfigurierten Flow-Listener, die
Gruppenanzahl und die effektive Mitigation pro [Hostgroup](/docs/hostgroups)) und beendet sich:

| Exit-Code | Bedeutung |
| --- | --- |
| `0` | Die Konfiguration ist gültig. |
| `1` | Die Konfiguration ist ungültig; der genaue Fehler wird auf stderr ausgegeben. |

Die saubere 0/1-Aufteilung fügt sich direkt in CI oder eine Pre-Deploy-Prüfung ein. Siehe
[Konfiguration validieren](/docs/configuration#konfiguration-validieren).

Eine gültige Konfiguration kann nach der `OK`-Zeile dennoch einen `WARNING`-Block ausgeben — gültige
Konfiguration, die der Daemon ausführen wird, aber fast sicher nicht das, was Sie gemeint haben.
Heute gibt es genau einen Fall: eine [statische Regel, die nie greifen
kann](/docs/dataplane-tuning#regeln-die-nie-greifen), samt Regelname und dem, was ihre Pakete nimmt.
Der Exit-Code bleibt `0`, eine bestehende Prüfung ist also nicht betroffen; sollen Warnungen den
Build ebenfalls brechen, prüfen Sie die Ausgabe zusätzlich zum Code auf `WARNING`.

### Das Schema ausgeben

```sh
kapkan -dump-schema
```

Gibt das JSON-Schema der Konfiguration auf stdout aus und endet mit `0` (oder `1` bei einem
internen Fehler). Der [Konfigurations-Builder](/config) nutzt dieses Schema, um Felder direkt in
Ihrem Browser zu prüfen.

```sh
kapkan -dump-zones-schema
```

Dasselbe für die [Zonendatei](/docs/zones), die ein Edge-Gehirn ausliefert (`edge.zones_file`): ihr
JSON-Schema, mit den Enums und Grenzen des Zonen-Vokabulars, für Ihren Editor oder das Tooling
eines Mandanten.

### Die Version ausgeben

```sh
kapkan -version
```

Gibt die Build-Version (Release-Tag plus kurze VCS-Revision, sofern bekannt) auf stdout aus und
beendet sich. Dieselbe Zeichenkette wird zur Laufzeit auf `/api/v1/status` bereitgestellt und von
der `kapkan_build_info`-[Metrik](/docs/metrics) getragen — so können Sie die Version eines Binarys
lokal ohne jeglichen Egress bestätigen.

### Nach Updates suchen

```sh
kapkan -check-update
```

Führt die [`update_check`](/docs/configuration) einmalig auf Anfrage aus und beendet sich: `0`,
wenn aktuell, `10`, wenn ein neueres Release verfügbar ist, `1` bei einem Fehler. Es fragt die
GitHub-Releases-API ab und sendet nur die Anfrage selbst (Ihre IP und einen generischen
User-Agent) — niemals Knotenidentität, Konfiguration oder Angriffsdaten. Die periodische
In-Process-Prüfung ist **standardmäßig deaktiviert**; dieses Flag funktioniert unabhängig von
dieser Einstellung.

## Befehle

### `dataplane status`

```sh
kapkan dataplane status              # human-readable report
kapkan dataplane status -json        # the same inspection as JSON
```

Meldet, ob die XDP-Datenebene tatsächlich filtert — und, falls nicht, warum nicht. Zwei
Eigenschaften machen den Befehl während eines Vorfalls brauchbar:

- **Er ist strikt lesend.** Er öffnet das gepinnte Programm und die Maps nur lesend — die
  Map-Dateideskriptoren tragen `BPF_F_RDONLY`, sodass der *Kernel* selbst einen Schreibzugriff
  darüber verweigert — und er lädt niemals ein Programm, legt keine Map an, schreibt keinen
  Map-Wert, hängt sich nicht an oder ab und entfernt keinen Pin. Der Start des Daemons übernimmt
  einen bestehenden Pin-Satz oder baut ihn neu auf; dieser Befehl kann das nicht und kann Sie
  deshalb niemals die Mitigation-Regeln kosten, die Sie gerade diagnostizieren wollen.
- **Er funktioniert auch bei gestopptem Daemon.** Das ist der Hauptfall, keine Dreingabe: mit dem
  Standard `dataplane.on_exit: keep` setzt der Kernel die statische Policy ganz ohne
  Kapkan-Prozess weiter durch, und dieser Befehl liest die Pins direkt aus, um Ihnen genau das
  mitzuteilen.

Der Bericht beginnt mit dem Urteil und der Abhilfe und liefert dann die Details: angebundene
Interfaces mit dem tatsächlich wirksamen Modus, die Kernel- und Map-Schema-Versionen, die aktive
Generation, die Anzahl statischer und dynamischer Regeln, Größe/Belegung/Speicher je Map, das
Dry-Run-Flag und die Verdict-Zähler.

Zwei Dinge an dieser Ausgabe sollten Sie vorab kennen:

- **Der Attach-Modus `GENERIC` wird in der ersten Zeile hervorgehoben.** `xdp_mode: auto` fällt
  ohne Fehlschlag vom Treiberpfad auf den generischen (skb-)Pfad zurück, und das kostet rund eine
  Größenordnung an Kapazität — deshalb ist es eine Schlagzeile und kein Feld unter zwanzig.
- **Die Verdict-Zähler werden in zwei Blöcken ausgegeben.** Die *terminalen* Zähler partitionieren
  den Verkehr — pro Paket wird genau einer erhöht —, deshalb werden sie aufsummiert. Die
  *Beobachtungs*-Zähler werden für dasselbe Paket *zusätzlich* zu einem terminalen Zähler erhöht
  (`dryrun_would_drop`, `pass_rule_expired`, `pass_frag_noports`, `err_policy_missing`); sie in die
  Summe aufzunehmen ergäbe eine Paketzahl, die größer wäre als die Zahl der Pakete — daher werden
  sie getrennt aufgeführt und nie mitgezählt.

| Flag | Standard | Beschreibung |
| --- | --- | --- |
| `-json` | `false` | Gibt die gesamte Inspektion als JSON aus, einschließlich des Feldes `state`, aus dem die Exit-Codes abgeleitet werden. |
| `-pin-path <dir>` | aus `-config` | Das zu inspizierende bpffs-Verzeichnis. Standard ist `dataplane.pin_path` aus der Konfiguration, die das globale `-config` benennt; lässt sich diese Datei nicht lesen, wird auf `/sys/fs/bpf/kapkan` zurückgefallen. Der Bericht nennt immer den Pfad, den er betrachtet hat, und woher dieser Pfad stammt. |

#### Exit-Codes

| Exit-Code | Gemeldeter Zustand | Bedeutung und was zu tun ist |
| --- | --- | --- |
| `0` | `enforcing` | Mindestens ein Interface hat eine aktive XDP-Anbindung. Nichts zu tun. |
| `10` | `no_pin_path`, `no_program`, `detached` | Die Datenebene **filtert nicht**, und dabei ist nichts kaputt — sie lief hier noch nie, oder sie ist gestoppt, oder ihre Anbindungen sind weg. Starten Sie Kapkan oder prüfen Sie, ob die konfigurierten Interfaces existieren. |
| `11` | `not_bpffs`, `torn`, `schema_skew` | Es muss erst etwas **behoben** werden, bevor sie arbeiten kann: bpffs ist nicht gemountet, der Pin-Satz ist unvollständig, oder die gepinnten Maps haben eine andere Schema-Version als dieses Binary. Der ausgegebene Grund benennt die Abhilfe (bpffs mounten; Kapkan neu starten). |
| `1` | `attach_unknown` oder ein beliebiger Lesefehler | Der Befehl **konnte keine Antwort geben** — meist wegen fehlender Berechtigung (siehe unten). Bewusst nicht als „filtert nicht" gemeldet, denn sie filtert möglicherweise sehr wohl. |
| `2` | — | Aufruffehler: ein unbekanntes Flag, ein unbekannter Befehl oder ein überzähliges Argument. |

Nur `enforcing` endet mit `0`, sodass sich `kapkan dataplane status >/dev/null` direkt in eine
Monitoring-Prüfung einfügt. Die Konvention, `10` für einen aussagekräftigen Zustand zu verwenden,
ist dieselbe wie bei [`-check-update`](#nach-updates-suchen).

#### Berechtigungen

Pins zu lesen ist weit billiger, als sie anzulegen: auf einem Kernel mit
`kernel.unprivileged_bpf_disabled=0` ist **überhaupt keine Capability** erforderlich — weder
`CAP_NET_ADMIN` noch `CAP_PERFMON`, die der Daemon zum *Laden und Anhängen* braucht, sind im
Spiel. Was den Zugriff tatsächlich begrenzt:

- Das Pin-Verzeichnis hat den Modus `0700` und gehört dem Benutzer, unter dem der Daemon läuft —
  in der Praxis wollen Sie also `sudo kapkan dataplane status`.
- Auf einem Kernel mit gesetztem `kernel.unprivileged_bpf_disabled` — der Standard auf Debian und
  Ubuntu — benötigt `bpf(2)` zusätzlich `CAP_BPF`, selbst um einen bestehenden Pin zu öffnen.
- **Link-Pins brauchen Schreib-, nicht nur Leserechte:** Der Kernel verweigert `BPF_OBJ_GET` auf
  einem `bpf_link`, sofern der Deskriptor nicht mit `O_RDWR` geöffnet wird. Ein Leser ohne
  root-Rechte sieht daher jede Map und keine Anbindung — das wird als `attach_unknown` (Exit `1`)
  gemeldet und nicht als „detached".

<Callout type="info" title="Er verändert niemals das, was er diagnostiziert">
Deshalb ist `dataplane status` ein eigener, rein lesender Pfad und keine Wiederverwendung des
Startcodes des Daemons. Der Start der Datenebene übernimmt einen bestehenden Pin-Satz — oder reißt
ihn, wenn das Schema nicht passt, ab und baut ihn neu auf, wobei jede dynamische Mitigation-Regel
im Kernel verworfen wird. Eine Diagnose, die das mitten im Angriff tun könnte, wäre schlimmer als
gar keine Diagnose.
</Callout>

### `scrub`

```sh
kapkan scrub -config /etc/kapkan/scrub.yaml
```

Führt die [Scrub-Knoten](/docs/scrubbing#verwaltete-scrubbing-knoten)-Rolle aus: dasselbe Binary,
ein anderer Job. Es gibt keine Erkennung, kein BGP und keinen Telemetrie-Listener — die Box
empfängt den Verkehr, den das Gehirn zu ihr umgeleitet hat, pollt per Long-Poll die Regeltabelle
des Gehirns und hält ihre lokale XDP-[Data Plane](/docs/dataplane) so, dass sie genau das
durchsetzt, was das Gehirn zu verwerfen anweist. Der Poll dient zugleich als Lebendigkeitssignal
des Knotens.

Alles Rollenspezifische liegt in seiner eigenen `scrub.yaml`; die `config.yaml` des Daemons wird
**nicht** gelesen (`-config` hat hier den Standardwert `/etc/kapkan/scrub.yaml`). Sie hat drei
Teile: den zu erreichenden Controller, die Identität des Knotens und denselben `dataplane:`-Block,
den ein Daemon trägt.

```yaml
dry_run: true                     # the remote-role default — counts, drops nothing
controller:
  url: "https://kapkan.example.net:8443"   # the brain's API base (no path)
  token_env: KAPKAN_AGENT_TOKEN            # env var holding the agent token (required)
  name: scrub-fra1                         # must equal a scrubbing.nodes[] name on the brain
dataplane:
  interfaces: [eth0]              # the dirty side (diverted traffic arrives here)
  xdp_mode: auto
  pin_path: /sys/fs/bpf/kapkan
```

<Callout type="warning" title="Ein Scrub-Knoten läuft standardmäßig im Dry-Run">
`dry_run` hat für eine entfernte Rolle den Standardwert **true** — der Knoten installiert die
Regeln und zählt, was sie verwerfen *würden*, verwirft aber nichts, bis Sie `dry_run: false`
explizit setzen. Er setzt niemals eine Regel durch, die das Gehirn als Dry-Run markiert hat,
solange diese aktiv ist, und er benötigt ein echtes agent-Token: Ohne eines tragen seine Polls
keine Identität, und das Gehirn würde ihn als tot werten. Verwenden Sie außerhalb eines Labors
`https` — eine `controller.url` im Klartext sendet das Token unverschlüsselt.
</Callout>

| Flag | Standard | Beschreibung |
| --- | --- | --- |
| `-config <path>` | `/etc/kapkan/scrub.yaml` | Die Scrub-Knoten-Konfiguration. |
| `-log-format <fmt>` | `json` | `json` oder `text`. |
| `-log-level <lvl>` | `info` | `debug`, `info`, `warn` oder `error`. |

Bestätigen Sie einen laufenden Knoten mit `kapkan dataplane status` auf dem Knoten selbst — es
meldet `ENFORCING` und die installierte Regelanzahl — und die [Nodes-Ansicht](/docs/dashboard) des
Gehirns zeigt ihn als lebendig. Den umgeleiteten Verkehr zum Knoten zu bekommen, ist Aufgabe des
[Leitfadens zur Netzwerkintegration](/docs/network-integration).

### `edge`

```sh
kapkan edge -config /etc/kapkan/edge.yaml
```

Führt die [Edge-Knoten](/docs/edge)-Rolle aus: Das nginx oder Angie der Box wird zu einem
verwalteten HTTPS-Frontend für die Zonen, die das Gehirn bedient. Die Rolle pollt per Long-Poll
das Zonendokument des Gehirns, rendert die Konfiguration des Terminators und installiert sie
hinter `nginx -t`, beantwortet das `auth_request` von nginx aus einem lokalen
Entscheidungsdienst, verdichtet das Access-Log zu Aggregaten pro Quelle, stellt die Zertifikate
der Zonen auf der Box aus und erneuert sie, und meldet sich selbst. Der Poll dient zugleich als
Lebendigkeitssignal des Knotens. Die Schritt-für-Schritt-Anleitung ist der
[Installationsleitfaden](/docs/edge-install).

Alles Rollenspezifische liegt in seiner eigenen `edge.yaml`; die `config.yaml` des Daemons wird
**nicht** gelesen (`-config` hat hier den Standardwert `/etc/kapkan/edge.yaml`).

```yaml
dry_run: true                          # the remote-role default — marks, refuses nothing
controller:
  url: https://kapkan.example.net:8443 # the brain's API base (no path); https outside a lab
  token_env: KAPKAN_EDGE_TOKEN         # env var holding the agent token (required)
  name: edge-1                         # must equal an edge.nodes[] name on the brain
  report_interval_seconds: 10          # self-report cadence
state_dir: /var/lib/kapkan-edge        # document cache, generations, ACME keys and certificates
sockets_dir: /run/kapkan-edge          # edge-decide.sock, edge-challenge.sock, edge-log.sock
socket_group: nginx                    # the terminator's worker group (nginx | www-data | angie)
terminator:
  binary: nginx                        # nginx (default) | angie
  main_conf: /etc/nginx/nginx.conf     # -c for `nginx -t` and `nginx -s reload`; empty = compiled default
  reload: exec                         # exec (default) | signal | command
  pid_file: /run/nginx.pid             # liveness check; required for reload: signal
  # command: [systemctl, reload, nginx]
acme:
  directory: ""                        # default CA; empty = Let's Encrypt production
  fallback: ""                         # optional second CA after three consecutive failures
  contact: ["mailto:ops@example.net"]
  # eab:                               # External Account Binding for CAs that require one
  #   - directory: https://acme.zerossl.com/v2/DV90
  #     kid: your-kid
  #     hmac_key_env: KAPKAN_EDGE_ZEROSSL_HMAC
  # disabled: true                     # issue nothing (zones stay on :80 answering 503)
status_listen: 127.0.0.1:9102          # /healthz + /metrics; unauthenticated, keep it private
omit_catch_all: false                  # true when nginx.conf has its own default_server
disable_ipv6: false                    # true on hosts without an IPv6 stack
```

| Schlüssel | Bedeutung |
| --- | --- |
| `dry_run` | Fehlt oder `true`: Entscheidungen werden gezählt und markiert (`X-Kapkan-Mark: would-deny:<reason>` erreicht den Origin), keine wird durchgesetzt. Setzen Sie `false`, um abzulehnen. |
| `controller.url` / `token_env` / `name` | Die API-Basis des Gehirns (kein Pfad, keine Anmeldedaten in der URL), die Umgebungsvariable mit dem **agent**-Token und der Name dieses Knotens — er muss einem `edge.nodes[]`-Eintrag auf dem Gehirn entsprechen, sonst ist jeder Poll ein lautstarker `404`. |
| `state_dir` / `sockets_dir` | Die eigenen Verzeichnisse der Rolle (Standard `/var/lib/kapkan-edge`, `/run/kapkan-edge`) — niemals `/var/lib/kapkan` und `/run/kapkan` des Gehirns, die systemd auf einem gemeinsam genutzten Host unter ihr weg-chownen und entfernen würde. Absolut, ohne Zeichen, die nginx falsch lesen würde. |
| `socket_group` | Die Worker-Gruppe des Terminators. Der Entscheidungs- und der Log-Socket sind für sie `0660`; der Challenge-Socket ist `0666` (er beantwortet öffentliche Tokens). Leer lässt die beiden gruppenbeschränkten Sockets nur für den Eigentümer zugänglich. |
| `terminator.binary` / `main_conf` | Was für `-t` und Reloads ausgeführt wird, und die Hauptkonfiguration, die als `-c` übergeben wird. Diese Datei muss einmal, innerhalb von `http {}`, `include /var/lib/kapkan-edge/conf/live/*.conf;` enthalten. |
| `terminator.reload` | `exec` führt `<binary> -s reload` aus (muss den nginx-Master signalisieren — die Unit läuft als root); `signal` sendet `HUP` an die PID in `pid_file`; `command` führt `terminator.command` aus, z. B. `[systemctl, reload, nginx]`. |
| `terminator.pid_file` | Wenn gesetzt, wird sie bei jedem Report-Tick gelesen und mit `0` signalisiert: `/healthz` antwortet `503` und der Report meldet `alive: false`, solange kein Prozess diese PID hat. |
| `acme.directory` / `fallback` / `contact` | Die Standard-CA des Knotens (der eigene `acme`-Block einer Zone übersteuert Directory und Fallback), der Fallback, der nach drei aufeinanderfolgenden Fehlschlägen versucht wird (muss sich von der aufgelösten primären CA unterscheiden), und der Kontakt des Kontos — jeder Eintrag eine `mailto:`-URL (`mailto:ops@example.net`), andernfalls wird die Datei abgelehnt. |
| `acme.eab[]` | External Account Binding pro Directory-URL (`directory`, `kid`, `hmac_key_env`) für CAs, die eines verlangen — ZeroSSL, Google Trust Services. Der HMAC-Schlüssel ist ein Geheimnis und wird aus der genannten Umgebungsvariable gelesen. |
| `acme.disabled` | Nichts ausstellen: Zonen bleiben auf `:80` und antworten `503` (ein Labor, das alles außer der Ausstellung durchspielt). Vom Betreiber bereitgestellte Zertifikate sind noch keine Funktion. |
| `status_listen` | Stellt `/healthz` und `/metrics` bereit, wenn gesetzt. Unauthentifiziert — Loopback oder eine private Adresse. |
| `omit_catch_all` / `disable_ipv6` | Kapkans `default_server`-Catch-all weglassen (Ihre `nginx.conf` deklariert selbst einen) / die `[::]`-Listener weglassen (kein IPv6-Stack). |

<Callout type="warning" title="Ein Edge-Knoten läuft standardmäßig im Dry-Run">
`dry_run` hat für eine entfernte Rolle den Standardwert **true** — der Knoten zählt und markiert,
was er ablehnen *würde*, lehnt aber nichts ab, bis Sie `dry_run: false` explizit setzen. Er
benötigt ein echtes agent-Token: Ohne eines tragen seine Polls keine Identität, und das Gehirn
würde ihn als tot werten. Verwenden Sie außerhalb eines Labors `https` — eine `controller.url` im
Klartext sendet das Token unverschlüsselt.
</Callout>

| Flag | Standard | Beschreibung |
| --- | --- | --- |
| `-config <path>` | `/etc/kapkan/edge.yaml` | Die Edge-Knoten-Konfiguration. |
| `-check` | aus | Die Datei und das, was sie auf dieser Box benennt, validieren — die Socket-Gruppe muss existieren und jeder EAB-Schlüssel wohlgeformt sein (Probleme); ein fehlendes Token, Terminator-Binary oder `main_conf` ist eine Warnung — und dann beenden. |
| `-log-format <fmt>` | `json` | `json` oder `text`. |
| `-log-level <lvl>` | `info` | `debug`, `info`, `warn` oder `error`. |

Bestätigen Sie einen laufenden Knoten mit `curl 127.0.0.1:9102/healthz` — `200` mit
`"converged":true`, sobald das Dokument gerendert und live ist — und das Inventar des Gehirns
(`GET /api/v1/edge/nodes`) zeigt ihn als lebendig. Das gehirnseitige Schema der Zonendatei liefert
`kapkan -dump-zones-schema`.

### `nginx-exporter`

```sh
KAPKAN_API_TOKEN=... kapkan nginx-exporter -log /var/log/nginx/kapkan.json.log -api http://127.0.0.1:8080
```

Liest ein nginx-JSON-Access-Log fortlaufend mit, misst Request-Raten pro Quelle und Fenster und
übergibt Urteile an den [Source-Block-Kanal](/docs/api#der-source-block-kanal) des Gehirns. Das
erforderliche `log_format`, die Schwellenwerte und die betrieblichen Grenzen stehen bei der
Funktion selbst: [der
Referenz-Exporter](/docs/dataplane#der-referenz-exporter-kapkan-nginx-exporter). Die globalen
Flags des Daemons werden nicht gelesen; er hat durchweg eigene:

| Flag | Standard | Beschreibung |
| --- | --- | --- |
| `-log <path>` | — (erforderlich) | Das nginx-Access-Log im dokumentierten JSON-`log_format`. |
| `-api <url>` | `http://127.0.0.1:8080` | Die API-Basis-URL des Gehirns. |
| `-token-env <name>` | `KAPKAN_API_TOKEN` | Umgebungsvariable mit einem **operator**-Token. |
| `-victim <ip>` | — | Festes Opfer; übersteuert das `dst`-Feld des Logs. |
| `-window <dur>` | `10s` | Messfenster. |
| `-rps <n>` | `50` | Requests/Sekunde pro Quelle, ab denen ein Block scharfgestellt wird. |
| `-min-requests <n>` | `100` | Untergrenze pro Fenster, bevor die Raten-Arithmetik greift. |
| `-error-ratio <r>` | `0` | Verlangt zusätzlich diesen 4xx/5xx-Anteil (`0` deaktiviert die Achse). |
| `-ttl <dur>` | `5m` | Block-TTL; eine noch heiße Quelle wird aufgefrischt, bevor sie verfällt. Muss mindestens `2×-window` betragen. |
| `-observe` | aus | Urteile loggen, ohne sie zu übergeben. |
| `-log-format` / `-log-level` | `json` / `info` | Das eigene Logging des Exporters. |
