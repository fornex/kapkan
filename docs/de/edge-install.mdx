# Einen Edge-Knoten installieren

Diese Anleitung führt eine Box vom unveränderten nginx- (oder Angie-)Paket zu einem verwalteten
[Edge-Knoten](/docs/edge), der Ihre Zonen mit ausgestellten Zertifikaten und Entscheidungen pro
Anfrage bedient. Lesen Sie zuerst die Konzeptseite, falls die Begriffe *Zone*,
*Entscheidungsdienst* oder *Fast/Slow-Trennung* neu für Sie sind.

Sie benötigen: ein Gehirn (den `kapkan`-Daemon), das von der Box über HTTPS erreichbar ist, ein
`agent`-Token darauf, eine Linux-Box mit installiertem nginx ≥ 1.22 oder Angie, TCP 80 und 443
offen zur Welt — und UDP 443 dazu, auf der Box, in der Security Group und in der ACL des
Vorgelagerten, falls eine Zone [HTTP/3](/docs/edge#http3-quic) sprechen wird —, und DNS für die
Zonen, das auf die Box zeigt (oder auf die Anycast-/VIP-Adresse, die sich die Boxen teilen).

## 1. Auf dem Gehirn: Zonen und Knoten

Schreiben Sie die Zonen-Datei — sie ist **Mandantendaten** und wird getrennt von `kapkan.yaml`
gehalten — und richten Sie das Gehirn darauf:

```yaml
# /etc/kapkan/zones.yaml
zones:
  - name: shop.example.com
    origins: ["10.0.0.10:8080"]
    policy: { mode: decide, failure_mode: open, rate: { rps: 50, concurrency: 20 } }
  - name: static.example.com
    origins: ["10.0.0.20:80"]
    policy: { mode: none }             # proxy only, no decisions
```

```yaml
# /etc/kapkan/config.yaml (the brain)
edge:
  zones_file: /etc/kapkan/zones.yaml   # absolute; the whole reload fails on a broken file
  nodes:
    - name: edge-1                     # must equal the node's controller.name
    - name: edge-2
  stale_after_seconds: 15              # a node unheard-from this long counts as lost
api:
  tokens:
    - { name: edge-1, token_env: KAPKAN_EDGE_1_TOKEN, role: agent, node: edge-1 }
    - { name: edge-2, token_env: KAPKAN_EDGE_2_TOKEN, role: agent, node: edge-2 }
```

**Grenzen Sie Zonen auf Knoten ein**, wenn die Flotte PoPs hat: Geben Sie jedem Knoten die
Hostgroups, deren Zonen er bedient (`edge.nodes[].hostgroups: [edge-us]`, mit dem wörtlichen
`global` für die flottenweiten Zonen) und jeder Zone ihre `hostgroup`; ein Knoten ohne
Geltungsbereich bedient nur die globalen Zonen, eine Zone ohne Hostgroup ist global. Die Regel, das
Literal `global` und das Runbook stehen in
[Zonen auf Knoten verteilen](/docs/edge#zonen-auf-knoten-verteilen); die Obergrenze für
Duplikat-Zertifikate wird pro Platzierung gezählt, nicht pro Flotte (siehe
[Grenzen](/docs/edge#grenzen-die-sie-kennen-sollten)). Sobald ein Knoten eingegrenzt ist, muss jedes
agent-Token gebunden sein, wie oben.

`kapkan -check-config /etc/kapkan/config.yaml` validiert beide Dateien (es folgt
`edge.zones_file`), und `kapkan -dump-zones-schema` gibt das JSON-Schema der Zonen-Datei für Ihren
Editor aus. Geben Sie jedem Knoten **sein eigenes `agent`-Token, mit `node` an ihn gebunden**: Ein
gebundenes Token wird als jeder andere Knoten abgewiesen, bevor das Gehirn irgendetwas mit dem
Namen tut, sodass ein von einer Box gestohlenes Token nicht mehr für irgendeinen anderen Knoten
sprechen kann — seine Präsenz, seine Reports und seine ACME-Slots bleiben die seinen — und nur
dieses eine Token rotiert werden muss. Eine Zonen-Datei, die sich bei einem Reload nicht
lesen oder validieren lässt, **hält die vorherigen Zonen live** — das Gehirn liefert niemals ein
halb defektes Dokument aus. Jeder Schlüssel steht in der [Zonen-Referenz](/docs/zones).

<Callout type="info" title="Das agent-Token ist ein Credential zum Ausstellen von Zertifikaten — binden Sie es">
Ein Edge-Knoten authentifiziert sich mit einem `agent`-Token (siehe
[Authentifizierung](/docs/authentication)). Neben dem Pollen des Dokuments nutzt er dieses Token,
um die Zertifikatsausstellung über das Gehirn zu koordinieren — ein **ungebundenes** Token kann
also als jeder Knoten handeln, und es bei einer Kompromittierung zu rotieren heißt, das Token der
ganzen Flotte zu rotieren. Binden Sie jedes Token an seinen Knoten (`api.tokens[].node`); bis jedes
agent-Token gebunden ist, sagen `-check-config`, das Log des Daemons und das `unbound_agent_tokens`
des Inventars es Ihnen. Was die Bindung bringt, sind Identitätsübernahme und Rotationsradius; was
die Menge der Zonen begrenzt, für die ein gestohlenes gebundenes Token Zertifikate ausstellen kann,
ist der [Platzierungs-Geltungsbereich](/docs/edge#zonen-auf-knoten-verteilen) des Knotens: Als sein
eigener Knoten handelnd kann es den Ausstellungs-Slot nehmen und eine ACME-Key-Authorization nur
für die Zonen veröffentlichen, die dieser Geltungsbereich abdeckt (in einer Flotte ohne
Geltungsbereiche für jede Zone) — behandeln Sie die Kompromittierung eines Knotens als
Zertifikats-Exposition für die Zonen seines Knotens. Eine Flotte von einem einzigen geteilten Token
migrieren: ein gebundenes Token pro Knoten hinzufügen, **mit eigenem Geheimnis** (ein Wert, den
sich der ungebundene Eintrag teilt, ist mehrdeutig und wird für jeden Knoten, der ihn präsentiert,
mit `401` abgelehnt), die Umgebungsdatei jedes Knotens umstellen und beobachten, wie das
`last_token` des Inventars umspringt, und den geteilten Eintrag zuletzt entfernen — ein ungebundenes
Token funktioniert derweil weiter. Bewahren Sie das Token in der Umgebungsdatei des Knotens auf,
niemals in der `edge.yaml`.
</Callout>

## 2. Auf der Box: nginx oder Angie

Kapkan besitzt ein Include-Verzeichnis und steuert `nginx -t` sowie die Reloads; es liefert nginx
weder mit noch überwacht es ihn. Lassen Sie Ihre Hauptkonfiguration die aktive Generation
**einmal** einbinden, innerhalb von `http {}`:

```nginx
http {
    # ... your defaults ...
    include /var/lib/kapkan-edge/conf/live/*.conf;
}
```

Entfernen Sie jeden `default_server` auf `:80`/`:443` (oder planen Sie, ihn zu behalten, siehe
unten) — Kapkan rendert sein eigenes Catch-all, das unbekannte Hosts abweist. Debians Default-Site
deklariert eines; deaktivieren Sie entweder die Site oder setzen Sie `omit_catch_all: true` in der
`edge.yaml`. Bestätigen Sie dann, dass das Include kompiliert, bevor irgendetwas gerendert ist (ein
Wildcard-Include eines Verzeichnisses, das noch nicht existiert, ist für nginx in Ordnung):

```sh
nginx -t
```

`live` selbst ist ein **Symlink**, den der Knoten bei jeder Generation anlegt und neu ausrichtet —
legen Sie ihn nicht von Hand an: Ein Verzeichnis an seiner Stelle stoppt jede Installation
(`apply: rename … live` im Journal), bis es entfernt ist.

Ermitteln Sie die **Gruppe des Workers** — `nginx` für nginx.org-Pakete und das Docker-Image,
`www-data` für Debians eigenes Paket, `angie` für Angie. Der Entscheidungs- und der Log-Socket
werden mit `0660` für diese Gruppe angelegt.

**Für HTTP/3** muss der Build das Modul tragen und die Adresse UDP annehmen:

```sh
nginx -V 2>&1 | grep -o -- --with-http_v3_module     # Angie: angie -V
```

Debian 12s nginx 1.22 hat keines (Zonen, die h3 verlangen, werden dort über TCP ausgeliefert, und
der Knoten sagt es); Debian 13s nginx 1.26.3, die Pakete von nginx.org ab 1.25 und Angie haben es.
Öffnen Sie UDP 443 überall, wo TCP 443 offen ist, geben Sie UDP-Flows auf jeder zustandsbehafteten
Firewall im Pfad ein Conntrack-Timeout, und halten Sie die Pfad-MTU auf 1280 Byte oder mehr — QUIC
fragmentiert nie, eine GRE/IPIP-Umleitung mit kleinerer MTU bricht also h3, während TCP durch
[MSS-Clamping](/docs/network-integration#off-path-umleitung-über-gre-oder-ipip) überlebt. Wenn Ihre
`nginx.conf` `ssl_protocols` auf `http`-Ebene setzt, muss `TLSv1.3` darin vorkommen — QUIC spricht
nichts anderes (Kapkans eigene QUIC-Listener sagen es selbst). `kapkan edge -check` gibt die
HTTP/3-Bereitschaft des Knotens aus, sobald die `edge.yaml` an Ort und Stelle ist.

## 3. Der Knoten: `edge.yaml`, das Token, die Unit

Installieren Sie dasselbe `kapkan`-Binary wie auf dem Gehirn, dann die eigene Konfiguration des
Knotens:

```yaml
# /etc/kapkan/edge.yaml
dry_run: true                          # watch-only until the counts look right
controller:
  url: https://kapkan.example.net:8443 # the brain's API base, https outside a lab
  token_env: KAPKAN_EDGE_TOKEN         # the agent token's environment variable
  name: edge-1                         # must equal an edge.nodes[] entry on the brain
  report_interval_seconds: 10
state_dir: /var/lib/kapkan-edge        # cached document, generations, keys, certificates
sockets_dir: /run/kapkan-edge          # the four unix sockets nginx talks to
socket_group: nginx                    # the terminator's worker group
terminator:
  binary: nginx                        # or angie
  main_conf: /etc/nginx/nginx.conf     # passed as -c to `nginx -t` and `-s reload`
  reload: exec                         # exec | signal | command
  pid_file: /run/nginx.pid             # liveness check; required for reload: signal
acme:
  directory: ""                        # Let's Encrypt production when empty
  fallback: ""                         # optional second CA after repeated failures
  contact: ["mailto:ops@example.net"]
status_listen: 127.0.0.1:9102          # /healthz + /metrics; keep it private
```

```sh
install -m 600 /dev/null /etc/kapkan/edge.env
echo 'KAPKAN_EDGE_TOKEN=...the agent token...' > /etc/kapkan/edge.env
kapkan edge -config /etc/kapkan/edge.yaml -check
```

`-check` validiert die Datei und das, was sie auf dieser Box benennt: Die Socket-Gruppe muss
existieren, und ein etwaiger External-Account-Binding-Schlüssel muss wohlgeformt sein (Probleme),
während ein fehlendes Token, ein fehlendes Binary oder eine fehlende `main_conf` eine Warnung ist —
die Prüfung darf laufen, bevor die Umgebungsdatei oder der Terminator an Ort und Stelle ist. Liegt
das Binary im `PATH`, gibt sie außerdem aus, was `nginx -V` sagt — Art, Version, nginx-Kern,
TLS-Bibliothek, ob der Build das HTTP/3-Modul hat — und die HTTP/3-Bereitschaft des Knotens; ein
Build, dessen nginx-Kern in den Bereich eines veröffentlichten QUIC-Sicherheitshinweises fällt,
bekommt eine Warnung, die die CVE benennt (prüfen Sie das Changelog Ihrer Distribution: Backports
bewegen die Version nicht). Setzen Sie `quic.h3: off` in der `edge.yaml`, um HTTP/3 auf diesem
Knoten abzuschalten; `-check` nennt die Bereitschaft dann `node_off` und wiederholt den Hinweis
nicht mehr, während der Report des Knotens ihn weiterhin als Tatsache über den Build trägt.

Installieren Sie die mitgelieferte Unit, `deploy/kapkan-edge.service`, und starten Sie sie:

```sh
install -m 644 deploy/kapkan-edge.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now kapkan-edge
journalctl -u kapkan-edge -f
```

Die Unit läuft als **root**, wie certbot und jeder Konfigurationsmanager, der nginx steuert:
`nginx -t` öffnet die eigenen Log- und PID-Pfade von nginx, und `nginx -s reload` signalisiert
einen root-Master. Sie ist mit `ProtectSystem=strict` und expliziten Schreibpfaden gehärtet
(`/var/lib/kapkan-edge`, `/run` und das Log-Verzeichnis von nginx oder Angie — mit `-`
vorangestellte Pfade werden übersprungen, wenn sie fehlen, sodass eine Unit beide Terminatoren
bedient), und ihr Zustandsverzeichnis ist `0711`, damit der Worker zum leeren `try_files`-Root
traversieren kann, während die ACME-Schlüssel in eigenen `0700`-Verzeichnissen bleiben. Die
Verzeichnisse der Rolle gehören ihr allein — niemals die `/var/lib/kapkan` und `/run/kapkan` des
Gehirns — sodass sich ein Gehirn und ein Edge einen Host teilen können.

<Callout type="warning" title="Die Startreihenfolge spielt keine Rolle, die Sockets schon">
Der Knoten bringt seine vier Unix-Sockets **zuerst** hoch, sodass nginx bereits laufen und sie
abfragen darf; dann prüft er den Terminator, stellt eine Generation wieder her, die ein
abgestürzter Vorgänger ungetestet hinterlassen hat, rendert das letzte Dokument, das er auf der
Platte hatte, und pollt erst dann das Gehirn. Eine Komponente, die nicht starten kann — ein
Socket, den ein anderer Prozess bereits bedient, eine Gruppe, die nicht existiert — beendet den
Prozess mit diesem Fehler, und systemd startet ihn neu.
</Callout>

## 4. Prüfen

- `journalctl -u kapkan-edge` zeigt `kapkan edge running`, dann `configuration installed` mit der
  Generationsnummer und der Zonenanzahl.
- `curl -s 127.0.0.1:9102/healthz` antwortet `200` mit `"healthy":true`, `"converged":true` und
  dem gerenderten ETag; `ls /var/lib/kapkan-edge/conf/live/` listet `kapkan_00_common.conf` und
  eine `kapkan_zone_<name>.conf` pro Zone.
- Das Inventar des Gehirns, `GET /api/v1/edge/nodes`, führt den Knoten als lebendig mit seinem
  Report auf, und die **Edge**-Ansicht der Konsole erscheint in der Navigation, sobald ein Knoten
  konfiguriert ist.
- Zertifikate: Die erste Bestellung braucht für jeden Zonennamen einen von der CA aus erreichbaren
  Port 80. Achten Sie im Journal auf `certificate issued`, dann
  `ls /var/lib/kapkan-edge/certs/<zone>/current/`. Bis eine Zone ein Zertifikat hat, antwortet ihr
  `:80`-Listener auf alles außer ACME-Challenges mit `503` — Kapkan reicht eine Zone niemals im
  Klartext per Proxy weiter.
- Anfragen: Mit `dry_run: true` erreicht ein Client über der Rate der Zone den Origin weiterhin,
  mit `X-Kapkan-Mark: would-deny:rate`. Beobachten Sie
  `kapkan_edge_decisions_total{result="would_deny"}` auf `/metrics` und die Logs Ihres Origins.
- Die Stufe: Geben Sie einer Zone `policy.challenge: auto` (ihr `challenge_options.dry_run` ist
  standardmäßig `true`, sodass noch niemand herausgefordert wird) und lesen Sie, **wer
  herausgefordert würde** — `GET /api/v1/edge/zones/status` auf dem Gehirn oder die Edge-Ansicht
  der Konsole —, während eine eigentlich fällige Challenge den Origin mit der Markierung
  `X-Kapkan-Mark: would-challenge:table:flood` erreicht. Nehmen Sie Ihre Health-Checks,
  API-Clients und Webhooks unter `challenge_options.exempt_paths` auf, bevor die Stufe in den
  Echtbetrieb geht.
- HTTP/3: Das `terminator.h3.state` des Inventars ist `ready` auf den Knoten, auf denen Sie es
  erwarten; mit einer Zone auf `tls.h3: true` benennt sie `terminator.h3.serving` und `listening`
  ist `true`, und `curl --http3-only https://<zone>/` von außen antwortet `200` — dann beginnt
  `kapkan_edge_requests_total{protocol="h3"}` zu steigen, sobald `advertise` an ist. Ein Knoten in
  `no_module`, `node_off` oder `unknown` führt die Zone unter `unsupported` und liefert sie über
  TCP aus.

## 5. Echtbetrieb

Setzen Sie `dry_run: false` in der `edge.yaml` und starten Sie die Unit neu. Von da an erhält ein
Client über seiner Obergrenze `429` mit `Retry-After: 1`, und eine Quelle, die die Rollups zu einer
Sperre hochgestuft haben, erhält `403`. Verschärfen Sie unter Angriff die `policy.rate` einer Zone
auf dem Gehirn — diese Änderung erreicht den Entscheidungsdienst beim nächsten Poll und **lädt
nginx niemals neu**.

Die Stufe geht pro Zone in den Echtbetrieb, in der Zonen-Datei: `challenge_options.dry_run: false`,
sobald die Kandidatenmenge die richtigen Clients benennt. Von da an erhält ein Flooder in einer
`auto`-Zone [die Freigabeseite](/docs/edge#die-freigabeseite), bevor er gesperrt wird, und eine
Zone unter Angriff kann sofort unter Challenge gestellt werden — `policy.challenge: manual` in der
Datei oder, für eine begrenzte Zeit und ohne Bearbeitung der Datei, [der Hebel](/docs/edge#der-hebel):

```sh
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  https://kapkan.example.net:8443/api/v1/edge/zones/shop.example.com/challenge \
  -d '{"mode":"manual","ttl_seconds":1800,"reason":"login flood"}'
```

Um Zonen eine nach der anderen zu staffeln, hält `policy.dry_run: true` eine Zone auf jedem Knoten
nur beobachtend, während ihre Schwesterzonen durchsetzen.

## Mehrere Knoten und eine gemeinsame Adresse

Richten Sie den `controller.name` jedes Knotens auf seinen eigenen `edge.nodes[]`-Eintrag und
stellen Sie dieselben Zonen vor alle — jeder Knoten hinter einer gemeinsamen Adresse muss die Zone
bedienen, also ihre Hostgroup in `edge.nodes[].hostgroups` auflisten (oder die Zone auf
uneingegrenzten Knoten global lassen). Unter Anycast oder einer gemeinsamen VIP kann die
HTTP-01-Validierung der CA auf jedem Knoten hinter dieser Adresse landen: Der bestellende Knoten
veröffentlicht seine Challenge-Antwort an das Gehirn, das sie im Dokument **jedes Knotens, der die
Zone bedient**, verteilt, und jeder von ihnen beantwortet sie; ein Knoten, auf dem die Zone nicht
platziert ist, weist den Host ab und kann nicht antworten. Die Ausstellung wird pro Zone über den
Slot des Gehirns serialisiert, damit eine Flotte nicht
an einem Nachmittag die Duplikat-Zertifikat-Obergrenze einer CA verbrennt, und die Erneuerung ist
pro Knoten mit Jitter versehen. All das ist beratend: Ohne Gehirn erneuert jeder Knoten weiterhin
selbstständig.

## Fehlerbehebung

| Symptom | Ursache und Behebung |
| --- | --- |
| `nginx -t` schlägt mit *a duplicate default server* fehl | Ihre `nginx.conf` deklariert bereits einen `default_server` auf `:80` oder `:443`. Setzen Sie `omit_catch_all: true` oder entfernen Sie Ihren. |
| `[crit] stat() ... failed` im Error-Log von nginx bei jeder Anfrage | Der Worker kann nicht zu `state_dir/empty` traversieren. `StateDirectoryMode=0711` der Unit erledigt das; ein von Hand angelegtes `state_dir` braucht `chmod 711`. |
| `connect() to unix:/run/kapkan-edge/edge-decide.sock failed (13: Permission denied)` | `socket_group` ist nicht die Gruppe des Workers. Korrigieren Sie sie und starten Sie die Unit neu. |
| `healthy: false`, `generation: 0` | Keine getestete Generation des Knotens selbst ist live: Der allererste Kandidat ist an `nginx -t` gescheitert (lesen Sie `test_error`), der Renderer hat das Dokument abgelehnt (lesen Sie `last_error`), eine wiederhergestellte Generation ist gescheitert — oder der Knoten hat überhaupt noch kein Dokument erhalten (`brain_seen` fehlt; lesen Sie die Poll-Fehler im Journal: `controller.url`, das Token, `controller.name`). |
| `apply: rename … live: file exists` (oder `is a directory`) bei jedem Apply | Ein Verzeichnis sitzt dort, wo der `live`-Symlink des Knotens hingehört — von Hand angelegt oder durch einen alten Installationsschritt. Verschieben Sie seinen Inhalt weg und entfernen Sie es mit `rmdir`; der nächste Versuch installiert. |
| `converged: false` mit `test_error` | Das neueste Dokument wurde abgelehnt; das vorherige bedient. Beheben Sie die Ursache (ein Origin, der sich nicht auflösen lässt, eine Direktive in `extra_directives_file`), und der Knoten versucht es selbstständig erneut. |
| Zone bleibt auf `:80` mit `503` | Noch kein Zertifikat. Prüfen Sie die Erreichbarkeit von Port 80 aus dem Internet für diesen Namen, `kapkan_edge_acme_attempts_total` und die Zeile `certificate order failed` im Journal. |
| Knoten wird auf dem Gehirn als verloren angezeigt, obwohl er läuft | Der Poll ist das Lebendigkeitssignal, und ein im Hold des Gehirns geparkter Poll zählt als lebendig — ein als verloren angezeigter Knoten erreicht das Gehirn also wirklich nicht mehr. Prüfen Sie `controller.url`, das Token (`401`/`403` im Journal), dass `controller.name` unter `edge.nodes[]` deklariert ist (`404`), und dass sich der Knoten kein Token mit mehr als vier anderen teilt (`429`). |
| `would-challenge`-Markierungen, aber niemand wird je herausgefordert | Eine der drei Nur-beobachten-Schichten ist aktiv: der `dry_run` des Knotens (`edge.yaml`), der `policy.dry_run` der Zone oder der eigene `challenge_options.dry_run` der Stufe — standardmäßig `true`. `GET /api/v1/edge/zones/status` nennt die Knoten, auf denen eine Zone nur beobachtend ist, und ob eine zonenweite Challenge nur eine Vorschau ist (`dry_run: true`). |
| Jede Anfrage an eine Zone erhält die Freigabeseite | Die Zone steht unter Challenge: `policy.challenge: manual` in der Datei, ein Hebel (`override` in `GET /api/v1/edge/zones/status`) oder der zonenweite Auslöser (`challenge_active` mit `reason: zone-rps`). Ein Client, der sie überwindet, wird für `cookie_ttl_seconds` nicht erneut gefragt; Clients, die keine Cookies behalten können, sehen sie jedes Mal. |
| Clients sehen `503` (oder passieren unherausgefordert) auf einer Zone, deren Stufe aktiv ist | nginx konnte die Freigabeseite nicht erreichen und ist dem `failure_mode` gefolgt. Suchen Sie im Error-Log von nginx nach `connect() to unix:/run/kapkan-edge/edge-clearance.sock failed`: Der Socket ist wie der Entscheidungs-Socket `0660` für `socket_group`, und der Knoten protokolliert `clearance page listening`, wenn er bereit ist. |
| `nginx -t` schlägt fehl mit *duplicate listen options for 0.0.0.0:443* | Ihre `nginx.conf` (mit `omit_catch_all: true`) hat schon ein `listen 443 quic` mit Socket-Optionen (`reuseport`, `rcvbuf`, …), und Kapkans QUIC-Anker trägt sein eigenes `reuseport`. Setzen Sie `quic.omit_anchor: true` und geben Sie Ihrem Server `reuseport` und `ssl_protocols TLSv1.3` selbst. |
| Eine Zone mit `tls.h3: true` wird auf einem Knoten nur über TCP ausgeliefert | Das `terminator.h3.state` dieses Knotens ist nicht `ready`: `no_module` (dem Build fehlt `--with-http_v3_module`), `node_off` (`quic.h3: off`) oder `unknown` (die Prüfung ist fehlgeschlagen — lesen Sie das Journal). Die Zone steht unter `terminator.h3.unsupported`; die anderen Knoten liefern sie über h3 aus. |
| Browser laden eine Zone nach `h3: true` langsam | UDP 443 ist weiter oben blockiert, während `Alt-Svc` h3 ankündigt: Jeder Browser lässt den QUIC-Versuch mitlaufen und wartet den Timeout ab, bevor er zurückfällt. Reparieren Sie die Firewall — oder setzen Sie `tls.h3_options.advertise: false`, bis Sie es getan haben; `terminator.h3.listening` sagt Ihnen nur die Hälfte auf der Box. |
| `curl --http3-only` schlägt fehl, während TCP funktioniert, mit einem Tunnel oder Overlay im Pfad | Pfad-MTU unter 1280 Byte: QUIC fragmentiert nie. Erhöhen Sie die MTU oder lassen Sie die Zone auf TCP (MSS-Clamping rettet TCP, nicht QUIC). |
| Jeder QUIC-Handshake schlägt fehl, während `nginx -t` besteht und `Alt-Svc` gesendet wird | Ein `ssl_protocols` auf `http`-Ebene in Ihrer `nginx.conf` ohne `TLSv1.3`, unter `omit_catch_all` mit `quic.omit_anchor: true` (Kapkans eigener Catch-all und der Anker pinnen `TLSv1.3`; Ihr Default-Server muss das auch). Suchen Sie im Error-Log von nginx nach `SSL_do_handshake() failed … unsupported protocol`. |
