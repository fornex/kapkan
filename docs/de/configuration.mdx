# Konfigurationsreferenz

<Callout type="info" title="Lieber ein geführtes Formular?">
Der [Konfigurations-Builder](/config) erstellt eine gültige Konfiguration in Ihrem Browser, mit
Inline-Prüfung und sicheren Dry-Run-Standardwerten — nichts davon verlässt die Seite.
</Callout>

Kapkan wird über eine einzige YAML-Datei konfiguriert, die mit `-config` übergeben wird. Das
Repository liefert zwei Ausgangspunkte: [`configs/dev.yaml`](/docs/quickstart) für die lokale
Entwicklung (Test-Präfixe, Loopback-Bind, `dry_run: true`) und
[`engine/deploy/config.example.yaml`](/docs/deployment) für den Produktivbetrieb, das maßgebliche Inline-
Kommentare und Standardwerte enthält. Kopieren Sie das Produktionsbeispiel nach
`/etc/kapkan/config.yaml` und passen Sie es an Ihr Netzwerk an.

<Callout type="info" title="Neu bei BGP / RTBH / FlowSpec?">
Diese Seite setzt voraus, dass Sie wissen, was diese Begriffe bedeuten. Falls nicht, lesen Sie zuerst
[Funktionsweise](/docs/how-it-works) oder halten Sie das [Glossar](/docs/glossary) in einem anderen Tab
offen — jedes Akronym hier unten ist dort definiert. Kurz gesagt: **BGP** (Border Gateway Protocol) ist
die Art und Weise, wie Router Routen austauschen, und Kapkan agiert als BGP-Sprecher, der Ihren Routern
mitteilt, welche Routen sie installieren sollen, um einen Angriff abzuwehren.
</Callout>

Die Datei ist zur Laufzeit neu ladbar. Senden Sie `SIGHUP` (`systemctl reload kapkan`) oder
`POST /api/v1/config/reload`, und Kapkan liest die Datei erneut ein und wendet die neuen
Einstellungen an, ohne die Flow-Erfassung zu unterbrechen. Nahezu alles wird live neu geladen,
darunter `dry_run`, Schwellenwerte, `networks`, Hostgroups, Baselines,
Benachrichtigungseinstellungen und `sampling.default_rate`. Sieben Dinge sind beim Start fixiert —
ein Reload, der eines davon ändert, wird **abgelehnt** (nicht stillschweigend ignoriert), sodass Sie
den Daemon neu starten müssen, um sie zu ändern:

- die `listen`-Adressen;
- die BGP-Identität (`bgp.local_asn`, `bgp.router_id`);
- `api.listen`;
- die `samples`-Einstellungen;
- die `storage`-Einstellungen;
- die `geoip`-Einstellungen;
- die Anbindung und Map-Dimensionierung der Datenebene (`dataplane.enabled`, `interfaces`,
  `xdp_mode`, `pin_path`, `on_exit` und alles unter `limits`) — keines davon kann sich unter einem
  geladenen XDP-Programm ändern. Die statische Policy im selben Block — `allowlist`, `static_rules`,
  `ratelimit_profiles` — wird live neu geladen.

<Callout type="warning" title="Dry-Run ist standardmäßig aktiviert">
`dry_run` ist standardmäßig `true`, und ein fehlender `dry_run`-Schlüssel wird als `true` behandelt.
Belassen Sie es dabei, bis Sie die Erkennung gegen Live-Telemetrie validiert haben. Siehe
[Live gehen](/docs/going-live).
</Callout>

## Konfiguration validieren

Bevor Sie neu laden oder live gehen, prüfen Sie eine Datei mit dem eigenen Validator der Engine:

```sh
kapkan -check-config /etc/kapkan/config.yaml
```

Er führt exakt dasselbe Parsen und dieselbe Validierung wie der Daemon aus — einschließlich der
feldübergreifenden Regeln, die ein Formular nicht ausdrücken kann (keine überlappenden `networks`,
Hostgroup-Präfixe innerhalb eines geschützten Netzes, monoton steigende
[Eskalations](/docs/escalation)-Stufen) — und gibt anschließend die aufgelöste Konfiguration aus
(Modus, geschützte Netze und die effektive Mitigation pro [Hostgroup](/docs/hostgroups)) und endet mit
`0`. Bei einem Problem gibt er den genauen Fehler aus und endet mit `1`, sodass er sich sauber in CI
oder eine Pre-Deploy-Prüfung einfügt.

`kapkan -dump-schema` gibt das JSON-Schema der Konfiguration auf stdout aus; der
[Konfigurations-Builder](/config) nutzt dieses Schema, um Felder direkt im Browser während der Eingabe
zu prüfen. Beide Flags sowie jeder weitere, den das Binary akzeptiert, sind in der
[CLI-Referenz](/docs/cli) aufgeführt.

## Geheimnisse und Umgebungsvariablen

Geheimnisse werden niemals in die Konfigurationsdatei geschrieben. Jedes nennt eine
Umgebungsvariable, und Kapkan liest den Wert beim Laden aus der Prozessumgebung:

- `notify.telegram.token_env` — das Telegram-Bot-Token.
- `notify.email.username_env` / `notify.email.password_env` — SMTP-Zugangsdaten.
- `storage.clickhouse.username_env` / `password_env` — ClickHouse-Zugangsdaten.
- `api.token_env` (oder jedes `api.tokens[].token_env`) — das/die Bearer-Token für REST-API / Dashboard.

Mit der systemd-Unit liegen diese in einer `EnvironmentFile` wie `/etc/kapkan/kapkan.env` mit den
Berechtigungen `0600`:

```sh
KAPKAN_TG_TOKEN=123456:abc...
KAPKAN_API_TOKEN=a-long-random-string
```

## Schlüssel der obersten Ebene

Jeder Schlüssel der obersten Ebene, seine Bedeutung und sein Standardwert. Für die größeren
Subsysteme verweist eine einzeilige Zusammenfassung auf die dedizierte Seite.

<Callout type="info" title="Minimalkonfiguration zum Starten">
Die meisten Schlüssel unten sind optional. Um den Daemon überhaupt zu starten, benötigen Sie nur:
mindestens eine `listen`-Adresse, `sampling.default_rate` (`>= 1`), mindestens ein geschütztes Präfix
in `networks` sowie `thresholds.pps` / `.mbps` / `.flows_per_sec` (alle `> 0`). Die Standard-`api.listen`
ist `127.0.0.1:8080`, sie kann also weggelassen werden. Um Blackholes tatsächlich **anzukündigen** (d. h.
sobald Sie `dry_run` abschalten), benötigen Sie zusätzlich einen `bgp`-Block. Alles andere — `carpet`,
`baseline`, `flowspec.source_anchored`, `flow_sources`, `geoip`, `escalation`, `dataplane` — ist
eine optionale Verfeinerung.
</Callout>

| Schlüssel | Bedeutung |
| --- | --- |
| `dry_run` | Wenn `true` (der Standard, auch bei Abwesenheit), werden Blackholes protokolliert und nachverfolgt, aber **niemals angekündigt**. |
| `listen.sflow` / `listen.netflow` | UDP-Lauschadressen. NetFlow v5/v9 und IPFIX teilen sich den `netflow`-Socket. Mindestens ein Listener ist erforderlich. Siehe [Funktionsweise](/docs/how-it-works). |
| `sampling.default_rate` | Sampling-Rate, die verwendet wird, wenn ein Exporter seine eigene nicht meldet. Muss `>= 1` sein. |
| `sampling.boundary` | Optionale Interface-Boundary-Zählung pro Exporter, die einen Flow dedupliziert, der an mehreren Sampling-Beobachtungspunkten gesehen wird (redundante Exporter, gleichzeitiges ingress+egress-Sampling, Transit-Links). Jeder Eintrag gibt die `external_ifindexes` eines Exporters (und optional `egress_sampling`) an; ein Flow wird dann nur gezählt, wenn er ein externes Interface überquert. Exporter ohne Eintrag zählen jedes Sample. Siehe Sampling-Korrektur weiter unten. |
| `sampling.boundary_debug` | Wenn `true`, wird `kapkan_engine_boundary_debug_bytes_total` (Bytes pro Exporter und Interface) exportiert, um externe Interfaces zu identifizieren. Nicht kardinalitätsbegrenzt — kurz aktivieren, dann wieder deaktivieren. |
| `flow_sources` | Optionale Allowlist vertrauenswürdiger Exporter-Quelladressen. Telemetrie kommt über nicht authentifiziertes UDP an, daher werden, wenn gesetzt, nur die aufgeführten Quellen in den Metriken nach Exporter beschriftet (alles andere wird unter `other` zusammengefasst), was die Kardinalität der Metrik-Labels begrenzt. Ist sie leer, wird stattdessen eine automatische Obergrenze angewendet. Hat keine Auswirkung auf die Erkennung. |
| `networks` | Geschützte [Präfixe](/docs/glossary) (IP-Bereiche in CIDR-Notation, z. B. `203.0.113.0/24`). Die Erkennung gilt **nur** für Ziele innerhalb dieser Präfixe, und sie dürfen sich nicht überschneiden. |
| `protected_whitelist` | Adressen, die **niemals** gesperrt werden, unabhängig vom Datenverkehr. Siehe [Sicherheitsmodell](/docs/safety). |
| `thresholds.pps` / `.mbps` / `.flows_per_sec` | Schwellenwerte pro Ziel nach Sampling-Korrektur. Alle müssen `> 0` sein. Siehe [Erkennung](/docs/detection). |
| `thresholds.tcp_pps` / `udp_pps` / `icmp_pps` / `tcp_syn_pps` / `frag_pps` (und jede `_mbps`-Variante) | Optionale Limits pro Protokoll. Ein Wert von `0` oder ein fehlender Schlüssel deaktiviert das jeweilige Limit. Jeder überschrittene Schwellenwert löst aus (ODER-Semantik). |
| `thresholds_outgoing` | Optional. Erkennt Angriffe, die **von** geschützten Hosts ausgehen (kompromittierte Maschinen). Gleiche Schlüssel wie `thresholds`; mindestens einer muss gesetzt sein. Fehlt der Block, wird ausgehender Datenverkehr nicht gezählt. Siehe [Erkennung](/docs/detection). |
| `hostgroups[]` | Optionale benannte Präfixgruppen mit eigenen Schwellenwerten und eigener Mitigation-Policy, einschließlich `per_host`- oder `total`-Berechnung. Jede kann ein `tenant`-Label tragen. Siehe [Hostgroups](/docs/hostgroups). |
| `tenant` | Optionales Tenant-Label für die implizite globale/Fallback-Gruppe. Siehe [Mandantenfähigkeit](/docs/multi-tenancy). |
| `samples.enabled` / `buffer_flows` / `flows_per_attack` | Kontinuierlicher Datenverkehrspuffer für Angriffs-Samples (Standardwerte: `true` / `65536` / `20`; `buffer_flows` max. `1048576`). Änderungen an der Dimensionierung erfordern einen Neustart. |
| `baseline` | Optionale kontinuierlich per EWMA gelernte Schwellenwerte pro Host, pro Hostgroup überschreibbar. Siehe [Baselines](/docs/baselines). |
| `carpet` | Optionale [Carpet-Bombing](/docs/glossary)-Erkennung (über ein Subnetz verteilt: Volumen dünn über viele Adressen in einem Präfix verteilt): löst einen präfixbezogenen Angriff aus, wenn der über ein `/24` (`aggregation_prefix_v4`/`v6`) aggregierte Verkehr `carpet.thresholds` über mindestens `min_hosts` verschiedene Hosts überschreitet — erkennt Floods, die unter jedem Per-Host-Schwellenwert bleiben. Nur Alarm, sofern nicht `carpet.mitigation` (`flowspec`, `dataplane` oder `blackhole`) gesetzt ist; `dataplane` verwirft den Vektor im Kernel dieser Maschine und erfordert einen `dataplane`-Block mit `enabled: true`. Jede Methode verweigert ein Präfix, das eine Whitelist-Adresse enthält, rechnet die gesamte Adressspanne des Präfixes auf `ban.max_banned_fraction` an und wird durch `carpet.max_active_prefix_bans` begrenzt. |
| `ban.ttl_seconds` | Wie lange eine Sperre ohne erneute Erkennung bestehen bleibt – ein anhaltender Angriff erneuert sie laufend, sodass die Route diese Zeitspanne nach dem Ende der Erkennung automatisch zurückgezogen wird. Keine dauerhaften Sperren. |
| `ban.unban_hysteresis_seconds` | Der Datenverkehr muss so lange unter dem Schwellenwert bleiben, bevor eine Sperre zurückgezogen wird; dies verhindert Flapping. |
| `ban.max_active_bans` | Harte Obergrenze für gleichzeitige Sperren. Neue Sperren über der Obergrenze werden abgelehnt. |
| `ban.fallback` | Was zu tun ist, wenn der Peer eine `flowspec`/`divert`-Ankündigung **ablehnt**: `blackhole` (Standard) stuft auf eine [RTBH](/docs/glossary)-Route herab (Remotely-Triggered Blackhole — eine Route, die allen Datenverkehr zur Opfer-IP nullroutet), damit das Opfer weiterhin geschützt ist; `none` lehnt die Sperre ab. `blackhole` ist endgültig. |
| `ban.max_banned_fraction` | Neue Sperren ablehnen, sobald mehr als dieser Anteil (`0`–`1`, pro Adressfamilie) des geschützten Raums per Blackhole verworfen wird — begrenzt den Schadensradius einer vergifteten Baseline oder eines Sturms mit gefälschten Quellen. `0` (Standard) deaktiviert dies. |
| `ban.max_bans_per_window` / `ban_window_seconds` | Sturmschutz: höchstens so viele **neue** Sperren pro Fenster (Sekunden). `max_bans_per_window: 0` (Standard) deaktiviert dies; das Fenster ist erforderlich, wenn die Rate gesetzt ist. |
| `ban.state_file` | Optionaler beschreibbarer Pfad (z. B. `/var/lib/kapkan/bans.json`), unter dem aktive Sperren persistiert werden, sodass ein Neustart sie rehydriert und **erneut ankündigt**, anstatt die Mitigation bis zur erneuten Erkennung fallen zu lassen. Wird mit `bgp.graceful_restart` kombiniert. Leer (Standard) deaktiviert die Persistenz. Siehe [Mitigation](/docs/mitigation). |
| `mitigation` | Mitigation-Methode: `blackhole` (Standard), `flowspec` ([FlowSpec](/docs/glossary) — eine BGP-Erweiterung, die auf mehr als die Ziel-IP filtert, z. B. Port/Protokoll, sodass Sie nur den Angriffsverkehr verwerfen können), `divert` oder `dataplane` (verwirft im Kernel dieses Hosts selbst und kündigt nichts an — erfordert einen `dataplane`-Block mit `enabled: true`, sonst wird die Konfiguration beim Start abgelehnt). Pro Hostgroup überschreibbar. Siehe [FlowSpec](/docs/flowspec), [Traffic-Umleitung](/docs/scrubbing) und [Datenebene im Kernel](/docs/dataplane). |
| `flowspec.action` / `rate_mbps` | FlowSpec-Regelaktion: `discard` oder `rate_limit` (mit `rate_mbps`). Siehe [FlowSpec](/docs/flowspec). |
| `flowspec.source_anchored` / `min_source_concentration` | Wenn aktiviert, fixiert eine FlowSpec-Regel **sowohl** das Opfer (Ziel) **als auch** eine dominante Angreiferquelle aus dem Angriffs-Sample — verwirft nur die Angreifer und schont legitime Clients — aber nur, wenn das Sample konzentriert genug ist (Standard `0.8`); andernfalls Rückfall auf opferbasierte Verankerung. Standardmäßig aus. |
| `escalation[]` | Optionale Leiter aus `{ after_seconds, action }`-Stufen (`none` / `dataplane` / `flowspec` / `divert` / `blackhole`, in dieser Reihenfolge der Härte), die `mitigation` außer Kraft setzt. Die Leiter muss nicht absteigen: sie darf halten oder verschärfen, nie abschwächen. Eine `dataplane`-Stufe erfordert einen `dataplane`-Block mit `enabled: true`. Siehe [Eskalationsstufen](/docs/escalation). |
| `edge` | Optional. Lässt dieses Gehirn [Edge-Knoten](/docs/edge) bedienen: `edge.zones_file` (absoluter Pfad der [Zonendatei](/docs/zones), erforderlich, wenn der Block vorhanden ist — eine Zonendatei, die sich nicht lesen oder validieren lässt, lässt den gesamten Reload scheitern, sodass die vorherigen Zonen aktiv bleiben), `edge.nodes[].name` (die Knoten, die pollen dürfen; jeder muss dem `controller.name` eines Knotens entsprechen) `edge.stale_after_seconds` (Standard `15`; wie lange ein Knoten ohne Pollen bleiben darf, bevor das Inventar ihn als verloren zählt) und `edge.state_file` (optionaler absoluter Pfad, unter dem das Gehirn die Freigabeschlüssel der Flotte aufbewahrt — die Signaturschlüssel der [Proof-of-Work-Stufe](/docs/edge#funktionsweise), Datei `0600` —, damit nach einem Neustart nicht jeder freigegebene Besucher erneut ein Rätsel lösen muss; leer hält sie im Speicher). Knoten authentifizieren sich mit einem `agent`-Token. Siehe [Einen Edge-Knoten installieren](/docs/edge-install). |
| `dataplane` | Optionaler Filter im Kernel: Kapkan bindet ein [XDP](/docs/glossary)-Programm an die NICs dieses Hosts und verwirft Angriffsverkehr bereits beim Empfang durch den Treiber, anstatt eine Route anzukündigen und einen Router darum zu bitten. Fehlt der Block (der Standard), ist die Funktion vollständig aus, und kein anderer Block verweist darauf. Erforderlich sind Linux 5.15 oder neuer sowie ein systemd-Drop-in, das `CAP_BPF`, `CAP_NET_ADMIN` und `CAP_PERFMON` gewährt — lesen Sie [Datenebene im Kernel](/docs/dataplane), bevor Sie es aktivieren. |
| `dataplane.enabled` | Standardmäßig `true`, wenn der Block vorhanden ist; der Schlüssel existiert also, um einen konfigurierten Block abzuschalten, ohne ihn zu löschen. Mit `false` wird der Block vollständig aufgelöst: eine `dataplane`-Stufe, `mitigation: dataplane` oder `carpet.mitigation: dataplane` wird dann beim Start genauso abgelehnt, als fehlte der Block. |
| `dataplane.interfaces` / `xdp_mode` | Die NICs, an die angebunden wird (**erforderlich**, mindestens eine; Namen müssen eindeutig und gültig sein — bis zu 15 Zeichen), und wie: `auto` (Standard) versucht natives XDP auf Treiberebene und fällt auf den generischen Pfad zurück, `native` scheitert sofort, wenn der Treiber kein natives XDP hat, `generic` erzwingt den langsameren skb-Pfad (virtio, Tests). Ob eine genannte NIC tatsächlich existiert, wird beim Anbinden beantwortet — durch einen Fehler beim Start. |
| `dataplane.pin_path` / `on_exit` | Das [bpffs](/docs/glossary)-Verzeichnis mit dem gepinnten Programm und den Maps, sodass die Policy einen Neustart *dieses Prozesses* überlebt (Standard `/sys/fs/bpf/kapkan`; muss absolut sein, und Kapkan startet nicht, wenn es nicht Modus `0700` hat und der uid gehört, unter der der Daemon läuft). `on_exit` bestimmt, was ein sauberes Herunterfahren tut: `keep` (Standard) lässt das Programm angebunden und die statische Policy weiter durchsetzen, `detach` entfernt es vollständig. |
| `dataplane.drop_malformed` | Frames verwerfen, die nicht geparst werden können, anstatt sie durchzulassen und zu zählen. Standard `false`: dies ist ein Vollstrecker der Mitigation und keine Firewall, sein Standardurteil lautet daher **pass**, und Unerkanntes wird nicht als feindlich behandelt. |
| `dataplane.allowlist` | **Quell**-Präfixe — oder einzelne Adressen, die als Host-Routen gelten —, die immer durchgelassen werden, geprüft vor jeder anderen Regel. Beachten Sie die Achse: hier geht es darum, *woher* Verkehr kommt, während `protected_whitelist` Ziele nennt, die nie gesperrt werden. Beide werden im Kernel durchgesetzt, und keines ersetzt das andere. Standardmäßig leer; wird live neu geladen. |
| `dataplane.ratelimit_profiles[]` | Benannte Obergrenzen, auf die das `profile` einer statischen Regel verweist: jeder Eintrag hat ein eindeutiges `name` sowie `pps` und/oder `mbps` (mindestens eines muss gesetzt sein; `0` lässt diese Dimension unbegrenzt). Ein Profil, auf das nichts verweist, wird beim Reload entfernt. Standardmäßig leer; wird live neu geladen. |
| `dataplane.static_rules[]` | Dauerhaft aktive Operator-Regeln, ausgewertet nach der Allowlist und vor allem, was der Detektor installiert. Jede hat ein eindeutiges `name`, eine `action` (`pass` / `drop` / `ratelimit`, letztere erfordert `profile`) und ein `match` aus `src`, `proto` (`tcp` / `udp` / `icmp` / `icmp6`), `src_port`, `dst_port` und `payload`. Die `match`-Felder werden mit UND verknüpft, und ein nicht gesetztes Feld passt auf alles — ein leeres `match` passt also auf jedes Paket, was nur mit `ratelimit` sinnvoll ist. Für `icmp`/`icmp6` werden Ports abgelehnt. `payload` grenzt darauf ein, womit die Nutzlast beginnt: `tls_client_hello` (ein TCP-Segment, das einen TLS ClientHello eröffnet, erfordert `proto: tcp`) oder `quic_initial` (ein UDP-Datagramm, das ein QUIC-v1-Initial eröffnet, erfordert `proto: udp`) — die beiden Formen, aus denen ein Handshake-Flood besteht. Keiner der beiden Werte setzt etwas wieder zusammen oder entschlüsselt etwas: Ein aufgeteilter ClientHello, ein QUIC-v2- oder Version-Negotiation-Paket und alles, was zu kurz für eine Entscheidung ist, matchen nicht und werden weitergeleitet. Bei den Regeln gewinnt **der erste Treffer**, eine Regel, deren Match eine frühere Regel bereits abdeckt, kann also nie greifen; Kapkan meldet solche Regeln — und alle, die die Allowlist abdeckt — bei jeder Policy-Anwendung, statt die Konfiguration abzulehnen, siehe [Regeln, die nie greifen](/docs/dataplane-tuning#regeln-die-nie-greifen). Standardmäßig leer; wird live neu geladen. |
| `dataplane.limits.max_dynamic_rules` / `max_static_rules` / `max_ratelimit_sources` | Größen der BPF-Maps, die beim Anbinden des Programms vollständig alloziert werden (Standard `4096` / `256` / `1048576`; jeder Wert muss `> 0` sein). `max_dynamic_rules` begrenzt die Regeln, die der Mitigator installieren darf, und muss **mindestens** `ban.max_active_bans * 8` betragen, da eine Sperre bis zu 8 Match-Regeln installieren kann — Kapkan weist einen kleineren Wert zurück, anstatt Installationen mitten im Angriff scheitern zu lassen, und beim Standardwert `4096` für `max_dynamic_rules` liegt die Obergrenze bei genau 512 aktiven Sperren. `max_static_rules` muss außerdem die von Ihnen geschriebenen `static_rules` abdecken. `max_ratelimit_sources` dimensioniert die Token-Bucket-Tabelle pro Quelle und ist der einzige der drei Werte, der wirklich Speicher kostet. Siehe [Datenebene im Kernel](/docs/dataplane). |
| `dataplane.fingerprint` | Optionale abseitige **Fingerprint-Ebene**: Der Kernel kopiert ein gesampeltes Präfix jedes TLS ClientHello und QUIC-v1-Initial in den Userspace, wo Kapkan den **JA4** des Clients berechnet und jede Quelle per Source-Block sperrt, deren JA4 auf `ja4_blocklist` steht. Erfordert `dataplane.enabled: true`; standardmäßig aus. Schlüssel: `enabled` und `sample_pps` (Kopien/s/CPU-Obergrenze, Standard `1000`) erfordern einen **Neustart**; `block_ttl_seconds` (Standard `300`, max. `86400`) und `ja4_blocklist` (Fingerprints mit exakter Übereinstimmung `a_b_c`, Duplikate werden zurückgewiesen) werden **hot-reloaded**. Ein JA4-Block wirkt auf die *behauptete* Quelle und der Auslöser ist fälschbar (spoofbar) — lesen Sie [Fingerprint-Ebene (JA4)](/docs/fingerprinting), bevor Sie sie einsetzen. |
| `bgp.local_asn` / `router_id` / `next_hop` / `next_hop6` / `community` | BGP-Identität, IPv4/IPv6-Blackhole-Next-Hops und die RTBH-[Community](/docs/glossary) — ein Routen-Tag in der Form `ASN:value` (z. B. `65000:666`), das Ihr Upstream abgleicht, um den Blackhole auszulösen. `router_id` muss eine IPv4-Adresse in Dotted-Quad-Notation sein. `next_hop6` ist optional, auch wenn ein IPv6-Präfix in `networks` steht; bleibt es ungesetzt, verwenden IPv6-Blackholes den RFC-6666-Discard-Next-Hop `100::1`. Siehe [Mitigation](/docs/mitigation). |
| `bgp.communities` / `local_pref` | Optionale Community-**Liste** (setzt `community` außer Kraft) und ein `LOCAL_PREF` (ein BGP-Attribut zur Routenpräferenz) für [iBGP](/docs/glossary)-Peers (internes BGP) — `LOCAL_PREF` wandert nur innerhalb Ihres eigenen Netzwerks, nicht zu externen ([eBGP](/docs/glossary)-)Peers, ist also nur für Ihre internen Nachbarn von Bedeutung. Alle `bgp`-Attribute sind pro Hostgroup überschreibbar. |
| `bgp.neighbors[]` | [eBGP](/docs/glossary)-Peers (externes BGP): `address`, `remote_asn` und ein optionaler `port` für Tests. |
| `bgp.graceful_restart` | BGP Graceful Restart (RFC 4724), **standardmäßig aktiviert**. Ein Peer, der dies unterstützt, behält Kapkans Mitigation-Routen als veraltet bei, während die Sitzung unterbrochen ist (z. B. bei einem Upgrade), anstatt sie zu verwerfen. Schlüssel: `enabled` (Standard `true`), `restart_seconds` (Standard `120`, Bereich `0`–`4095`, wobei `0` „den Standard 120 verwenden“ bedeutet), `long_lived` (LLGR — Long-Lived Graceful Restart, Standard `false`) und `long_lived_stale_seconds` (Standard `3600`, `≤ 86400`). Siehe [Mitigation](/docs/mitigation). |
| `scrubbing.next_hop` / `next_hop6` / `community` / `communities` / `local_pref` | Das Scrubbing-Center, zu dem die `divert`-Aktion den Datenverkehr lenkt. `next_hop` ist zum Umleiten erforderlich (`next_hop6` ebenfalls, wenn IPv6 geschützt wird); die Community ist optional. Pro Hostgroup überschreibbar. Siehe [Traffic-Umleitung](/docs/scrubbing). |
| `scrubbing.nodes[]` / `node_selection` / `on_all_nodes_lost` / `stale_after_seconds` | Verwaltete [Scrubbing-Knoten](/docs/scrubbing#verwaltete-scrubbing-knoten) — Boxen, die `kapkan scrub` ausführen und zu denen Kapkan umleitet und denen es mitteilt, was zu verwerfen ist. Jeder Knoten hat einen `name`, `next_hop`/`next_hop6`, optional `capacity_mbps` und `hostgroups`. Eine Gruppe, deren Stufenleiter umleitet, benötigt einen Knoten, der sie bedient, oder den skalaren `next_hop`. Siehe [Traffic-Umleitung](/docs/scrubbing#verwaltete-scrubbing-knoten). |
| `notify.*` | Telegram-, Slack-, E-Mail-, Webhook- und Exec-Hook-Kanäle. Siehe [Benachrichtigungen](/docs/notifications). |
| `storage.clickhouse.*` | Optionale ClickHouse-Persistenz für Angriffs- und Datenverkehrshistorie (`url`, `database`, `username_env`, `password_env`, `ttl_days`, …). Siehe [Speicherung](/docs/storage). |
| `geoip` | Optionale MaxMind-GeoLite2/GeoIP2-ASN- (und Länder-)Attribution der Quellen von Angriffs-Samples (`enabled`, `asn_database`, `country_database`). Standardmäßig deaktiviert; beim Start fixiert. |
| `api.listen` | Lauschadresse für REST-API und Metriken. Standard `127.0.0.1:8080`. |
| `api.dashboard` | Stellt die eingebettete Web-UI unter `/` auf dem API-Listener bereit. Standard `true`. Siehe [Dashboard](/docs/dashboard). |
| `api.token_env` | Nennt die Umgebungsvariable, die ein einzelnes Operator-Bearer-Token enthält. Erforderlich, bevor der Listener über localhost hinaus exponiert wird. Siehe [Authentifizierung](/docs/authentication). |
| `api.tokens[]` | Rollenbasierte Tokens: jeder Eintrag hat einen `name`, ein `token_env`, eine `role` (`viewer` oder `operator`) und einen optionalen `tenant`-Geltungsbereich. Setzt `token_env` außer Kraft (gegenseitig ausschließend). Siehe [Authentifizierung](/docs/authentication) und [Mandantenfähigkeit](/docs/multi-tenancy). |
| `update_check` | Optionale, **per Opt-in aktivierbare** Prüfung auf eine neuere Kapkan-Version — **standardmäßig deaktiviert**, sodass Kapkan niemals nach Hause telefoniert, sofern Sie es nicht aktivieren. Schlüssel: `enabled` (Standard `false`), `interval_seconds` (Standard `21600` = 6 Std.; muss `>= 3600` / 1 Std. sein, sonst wird die Konfiguration beim Laden **abgelehnt**), `channel` (`stable` oder `prerelease`), `notify` (sendet zusätzlich „Update verfügbar“ an Ihre Benachrichtigungskanäle, sobald eine neue Version erstmals erkannt wird; Standard `false`) und eine optionale `url`-Mirror-Überschreibung. Wenn aktiviert, fragt es die GitHub-Releases-API ab und gibt ein Ergebnis unter `/api/v1/status` und über die [Metrik](/docs/metrics) `kapkan_update_available` aus. Die laufende Version wird unabhängig davon immer lokal exponiert. Sie können auch `kapkan -check-update` ausführen, um die Prüfung einmalig auf Anforderung durchzuführen, ohne den Poller zu aktivieren (Exit `10` = Update verfügbar, `0` = aktuell, `1` = Fehler). |

### Details zu Schwellenwerten

Die drei Basis-Schwellenwerte — `pps`, `mbps`, `flows_per_sec` — sind verpflichtend und müssen
alle `> 0` sein. Die Limits pro Protokoll sind optionale Verfeinerungen: `tcp_syn_pps` zählt reine
SYNs (SYN gesetzt, ACK nicht gesetzt) und `frag_pps` zählt IP-Fragmente, die nicht das erste sind.
Die Erkennung verwendet ODER-Semantik — bereits ein einziger überschrittener Schwellenwert löst den
Angriff aus. Alle Werte werden in realen, nicht gesampelten Einheiten ausgedrückt (siehe
[Sampling-Korrektur](#sampling-korrektur)).

`flows_per_sec` ist nur für NetFlow/IPFIX-Exporter aussagekräftig. sFlow exportiert ein Sample pro
Paket (keine Flow-Aggregation), sodass Hosts aus sFlow-Quellen immer `flows_per_sec = 0` melden und
dieser Schwellenwert für sie nie auslöst — verwenden Sie stattdessen `pps`/`tcp_syn_pps`/`udp_pps`.
Siehe [Erkennung](/docs/detection).

## Ein vollständiges Beispiel

Eine realistische Produktionskonfiguration, angepasst aus `engine/deploy/config.example.yaml`:

```yaml
dry_run: true                       # keep until detection is validated

listen:
  sflow: ":6343"
  netflow: ":2055"                  # NetFlow v5/v9 + IPFIX share this socket

sampling:
  default_rate: 1000                # used only when an exporter omits its own rate
  # boundary: optional interface-boundary counting (deduplicates a flow seen at
  # several vantage points). List each exporter's external/uplink interfaces;
  # set egress_sampling only if calibration shows that ifIndex double-counts (see
  # Sampling correction) — not just because the device samples on egress.
  # boundary_debug: false
  # boundary:
  #   - exporter: "10.1.32.2"
  #     external_ifindexes: [1000025]
  #     egress_sampling: false   # true only if boundary_debug shows ~2x

networks:                           # detection applies ONLY inside these prefixes
  - "203.0.113.0/24"
  - "2001:db8::/32"

protected_whitelist:                # never banned, regardless of traffic
  - "203.0.113.1"                   # gateway / router
  - "203.0.113.2"                   # authoritative nameserver

thresholds:                         # per destination host, after sampling correction
  pps: 80000
  mbps: 1000
  flows_per_sec: 35000
  tcp_syn_pps: 5000                 # optional per-protocol; 0/absent disables
  udp_pps: 60000

thresholds_outgoing:                # detect compromised hosts attacking outward
  pps: 50000
  udp_pps: 20000

dataplane:                          # optional; needs Linux 5.15+ and the systemd drop-in
  interfaces: ["eth0"]              # required; at least one NIC (restart to change)
  # xdp_mode: auto                  # auto (default) | native | generic
  # pin_path: /sys/fs/bpf/kapkan    # bpffs dir; mode 0700, owned by the daemon's uid
  # on_exit: keep                   # keep (default) stays attached and enforcing on shutdown
  # drop_malformed: false           # default: unparseable frames pass and are counted
  allowlist:                        # SOURCE prefixes that always pass, checked first
    - "198.51.100.7"                # monitoring (a bare address is a host route)
    - "192.0.2.0/24"                # management network
  ratelimit_profiles:               # named ceilings; set pps, mbps or both
    - {name: icmp_cap, mbps: 10}
    - {name: handshake_cap, pps: 20}
    - {name: quic_handshake_cap, pps: 20}
  static_rules:                     # always-on, before any rule the detector installs
    - name: drop_chargen
      match: {proto: udp, src_port: 19}
      action: drop
    - name: cap_icmp
      match: {proto: icmp}
      action: ratelimit
      profile: icmp_cap             # must name a declared profile
    - name: cap_tls_handshakes      # per-source ceiling on new TLS handshakes
      match: {proto: tcp, dst_port: 443, payload: tls_client_hello}
      action: ratelimit
      profile: handshake_cap
    - name: cap_quic_handshakes     # …and its own ceiling for QUIC/HTTP-3
      match: {proto: udp, dst_port: 443, payload: quic_initial}
      action: ratelimit
      profile: quic_handshake_cap
  # limits:
  #   max_dynamic_rules: 4096       # must be >= ban.max_active_bans * 8
  #   max_static_rules: 256
  #   max_ratelimit_sources: 1048576  # per-source token buckets (kernel memory)

ban:
  ttl_seconds: 600                  # every ban auto-withdraws after this
  unban_hysteresis_seconds: 120     # stay below threshold this long before unban
  max_active_bans: 50               # refuse new bans past this cap
  # fallback: blackhole             # degrade a rejected flowspec/divert announce to RTBH (default)
  # max_banned_fraction: 0.05       # never blackhole more than 5% of protected space (per family)
  # max_bans_per_window: 100        # storm guard: at most 100 new bans per window
  # ban_window_seconds: 60          # the window for max_bans_per_window

bgp:
  local_asn: 65001
  router_id: "10.0.0.1"             # must be an IPv4 dotted-quad
  next_hop: "192.0.2.1"             # IPv4 blackhole (discard) next-hop
  next_hop6: "100::1"               # IPv6 blackhole next-hop
  community: "65000:666"            # RTBH community your upstream honors
  neighbors:
    - address: "10.0.0.254"
      remote_asn: 65000

notify:
  telegram:
    token_env: "KAPKAN_TG_TOKEN"    # token read from this env var, never the file
    chat_id: "-1001234567890"
  slack:
    webhook_url: ""                 # optional Slack incoming webhook
  email:
    smtp_host: ""                   # "mail.example.com:587"; empty disables
    from: ""
    to: []
    username_env: "KAPKAN_SMTP_USER"
    password_env: "KAPKAN_SMTP_PASS"
    require_tls: false              # STARTTLS auto-required when credentials are set

api:
  listen: "127.0.0.1:8080"          # default localhost bind needs no auth
  dashboard: true                   # embedded web UI at /; false = JSON API only
  # token_env: "KAPKAN_API_TOKEN"   # REQUIRED before exposing beyond localhost
```

Die Blöcke `hostgroups`, `baseline` und `samples` sind hier aus Gründen der Kürze weggelassen.
Siehe die dedizierten Seiten für ihre vollständigen Schemata:

- [Hostgroups](/docs/hostgroups) — Schwellenwerte pro Präfix, `ban: false` und `calculation: total`.
- [Baselines](/docs/baselines) — `factor`, `half_life_seconds`, `warmup_seconds`, `floor`.
- Der `samples`-Block: `enabled` (Standard `true`), `buffer_flows` (Standard `65536`, max.
  `1048576`) und `flows_per_attack` (Standard `20`). Diese steuern den kontinuierlichen Flow-Ring, der genutzt
  wird, um in dem Moment, in dem ein Angriff auslöst, die dominierenden Quellen, Ports und
  Protokolle an jeden Angriff anzuhängen. Eine Änderung der Dimensionierung erfordert einen
  Neustart.

Der `dataplane`-Block oben zeigt nur die Form. Er ist nicht selbstgenügsam: Ein Host mit
`dataplane.enabled: true` **scheitert beim Start**, solange der Kernel nicht 5.15 oder neuer ist und
das mitgelieferte systemd-Drop-in `kapkan-dataplane.conf` nicht installiert ist, denn die gehärtete
Unit gewährt keine der drei Capabilities, die das XDP-Programm braucht. Installieren Sie das Drop-in
zusammen mit der Konfigurationsänderung, nicht erst nach dem ersten Fehlstart — [Datenebene im Kernel](/docs/dataplane) behandelt die Host-Vorbereitung, den einzuplanenden Map-Speicher und die
Bedeutung jeder Startfehlermeldung.

## Sampling-Korrektur

Flow-Telemetrie ist gesampelt — ein Router exportiert einen Datensatz pro N Pakete. Kapkan
multipliziert jede beobachtete Rate mit der Sampling-Rate des Exporters, sodass Schwellenwerte in
realen, nicht gesampelten Datenverkehrseinheiten ausgedrückt werden. Die Rate stammt aus dem
Flow-Paket, wenn der Exporter sie meldet, andernfalls aus `sampling.default_rate`.

Das bedeutet, dass ein Schwellenwert wie `pps: 80000` die reale Angriffsrate ist, auf die Sie
reagieren möchten, nicht ein gesampelter Zählwert. Wenn Ihr Exporter mit `1:1000` sampelt und die
Rate nicht bekanntgibt, setzen Sie `sampling.default_rate: 1000`, damit ein einzelnes gesampeltes
Paket pro Sekunde korrekt als 1000 reale Pakete pro Sekunde gezählt wird.

<Callout type="warning" title="Sampling vor dem Live-Gang richtig einstellen">
Eine falsche `sampling.default_rate` skaliert jeden Schwellenwert um denselben Faktor. Stellen Sie
sie so ein, dass sie dem entspricht, was Ihre Router tatsächlich exportieren, und bestätigen Sie
dann im Dry-Run, dass die Erkennung bei den von Ihnen erwarteten Raten auslöst.
</Callout>

### Jedes Paket einmal zählen

Die Korrektur setzt voraus, dass jedes Paket einmal beobachtet wird. Wenn dasselbe Paket an mehr als
einem Beobachtungspunkt gesampelt wird — redundante Exporter (z. B. ein MLAG-Paar), ingress- **und**
egress-Sampling auf einem Gerät (Arista `sflow sample output`) oder Transit-/Peer-Links — würde
Kapkan andernfalls jede Kopie summieren und `pps`, `mbps` sowie `flows_per_sec` um einen konstanten
Faktor überzählen.

Die Interface-Boundary-Zählung behebt dies, ohne den Exporter zu verändern. Klassifizieren Sie die
externen Interfaces jedes Exporters (uplink/border); ein Flow wird dann nur einem geschützten Host
zugerechnet, wenn er die Grenze überquert — eingehend auf einem externen Input-Interface, ausgehend
auf einem externen Output-Interface. Exporter ohne `boundary`-Eintrag zählen weiterhin jedes Sample,
sodass Sie dies Exporter für Exporter aktivieren können.

```yaml
sampling:
  default_rate: 2500
  boundary:
    - exporter: "10.1.32.2"          # one entry per flow exporter (sampler/agent IP)
      external_ifindexes: [1000025]  # the uplink/border interface ifIndex values
      egress_sampling: false         # only if calibration shows this ifIndex double-counts (see below)
```

Um herauszufinden, welche Interfaces extern sind, setzen Sie kurz `sampling.boundary_debug: true` und
lesen Sie `kapkan_engine_boundary_debug_bytes_total`, aufgeschlüsselt nach Exporter und Interface.

<Callout type="warning" title="egress_sampling kalibrieren — nicht annehmen">
`egress_sampling: true` halbiert die an der Grenze gezählte Rate, um eine in+out-Doppelzählung
rückgängig zu machen, aber **`sflow sample output` bedeutet nicht automatisch, dass Sie es
brauchen.** Ob eine Egress-Kopie die Grenze tatsächlich aufbläht, hängt von der Topologie ab: Bei
einem Arista MLAG wird die Egress-Kopie eines eingehenden Pakets auf dem Access-Port mit einem
*anderen* Input-Interface gesampelt, sodass sie nie das Input-Interface-Gate der Grenze passiert —
das Paket ist bereits einmal gezählt, und `egress_sampling: true` würde es dann um die Hälfte
*unter*-zählen. Kalibrieren Sie: Vergleichen Sie die `boundary_debug`-Rate des externen Interface mit
dem realen Zähler dieses Interface (z. B. `show interfaces`). Setzen Sie `egress_sampling: true` nur,
wenn das Grenz-Interface ~2x die reale Rate anzeigt; andernfalls belassen Sie es bei `false` (dem
Standard).
</Callout>
