# REST-API

Kapkan stellt eine kleine JSON-REST-API bereit, um die Erkennung zu beobachten und die manuelle
Mitigation zu steuern. Sie wird unter der in `api.listen` angegebenen Adresse bereitgestellt, die
standardmäßig `127.0.0.1:8080` lautet. Derselbe Listener bedient auch das eingebettete
[Dashboard](/docs/dashboard) und den Prometheus-Endpunkt [`/metrics`](/docs/metrics).

Die API ist überwiegend lesend: Status, aktive und kürzlich beendete Angriffe, der Snapshot der
verfolgten Hosts sowie die Sperrtabelle sind allesamt `GET`-Aufrufe. Drei `POST`-Endpunkte ändern
den Zustand — manuelles Sperren, manuelles Entsperren und Konfigurations-Reload.

<Callout type="warning" title="Vor dem Freigeben authentifizieren">
Standardmäßig bindet `api.listen` an `127.0.0.1`, sodass die API nur auf localhost ohne
Authentifizierung sicher ist. Bevor Sie über das Loopback-Interface hinaus binden, legen Sie ein
Bearer-Token fest. Siehe [Authentifizierung](/docs/authentication).
</Callout>

Alle `/api/v1`-Routen durchlaufen die Token-Prüfung, sobald die Authentifizierung konfiguriert ist;
ist sie einmal konfiguriert, muss jede Anfrage `Authorization: Bearer <token>` mitführen. Tokens
tragen eine **Rolle**: Die `GET`-Routen benötigen die Rolle **viewer**, und die zustandsändernden
Routen (`ban`, `unban`, `config/reload`) benötigen die Rolle **operator**. `config/reload` geht
noch weiter: Es erfordert ein **ungebundenes (Admin-)Token**, sodass selbst ein operator-Token, das
tenant-bezogen ist, mit `403` abgewiesen wird. Der
[Scrub-Knoten-Kanal](#der-scrub-knoten-kanal) verlangt die Rolle **agent** — das Credential eines
Scrub-Knotens, das genau jene Routen und nichts sonst erreicht. Ein Lesezugriff mit einem
viewer-Token funktioniert; eine Änderung mit einem viewer-Token liefert `403`; ein unbekanntes Token
liefert `401`. Die `POST`-Endpunkte verlangen zusätzlich einen JSON-Content-Type — senden Sie
`Content-Type: application/json`. Ein `POST` ohne diesen Header wird mit
HTTP `415 Unsupported Media Type` abgewiesen, sodass ein fehlender Header fast immer der Grund ist,
wenn ein `curl`-Ban mit einem 415 fehlschlägt. Beachten Sie, dass `/metrics` und das statische Dashboard-Gerüst
ohne Token bereitgestellt werden; die Daten, die das Dashboard lädt, werden über die geschützte API
abgerufen. Siehe [Authentifizierung](/docs/authentication) zu den Token-Rollen.

Ein Token kann zudem **tenant-bezogen** (mandantengebunden) sein: Es sieht dann auf jedem
Lese-Endpunkt nur die Zeilen seines Tenants (`/status` wird auf die eigenen Hostgroups und
Zählungen umgebaut) und darf nur innerhalb seines Tenants `ban`/`unban` ausführen — ein Ziel
außerhalb des Tenants liefert ein einheitliches `403`. Ein tenant-bezogenes Token kann die
Konfiguration überhaupt nicht neu laden: `config/reload` ist auf ungebundene (Admin-)Tokens
beschränkt und liefert andernfalls `403`. Siehe
[Mandantenfähigkeit](/docs/multi-tenancy).

## Endpunkte

| Methode | Pfad | Beschreibung |
| --- | --- | --- |
| GET | `/api/v1/status` | Modus, Uptime, geschützte Netzwerke, Schwellenwerte, Hostgroups, Anzahl aktiver Angriffe/Sperren. |
| GET | `/api/v1/attacks` | Aktive Angriffe sowie die letzten 100 beendeten, mit Samples und Klassifizierung. |
| GET | `/api/v1/hosts` | Snapshot der verfolgten Hosts: Raten je Richtung, gelernte Baselines, Angriffszustand. |
| GET | `/api/v1/bans` | Alle Sperren, aktive und historische. |
| GET | `/api/v1/traffic` | Persistierte Ratenhistorie je Host (viewer); `{available:false, points:[]}`, wenn der Speicher deaktiviert ist. |
| GET | `/api/v1/audit` | Operator-zugeordneter Audit-Trail von Änderungen (wer wann gesperrt/neu geladen hat, mit Ergebnis). |
| POST | `/api/v1/ban` | Eine Adresse manuell sperren. |
| POST | `/api/v1/unban` | Eine Sperre manuell zurückziehen. |
| POST | `/api/v1/config/reload` | Konfigurationsdatei neu einlesen (entspricht `SIGHUP`). |
| POST | `/api/v1/dataplane/sources` | Eine Quelle in der [Datenebene](/docs/dataplane) verwerfen, gebunden an ein Opfer, mit verpflichtender TTL. |
| POST | `/api/v1/dataplane/sources/unblock` | Einen Source-Block sofort entfernen. |
| GET | `/api/v1/dataplane/rules` | Der Regel-Feed für [Scrub-Knoten](/docs/scrubbing#verwaltete-scrubbing-knoten) (`agent`/ungebundenes `operator`); ETag-Long-Poll, bis zu 30 s gehalten. |
| POST | `/api/v1/dataplane/nodes/{name}/report` | Der beratende Selbstreport eines Scrub-Knotens (`agent`/ungebundenes `operator`). |
| GET | `/api/v1/dataplane/nodes` | Inventar der verwalteten Knoten: Lebendigkeit, Konfiguration, Ban-Zähler pro Knoten (ungebundenes `viewer`+). |
| GET | `/api/v1/edge/history` | Die [Edge-Historie](/docs/storage#edge-historie) einer Zone, über einen Zeitraum gebucketet (`viewer`; ein tenant-bezogenes Token auf seinen eigenen Zonen); `{available:false, points:[]}`, wenn die Speicherung deaktiviert ist. |
| GET | `/api/v1/edge/history/sources` | Die aussagekräftigen Quellen der Zone über einen Zeitraum — wer abgewiesen, herausgefordert oder es beinahe worden wäre (`viewer`; ein tenant-bezogenes Token auf seinen eigenen Zonen). |
| GET | `/api/v1/edge/events` | Die Übergänge, die das Gehirn in der Edge-Flotte gesehen hat, neueste zuerst (ungebundenes `viewer`+). |
| GET | `/metrics` | Prometheus-Metriken. |
| GET | `/healthz` | Unauthentifizierte Liveness-/Readiness-Probe: `503`, bis vollständig gestartet, danach `200`. |

Alle Antworten sind JSON. Fehler liefern ein Objekt der Form `{"error": "..."}` mit einem
passenden HTTP-Status zurück.

### GET /api/v1/status

Gibt den aktuellen Betriebsmodus und eine Zusammenfassung dessen zurück, was Kapkan schützt. Zum
Auslesen (lassen Sie den `Authorization`-Header weg, wenn kein Token konfiguriert ist):

```sh
curl -fsS localhost:8080/api/v1/status \
  -H "Authorization: Bearer $TOKEN" | jq
```

```json
{
  "dry_run": true,
  "uptime_seconds": 8123,
  "version": "v1.2.0 · a1b2c3d",
  "update_available": false,
  "role": "operator",
  "unscoped": true,
  "networks": ["203.0.113.0/24", "198.51.100.0/24"],
  "active_attacks": 1,
  "active_bans": 1,
  "thresholds": {
    "pps": 80000,
    "mbps": 1000,
    "flows_per_sec": 20000
  },
  "hostgroups": [
    { "name": "web", "calculation": "per_host", "mitigation": "blackhole", "ban": true }
  ]
}
```

`dry_run` gibt den globalen Modus an: Bei `true` wird kein Blackhole an Ihre Router angekündigt.
`version` ist der laufende Build, stets vorhanden und ohne ausgehenden Datenverkehr. `update_available`
ist `false`, sofern nicht der opt-in [`update_check`](/docs/configuration) aktiviert ist und eine
neuere Version findet — dann ist es `true` und `latest_version`, `latest_is_security` und `latest_url`
werden zusätzlich mitgeliefert. Siehe [Aktualisieren](/docs/upgrading).
`thresholds` und `hostgroups` spiegeln die aktive Konfiguration wider; ihre
vollständige Struktur finden Sie unter [Erkennung](/docs/detection) und [Hostgroups](/docs/hostgroups).
`role` und `unscoped` sind stets vorhanden — sie teilen dem Dashboard mit, welches Token es
verwendet. Die Felder `networks`, `thresholds`, `bgp`, `scrubbing` und `notify` sind
deploymentweite Konfiguration und werden nur an ein ungebundenes (Admin-)Token zurückgegeben; ein
tenant-bezogenes Token erhält ein Status-Objekt ohne sie (nur `dry_run`, `version`,
`uptime_seconds`, `update_available`, `role`, `unscoped`, seine eigenen `hostgroups` und die
Zählungen). Ein Admin-Token erhält zusätzlich `bgp`-, `scrubbing`- und `notify`-Objekte — `notify`
gibt nur preis, welche Kanäle aktiviert sind, niemals Tokens oder URLs. Wenn ein Feld also zu
„fehlen“ scheint, prüfen Sie, ob Ihr Token tenant-bezogen ist, statt anzunehmen, dass Kapkan defekt
ist.

### GET /api/v1/attacks

Gibt die aktuell aktiven Angriffe sowie die letzten 100 beendeten zurück (neueste zuerst). Beide
Arrays enthalten `Attack`-Objekte.

| Feld | Typ | Hinweise |
| --- | --- | --- |
| `scope` | string | `host` oder `group`. Gruppenbezogene Angriffe führen kein `target`. |
| `target` | string | Die angegriffene Adresse (Host-Scope). |
| `group` | string | Hostgroup-Name (Gruppen-Scope oder die Gruppe des Hosts). |
| `tenant` | string | Der Tenant der besitzenden Gruppe, sofern einer zugewiesen ist (siehe [Mandantenfähigkeit](/docs/multi-tenancy)). |
| `direction` | string | `incoming` oder `outgoing`. |
| `metric` | string | Die Metrik, die ausgelöst hat, z. B. `pps`, `mbps`, `tcp_syn_pps`. |
| `rate` | number | Die Rate der auslösenden Metrik, in deren Einheit: solange der Angriff aktiv ist die aktuelle Messung der Engine, danach die letzte vor seinem Ende. |
| `threshold` | number | Der überschrittene Schwellenwert. |
| `rates` | object | Vollständige Ratenaufschlüsselung je Protokoll (siehe unten), aus derselben Messung wie `rate`. |
| `active` | bool | `true`, solange der Angriff andauert. |
| `ban_state` | string | `active`, `withdrawn` oder `rejected`. Entfällt, wenn keine Sperre vorliegt. |
| `method` | string | Mitigationsmethode: `blackhole`, `flowspec` oder `divert`. Entfällt, wenn keine Sperre vorliegt. |
| `route` | string | Der Routen-String (`blackhole …` / `divert …`) oder eine `flowspec: ...`-Zusammenfassung, wenn eine Sperre existiert. |
| `flowspec` | array | Die generierten [FlowSpec](/docs/flowspec)-Regeln, wenn `method` gleich `flowspec` ist. |
| `dry_run` | bool | Ob die Sperre virtuell war. |
| `started_at` | string | RFC-3339-Zeitstempel. |
| `ended_at` | string | RFC-3339-Zeitstempel; entfällt, solange aktiv. |
| `sample` | object | Bei der Erkennung erfasstes Flow-Sample; entfällt, wenn Sampling deaktiviert ist. |
| `classification` | object | Abgeleiteter Angriffsvektor; entfällt, wenn nicht klassifiziert. |
| `reason` | object | Warum die Erkennung ausgelöst hat — Herkunft des Schwellenwerts, Warm-up, Protokollanteile. Wird beim Start angehängt. |

```json
{
  "active": [
    {
      "scope": "host",
      "target": "203.0.113.66",
      "group": "web",
      "direction": "incoming",
      "metric": "pps",
      "rate": 412000,
      "threshold": 80000,
      "rates": {
        "pps": 412000,
        "mbps": 3100,
        "flows_per_sec": 9800,
        "udp_pps": 405000,
        "udp_mbps": 3080
      },
      "active": true,
      "ban_state": "active",
      "route": "blackhole 203.0.113.66/32 next-hop 192.0.2.1 community 65000:666",
      "dry_run": false,
      "started_at": "2026-06-13T09:41:07Z",
      "sample": {
        "top_sources": [
          { "key": "198.51.100.23", "packets": 1240000, "bytes": 1612000000 }
        ],
        "top_src_ports": [
          { "key": "123", "packets": 1180000, "bytes": 1534000000 }
        ],
        "top_dst_ports": [
          { "key": "443", "packets": 1240000, "bytes": 1612000000 }
        ],
        "protocols": [
          { "key": "udp", "packets": 1240000, "bytes": 1612000000 }
        ],
        "total_packets": 1240000
      },
      "classification": {
        "type": "ntp_amplification",
        "confidence": 0.95,
        "src_port": 123
      }
    }
  ],
  "recent": []
}
```

Solange ein Angriff aktiv ist, werden `rate` und `rates` bei jeder Anfrage neu aus der
Engine gelesen. Sie folgen damit dem Angriff, statt den Moment seiner Erkennung zu melden —
als das Zeitfenster nur eine Sekunde enthielt und einen anhaltenden Flood um ein Mehrfaches
zu niedrig auswies. `metric` und `threshold` bleiben, wie sie bei der Erkennung erfasst
wurden: sie benennen den Auslöser, und die Engine beurteilt das Ende des Angriffs anhand der
zu seinem Beginn eingefrorenen Schwellenwerte.

Das `rates`-Objekt führt das Basistrio (`pps`, `mbps`, `flows_per_sec`) sowie die Felder je
Protokoll, die ungleich null sind: `tcp_pps`, `tcp_mbps`, `udp_pps`, `udp_mbps`, `icmp_pps`,
`icmp_mbps`, `tcp_syn_pps`, `tcp_syn_mbps`, `frag_pps`, `frag_mbps`. Das `sample`-Objekt fasst die
gepufferten Flows hinter der Erkennung zusammen — `top_sources`, `top_src_ports`, `top_dst_ports`,
`protocols` (jeweils eine Liste von `{key, packets, bytes}`-Zählern), eine optionale rohe
`flows`-Liste und `total_packets`. Der `type` der `classification` ist einer der unter
[Erkennung](/docs/detection) dokumentierten Vektoren; `confidence` ist der Anteil (`0..1`) des
Angriffsverkehrs, der zur erkannten Signatur passt, und `src_port` ist der reflektierte
Dienst-Port für Amplification-Vektoren.

Das `reason`-Objekt erklärt, **warum** die Erkennung ausgelöst hat — einmal beim Start erfasst,
abseits des Hot Paths. `threshold_source` ist `static` oder `baseline`: ob der überschrittene
Grenzwert aus der statischen Konfiguration oder aus einer aufgewärmten
[gelernten Baseline](/docs/baselines) stammt. Ist er `baseline`, führt ein `baseline`-Objekt die
effektive Rechnung (`min(ceiling, max(floor, normal × factor))`). `baseline_configured`,
`warming_up` und `warmup_remaining_seconds` erklären einen statischen Schwellenwert, der nur galt,
weil die Baseline noch nicht aufgewärmt war. `shares` ist der Protokollanteil je Protokoll an der
gesamten PPS, der die Klassifizierung bestimmt hat, und `dominant_share_gate` ist der Anteil, den
ein Protokoll braucht, um einen Vektor zu gewinnen (andernfalls ist der Angriff `mixed`). Siehe
[Erkennung](/docs/detection), wie man es liest.

```json
{
  "reason": {
    "threshold_source": "baseline",
    "baseline": { "normal": 1200, "factor": 8, "floor": 5000, "ceiling": 80000 },
    "baseline_configured": true,
    "shares": { "udp": 0.98, "syn": 0, "tcp": 0.01, "icmp": 0, "frag": 0 },
    "dominant_share_gate": 0.5
  }
}
```

### GET /api/v1/hosts

Gibt einen Snapshot jedes verfolgten Hosts zurück — die Top-Talker-Daten. Jeder Eintrag ist ein
`HostStat`.

| Feld | Typ | Hinweise |
| --- | --- | --- |
| `target` | string | Die Host-Adresse. |
| `group` | string | Der Hostgroup-Name des Hosts. |
| `rates` | object | Aktuelle eingehende Raten über das Zeitfenster. |
| `rates_out` | object | Ausgehende Raten; nur ungleich null, wenn die ausgehende Erkennung aktiviert ist. |
| `in_attack` | bool | Ob sich der Host in einem aktiven Angriff befindet. |
| `metric` | string | Die Metrik des aktiven Angriffs; entfällt, wenn kein Angriff vorliegt. |
| `direction` | string | Die Richtung des aktiven Angriffs; entfällt, wenn kein Angriff vorliegt. |
| `baseline` | object | Gelernte eingehende Baseline; vorhanden, wenn Baselines konfiguriert sind. |
| `baseline_out` | object | Gelernte ausgehende Baseline; vorhanden, wenn Baselines konfiguriert sind. |

```json
{
  "hosts": [
    {
      "target": "203.0.113.66",
      "group": "web",
      "rates": {
        "pps": 412000,
        "mbps": 3100,
        "flows_per_sec": 9800,
        "udp_pps": 405000
      },
      "rates_out": {
        "pps": 120,
        "mbps": 2
      },
      "in_attack": true,
      "metric": "pps",
      "direction": "incoming",
      "baseline": {
        "pps": 950,
        "mbps": 7,
        "flows_per_sec": 60
      },
      "baseline_out": {
        "pps": 110,
        "mbps": 2,
        "flows_per_sec": 14
      }
    }
  ]
}
```

Die Objekte `baseline` und `baseline_out` führen das gelernte Normal-Basistrio (`pps`, `mbps`,
`flows_per_sec`) und erscheinen nur, solange EWMA-Baselines für die Gruppe des Hosts konfiguriert
sind. Siehe [Baselines](/docs/baselines).

### GET /api/v1/bans

Gibt die vollständige Sperrtabelle zurück — aktive und historische. Jeder Eintrag ist ein `Ban`.

| Feld | Typ | Hinweise |
| --- | --- | --- |
| `target` | string | Die gesperrte Adresse. |
| `prefix` | string | Das Blackhole-Präfix (`/32` oder `/128`). |
| `metric` | string | Die Metrik, die die Sperre ausgelöst hat; entfällt bei manuellen Sperren. |
| `rate` | number | Beobachtete Rate zum Sperrzeitpunkt; entfällt, wenn null. |
| `threshold` | number | Überschrittener Schwellenwert; entfällt, wenn null. |
| `next_hop` | string | Der Discard-Next-Hop. |
| `community` | string | Die an die Route angehängte Community-Menge — die RTBH-Community bei einem Blackhole, die Divert-(Scrubbing-)Community bei einer Divert-Sperre — bei mehr als einer durch Leerzeichen verbunden. |
| `local_pref` | number | Der an die Route angehängte `LOCAL_PREF`; entfällt, wenn null. |
| `node` | string | Der [verwaltete Scrubbing-Knoten](/docs/scrubbing#verwaltete-scrubbing-knoten), auf den dieser Divert-Ban eingefroren ist; entfällt, wenn der Ban nicht zu einem verwalteten Knoten umleitet. |
| `route` | string | Der vollständige Routen-String oder eine `flowspec: ...`-Zusammenfassung bei FlowSpec-Sperren. |
| `state` | string | `active`, `withdrawn` oder `rejected`. |
| `dry_run` | bool | Ob die Sperre virtuell war. |
| `manual` | bool | `true` bei vom Operator angeforderten Sperren. |
| `started_at` | string | RFC-3339-Zeitstempel. |
| `expires_at` | string | TTL-Ablauf; Sperren sind niemals dauerhaft. |
| `withdrawn_at` | string | Wann die Route zurückgezogen wurde; entfällt, solange aktiv. |
| `reason` | string | Warum eine Sperre abgelehnt oder zurückgezogen wurde; entfällt andernfalls. |
| `method` | string | Mitigationsmethode: `blackhole`, `flowspec` oder `divert`. |
| `flowspec` | array | Die generierten [FlowSpec](/docs/flowspec)-Regeln, wenn `method` gleich `flowspec` ist. |
| `escalation` | array | Die konfigurierte [Eskalationsleiter](/docs/escalation), sofern eine festgelegt ist. |
| `escalation_step` | number | Index der aktuellen Stufe der Leiter. |

```json
{
  "bans": [
    {
      "target": "203.0.113.66",
      "prefix": "203.0.113.66/32",
      "metric": "pps",
      "rate": 412000,
      "threshold": 80000,
      "next_hop": "192.0.2.1",
      "community": "65000:666",
      "route": "blackhole 203.0.113.66/32 next-hop 192.0.2.1 community 65000:666",
      "state": "active",
      "dry_run": false,
      "manual": false,
      "started_at": "2026-06-13T09:41:07Z",
      "expires_at": "2026-06-13T10:41:07Z"
    }
  ]
}
```

Siehe [Mitigation](/docs/mitigation), wie TTL, Hysterese und die Sperrobergrenze diesen
Lebenszyklus prägen.

### GET /api/v1/audit

Gibt den operator-zugeordneten Audit-Trail zurück — wer jeweils `ban`, `unban`,
`config_reload`, `source_block`, `source_unblock` oder `edge_challenge` ausgelöst hat, wann und mit
welchem Ergebnis (einschließlich **abgelehnter** Aktionen). Datensätze sind neueste zuerst und der
Endpunkt ist serverseitig tenant-bezogen. Er nimmt optionale Query-Parameter `from`/`to` (RFC 3339),
`action` (`ban`/`unban`/`config_reload`/`source_block`/`source_unblock`/`edge_challenge`) und
`target` (eine IP) entgegen und liefert standardmäßig die letzte Stunde:

```json
{
  "available": true,
  "events": [
    {
      "event_time": "2026-06-22 03:14:09",
      "action": "ban",
      "result": "rejected",
      "operator": "alice",
      "role": "operator",
      "tenant": "customerA",
      "target": "203.0.113.66",
      "target_type": "host",
      "reason": "whitelisted",
      "source": "api",
      "ban_state": "rejected",
      "dry_run": 0
    }
  ]
}
```

Wenn der Speicher deaktiviert ist, lautet die Antwort `{"available": false, "events": []}`. `events`
ist immer ein Array — leer statt `null`, auch bei einem Mandanten, dessen Zeitraum keinen Datensatz
enthält —, ein Client darf also ohne Absicherung darüber iterieren. Beachten
Sie, dass Audit-Datensätze `dry_run` als Ganzzahl (`0`/`1`) kodieren, nicht als JSON-Boolean wie an
anderer Stelle auf dieser Seite. Die vollständige Feldliste, die Query-Regeln sowie das Modell für
Operator-Identität und Tenant-Bezug finden Sie auf der eigenen Seite [Audit-Log](/docs/audit).

### POST /api/v1/ban

Sperrt eine Adresse manuell per Blackhole. Der Body ist eine einzelne IP:

```http
POST /api/v1/ban
Content-Type: application/json

{"ip": "203.0.113.66"}
```

Als ausführbarer Befehl (lassen Sie den `Authorization`-Header weg, wenn Sie noch kein Token konfiguriert haben):

```sh
curl -fsS -X POST localhost:8080/api/v1/ban \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"ip":"203.0.113.66"}'
```

Die Antwort ist das resultierende `Ban`-Objekt. Eine manuelle Sperre beachtet jede Sicherheitsregel,
die auch eine automatische Sperre beachtet:

- Ein **auf der Whitelist stehendes** Ziel wird mit HTTP `409 Conflict` und `reason: "whitelisted"` abgelehnt; es wird niemals angekündigt.
- Ein Ziel **außerhalb der konfigurierten `networks`** wird mit HTTP `409` und `reason: "outside configured networks"` abgelehnt.
- Eine Anfrage, die **`max_active_bans`** überschreiten würde, wird mit HTTP `409` und `reason: "max_active_bans reached"` abgelehnt.

In jedem `409`-Fall ist der Body weiterhin ein `Ban`-Objekt mit `state: "rejected"` und gesetztem
`reason`-Feld. Eine ungültige oder nicht parsbare IP liefert HTTP `400` zurück.

<Callout type="warning" title="Dry-run gilt weiterhin">
Eine manuelle Sperre respektiert den globalen Modus. Solange `dry_run` gleich `true` ist, wird die
Sperre aufgezeichnet und mit `dry_run: true` zurückgegeben, aber keine Route wird angekündigt. Siehe
das [Sicherheitsmodell](/docs/safety).
</Callout>

### POST /api/v1/unban

Zieht eine aktive Sperre für die angegebene Adresse zurück. Der Body hat dieselbe
`{"ip": "..."}`-Struktur und derselbe JSON-Content-Type ist erforderlich:

```http
POST /api/v1/unban
Content-Type: application/json

{"ip": "203.0.113.66"}
```

Bei Erfolg gibt er die zurückgezogene `Ban` zurück. Wenn keine aktive Sperre für die Adresse
existiert, liefert er HTTP `404` zurück.

### POST /api/v1/config/reload

Liest die Konfigurationsdatei neu von der Festplatte ein und wendet sie an — derselbe Effekt wie das
Senden von `SIGHUP`. Der Body ist leer; der JSON-Content-Type ist dennoch erforderlich. Anders als
`ban`/`unban` erfordert dieser Endpunkt ein **ungebundenes (Admin-)Token**: Ein Reload tauscht die
gesamte Konfiguration aus, sodass ein tenant-bezogenes Token mit `403` und `config reload is
restricted to unscoped (admin) tokens` abgewiesen wird.

```json
{
  "reloaded": true,
  "dry_run": false,
  "thresholds": {
    "pps": 80000,
    "mbps": 1000,
    "flows_per_sec": 20000
  }
}
```

Falls die neue Konfiguration nicht geparst oder validiert werden kann, bleibt die laufende
Konfiguration unverändert und der Endpunkt liefert HTTP `400` mit dem Fehler zurück. Siehe
[Konfiguration](/docs/configuration).

### Der Source-Block-Kanal

Zwei Endpunkte erlauben es dem, was den Verkehr eines Opfers ohnehin terminiert — ein nginx davor,
ein Log-Exporter, ein Operator um 3 Uhr morgens —, Kapkan eine **Quelle** zum Verwerfen in der
[XDP-Datenebene](/docs/dataplane) zu übergeben, gebunden an dieses Opfer und mit verpflichtender
TTL. Die Entscheidung fällt dort, wo die Requests sichtbar sind; die Durchsetzung passiert im
Kernel. Beide verlangen ein `operator`-Token; die Rolle `agent` wird verweigert.

```sh
curl -fsS -X POST localhost:8080/api/v1/dataplane/sources \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"victim":"203.0.113.10","source":"198.51.100.7","ttl_seconds":600,"reason":"login flood"}'
```

| Feld | Erforderlich | Bedeutung |
| --- | --- | --- |
| `victim` | ja | Das geschützte Ziel, an das der Block gebunden ist. Daran wird ein Mandanten-Token geprüft, und es verhindert, dass die Evidenz eines Aufrufers zu einem globalen Verwerfen wird. |
| `source` | ja | Die zu verwerfende Adresse. Muss dieselbe Adressfamilie wie `victim` haben. |
| `ttl_seconds` | ja für einen Block | Wie lange der Block lebt, von `1` bis `86400` (24 h). Permanente Einträge gibt es nicht. Dasselbe Paar erneut zu blocken behält das ursprüngliche `created_at` und übernimmt die neue TTL — das Refresh, das ein Exporter braucht, um einen beharrlichen Störer ohne Unblock/Re-Block-Geklapper zu halten. |
| `reason` | nein | Eine freie Notiz, die in den [Audit-Trail](/docs/audit) übernommen wird. |

Die Antwort ist der resultierende `SourceBlock`:

```json
{
  "source": "198.51.100.7",
  "victim": "203.0.113.10",
  "created_at": "2026-08-17T21:04:11Z",
  "expires_at": "2026-08-17T21:14:11Z",
  "dry_run": false,
  "reason": "login flood"
}
```

`POST /api/v1/dataplane/sources/unblock` nimmt dasselbe `victim` und `source` (ein `ttl_seconds`
wird ignoriert) und entfernt genau dieses Paar sofort, damit niemand eine TTL abwarten muss, die er
selbst getippt hat. Es liefert den entfernten `SourceBlock` zurück oder `404`, wenn kein solches
Paar lebt.

#### Ablehnungen

Ein Eingabefehler ist `400`; eine wohlgeformte, von der Policy abgelehnte Anfrage ist `409`. Jeder
Aufruf — auch eine Ablehnung — schreibt ein zugeordnetes Audit-Event, denn ein abgelehnter Block ist
selbst eine Operator-Aktion.

| Status | Ursache |
| --- | --- |
| `400` | Nicht parsbares JSON oder Adresse, `victim` und `source` aus verschiedenen Adressfamilien oder `ttl_seconds` außerhalb von `[1, 86400]`. |
| `403` | `victim` liegt außerhalb Ihres Mandanten. Dieselbe einheitliche Ablehnung wie bei den Ban-Endpunkten, damit der Endpunkt kein Existenz-Orakel für die Hosts anderer Mandanten ist. |
| `404` | Nur beim Unblock: kein lebender Block für dieses Paar. |
| `409` | Die Datenebene fehlt oder ist deaktiviert; `victim` steht in `protected_whitelist`; `source` steht in `dataplane.allowlist`; `source` liegt innerhalb der geschützten `networks`; diese Quelle hält bereits 8 Opfer; oder es sind keine Policy-Slots mehr frei. |

Die beiden Allowlist-Ablehnungen sind die interessanten, und sie sind Ablehnungen genau deshalb,
weil die Alternative Stille ist: Der Datenpfad lässt eine Quelle aus der Allowlist auf Präzedenz 1
und Verkehr zu einem geschützten Ziel auf Präzedenz 2 durch, beides **bevor** irgendeine Regel
ausgewertet wird — so ein Block würde sich installieren und dann nie ein Paket treffen. Eine
`source` innerhalb Ihrer eigenen `networks` wird ebenfalls abgelehnt: ein interner Host ist eine
[Sperre](/docs/mitigation), kein Source-Block.

<Callout type="warning" title="Ein Installationsfehler entfernt jedes Paar dieser Quelle">
Die Paare einer Quelle teilen einen einzigen Kernel-Policy-Block, und das Rollback des Installers
ist über diesen Block alles-oder-nichts. Schlägt eine Installation fehl, wird jedes Paar dieser
Quelle entfernt, statt aufgezeichnet-aber-nicht-durchgesetzt zu bleiben, und der Fehler sagt das
auch — fügen Sie die wieder hinzu, die Sie noch brauchen. Die Tabelle behauptet nie, etwas
durchzusetzen, was der Kernel nicht tut.
</Callout>

<Callout type="info" title="Dieselben Garantien wie bei einer Sperre">
TTLs sind verpflichtend und begrenzt, jedes Paar trägt seinen eigenen Ablauf in den Kernel (es endet
also planmäßig, selbst wenn Kapkan stirbt), Installationen werden gegen
`dataplane.limits.max_dynamic_rules` verbucht, Blocks überleben einen Neustart über die
State-Datei, und `dry_run` wird beachtet — das Paar wird aufgezeichnet, mit `dry_run: true`
zurückgegeben, und nichts erreicht eine Kernel-Map. Siehe
[Source-Blocks](/docs/dataplane#source-blocks-aus-ihrem-eigenen-stack) für die Grenzen und
[Sicherheitsmodell](/docs/safety).
</Callout>

### Der Scrub-Knoten-Kanal

Diese drei Endpunkte existieren für [verwaltete Scrubbing-Knoten](/docs/scrubbing#verwaltete-scrubbing-knoten)
— Boxen, die [`kapkan scrub`](/docs/cli) ausführen. Sie verlangen die Rolle `agent` (das Credential
eines Scrub-Knotens; siehe [Authentifizierung](/docs/authentication)) oder ein ungebundenes
`operator`-Token, niemals ein `viewer`- oder ein tenant-bezogenes Token: Die Dokumente umspannen
jeden Tenant, sodass ihre Begrenzung eine Flotten- und keine Pro-Anfrage-Angelegenheit ist.

#### GET /api/v1/dataplane/rules

Die Regeltabelle, die ein Knoten durchsetzt: jedes aktive [umgeleitete](/docs/scrubbing) Opfer, mit
den zu verwerfenden [FlowSpec](/docs/flowspec)-Regeln und der zu spiegelnden TTL. Ein einfacher
`GET` liefert das aktuelle Dokument mit einem Content-Hash-`ETag`; ein `GET`, dessen
`If-None-Match` dieses ETag nennt, wird **gehalten**, bis sich die Tabelle ändert oder bis zu 30 s,
und dann mit `304` beantwortet — ein Long-Poll, der Regel-Updates im Sub-Sekunden-Bereich über
gewöhnliches HTTP liefert. Ein Knoten identifiziert sich mit `?node=<name>`, und **dieser Poll ist
das Lebendigkeitssignal des Knotens** — der Name muss also ein konfigurierter Knoten sein (ein
unbekannter Name ist `404`) und, außerhalb des token-losen lokalen Modus, muss die Anfrage ein
echtes Token mitführen. Ein an einen Knoten gebundenes Token (`api.tokens[].node`) darf nur als
dieser Knoten pollen: ein anderer Name oder gar keiner ist ein einheitliches `403`, bevor
irgendeine Präsenz festgehalten wird. Ein Reload, der den Knoten entfernt, das Token entfernt oder
die Bindung des Tokens verschiebt, beendet einen geparkten Poll mit der Antwort, die ein erster
Poll jetzt bekäme (`404`, `401`, `403`). Präsenz wird nur von `agent`-Tokens gestempelt — das
`?node=X` eines Operators ist eine Vorschau auf das Dokument von X und bewegt keine Lebendigkeit.

```json
{
  "version": 1,
  "bans": [
    {
      "target": "203.0.113.10",
      "prefix": "203.0.113.10/32",
      "method": "divert",
      "expires_at": "2026-08-13T10:00:00Z",
      "flowspec": [ { "dst": "203.0.113.10/32", "proto": 17, "action": "discard" } ]
    }
  ]
}
```

#### POST /api/v1/dataplane/nodes/\{name\}/report

Der beratende Selbstreport eines Knotens — Version, XDP-Modus, knotenseitiger Dry-Run, Last- und
Drop-Summen — gespeichert für die [Konsole](/docs/dashboard). Er ist **niemals** ein
Lebendigkeitssignal (das ist der Poll): Ein Report kann niemals einen toten Knoten als aktiv
markiert halten. Der Body ist auf 64 KiB begrenzt (`413` darüber) und ein unbekanntes `{name}` ist
`404`. Erfolg ist `204 No Content`.

#### GET /api/v1/dataplane/nodes

Das Knoteninventar, das die Nodes-Ansicht der Konsole rendert: jeder konfigurierte Knoten mit dem,
was das Gehirn weiß (Konfiguration, Poll-Lebendigkeit, wie viele Bans zu ihm umleiten), verbunden
mit seinem letzten Report. Ein Lesezugriff mit `viewer`-Rang, aber nur ungebundene Tokens — das
Inventar nennt Next-Hops und Hostgruppen, was Deployment-Topologie ist. Die Anzahl allein
(`nodes_total`) reitet für jede Rolle auf `/api/v1/status` mit, sodass eine Konsole ohne diesen
Aufruf entscheiden kann, ob sie Knoten-Bedienelemente anzeigt.

### Der Edge-Kanal

Diese Endpunkte existieren für [Edge-Knoten](/docs/edge) — Boxen, die [`kapkan edge`](/docs/cli#edge)
ausführen. Wie beim Scrub-Knoten-Kanal verlangen die knotenseitigen Endpunkte die Rolle `agent`
oder ein ungebundenes `operator`-Token, niemals ein `viewer`- oder ein tenant-bezogenes Token: Das
Zonendokument umspannt jeden Tenant. Bei den menschenseitigen ist es anders: Das Knoteninventar und
die Ereignisse der Flotte (`GET /api/v1/edge/events`) sind Lesezugriffe mit `viewer`-Rang für
ungebundene Tokens; der Zonenstatus, die [Edge-Historie](#get-apiv1edgehistory) mit ihren
aussagekräftigen Quellen (`viewer`-Rang) und der Hebel (`operator`-Rang) lassen ein
[tenant-bezogenes](/docs/multi-tenancy) Token für dessen eigene Zonen zu. **Das Gehirn verteilt
Richtlinien, niemals Urteile** — weder hier noch
anderswo existiert ein Aufruf pro Anfrage; ein Knoten beantwortet Anfragen allein. Die Anzahl der
konfigurierten Edge-Knoten (`edge_nodes_total`) reitet für jede Rolle auf `/api/v1/status` mit,
sodass eine Konsole ohne einen dieser Aufrufe entscheiden kann, ob sie die Edge-Ansicht anzeigt.

#### GET /api/v1/edge/zones

Das Zonendokument, das ein Knoten rendert und durchsetzt: die Zonen der
[Zonendatei](/docs/zones), die der
[Platzierungs-Geltungsbereich](/docs/edge#zonen-auf-knoten-verteilen) des Knotens abdeckt — jede
Zone beim bloßen `GET` eines Operators oder bei einer Flotte, deren Zonen keine `hostgroup` tragen
(eine beschriftete Zone wird nur von Knoten bedient, die ihre Gruppe auflisten) — mit ihren
Origins, ihrer TLS-Mindestversion, ihren ACME-Directories und ihrer Richtlinie, dazu die aktiven
Ausstellungsfreigaben, die verteilten ACME-Challenges, die Freigabeschlüssel und die Hebel dieser
Zonen; das `ETag` ist das des Knotens selbst. Ein einfacher
`GET` liefert das Dokument mit einem Content-Hash-`ETag`; ein `GET`, dessen `If-None-Match` dieses
ETag nennt, wird **gehalten**, bis sich das Dokument ändert — ein erfolgreicher Reload der
Zonendatei, eine von einem Knoten veröffentlichte Zertifikats-Challenge — oder bis zu 25 s, und
dann mit `304` beantwortet. Ein Reload, der den Knoten entfernt, das Token entfernt oder die
Bindung des Tokens verschiebt, beendet einen geparkten Poll mit der Antwort, die ein erster Poll
jetzt bekäme (`404`, `401`, `403`), niemals mit einem Dokument. Ein Knoten identifiziert sich mit
`?node=<name>`, und **dieser Poll
ist das Lebendigkeitssignal des Knotens** — der Name muss also ein konfigurierter
`edge.nodes[]`-Eintrag sein (ein unbekannter Name ist `404`) und die Anfrage muss ein echtes Token
mitführen. Ein an einen Knoten gebundenes Token (`api.tokens[].node`) darf nur als dieser Knoten
pollen, berichten und ACME koordinieren — der Name eines anderen Knotens oder ein Poll ohne
`?node=` ist ein einheitliches `403`, das den gebundenen Knoten nie nennt und abgewiesen wird,
bevor irgendeine Präsenz gestempelt oder irgendetwas gespeichert wird; nur `agent`-Tokens stempeln
Präsenz, das `?node=X` eines Operators ist also eine präsenzfreie Vorschau auf das Dokument von X.
Höchstens 4 Polls pro Token-Name und `max(8, 2 × die Anzahl der Edge-Knoten)` insgesamt dürfen
gleichzeitig geparkt sein; ein
weiterer passender Poll wird mit `429` und `Retry-After: 1` beantwortet
(`too many concurrent zone holds`), was der Knoten als Fehlschlag wertet und mit Backoff
beantwortet (1 s, verdoppelt bis 30 s) — geben Sie jedem Knoten ein eigenes agent-Token.

```json
{
  "version": 1,
  "zones": [
    {
      "name": "shop.example.com",
      "origins": ["10.0.0.10:8080"],
      "tls": { "min_version": "1.2" },
      "policy": { "mode": "decide", "failure_mode": "open", "challenge": "auto", "rate": { "rps": 50, "concurrency": 20 } }
    }
  ],
  "acme_challenges": [],
  "issuance_grants": []
}
```

`acme_directory`, `acme_fallback`, `extra_directives_file` und `tls.h3` werden weggelassen, wenn sie
nicht gesetzt sind; `tls.h3_options {advertise, alt_svc_max_age_seconds}` erscheint nur dort, wo
eine Zone von den Standards abweicht (`advertise: false`, oder ein `ma` abseits des Standards) —
fehlt es, heißt das ankündigen und `86400` —, sodass eine Zonendatei, die `h3` nur einschaltet, die
Bytes und das ETag des Dokuments im Übrigen unverändert lässt. Ein fehlendes `acme_directory`
bedeutet, dass der Knoten bei seiner eigenen Standard-CA bestellt (Let's Encrypt, sofern seine
`edge.yaml` nichts anderes sagt). Die Richtlinie
trägt `dry_run` und die `challenge_options`, die eine Zone setzt; `clearance_keys` (nicht gezeigt)
sind die Signaturschlüssel der Stufe pro Zone (der des aktuellen und der des vorherigen UTC-Tages, jeder
48 h anerkannt — das Dokument trägt Geheimnisse, und ein Knoten speichert es mit `0600` zwischen);
eine Zone, auf der ein Betreiber [den Hebel](/docs/edge#der-hebel) gezogen hat, trägt
`challenge_override` `{mode, until, reason}` mit einem festen `until`, sodass sich Bytes und ETag
des Dokuments genau dann bewegen, wenn der Betreiber handelt, und noch einmal, wenn er abläuft.

#### POST /api/v1/edge/nodes/\{name\}/report

Der beratende Selbstreport eines Knotens — Version, knotenseitiger Dry-Run, das ETag des
Dokuments, das er **gerendert** hat (damit ein Betreiber einen hinterherhinkenden oder
verweigernden Knoten erkennt), Art, Version und Lebendigkeit des Terminators, seine
HTTP/3-Bereitschaft aus der `nginx -V`-Prüfung des Knotens (`terminator.h3 {state, module,
tls_library, early_data_capable, advisory, serving, unsupported, listening}` — `state` ist `ready`,
`no_module`, `node_off` oder `unknown`; `advisory` benennt einen veröffentlichten
QUIC-Sicherheitshinweis, in dessen Bereich der nginx-Kern des Builds fällt, als Hinweis:
Distributionen backporten Fixes, ohne die Version zu bewegen; `serving` listet die Zonen, für die
die aktive Generation über QUIC lauscht, `unsupported` die Zonen, die danach verlangt haben und
hier über TCP ausgeliefert werden; `listening` sagt, ob irgendetwas auf der Box UDP 443 hält,
während QUIC-Listener gerendert sind — die lokale Hälfte von „ist HTTP/3 erreichbar?“, die andere
ist die Firewall, und es fehlt, solange hier keine Zone über QUIC ausgeliefert wird, sowie auf
einer Box ohne `/proc/net/udp`), die aktive
Generation und ihr `nginx -t`-Ergebnis, die Zertifikate, die er hält (nur öffentliche Metadaten,
niemals ein Schlüssel; eine lange Liste wird auf die Body-Grenze von 64 KiB gekürzt, mit einem
`certs_truncated`-Zähler), und ein **Zonenabschnitt**: für jede entscheidende Zone, die die aktive
Generation bedient, das letzte abgeschlossene Zehn-Sekunden-Fenster (`at`, `window_seconds`,
`rps`, `requests`, `decided`, `denied`, `challenged`, `cleared`, `would_deny`, `would_challenge`,
`status_2xx..5xx`, `h3_requests` — die Anfragen, die über HTTP/3 ankamen), der Challenge-Modus der
Zone, so wie der Knoten ihn anwendet, ob die Zone auf
diesem Knoten nur beobachtend ist (`dry_run`) und ob ihre Stufe dort nur eine Vorschau zeigt
(`rung_dry_run`: der `dry_run` des Knotens, der der Zone oder der eigene `challenge_options.dry_run`
der Stufe), eine wirksame zonenweite Challenge (`challenge_active {reason, until, dry_run}` —
`dry_run` sagt, dass die Umstellung dort nur eine Vorschau ist) und die Quellen des Fensters —
zuerst die Kandidaten (eine Challenge oder eine Sperre in der Vorschau), dann die abgewiesenen und
herausgeforderten, dann die aktivsten der übrigen —, jede mit dem Stärksten, was der Knoten ihr
angetan hat (`state`: `denied`, `challenged`, `would-deny`, `would-challenge`, `cleared`, `marked`,
`allow`). Ein Report, der zu groß für die Grenze ist, gibt Details Stück für Stück ab — zuerst die
Quellen, die nichts aussagen (ungezählt: sie stehen nicht in der Kandidatenmenge), dann die Liste
jeder Zone halbiert, dann Zertifikate, dann Zonen — und jeder Schnitt wird gezählt:
`sources_truncated` sind die Kandidaten, die in der Liste fehlen (die, die die eigene Grenze des
Knotens von 20 pro Fenster weggelassen hat, und die, die ein schrumpfender Report abgegeben hat),
`certs_truncated` und `zones_truncated` die verworfenen Einträge. Gespeichert und von
`GET /api/v1/edge/nodes` zurückgegeben. Mit eingeschalteter
[Speicherung](/docs/storage#edge-historie) werden die Fenster und die aussagekräftigen Quellen des
Reports zusätzlich in die Edge-Historie geschrieben, und was sich seit dem vorherigen Report des
Knotens geändert hat, wird zu Ereignissen — nachdem der Report gespeichert ist und ohne dass die
Antwort jemals darauf wartet. Niemals ein Lebendigkeitssignal (das ist der Poll). Ein
unbekanntes `{name}` ist `404`; ein Body über 64 KiB ist `413 report exceeds 64 KiB` — die Grenze,
unter die ein Knoten sich durch Abgeben von Details hält, ein `413` hier ist also ein Client, der
das nicht getan hat, und nichts vom Report wird gelesen; Erfolg ist `204 No Content`.

#### GET /api/v1/edge/nodes

Das Knoteninventar: jeder konfigurierte Edge-Knoten mit seiner Poll-Lebendigkeit, verbunden mit
seinem letzten Report, seinem Platzierungs-Geltungsbereich (`hostgroups` — der effektive
Geltungsbereich, `["global"]` für einen Knoten ohne einen — und `zones_placed`, die Zonen der
Datei, die er abdeckt), dazu `tokens` (die Namen der agent-Tokens, die mit `api.tokens[].node` an
ihn gebunden sind) und
`last_token` (der Name des Tokens, das zuletzt als er gepollt hat — niemals ein Geheimnis); das
Dokument trägt `unbound_agent_tokens`, solange irgendein agent-Token ungebunden ist und es Knoten
gibt, an die es gebunden werden könnte (fehlt sonst) — die Migrationsansicht von
[Ein Agent-Token an seinen Knoten binden](/docs/authentication#ein-agent-token-an-seinen-knoten-binden).
`hostgroups` und `zones_placed` sind immer vorhanden; `tokens`, `last_token` und
`unbound_agent_tokens` werden weggelassen, wenn sie leer sind. Das Dokument trägt außerdem
`nodes_total` und die `stale_after_seconds`, mit denen das Urteil gefällt wird; jeder Knoten trägt
`alive`, `holding` und `last_seen`.

**Eine Sichtung wird gestempelt, wenn ein Poll beginnt, und noch einmal, wenn er endet — solange
ein Poll geparkt ist, hält `last_seen` also dessen Beginn** und ist auf einem völlig gesunden
Knoten bis zu 25 s alt, älter als `stale_after_seconds` in den Standardwerten. `holding` sagt, dass
gerade jetzt ein Poll geparkt ist, und ein darin geparkter Knoten ist lebendig, was auch immer
`last_seen` sagt; `alive` heißt *geparkt, oder innerhalb von `stale_after_seconds` gesehen*, niemals
irgendetwas, was der Knoten in seinem eigenen Report behauptet. Die Folge, mit der Sie planen
sollten: Eine Änderung, die einen Knoten abschneidet — ein entferntes Token, eine verschobene
Bindung —, beendet seinen geparkten Poll mit der Abweisung, die ein erster Poll bekäme, und das
stempelt eine eigene Sichtung; `alive` wird also erst `stale_after_seconds` danach falsch, in den
Standardwerten bis zu etwa 40 s nach der Änderung. Ein Lesezugriff mit `viewer`-Rang,
nur ungebundene Tokens.

#### GET /api/v1/edge/zones/status

Die Zonen über die Flotte hinweg: die Zonenabschnitte der **lebendigen** Knoten zusammengeführt —
pro Zone die Fensterwerte summiert (die Fenster sind nicht ausgerichtet, das Ergebnis ist also eine
flottenweite Rate auf das nächste Fenster genau), der Challenge-Modus der Zone, die Knoten, auf
denen sie nur beobachtend ist (`watch_only`), und die, auf denen ihre Stufe nur eine Vorschau zeigt
(`rung_watch_only` — eine `manual`- oder `auto`-Zone fordert auf den dort nicht genannten Knoten
wirklich heraus), die Knoten mit einer wirksamen zonenweiten Challenge und ob diese jeweils greift
oder nur eine Vorschau ist, der wirksame Hebel (`override`), das HTTP/3 der Zone über die Flotte
hinweg (`h3 {enabled, serving, unsupported, requests}` — `enabled` ist das `tls.h3` der Zonendatei,
so wie das Gehirn es hält, `serving` die lebendigen Knoten, deren aktive Generation für die Zone
über QUIC lauscht, `unsupported` die, auf denen sie danach verlangt hat und über TCP ausgeliefert
wird, `requests` die HTTP/3-Anfragen der Knoten im letzten Fenster, summiert; es fehlt bei einer
Zone, für die niemand h3 spricht oder verlangt. `enabled` erscheint für jede Zone der Datei, die h3
einschaltet — eine Zone mit `mode: none` eingeschlossen —, und `serving`/`unsupported` benennen die
aktiven QUIC-Listener der lebendigen Knoten für die Zone aus deren `terminator.h3`, entscheidende
Zone oder nicht; `requests` kommt aus dem Zonenabschnitt der Reports, und der listet nur
**entscheidende** Zonen), und die **Kandidatenmenge**: die
Vereinigung der Quellen, für die die Knoten eine Challenge oder eine Sperre als Vorschau gezeigt
haben, der stärkere Zustand behalten, die aktivsten zuerst, begrenzt auf 20 pro meldendem Knoten
(`would_be_truncated` zählt den Rest). `partial` sagt, dass die Kandidaten eines Knotens nicht
alle Platz fanden — seine Grenze pro Fenster, oder ein Report, der schrumpfen musste —, die Menge
ist also, was übrig blieb, nicht jeder; `zones_truncated` auf dem
Dokument summiert die Zoneneinträge, die die lebendigen Knoten aus ihren Reports geschnitten
haben — Zonen, die hier fehlen oder zu niedrig gezählt sind; eine flottenweite Zahl, vor dem
Mandantenfilter genommen, sodass ein tenant-bezogener Aufrufer eine Zahl sehen kann, die Zonen
abdeckt, die er nicht sehen kann. Auch jede Zone der Zonendatei hat eine
Zeile — `mode` (ihr `policy.mode`) und `file_challenge` (ihr `policy.challenge`) sind das Wort des
Gehirns, `challenge` das, was die Knoten anwenden —, und `certs` führt das Zertifikat auf, das jeder
lebendige Knoten für die Zone hält (`node`, `not_after`, `issuer` — letzteres fehlt, wenn der Knoten
keines meldet; nur Metadaten, aus den Reports; `certs_truncated` auf dem Dokument summiert die
Einträge, die die Knoten aus ihren Reports geschnitten haben, um in die Größengrenze zu passen —
flottenweit, wie `zones_truncated` —, eine kurze Liste ist also, was übrig blieb, nicht was
gehalten wird). Jede Zone der Datei trägt außerdem
ihre `placement {hostgroup, nodes, alive}` — die Gruppe, in die die Datei sie steckt, die
konfigurierten Knoten, deren Geltungsbereich sie abdeckt, und welche davon lebendig sind — und
`unserved: true`, wenn sie Knoten hat, aber keiner davon lebendig ist (eine Zone, die kein
Geltungsbereich eines Knotens abdeckt, zeigt `nodes: []` und ist stattdessen eine
`-check-config`-Warnung). Die Behauptungen eines Knotens über eine Zone außerhalb seines
Geltungsbereichs werden in seinem Report gespeichert und weder hier zusammengeführt noch in die
[Edge-Historie](#get-apiv1edgehistory) geschrieben
(`kapkan_edge_history_dropped_total{reason="outside_scope"}`). `placement.hostgroup` ist nur für
ungebundene Tokens vorhanden: Ein Mandant sieht die Namen der Knoten, auf denen seine Zone bedient
wird, nicht, wie der Betreiber sie gruppiert. Ein Lesezugriff mit `viewer`-Rang. Ein ungebundenes
Token sieht jede Zone, beschriftete mit ihrem `tenant` (der Schlüssel fehlt bei einer unbeschrifteten
Zone); ein [tenant-bezogenes](/docs/multi-tenancy) Token genau seine eigenen Zonen — kein Hostname
eines anderen Mandanten in irgendeiner Zeile, Kandidatenmenge oder HTTP/3-Liste und kein
`tenant`-Feld. Knotennamen sind für einen Mandanten sichtbar; das Inventar nicht. Das ist das
*wer herausgefordert worden wäre* der
Edge-Spezifikation: Lesen Sie es, bevor die Stufe einer Zone in den Echtbetrieb geht.

```json
{
  "nodes_alive": 2,
  "nodes_reporting": 2,
  "zones": [
    {
      "zone": "shop.example.com",
      "tenant": "shop",
      "mode": "decide",
      "file_challenge": "auto",
      "nodes": 2,
      "challenge": "auto",
      "rps": 812.4,
      "requests": 8124, "decided": 8124, "would_deny": 37, "would_challenge": 1240,
      "watch_only": ["edge-2"],
      "rung_watch_only": ["edge-2"],
      "challenge_active": [
        { "node": "edge-1", "reason": "zone-rps", "until": "2026-09-06T12:05:00Z", "dry_run": true }
      ],
      "would_be": [
        { "source": "203.0.113.7", "state": "would-deny", "requests": 1210, "nodes": ["edge-1", "edge-2"] },
        { "source": "198.51.100.23", "state": "would-challenge", "requests": 640, "nodes": ["edge-1"] }
      ],
      "certs": [
        { "node": "edge-1", "not_after": "2026-11-20T09:12:00Z", "issuer": "R11" },
        { "node": "edge-2", "not_after": "2026-11-20T09:12:00Z", "issuer": "R11" }
      ]
    }
  ]
}
```

Eine Zone, die noch kein lebendiger Knoten gemeldet hat — eine in `policy.mode: none` oder eine,
deren Knoten nicht laufen —, hat trotzdem ihre Zeile: `nodes: 0`, `rps: 0`, ihr `mode` und ihr
`file_challenge`, und `override`, wenn ein Hebel gesetzt ist. Auch ein Hebel auf einer Zone, die ein
Reload inzwischen aus der Datei entfernt hat, behält eine Zeile, ohne `mode` (nur für ungebundene
Aufrufer — es ist ihre Sache, ihn zu löschen). Die Anfragezähler (`requests`,
`decided`, `denied`, `challenged`, `cleared`, `would_deny`, `would_challenge`) werden weggelassen,
wenn sie null sind; `nodes` und `rps` sind immer vorhanden.

#### GET /api/v1/edge/history

Die [Edge-Historie](/docs/storage#edge-historie) einer Zone: die Zehn-Sekunden-Fenster der Knoten,
summiert in `step`-Sekunden-Buckets zwischen `from` und `to` (RFC 3339; standardmäßig die letzte
Stunde; höchstens 31 Tage; `step` ist standardmäßig 60 s, wird angehoben, damit ein Zeitraum
höchstens 5 000 Buckets fasst, und beträgt höchstens 86 400 s — einen Tag) — `{available, zone,
node, step_seconds, points: [{ts, nodes, window_seconds, requests, decided, denied, challenged,
cleared, would_deny, would_challenge, status_2xx, status_3xx, status_4xx, status_5xx,
h3_requests}]}`. `nodes` zählt die verschiedenen Knoten, die im Bucket berichtet haben;
`step_seconds` ist der tatsächlich angewendete Schritt; `zone` und `node` geben die Anfrage wieder,
`node` nur, wenn der Filter gesetzt war; die Rate leiten Sie als `requests / window_seconds` ab und
den HTTP/3-Anteil als `h3_requests / requests`. Diese Regeln für Zeitraum und Schritt teilt sich
der Endpunkt mit `/api/v1/traffic` und `/api/v1/audit` — eine Implementierung, die drei antworten
auf einen fehlerhaften Zeitraum also mit derselben Meldung. `zone` ist erforderlich, wird wie die Namen der
Datei in Kleinbuchstaben gefaltet und muss in der Zonendatei stehen (sonst `404 unknown zone`);
`node=<name>` grenzt auf einen konfigurierten Knoten ein (`404 unknown edge node`). `viewer`-Rang.
Ein [tenant-bezogenes](/docs/multi-tenancy) Token liest seine eigenen Zonen; jede andere Zone — die
eines anderen Mandanten, eine unbeschriftete, eine aus der Datei verschwundene oder eine nicht
existierende — ist ein einziges einheitliches `403` (`zone is outside your tenant`), gezählt in
`kapkan_api_zone_refused_total{route="edge_history"}` und einmal pro Minute und Token protokolliert,
und `node=` gibt es nur für ungebundene Tokens (ein Mandant bekommt `nodes` als Anzahl, nie die
Historie eines einzelnen Knotens). Speicherung aus: `{available: false, points: []}`, niemals ein
Fehler — die Zone wird gar nicht erst angesehen, jedes Token bekommt also für jede Zone diese
Antwort, und nichts wird gezählt oder protokolliert; eine fehlgeschlagene Abfrage ist `502`.

#### GET /api/v1/edge/history/sources

Die aussagekräftigen Quellen der Zone über den Zeitraum — das *wer herausgefordert worden wäre* der
Edge-Spezifikation, über eine Zeitspanne statt über ein Zehn-Sekunden-Fenster gefragt:
`{available, zone, state, sources: [{source, state, requests, windows, nodes, first_seen,
last_seen}]}`, die aktivsten zuerst, höchstens 1 001 Zeilen. Der `state` jeder Quelle ist das
Stärkste, was irgendein Knoten ihr über den Zeitraum angetan hat (`denied` vor `challenged` vor
`would-deny` vor `would-challenge`); `state=` filtert auf eines dieser vier (`400` für alles andere
— Besucher werden nie gespeichert), und der `state` auf oberster Ebene gibt diesen Filter wieder, er
fehlt ohne einen. Dieselben Regeln für `zone`, Zeitraum und Scope wie bei der Historie oben.

#### GET /api/v1/edge/events

Die Übergänge, die das Gehirn gesehen hat, neueste zuerst, höchstens 1 001: `{available, events:
[{event_time, node, zone, kind, detail}]}`, mit optionalen Filtern `node=`, `zone=` und `kind=` —
`kind` ist eines von `node_alive`, `node_lost`, `version`, `dry_run`, `document_rendered`,
`generation_installed`, `generation_refused`, `terminator_alive`, `h3_state`, `cert_issued`,
`cert_renewed`, `cert_gone`, `challenge_started`, `challenge_ended`, `clock_skew`,
`report_truncated` (sonst `400`). `viewer`-Rang, **nur ungebundene Tokens**: Die Ereignisse benennen
Knoten und die Veränderungen der Flotte. Dieselben Zeitraumregeln; ist die Speicherung aus, lautet
die Antwort `{available: false, events: []}`.

Jede Art ist ein **Übergang**, ein Zustand, den das Gehirn immer nur einmal gesehen hat, steht also
nicht hier drin. Der erste Report nach einem Start des Gehirns ist eine stille Grundlinie, und die
Präsenz ebenso: Ein Knoten wird bei seinem ersten Poll auf die Grundlinie gesetzt — oder, wenn das
Gehirn nie von ihm hört, als verloren, sobald `stale_after_seconds` seit dem Start des
Präsenz-Tickers vergangen sind, ohne dass `node_lost` geschrieben wird. Ein Knoten, der über einen
Neustart des Gehirns hinweg ausgefallen war, hat deshalb kein Ereignis, bis er zurückkommt, und
sein erstes ist `node_alive`. Was ein Knoten *jetzt* ist, lesen Sie im Inventar, nicht in dieser
Liste.

#### POST /api/v1/edge/nodes/\{name\}/acme/slot und …/acme/challenges

Der **Ausstellungskoordinator**, beratend und im Speicher. Ein Knoten fragt vor dem Bestellen
eines Zertifikats einen Slot pro Zone an (`{"zone": "…"}` → `{"granted": true, "expires_at": …}`
oder `{"granted": false, "holder": "…", "retry_after_seconds": …}`; `{"release": true}` gibt ihn
zurück), damit eine Flotte nicht an einem einzigen Nachmittag das Duplicate-Certificate-Limit
einer CA aufbraucht; er wartet höchstens 15 Minuten und bestellt dann trotzdem. Ein Knoten, der
den Slot hält, veröffentlicht seine ausstehende HTTP-01-Challenge
(`{"zone", "token", "key_authorization"}`), und das Gehirn verteilt sie zehn Minuten lang im
Dokument jedes Knotens, der die Zone bedient, sodass jeder von ihnen sie beantwortet — die
Validierung der CA kann auf jedem Knoten hinter der gemeinsamen Adresse der Zone landen. Eine
aktive Challenge wird niemals durch
eine andere Key Authorization überschrieben (`409`), ein Knoten darf 16 aktive Challenges halten,
und jeder Aufruf wird mit Knoten, Zone und dem Präfix des Tokens protokolliert: Ein agent-Token
ist ein zertifikatsausstellendes Credential — rotieren Sie es bei jeder Kompromittierung eines
Knotens. Beide nehmen nur die Zonen, die der
[Platzierungs-Geltungsbereich](/docs/edge#zonen-auf-knoten-verteilen) des Knotens abdeckt: Eine
Zone, die der Knoten nicht bedient, ist für ihn `404 unknown zone`, Byte für Byte die Antwort, die
eine nicht existierende Zone bekommt (ein `{"release": true}` ist die Ausnahme: Es berührt nur die
eigene Freigabe des Aufrufers, ist idempotent und wird für jeden Zonennamen mit `204` beantwortet,
bedient oder nicht).

#### POST /api/v1/edge/zones/\{name\}/challenge und DELETE

[Der Hebel](/docs/edge#der-hebel): Setzt den Challenge-Modus einer Zone für eine begrenzte Zeit,
was auch immer die Zonendatei sagt. `operator`-Rang. Ein
[tenant-bezogener](/docs/multi-tenancy) Operator darf ihn nur auf seinen eigenen Zonen ziehen; jede
andere Zone — die eines anderen Mandanten, eine unbeschriftete oder eine aus der Datei
verschwundene — ist für ihn `404 unknown zone`, dieselbe Antwort, die ein unbekannter Name bekommt,
entschieden, bevor der Body gelesen wird. Der Aufrufer erfährt nichts weiter; der Betreiber schon:
Jede solche Abweisung zählt in `kapkan_api_zone_refused_total{route="edge_lever"}` und wird einmal
pro Minute und Token protokolliert, und es wird keine Audit-Zeile geschrieben.

```json
{ "mode": "manual", "ttl_seconds": 1800, "reason": "credential stuffing from residential proxies" }
```

`mode` ist `manual`, `auto` oder `off` (`off` löscht die Übersteuerung, wie `DELETE`);
`ttl_seconds` ist `60..86400` und erforderlich, sofern `mode` nicht `off` ist; `reason` ist für das
Log, die Audit-Zeile und die Antworten der API — `override.reason` in
`GET /api/v1/edge/zones/status` und die eigene Antwort dieses Endpunkts (höchstens 200 Zeichen).
Eine unbekannte Zone ist `404`; eine
Zone in `policy.mode: none` ist `409` — dort fordert nichts heraus. Die Übersteuerung reist als
`challenge_override` im Zonendokument (geparkte Polls werden sofort geweckt), und jeder Knoten, der
die Zone bedient, wendet den effektiven Modus auf seinem schnellen Pfad an, sodass sie zu `until`
endet, mit oder ohne Gehirn. Auditiert als `edge_challenge` `set` / `cleared`. Beide Methoden antworten `200` mit
der Stufe, wie sie jetzt steht, und wo der Hebel greift:

```json
{
  "zone": "shop.example.com",
  "mode": "manual",
  "until": "2026-09-06T12:30:00Z",
  "reason": "credential stuffing from residential proxies",
  "file_mode": "auto",
  "zone_watch_only": false,
  "rung_watch_only": false,
  "nodes": [
    { "name": "edge-1", "alive": true, "dry_run": false },
    { "name": "edge-2", "alive": false }
  ]
}
```

`file_mode` ist `policy.challenge`, wie die Datei es hat; `zone_watch_only` und `rung_watch_only`
sind `policy.dry_run` und `challenge_options.dry_run` der Zone — bei einem von beiden zeigt der
Hebel auf jedem Knoten nur eine Vorschau, statt zu greifen; `nodes[]` führt die Knoten auf, auf
denen die Zone [platziert](/docs/edge#zonen-auf-knoten-verteilen) ist — jeden konfigurierten Knoten
bei einer Zone, die ein Reload inzwischen aus der Datei entfernt hat —, mit seiner Lebendigkeit und
seinem gemeldeten `dry_run` (fehlt, bis er gemeldet hat) —
ein Knoten, der nur zählt, muss gesehen werden, bevor man dem Hebel vertraut. `mode`, `until` und
`reason` fehlen, wenn die Zone ihrer Datei folgt, und `file_mode` ist leer für eine Zone, die ein
Reload inzwischen aus der Datei entfernt hat — ein solcher Hebel kann noch gelöscht, aber nicht
mehr gesetzt werden. Der Hebel wird im Speicher des Gehirns gehalten, wie der
Ausstellungskoordinator; der eigene `dry_run` des Gehirns hält ihn nicht zurück. Ein Knoten mit
einer Version von vor dem Hebel kennt `challenge_override` nicht und folgt seiner Datei, während
`nodes[]` ihn trotzdem aufführt: Aktualisieren Sie zuerst die Knoten.

### GET /metrics

Stellt Prometheus-Metriken im standardmäßigen Text-Expositionsformat bereit. Dieser Endpunkt liegt
nicht unter `/api/v1` und wird ohne das Bearer-Token bereitgestellt, damit ein Scraper ihn erreichen
kann. Die vollständige Metrikliste finden Sie unter [Metriken](/docs/metrics).

### GET /healthz

Eine Liveness-/Readiness-Probe, nicht unter `/api/v1` und **ohne** Bearer-Token bereitgestellt (sie
gibt nichts preis), damit ein Supervisor oder das Upgrade-Skript [`update.sh`](/docs/upgrading)
bestätigen kann, dass der Daemon nach einem Neustart läuft. Sie liefert `503 starting`, bis jede
Komponente gestartet ist, danach `200 ok`. Da der API-Listener erst zu akzeptieren beginnt, sobald
der Daemon gestartet ist, bedeutet jedes `200` hier, dass die Konfiguration geparst wurde, die
Komponenten laufen und Kapkan bereitsteht.

```sh
curl -fsS localhost:8080/healthz   # exits non-zero (503) until ready, then prints "ok"
```
