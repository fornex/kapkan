# Authentifizierung

Standardmäßig sind die Kapkan-API und das Dashboard **nicht authentifiziert**. Das ist nur
deshalb sicher, weil der Standardwert von `api.listen` an `127.0.0.1` bindet — der Listener
ist also nur vom Host selbst aus erreichbar, sodass kein Token erforderlich ist, um den
Status abzurufen, Angriffe aufzulisten oder manuelle Sperren auszulösen. In dem Moment, in
dem Sie den Listener an eine routbare Adresse binden, verschwindet dieser Schutz.

<Callout type="danger" title="Setzen Sie ein Token, bevor Sie den Listener verfügbar machen">
Wenn Sie `api.listen` auf etwas anderes als localhost ändern — zum Beispiel `0.0.0.0:8080`
oder eine bestimmte Schnittstelle — konfigurieren Sie zuerst ein Token. Ein nicht
authentifizierter Listener auf einer routbaren Adresse erlaubt es jedem, die [API](/docs/api)
zu erreichen, einschließlich der Endpunkte zum manuellen Sperren und Entsperren.
</Callout>

## Ein Token setzen

Die Kurzform ist ein einzelnes Operator-Token. Fügen Sie `token_env` zum `api`-Block hinzu —
es benennt die Umgebungsvariable, die das Token enthält; das Geheimnis selbst wird pro
Anfrage aus der Prozessumgebung gelesen, niemals aus der Konfigurationsdatei:

```yaml
api:
  listen: "0.0.0.0:8080"
  token_env: "KAPKAN_API_TOKEN"   # token read from this env var, never the file
```

Stellen Sie den Wert anschließend außerhalb der Konfiguration bereit, zum Beispiel über die
Umgebung Ihres Service-Managers oder eine Secrets-Datei:

```sh
export KAPKAN_API_TOKEN="$(openssl rand -hex 32)"
./kapkan -config /etc/kapkan/config.yaml
```

Das Token in einer Umgebungsvariablen statt in der YAML aufzubewahren bedeutet, dass die
Konfiguration sicher in Git committet und zusammen mit dem Rest Ihrer
[Konfiguration](/docs/configuration) verglichen werden kann.

Dieses eine Token ist alles, was die meisten Deployments brauchen — der Rest dieser Seite
(Rollen, Mandanten) ist optional und kann warten.

## Rollen

Für rollenbasierten Zugriff verwenden Sie `tokens` anstelle von `token_env` — eine Liste, in
der jeder Eintrag die Umgebungsvariable benennt, die sein Geheimnis enthält, sowie eine Rolle:

```yaml
api:
  listen: "0.0.0.0:8080"
  tokens:
    - { name: dashboard,  token_env: "KAPKAN_API_RO", role: viewer }
    - { name: automation, token_env: "KAPKAN_API_RW", role: operator }
```

`name`, `token_env` und `role` sind für jeden Eintrag erforderlich; `role` muss exakt
`viewer`, `operator` oder `agent` sein. Ein fehlender oder falsch geschriebener Wert ist beim Start
ein harter Validierungsfehler, kein stiller Default.

| Rolle | Darf |
| --- | --- |
| `viewer` | Nur lesen: Status, Angriffe, Hosts, Sperren, Metriken. |
| `operator` | Alles, was ein viewer darf, plus manuelles Sperren/Entsperren, [Source-Blocks](/docs/api#der-source-block-kanal) und Neuladen der Konfiguration (das Neuladen ist nur für Admins — siehe unten). |
| `agent` | Das Credential eines Knotens — eines [Scrub-Knotens](/docs/scrubbing#verwaltete-scrubbing-knoten) oder eines [Edge-Knotens](/docs/edge): die Regel- und Zonen-Polls, sein eigener Report und die ACME-Koordination am Edge, und **sonst nichts**. Binden Sie es mit `node` an seinen Knoten (siehe unten). |

Es gibt keine separate `admin`-Rolle zum Zuweisen — ein *Admin* ist schlicht ein Operator-Token
ohne gesetzten `tenant`. Die Rollenwerte, die die Engine akzeptiert, sind `viewer`, `operator` und
`agent`; die Unterscheidung admin/eingegrenzt ist die Achse [Mandantenfähigkeit](/docs/multi-tenancy),
die unten behandelt wird.

<Callout type="info" title="Die agent-Rolle ist kein abgeschwächter viewer">
`agent` steht **außerhalb** der Berechtigungsleiter, unterhalb von `viewer`: Es gewährt genau die
Knoten-Routen (die Regel- und Zonen-Polls, die beiden Selbstreports, den ACME-Slot und das
Veröffentlichen von Challenges am Edge) und wird für jeden anderen Endpunkt verweigert,
einschließlich des Source-Block-Kanals, der Kernel-Regeln installiert und deshalb operator-only
bleibt — ein kompromittiertes agent-Token, das auf einer entfernten Box lebt, darf nicht zu einem
Alles-lesen-Schlüssel werden. Es kann außerdem nicht
tenant-bezogen sein: Der Regel-Feed gilt deploymentweit, sodass ein `tenant` auf einem agent-Token
ein harter Validierungsfehler ist. Geben Sie jedem Knoten sein eigenes agent-Token, niemals ein
Operator-Token, und **binden Sie es an den Knoten** (siehe unten).
</Callout>

### Ein Agent-Token an seinen Knoten binden

Ein agent-Token trägt `node`: den Namen genau eines `edge.nodes[]`- oder
`scrubbing.nodes[]`-Eintrags. Das Gehirn weist dieses Token dann auf jeder Route ab, auf der ein
Knoten sich selbst benennt — die Polls (`?node=<name>`), die Selbstreports, den ACME-Slot und das
Veröffentlichen von Challenges —, wenn der präsentierte Name der eines anderen Knotens ist, und es
weist **ab, bevor** es irgendetwas mit dem Namen tut: keine Präsenz gestempelt, kein Report
gespeichert, kein Slot gewährt, keine Key-Authorization veröffentlicht. Die Abweisung ist ein
einheitliches `403`, das den gebundenen Knoten nicht nennt, eine Warnung pro Minute und Token im
Log des Gehirns und ein Zähler in `kapkan_api_node_binding_refused_total{route}`. Es wird keine
Zeile im [Audit-Log](/docs/audit) geschrieben: Der Audit-Trail ordnet zu, was ein Operator geändert
hat, und eine abgewiesene Maschine hat nichts geändert — die Log-Zeile und der Zähler sind der Ort,
an dem ein falsch konfiguriertes oder gestohlenes Knoten-Token auftaucht. Ein an einen Knoten
gebundenes Token, das ohne `?node=` pollt, wird ebenfalls abgewiesen: Seine Bindung sagt, welcher
Knoten es ist.

```yaml
api:
  tokens:
    - { name: edge-fra1, token_env: KAPKAN_EDGE_FRA1, role: agent, node: edge-fra1 }
    - { name: edge-nyc1, token_env: KAPKAN_EDGE_NYC1, role: agent, node: edge-nyc1 }
    - { name: scrub-1,   token_env: KAPKAN_SCRUB_1,   role: agent, node: fra1 }
```

Regeln: `node` ist nur auf `agent`-Tokens erlaubt; der Name muss in genau einer der beiden
Knotenlisten existieren (ein Name, der in beiden steht, wird als mehrdeutig abgelehnt — die beiden
Kanäle sind unterschiedliche Vertrauensbereiche); mehrere Tokens dürfen denselben Knoten binden, und
genau so wird ein Token ohne Lücke rotiert.

Ohne `node` ist ein agent-Token ein **flottenweites Credential**: Es darf als jeder Knoten pollen
und als jeder Knoten berichten — der Grund, warum ein gestohlenes Token früher bedeutete, es für die
ganze Flotte zu rotieren. Was `node` ändert, sind Identitätsübernahme und Rotationsradius; was die
Menge der Zonen begrenzt, für die ein gestohlenes gebundenes Token Zertifikate ausstellen kann, ist
der [Platzierungs-Geltungsbereich](/docs/edge#zonen-auf-knoten-verteilen) des Knotens: Als sein
eigener Knoten handelnd kann es den Ausstellungs-Slot nur für die Zonen nehmen und eine
ACME-Key-Authorization nur für die Zonen veröffentlichen, die dieser Geltungsbereich abdeckt — in
einer Flotte ohne Geltungsbereiche für jede Zone. Behandeln Sie die Kompromittierung eines Knotens
als Zertifikats-Exposition für die Zonen seines Knotens und rotieren Sie das Token dieses Knotens.
Ein ungebundenes Token funktioniert genau wie zuvor weiter, sodass eine Flotte Knoten für Knoten
migriert — es sei denn, irgendein Knoten hat einen
[Platzierungs-Geltungsbereich](/docs/edge#zonen-auf-knoten-verteilen)
(`edge.nodes[].hostgroups`): Dann muss jedes `agent`-Token ein `node` tragen, ein harter
Validierungsfehler, denn ein Geltungsbereich, der gegen ein geteiltes Token durchgesetzt wird, ist
ein Versprechen, das nichts hält — und es wird benannt, bis es gebunden ist: von
`kapkan -check-config` (als WARNING), im Log des Daemons beim Start und bei jedem Reload und im
Edge-Inventar (`unbound_agent_tokens`; pro Knoten listet `tokens` die Namen der gebundenen Tokens
und `last_token` das Token, das zuletzt als er gepollt hat — beobachten Sie, wie es während einer
Migration umspringt). Ein ungebundenes agent-Token auch auf Flotten ohne Geltungsbereiche zu einem
Fehler zu machen, ist für ein MAJOR-Release vorgesehen.

Präsenz wird nur von agent-Tokens gestempelt: Ein Operator, der mit `?node=X` pollt, erhält das
Dokument von X als **Vorschau** und lässt X nicht lebendig erscheinen.

**Geben Sie einem Migrationsschritt Zeit, sichtbar zu werden.** Eine Token-Änderung trifft auf einen
bereits geparkten Poll: Das Reload beendet ihn mit der Antwort, die ein erster Poll jetzt bekäme
(`401` für ein verschwundenes Token, `403` für eines, dessen Bindung verschoben wurde), und der
Knoten verbindet sich mit dem neu, was er jetzt hat. Das *Inventar* ist langsamer, denn eine
Sichtung wird gestempelt, wenn ein Poll beginnt, und noch einmal, wenn er endet — die Abweisung
eingeschlossen —, sodass ein Knoten, den Sie gerade abgeschnitten haben, für den Rest seines Holds
(bis zu 25 s) als `alive` gelesen wird und danach noch `edge.stale_after_seconds` obendrauf, in den
Standardwerten also rund 40 s. Warten Sie das ab, bevor Sie das Umspringen von `last_token` lesen,
sonst sehen Sie den Zustand vor Ihrer Änderung.

`token_env` und `tokens` schließen sich **gegenseitig aus** — `token_env` ist genau ein
Operator-Token. Eine Anfrage wird gegen jedes konfigurierte Token abgeglichen (in konstanter
Zeit); es gilt die höchste passende Rolle. Ein Lesezugriff mit einem viewer-Token
funktioniert; eine Mutation mit einem viewer-Token wird mit `403 Forbidden` abgelehnt; eine
Anfrage ohne gültiges Token ergibt `401 Unauthorized`. Eine leere oder nicht gesetzte
Umgebungsvariable passt niemals, sodass ein fehlkonfiguriertes Geheimnis fail-closed ist.

Geben Sie jedem Token ein eindeutiges Geheimnis — wenn ein Geheimniswert für zwei Tokens mit
unterschiedlichen Rollen, Mandanten oder Knoten-Bindungen konfiguriert ist (ein ungebundener und
ein gebundener Eintrag eingeschlossen), wird die Anfrage abgelehnt (`401 Unauthorized`), statt zu
raten, welches Sie gemeint haben. Der Daemon protokolliert in diesem Fall `ambiguous API token`.

Der Geheimnis-*Wert* eines Tokens wird bei jeder Anfrage aus der Umgebung gelesen, sodass sein
Rotieren bereits bei der nächsten Anfrage wirksam wird. Das Hinzufügen oder Entfernen von Token-*Einträgen*
in der YAML ändert den Token-Satz, was beim nächsten [Neuladen der Konfiguration](/docs/api) wirksam
wird. Keines von beidem erfordert einen Neustart.

Ein Token kann außerdem einen optionalen `tenant` tragen, der es auf die Daten eines einzelnen
Kunden eingrenzt. Das ist die Funktion [Mandantenfähigkeit](/docs/multi-tenancy), aufgesetzt
auf die hier beschriebenen Rollen.

Manuelles Sperren/Entsperren erfordert nur ein Operator-Token, aber `POST /api/v1/config/reload`
ist zusätzlich [nur für Admins](/docs/multi-tenancy): Das Token muss ungebunden sein (keinen
`tenant` tragen), denn ein Neuladen schreibt die Policy jedes Mandanten sowie den Token-Satz
selbst neu. Ein mandantengebundenes Operator-Token wird mit `403 Forbidden` abgelehnt —
`config reload is restricted to unscoped (admin) tokens`.

<Callout type="info" title="Der Token-Name ist die Operator-Identität">
Der `name` jedes Tokens ist das, was das [Audit-Log](/docs/audit) als `operator` für jede
Sperre, Entsperrung und jedes Neuladen der Konfiguration aufzeichnet, die es auslöst — geben
Sie Tokens also aussagekräftige Namen. Bei einer offenen (token-losen) API gibt es kein
Principal, dem etwas zugeordnet werden könnte, und der Audit-`operator` ist leer.
</Callout>

## Was es schützt

Ist ein Token gesetzt, muss jede `/api/v1`-Anfrage es in einem `Authorization`-Header gemäß
dem Bearer-Schema mitführen:

```http
GET /api/v1/status HTTP/1.1
Host: kapkan.internal:8080
Authorization: Bearer <token>
```

Das übermittelte Token wird in **konstanter Zeit** mit dem konfigurierten verglichen, sodass
der Vergleich selbst das Geheimnis nicht über das Zeitverhalten preisgibt.

Was offen bleibt und was geschützt wird:

| Pfad | Bei gesetztem Token |
| --- | --- |
| `GET /api/v1/*` | Erfordert ein **viewer**- (oder operator-) Token |
| `POST /api/v1/*` | Erfordert ein **operator**-Token **und** einen JSON-Content-Type |
| `GET /metrics` | Offen — der Prometheus-Scrape bleibt nicht authentifiziert |
| Statische UI-Shell (`/`) | Offen — die dahinterliegenden Daten jedoch nicht |

Die statische UI-Shell des Dashboards bleibt erreichbar, damit ein Browser sie laden kann,
aber sie verfügt über keine eigenen Daten: Sie fragt `/api/v1` ab, fordert daher zur Eingabe
des Tokens auf und bewahrt es im `sessionStorage` auf. `/metrics` bleibt ebenso offen für
Ihren Prometheus-Scraper. Auf der Seite zum [Dashboard](/docs/dashboard) erfahren Sie, wie
die UI die Token-Abfrage handhabt.

## CSRF

POST-Endpunkte erfordern zusätzlich zum Token `Content-Type: application/json`. Ein Browser,
der eine seitenübergreifende Anfrage ausführt, kann ohne einen CORS-Preflight keinen
benutzerdefinierten `Authorization`-Header setzen, und ein einfacher Formular-Post kann den
JSON-Content-Type nicht senden. Indem beides erforderlich ist — das Token in einem
Anfrage-Header und der JSON-Content-Type — wird Cross-Site Request Forgery gegen die
Endpunkte zum manuellen Sperren, Entsperren und Neuladen der Konfiguration blockiert.

<Callout type="info" title="Rollen und Mandanten sind verschiedene Achsen">
Eine Rolle grenzt ein, was ein Token *tun* darf (lesen vs. mutieren). Der optionale `tenant`
eines Tokens grenzt ein, welche Daten es *sehen und anfassen* darf. Sie ergänzen sich: ein
viewer kann ungebunden sein (alle Mandanten) oder auf einen eingegrenzt. Siehe
[Mandantenfähigkeit](/docs/multi-tenancy).
</Callout>
