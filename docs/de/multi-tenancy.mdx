# Mandantenfähigkeit

Eine einzelne Kapkan-Instanz kann viele Kunden bedienen (Anwendungsfall eines Managed Service
Provider (MSP) oder Internet Data Center (IDC)) und jedem ein Token geben, das **nur dessen
eigene** Angriffe, Bans und Hosts sieht und verändert. Ein Mandant (tenant) ist lediglich ein
optionales Label an einer [Hostgruppe](/docs/hostgroups) — oder, auf einem Edge-Gehirn, an einer
[Zone](/docs/zones) — es gibt kein neues Top-Level-Objekt, keine separate Mandantenregistrierung,
und der heiße Erkennungspfad bleibt unberührt.

```yaml
tenant: "house"                 # optional: label the global/fallback group

hostgroups:
  - name: custA-web
    tenant: "customerA"         # this group belongs to customerA
    networks: ["203.0.113.0/26"]
  - name: custA-dns
    tenant: "customerA"         # a tenant can span several groups
    networks: ["203.0.113.64/26"]
  - name: custB
    tenant: "customerB"
    networks: ["198.51.100.0/24"]
  - name: shared-infra          # no tenant → visible only to admin tokens
    networks: ["192.0.2.0/24"]

api:
  tokens:
    - { name: admin,    token_env: KAPKAN_ADMIN, role: operator }
    - { name: a-portal, token_env: KAPKAN_A,     role: viewer,   tenant: "customerA" }
    - { name: b-ops,    token_env: KAPKAN_B,     role: operator, tenant: "customerB" }
```

## So richten Sie es ein

Drei Schritte entsprechen direkt dem YAML oben:

1. **Markieren Sie die Hostgruppe(n) jedes Kunden** mit `tenant: "customerA"` (dasselbe Label kann sich über mehrere Gruppen wiederholen — etwa die Web- und DNS-Gruppe eines Kunden), oder seine [Edge-Zonen](/docs/zones) mit `zones[].tenant` für einen Kunden mit Hostnamen und ohne Präfixe.
2. **Fügen Sie ein API-Token** unter `api.tokens` hinzu, das denselben `tenant:` plus eine `role:` trägt — `viewer` ist schreibgeschützt, `operator` kann zusätzlich bannen/entbannen.
3. **Übergeben Sie dem Kunden dieses Token.** Er sieht und verändert nun nur seine eigenen Präfixe; alles andere (andere Mandanten, unmarkierte Gruppen) ist für ihn unsichtbar.

Das ist der gesamte Workflow. Der Rest dieser Seite erklärt, wie Eigentümerschaft aufgelöst wird und was ein gebundenes Token genau tun und nicht tun kann.

## Das Modell

„Welcher Mandant besitzt diese IP" wird durch **denselben** Longest-Prefix-Hostgruppen-Lookup
beantwortet, den Engine und Mitigator bereits zur Zuordnung von Traffic verwenden — wenn sich
Präfixe überlappen, gewinnt die spezifischste passende Hostgruppe
([Longest-Prefix-Match](/docs/glossary)). Ein Mandant kann sich über mehrere Hostgruppen
erstrecken (ein Kunde mit getrennten Web- und DNS-Gruppen). Eine [Edge-Zone](/docs/zones) trägt
dasselbe Label (`zones[].tenant`), sodass ein Kunde Hostnamen und überhaupt keine Präfixe besitzen
kann.

Jede IP, die außerhalb jeder benannten Hostgruppe liegt, wird von der impliziten
**globalen/Fallback-Gruppe** (dem Catch-all) behandelt. Diese globale Gruppe kann ein
Top-Level-`tenant` tragen, sodass dieser Catch-all-Traffic einem „House"-Mandanten zugeordnet
wird; eine benannte Hostgruppe **ohne** `tenant` ist unbeschriftet und nur für Admin-Tokens
sichtbar.

Ein Mandanten-Label ist **keine** Einheit der Mitigation-Policy — Schwellenwerte,
BGP-Attribute und Eskalation bleiben pro Hostgruppe. Es ist rein ein Eigentümerschafts-Tag, das
zum Eingrenzen der API dient.

## Token-Scope

Ein [API-Token](/docs/authentication) erhält einen optionalen `tenant`, der auf seiner Rolle
aufbaut: ein `viewer` kann lesen, aber nichts ändern; ein `operator` kann zusätzlich
bannen/entbannen.

| Token | Sieht | Darf verändern |
| --- | --- | --- |
| ungebunden (kein `tenant`) | alle Mandanten (Admin) | alles, was seine Rolle erlaubt (ein Viewer liest alle Mandanten; ein Operator darf in allen Mandanten bannen/entbannen) |
| `tenant: customerA`, `role: viewer` | nur customerA | nichts |
| `tenant: customerA`, `role: operator` | nur customerA | nur customerA |

Ein ungebundenes Token ist ein Admin — das standardmäßige, vollständig abwärtskompatible
Verhalten. Ein Token, das an einen Mandanten gebunden ist, den keine Hostgruppe — und, bei
vorhandenem `edge`-Block, keine [Zone](/docs/zones) — nutzt, wird beim Laden der Konfiguration
abgelehnt (ein Tippfehler würde sonst stillschweigend nichts sehen). Mit einem Edge-Block braucht
diese Prüfung beide Dateien, sie läuft also, wenn der Daemon sie lädt; der Validator im Browser
sieht nur die `kapkan.yaml`, und `kapkan -check-config` auf dem Host ist die eigentliche Prüfung.

<Callout type="info" title="Die agent-Rolle liegt außerhalb dieser Achse">
Das `agent`-Token eines [Scrub-Knotens](/docs/scrubbing#verwaltete-scrubbing-knoten) ist **kein**
abgeschwächter viewer mit einem Mandanten — es steht vollständig außerhalb der Rollenleiter und
**kann nicht** tenant-bezogen sein (die Kombination ist ein Konfigurationsfehler). Der [Regel-Feed
und das Knoteninventar](/docs/api) umspannen bewusst jeden Mandanten: Ein Scrub-Knoten filtert für
das gesamte Deployment, sodass die tenant-Begrenzung pro Knoten eine [Flotten](/docs/scrubbing)-
und keine Token-Angelegenheit ist. Behandeln Sie ein agent-Token als deploymentweit und halten Sie
es von Boxen fern, die kundenbezogene Daten vorhalten.
</Callout>

## Durchsetzung

Das Scoping ist **default-deny: ein gebundenes Token sieht immer nur seinen eigenen Mandanten.**
Der Mandant wird einmal während der Authentifizierung abgeleitet und auf jede Zeile angewendet,
sodass ein gebundenes Token niemals auf die Daten eines anderen Mandanten durchfallen kann.

- **Lesezugriffe** — `/api/v1/status`, `/attacks`, `/hosts`, `/bans` und `/audit` geben nur
  Zeilen zurück, deren besitzende Gruppe den Mandanten des Aufrufers trägt. `/status` wird pro
  Scope neu aufgebaut: ein gebundenes Token erhält nur seine eigenen Hostgruppen und Zähler,
  niemals die globalen geschützten Netze, die globalen Schwellenwerte oder die Konfigurationszeile
  der deployment-weiten Fallback-Gruppe — sodass ein Mandant nie die Präfixe oder die
  BGP-Aufstellung eines anderen erfährt. Ein House-Mandant (die mit einem `tenant` beschriftete
  Fallback-Gruppe) sieht weiterhin seine Catch-all-Angriffe, Bans und Hosts; nur die
  Konfigurationszeile dieser Gruppe ist verborgen. Das [Audit-Log](/docs/audit) ist serverseitig
  an den Mandanten des Aufrufers gebunden,
  und ein `target`-Filter, der eine Adresse außerhalb des Mandanten benennt, wird verweigert —
  kein mandantenübergreifendes Existenz-Orakel.
- **Mutationen** — ein gebundener Operator darf nur innerhalb seiner eigenen Präfixe
  `ban`/`unban`. Ein Ziel außerhalb des Mandanten gibt ein einheitliches `403` zurück,
  unabhängig davon, ob ein Ban existiert, sodass ein Mandant den Ban-Zustand eines anderen nicht
  ausspähen kann. Der [Source-Block-Kanal](/docs/api#der-source-block-kanal) hängt über sein
  `victim` an derselben Achse: Ein gebundenes Token darf eine Quelle nur *für seine eigenen* Opfer
  blocken, und ein Opfer außerhalb des Mandanten erhält beim Blocken wie beim Entblocken dasselbe
  einheitliche `403`. `POST /api/v1/config/reload` ist **nur für Admins** — ein Reload schreibt die
  Policy jedes Mandanten und das Token-Set selbst neu.
- **Edge-Zonen** — eine Zone in der [Zonendatei](/docs/zones) trägt ebenfalls ein optionales
  `tenant`. `GET /api/v1/edge/zones/status` gibt einem gebundenen Token nur dessen eigene Zonen
  zurück — der Hostname eines anderen Mandanten erscheint in keiner Zeile, in keiner
  Kandidatenmenge und in keiner HTTP/3-Liste, und das Feld `tenant` entfällt —, und ein gebundener
  Operator zieht den [Hebel](/docs/edge#der-hebel) nur auf seinen eigenen Zonen: Jede andere Zone,
  die eines anderen Mandanten, eine unmarkierte oder eine aus der Datei verschwundene, antwortet
  mit demselben `404 unknown zone` wie ein unbekannter Name. Die
  [Edge-Historie](/docs/api#get-apiv1edgehistory) folgt derselben Linie: Ein gebundenes Token liest
  die Historie und die aussagekräftigen Quellen seiner eigenen Zonen, jede andere Zone ist ein
  einziges einheitliches `403`, und der Filter pro Knoten sowie die Ereignisse der Flotte bleiben
  ungebunden. Die Namen der Knoten, auf denen eine Zone bedient wird, sind für ihren Mandanten
  sichtbar; das Zonendokument, die Knoten-Reports, die ACME-Koordination, das Knoteninventar und
  `config/reload` bleiben ungebunden.
- **Mehrdeutigkeit schlägt geschlossen fehl** — wenn ein einzelnes Bearer-Secret zu Tokens
  unterschiedlicher Rolle oder unterschiedlichen Mandanten passt (ein wiederverwendetes Secret),
  wird die Anfrage abgelehnt, statt auf den weiteren Scope aufgelöst zu werden.

<Callout type="warning" title="Eine Ressource ist mandantenübergreifend geteilt: die 8 Opfer-Slots einer Quelle">
Die Zugriffskontrolle läuft pro Mandant, eine Kernel-Struktur aber nicht. Ein Source-Block verankert
genau einen Kernel-Policy-Block an der **Quelle**, und dieser Block hält höchstens 8 Opfer,
unabhängig davon, wem sie gehören. Trifft derselbe Angreifer Opfer in zwei Mandanten, konkurrieren
diese Opfer um dieselben 8 Slots, und der neunte Block wird abgelehnt, welcher Mandant auch fragt.
Verschiedene geblockte Quellen ziehen zudem aus dem deployment-weiten Policy-Pool. Keine der beiden
Grenzen lässt sich pro Mandant aufteilen — das folgt aus dem Layout „ein Policy-Block pro Quelle“ —,
behandeln Sie den Source-Block-Kanal auf einem geteilten Deployment also als geteilte Ressource und
beschränken Sie seine Nutzung auf den Mandanten, der den Verkehr beobachtet hat. Siehe
[Source-Blocks](/docs/dataplane#source-blocks-aus-ihrem-eigenen-stack).
</Callout>

### Isolation überprüfen

Übergeben Sie das gebundene Token an `curl` und bestätigen Sie, dass es nur seinen eigenen
Mandanten sieht. `/api/v1/status` gibt nur die Hostgruppen dieses Mandanten zurück:

```bash
curl -H "Authorization: Bearer $KAPKAN_A" http://127.0.0.1:8080/api/v1/status
# → only customerA's hostgroups and counts; no other tenant, no global config
```

Bestätigen Sie dann, dass ein mandantenübergreifender Ban verweigert wird — das Bannen einer
Adresse außerhalb des Mandanten des Tokens gibt `403` zurück:

```bash
curl -X POST -H "Authorization: Bearer $KAPKAN_A" \
  -d '{"ip":"198.51.100.5"}' http://127.0.0.1:8080/api/v1/ban
# → 403 {"error":"target is outside your tenant"}
```

<Callout type="info" title="/metrics und das Dashboard">
`/metrics` ist nicht mandantengebunden — es bleibt für das Prometheus-Scraping offen und benötigt
kein Token, selbst wenn die API-Authentifizierung konfiguriert ist. Die
Dashboard-Shell ist geteilt (sie hält keine eigenen Daten); jeder Datenaufruf, den sie tätigt,
wird durch das eingefügte Token gefiltert, sodass das Viewer-Token eines Mandanten nur dessen
eigene Daten anzeigt.
</Callout>

<Callout type="warning" title="Eigentümerschaft folgt der aktuellen Konfiguration">
Die Sichtbarkeit eines gebundenen Tokens wird gegen die Live-Konfiguration berechnet: Das
Neuzuweisen eines Präfixes an einen Mandanten (ein nur für Admins zulässiger Reload) übergibt
dessen laufende Angriffe und Bans sofort an den **neuen** Eigentümer. Das ist beabsichtigt — die
Kontrolle folgt der aktuellen Eigentümerschaft — bedeutet aber, dass ein fehlerhafter Reload
Zeilen kurzzeitig zwischen Mandanten verschieben kann.
</Callout>

## Abwärtskompatibilität

Kein Mandant irgendwo konfiguriert = Single-Tenant-Verhalten, Byte für Byte: jede Gruppe ist
unbeschriftet, jedes Token ist ein ungebundener Admin, und die API gibt alles wie zuvor zurück.
Mandantenfähigkeit ist opt-in, und auf einer offenen (token-losen) API lässt sich keine
Isolation erreichen — es gibt kein Principal, das eingegrenzt werden könnte.
