# Autenticación

De forma predeterminada, la API y el panel de Kapkan **no requieren autenticación**. Esto solo es
seguro porque el valor predeterminado de `api.listen` se enlaza a `127.0.0.1`: el listener solo es
accesible desde el propio host, por lo que no se necesita ningún token para leer el estado, listar
ataques o emitir baneos manuales. En el momento en que enlazas el listener a una dirección enrutable,
esa protección desaparece.

<Callout type="danger" title="Configura un token antes de exponer el listener">
Si cambias `api.listen` a cualquier valor distinto de localhost —por ejemplo `0.0.0.0:8080`
o una interfaz específica—, configura primero un token. Un listener sin autenticación en una
dirección enrutable permite que cualquiera alcance la [API](/docs/api), incluidos los endpoints
de baneo y desbaneo manual.
</Callout>

## Configurar un token

La forma abreviada es un único token de operator. Añade `token_env` al bloque `api`: nombra la
variable de entorno que contiene el token; el secreto en sí se lee del entorno del proceso en cada
solicitud, nunca del archivo de configuración:

```yaml
api:
  listen: "0.0.0.0:8080"
  token_env: "KAPKAN_API_TOKEN"   # token read from this env var, never the file
```

Luego proporciona el valor fuera de banda, por ejemplo a través del entorno de tu gestor de servicios
o de un archivo de secretos:

```sh
export KAPKAN_API_TOKEN="$(openssl rand -hex 32)"
./kapkan -config /etc/kapkan/config.yaml
```

Mantener el token en una variable de entorno en lugar de en el YAML significa que la configuración
sigue siendo segura para confirmarla en git y compararla junto con el resto de tu [configuración](/docs/configuration).

Ese único token es todo lo que necesitan la mayoría de los despliegues: el resto de esta página
(roles, tenants) es opcional y puede esperar.

## Roles

Para el control de acceso basado en roles usa `tokens` en lugar de `token_env`: una lista donde cada
entrada nombra la variable de entorno que contiene su secreto y un rol:

```yaml
api:
  listen: "0.0.0.0:8080"
  tokens:
    - { name: dashboard,  token_env: "KAPKAN_API_RO", role: viewer }
    - { name: automation, token_env: "KAPKAN_API_RW", role: operator }
```

`name`, `token_env` y `role` son obligatorios en cada entrada; `role` debe ser exactamente
`viewer`, `operator` o `agent`. Un valor ausente o mal escrito es un error de validación grave al
arrancar, no un valor predeterminado silencioso.

| Rol | Qué puede hacer |
| --- | --- |
| `viewer` | Solo lectura: estado, ataques, hosts, baneos, métricas. |
| `operator` | Todo lo que puede hacer un viewer, además de baneo/desbaneo manual, [bloqueos de origen](/docs/api#el-canal-de-bloqueo-de-orígenes) y recarga de configuración (la recarga es exclusiva de admin; consulta más abajo). |
| `agent` | La credencial de un nodo — de un [nodo de scrubbing](/docs/scrubbing#nodos-de-scrubbing-gestionados) o de un [nodo edge](/docs/edge): los sondeos de reglas y de zonas, su propio reporte y la coordinación ACME del edge, y **nada más**. Vincúlalo a su nodo con `node` (más abajo). |

No hay un rol `admin` aparte que asignar: un *admin* es simplemente un token de operator sin ningún `tenant` definido. Los valores de rol que el motor acepta son `viewer`, `operator` y `agent`; la distinción admin/acotado es el eje de [Multi-tenencia](/docs/multi-tenancy), que se trata más abajo.

<Callout type="info" title="El rol agent no es un viewer de menor rango">
`agent` queda **fuera** de la escala de privilegios, por debajo de `viewer`: concede exactamente las
rutas de nodo (los sondeos de reglas y de zonas, los dos autorreportes, el turno ACME del edge y la
publicación de desafíos) y se le deniega
cualquier otro endpoint, incluido el canal de bloqueo de orígenes, que instala reglas en el kernel y
por eso queda reservado al rol operator — un token agent comprometido, que vive en una máquina remota,
no debe convertirse en una llave que lo lee todo. Tampoco puede acotarse a un tenant: el feed de
reglas es de todo el despliegue, así que un `tenant` en un token agent es un error de validación
grave. Dale a cada nodo su propio token agent, nunca uno de operator, y **vincúlalo al nodo**
(más abajo).
</Callout>

### Vincular un token de agente a su nodo

Un token agent lleva `node`: el nombre de exactamente una entrada de `edge.nodes[]` o
`scrubbing.nodes[]`. El cerebro rechaza entonces ese token en cada ruta en la que un nodo se nombra a
sí mismo — los sondeos (`?node=<name>`), los autorreportes, el turno ACME y la publicación de
desafíos — cuando el nombre presentado es el de otro nodo, y lo rechaza **antes** de hacer nada con
ese nombre: no se marca presencia, no se guarda ningún reporte, no se concede ningún turno, no se
publica ninguna autorización de clave. El rechazo es un `403` uniforme que no nombra al nodo
vinculado, un aviso por minuto y token en el log del cerebro, y un incremento en
`kapkan_api_node_binding_refused_total{route}`. No se escribe ninguna fila de
[auditoría](/docs/audit): el rastro de auditoría atribuye lo que un operador cambió, y una máquina
rechazada no cambió nada — la línea del log y el contador son donde aparece un token de nodo mal
configurado o robado. Un token vinculado que sondea sin `?node=` también se
rechaza: su vinculación ya dice qué nodo es.

```yaml
api:
  tokens:
    - { name: edge-fra1, token_env: KAPKAN_EDGE_FRA1, role: agent, node: edge-fra1 }
    - { name: edge-nyc1, token_env: KAPKAN_EDGE_NYC1, role: agent, node: edge-nyc1 }
    - { name: scrub-1,   token_env: KAPKAN_SCRUB_1,   role: agent, node: fra1 }
```

Reglas: `node` solo se permite en tokens `agent`; el nombre debe existir en exactamente una de las dos
listas de nodos (un nombre presente en ambas se rechaza por ambiguo — los dos canales son dominios de
confianza distintos); varios tokens pueden vincularse al mismo nodo, que es como se rota un token sin
dejar un hueco.

Sin `node`, un token agent es una **credencial para toda la flota**: puede sondear como cualquier nodo
y reportar como cualquier nodo — la razón por la que un token robado obligaba antes a rotarlo para
toda la flota. Lo que `node` cambia es la suplantación y el radio de rotación; lo que limita el
conjunto de zonas para las que un token vinculado robado puede emitir es el
[alcance de colocación](/docs/edge#colocar-zonas-en-los-nodos) del nodo: actuando como su propio nodo
puede tomar el turno de emisión y publicar una autorización de clave ACME solo para las zonas que ese
alcance cubre — todas las zonas en una flota sin alcances. Trata el compromiso de un nodo como una
exposición de certificado para las zonas de ese nodo, y rota el token de ese nodo. Un token sin
vincular sigue funcionando exactamente como antes, así que una flota migra nodo a nodo — salvo que
algún nodo tenga un [alcance de colocación](/docs/edge#colocar-zonas-en-los-nodos)
(`edge.nodes[].hostgroups`): entonces todo token `agent` debe llevar `node`, un error de validación
grave, porque un alcance aplicado contra un token compartido es una promesa que nadie cumple — y se
lo nombra hasta que esté vinculado: por `kapkan -check-config` (un WARNING), en el log del demonio al
arrancar y en cada recarga, y en el inventario edge (`unbound_agent_tokens`; por nodo, `tokens` lista
los nombres de los tokens vinculados y `last_token` el token que sondeó por última vez como él —
míralo cambiar durante una migración). Hacer que un token agent sin vincular sea también un error en
flotas sin alcances está previsto para una versión MAJOR.

La presencia solo la marcan los tokens agent: un operator que sondea con `?node=X` recibe el documento
de X como **vista previa** y no hace que X parezca vivo.

**Dale tiempo a un paso de migración para que se note.** Un cambio de token alcanza a un sondeo que ya
está aparcado: la recarga lo termina con la respuesta que recibiría ahora un sondeo nuevo (`401` para
un token que ya no existe, `403` para uno cuya vinculación se ha movido), y el nodo se reconecta con
lo que ahora tenga. El *inventario* es más lento, porque se marca un avistamiento cuando un sondeo
empieza y otra vez cuando termina — el rechazo incluido —, así que un nodo al que acabas de dejar
incomunicado figura como `alive` durante lo que le quede de espera (hasta 25 s) y después
`edge.stale_after_seconds` encima, unos 40 s con los valores predeterminados. Espera a que eso pase
antes de leer el cambio de `last_token`, o estarás mirando el estado anterior a tu cambio.

`token_env` y `tokens` son **mutuamente excluyentes**: `token_env` es exactamente un único token de
operator. Una solicitud se coteja con cada token configurado (en tiempo constante); se aplica el rol
coincidente más alto. Una lectura con un token de viewer funciona; una mutación con un token de viewer
se rechaza con `403 Forbidden`; una solicitud sin un token válido es `401 Unauthorized`. Una variable
de entorno vacía o sin definir nunca coincide, de modo que un secreto mal configurado falla de forma
cerrada.

Dale a cada token un secreto distinto: si un mismo valor secreto se configura para dos tokens con
roles, tenants o vinculaciones de nodo diferentes (incluidos una entrada sin vincular y otra
vinculada), la solicitud se rechaza (`401 Unauthorized`) en lugar de adivinar
cuál querías. El daemon registra `ambiguous API token` cuando esto ocurre.

El *valor* secreto de un token se lee del entorno en cada solicitud, así que rotarlo surte efecto en
la siguiente solicitud. Añadir o quitar *entradas* de token en el YAML cambia el conjunto de tokens, lo
que surte efecto en la siguiente [recarga de configuración](/docs/api). Ninguno de los dos requiere reinicio.

Un token también puede llevar un `tenant` opcional, acotándolo a los datos de un único cliente. Esa es
la función de [Multi-tenencia](/docs/multi-tenancy), superpuesta a los roles descritos aquí.

El baneo/desbaneo manual solo requiere un token de operator, pero `POST /api/v1/config/reload` es
además [exclusivo de admin](/docs/multi-tenancy): el token debe estar sin acotar (no llevar ningún
`tenant`), porque una recarga reescribe la política de cada tenant y el propio conjunto de tokens. Un
token de operator acotado a un tenant se rechaza con `403 Forbidden`: `config reload is restricted
to unscoped (admin) tokens`.

<Callout type="info" title="El nombre del token es la identidad del operator">
El `name` de cada token es lo que el [registro de auditoría](/docs/audit) anota como el `operator` de
cada baneo, desbaneo y recarga de configuración que emite, así que dales nombres significativos a los
tokens. En una API abierta (sin token) no hay ningún principal al que atribuir, y el `operator` de la
auditoría queda vacío.
</Callout>

## Qué protege

Con un token configurado, cada solicitud `/api/v1` debe incluirlo en una cabecera `Authorization`
usando el esquema de portador (bearer):

```http
GET /api/v1/status HTTP/1.1
Host: kapkan.internal:8080
Authorization: Bearer <token>
```

El token proporcionado se compara con el configurado en **tiempo constante**, de modo que la
comparación en sí no filtra el secreto a través de la temporización.

Qué permanece abierto y qué pasa a estar protegido:

| Ruta | Con autenticación configurada |
| --- | --- |
| `GET /api/v1/*` | Requiere un token de **viewer** (u operator) |
| `POST /api/v1/*` | Requiere un token de **operator** **y** un tipo de contenido JSON |
| `GET /metrics` | Abierto: el scrape de Prometheus sigue sin autenticación |
| Shell estático de la UI (`/`) | Abierto, pero los datos que hay detrás no lo están |

El shell estático de la UI del panel sigue siendo accesible para que un navegador pueda cargarlo, pero
no tiene datos propios: consulta `/api/v1`, por lo que solicita el token y lo guarda en
`sessionStorage`. `/metrics` igualmente permanece abierto para tu scraper de Prometheus. Consulta la
página del [panel](/docs/dashboard) para ver cómo la UI gestiona la solicitud del token.

## CSRF

Los endpoints POST requieren `Content-Type: application/json` además del token. Un navegador que
realiza una solicitud entre sitios no puede establecer una cabecera `Authorization` personalizada sin
un preflight de CORS, y un simple envío de formulario no puede mandar el tipo de contenido JSON. Exigir
ambos —el token en una cabecera de la solicitud y el tipo de contenido JSON— bloquea la falsificación
de solicitudes entre sitios (CSRF) contra los endpoints de baneo manual, desbaneo y recarga de
configuración.

<Callout type="info" title="Los roles y los tenants son ejes distintos">
Un rol acota lo que un token puede *hacer* (leer frente a mutar). El `tenant` opcional de un token
acota qué datos puede *ver y tocar*. Se componen: un viewer puede no estar acotado (todos los tenants)
o acotado a uno solo. Consulta [Multi-tenencia](/docs/multi-tenancy).
</Callout>
