# Referencia de CLI

Kapkan es un único binario. Lo que hace se selecciona mediante opciones de línea de comandos al
arrancar, más un pequeño número de **comandos** que inspeccionan el sistema en ejecución y
terminan. Todos los registros van a **stderr**; la API REST y las métricas de Prometheus se sirven
por HTTP en `api.listen` (predeterminado `127.0.0.1:8080`), mientras que las flags de utilidad
(`-version`, `-dump-schema`) y los comandos imprimen su salida en **stdout**.

```sh
kapkan [flags]                     # run the daemon
kapkan [flags] <command> [args]    # run a command and exit
```

Las flags globales van **antes** del comando; las flags propias del comando van después. Así,
`kapkan -config /etc/kapkan/config.yaml dataplane status -json` lee la ruta de la configuración de
la `-config` global y pasa `-json` a `dataplane status`. Una flag que ya termina por sí sola
(`-version`, `-check-config`, `-dump-schema`, `-check-update`, `-s`) no se puede combinar con un
comando: Kapkan rechaza la combinación en lugar de atender en silencio solo a una de ellas.

## Flags

| Flag | Predeterminado | Descripción |
| --- | --- | --- |
| `-config <path>` | `configs/dev.yaml` | Ruta al [archivo de configuración](/docs/configuration) YAML. |
| `-log-format <fmt>` | `json` | Formato de salida de los registros: `json` (estructurado, para recolectores de logs) o `text` (legible para humanos, para ejecuciones locales). Cualquier valor distinto de `text` se trata como `json`. |
| `-log-level <lvl>` | `info` | Nivel mínimo de registro: `debug`, `info`, `warn`, `error`. Un valor no reconocido recae en `info`. |
| `-check-config <path>` | — | Valida el archivo de configuración en `<path>` y termina; **no** inicia el demonio. Consulta [más abajo](#validar-una-configuración). |
| `-dump-schema` | `false` | Imprime el esquema JSON de la configuración en stdout y termina. Consulta [más abajo](#volcar-el-esquema). |
| `-version` | `false` | Imprime la versión de compilación y termina. La misma versión se expone en tiempo de ejecución mediante `/api/v1/status` y la [métrica](/docs/metrics) `kapkan_build_info`. |
| `-check-update` | `false` | Ejecuta la [comprobación de actualizaciones](/docs/configuration) opcional una vez y termina: `0` actualizado, `10` hay una actualización disponible, `1` ante un error. Consulta la API de Releases de GitHub; envía solo la propia solicitud, nunca la identidad del nodo ni la configuración. |
| `-pid-file <path>` | `/run/kapkan/kapkan.pid` | Dónde escribe el demonio su id de proceso al arrancar (se elimina al apagarse limpiamente); lo lee `-s` para localizar el demonio en ejecución. Un fallo de escritura no es fatal: el demonio sigue ejecutándose, solo que `-s` no está disponible. |
| `-s <signal>` | — | Envía una señal a un demonio en ejecución y termina, leyendo `-pid-file`: `reload`, `stop` o `quit`. **No** inicia un demonio. Consulta [más abajo](#controlar-un-demonio-en-ejecución). |

<Callout type="info" title="¿json o text?">
Usa `-log-format text` para el desarrollo local; es el formato que emplea la
[Guía rápida](/docs/quickstart). Mantén el valor predeterminado `json` en producción para
que un recolector de logs pueda analizar los campos estructurados; la [unidad de systemd](/docs/deployment)
se entrega con `-log-format json -log-level info`.
</Callout>

## Ejecutar el demonio

Sin ninguna flag de utilidad, Kapkan abre sus listeners de flow, la API REST y (cuando no está en
modo dry-run) el hablante BGP, y luego se ejecuta hasta que recibe `SIGINT` o `SIGTERM`, momento en
el que se apaga limpiamente. Solo termina con un código distinto de cero ante un error fatal de
arranque o de ejecución.

```sh
# Local, human-readable logs against the bundled dev config:
kapkan -config configs/dev.yaml -log-format text

# Production-style: structured logs at info level:
kapkan -config /etc/kapkan/config.yaml -log-format json -log-level info
```

El archivo de configuración se puede recargar en tiempo de ejecución sin reiniciar: ejecuta
[`kapkan -s reload`](#controlar-un-demonio-en-ejecución), envía `SIGHUP` directamente
(`systemctl reload kapkan`) o `POST /api/v1/config/reload`. Consulta la
[referencia de configuración](/docs/configuration) para saber qué se recarga y qué queda fijado al arrancar.

## Controlar un demonio en ejecución

```sh
kapkan -s reload    # re-read the config file (SIGHUP)
kapkan -s stop      # graceful shutdown (SIGTERM)
kapkan -s quit      # alias of stop
```

`-s` lee el id de proceso de `-pid-file` (predeterminado `/run/kapkan/kapkan.pid`, escrito por el
demonio al arrancar) y entrega la señal correspondiente a ese proceso: el mismo control local al
estilo nginx que `nginx -s reload`. No necesita conexión de red ni token de API, así que funciona
incluso si la API REST está caída; sí necesita permiso para enviar señales al demonio, así que
ejecútalo como `root` o como el usuario `kapkan`.

| Valor de `-s` | Señal | Efecto |
| --- | --- | --- |
| `reload` | `SIGHUP` | Recarga en caliente el archivo de configuración. Igual que `systemctl reload kapkan` o `POST /api/v1/config/reload`. |
| `stop` / `quit` | `SIGTERM` | Apagado graceful. Igual que `systemctl stop kapkan`. Los dos son alias: el apagado de Kapkan siempre es graceful (pide a los peers BGP que conserven las rutas de mitigación mediante [Graceful Restart](/docs/mitigation)). |

Si el pid file falta o está obsoleto (no existe tal proceso), o si no tienes permiso para enviarle
señales, `-s` imprime el motivo en stderr y termina con `1`.

<Callout type="info" title="Dónde vive el pid file">
La [unidad de systemd](/docs/deployment) incluida establece `RuntimeDirectory=kapkan`, de modo que
`/run/kapkan` existe y el usuario `kapkan` puede escribir en él; el demonio escribe ahí
`/run/kapkan/kapkan.pid` y lo elimina al detenerse limpiamente. En una ejecución de desarrollo local
ese directorio puede no existir: el demonio registra una advertencia y continúa, y `-s` informará de
"no pid file". Pasa `-pid-file /tmp/kapkan.pid` tanto al demonio como a `-s` si quieres el atajo en local.
</Callout>

## Flags de utilidad

Estas flags terminan antes de que arranque el demonio; nunca abren un listener ni envían un
anuncio de ruta, así que son seguras de ejecutar en un host de producción. (`-check-update` realiza
una única solicitud saliente a la API de releases; las demás son totalmente offline.)

### Validar una configuración

```sh
kapkan -check-config /etc/kapkan/config.yaml
```

Ejecuta exactamente el mismo análisis y la misma validación del motor —incluidas las reglas entre
campos que un esquema estático no puede expresar— y luego imprime la configuración resuelta (modo,
redes protegidas, los listeners de flow configurados, el recuento de grupos y la mitigación efectiva
por cada [hostgroup](/docs/hostgroups)) y termina:

| Código de salida | Significado |
| --- | --- |
| `0` | La configuración es válida. |
| `1` | La configuración no es válida; el error exacto se imprime en stderr. |

La división limpia 0/1 encaja directamente en CI o en una comprobación previa al despliegue. Consulta
[Validar la configuración](/docs/configuration#validar-la-configuración).

Una configuración válida todavía puede imprimir un bloque `WARNING` después de la línea `OK`:
configuración legal que el demonio ejecutará, pero casi con seguridad no lo que querías decir. Hoy
hay uno: una [regla estática que nunca puede
actuar](/docs/dataplane-tuning#reglas-que-nunca-pueden-actuar), nombrando la regla y qué se lleva sus
paquetes. El código de salida sigue siendo `0`, así que una comprobación existente no se ve
afectada; si quieres que los avisos también rompan la build, busca `WARNING` en la salida además del
código.

### Volcar el esquema

```sh
kapkan -dump-schema
```

Imprime el esquema JSON de la configuración en stdout y termina con `0` (o con `1` ante un error
interno). El [generador de configuración](/config) usa este esquema para validar los campos en tu navegador.

### Imprimir la versión

```sh
kapkan -version
```

Imprime la versión de compilación (la etiqueta de la release más la revisión corta de VCS cuando se
conoce) en stdout y termina. La misma cadena se sirve en tiempo de ejecución en `/api/v1/status` y
la transporta la [métrica](/docs/metrics) `kapkan_build_info`, así que puedes confirmar la versión de
un binario localmente sin ninguna salida de red.

### Comprobar actualizaciones

```sh
kapkan -check-update
```

Ejecuta la comprobación [`update_check`](/docs/configuration) una vez bajo demanda y termina: `0` si
está actualizado, `10` si hay una release más reciente disponible, `1` ante un error. Consulta la API
de Releases de GitHub y envía solo la propia solicitud (tu IP y un User-Agent genérico), nunca la
identidad del nodo, la configuración ni datos de ataques. La comprobación periódica en proceso está
**desactivada de forma predeterminada**; esta flag funciona independientemente de ese ajuste.

## Comandos

### `dataplane status`

```sh
kapkan dataplane status              # human-readable report
kapkan dataplane status -json        # the same inspection as JSON
```

Informa de si el plano de datos XDP está filtrando de verdad y, cuando no lo está, de por qué no.
Dos propiedades lo hacen utilizable durante un incidente:

- **Es estrictamente de solo lectura.** Abre en modo solo lectura el programa y los mapas fijados
  en bpffs —los descriptores de archivo de los mapas llevan `BPF_F_RDONLY`, así que es el *kernel*
  el que rechaza cualquier escritura a través de ellos— y nunca carga un programa, ni crea un mapa,
  ni escribe un valor en un mapa, ni conecta, ni desconecta, ni elimina un pin. Arrancar el demonio
  adopta o reconstruye un conjunto de pins; este comando no puede hacerlo, así que jamás puede
  costarte las reglas de mitigación que estás intentando diagnosticar.
- **Funciona con el demonio detenido.** Ese es el caso principal, no un extra: con el valor
  predeterminado `dataplane.on_exit: keep`, el kernel sigue aplicando la política estática sin
  ningún proceso de Kapkan, y este comando lee los pins directamente para decírtelo.

El informe empieza por el veredicto y el remedio, y luego da el detalle: las interfaces conectadas
con el modo realmente en vigor, las versiones del kernel y del esquema de mapas, la generación
activa, los recuentos de reglas estáticas y dinámicas, el tamaño, la ocupación y la memoria de cada
mapa, la flag de dry-run y los contadores de veredictos.

Merece la pena conocer de antemano dos cosas de esa salida:

- **El modo de conexión `GENERIC` se destaca en la primera línea.** `xdp_mode: auto` recae de la
  ruta del driver a la ruta genérica (skb) sin fallar, y eso cuesta aproximadamente un orden de
  magnitud de capacidad, así que es un titular y no un campo entre veinte.
- **Los contadores de veredictos se imprimen en dos bloques.** Los contadores *terminales* reparten
  el tráfico sin solaparse —se incrementa exactamente uno por paquete—, así que se suman en un
  total. Los contadores de *observación* se incrementan *junto* a uno terminal para el mismo
  paquete (`dryrun_would_drop`, `pass_rule_expired`, `pass_frag_noports`, `err_policy_missing`);
  añadirlos al total daría un recuento de paquetes mayor que el número de paquetes, así que se
  listan aparte y nunca se suman.

| Flag | Predeterminado | Descripción |
| --- | --- | --- |
| `-json` | `false` | Imprime la inspección completa como JSON, incluido el campo `state` del que se derivan los códigos de salida. |
| `-pin-path <dir>` | de `-config` | El directorio bpffs que se va a inspeccionar. De forma predeterminada, `dataplane.pin_path` de la configuración indicada por la `-config` global, recayendo en `/sys/fs/bpf/kapkan` cuando ese archivo no se puede leer. El informe siempre indica qué ruta miró y de dónde salió esa ruta. |

#### Códigos de salida

| Código de salida | Estado informado | Significado y qué hacer |
| --- | --- | --- |
| `0` | `enforcing` | Al menos una interfaz tiene una conexión XDP activa. Nada que hacer. |
| `10` | `no_pin_path`, `no_program`, `detached` | El plano de datos **no está filtrando**, y no hay nada roto: nunca se ha ejecutado aquí, o está detenido, o sus conexiones han desaparecido. Arranca Kapkan, o comprueba que las interfaces configuradas existen. |
| `11` | `not_bpffs`, `torn`, `schema_skew` | Hay algo que **arreglar** antes de que pueda funcionar: bpffs no está montado, el conjunto de pins está incompleto, o los mapas fijados tienen una versión de esquema distinta de la de este binario. El motivo impreso nombra la solución (montar bpffs; reiniciar Kapkan). |
| `1` | `attach_unknown`, o cualquier fallo de lectura | El comando **no ha podido responder**: casi siempre por permisos (ver más abajo). Deliberadamente no se informa como "no está filtrando", porque bien podría estar filtrando. |
| `2` | — | Error de uso: una flag o un comando desconocidos, o un argumento sobrante. |

Solo `enforcing` termina con `0`, así que `kapkan dataplane status >/dev/null` encaja directamente
en una comprobación de monitorización. La convención de usar `10` para un estado con significado es
la misma que emplea [`-check-update`](#comprobar-actualizaciones).

#### Permisos

Leer pins sale mucho más barato que crearlos: en un kernel con
`kernel.unprivileged_bpf_disabled=0` no hace falta **ninguna capability**; ni `CAP_NET_ADMIN` ni
`CAP_PERFMON`, que el demonio sí necesita para *cargar y conectar*, entran en juego. Lo que sí lo
condiciona:

- El directorio de pins tiene modo `0700` y pertenece al usuario con el que se ejecuta el demonio,
  así que en la práctica querrás `sudo kapkan dataplane status`.
- En un kernel con `kernel.unprivileged_bpf_disabled` activado —el valor predeterminado en Debian y
  Ubuntu— `bpf(2)` necesita además `CAP_BPF`, incluso para abrir un pin existente.
- **Los pins de link necesitan permiso de escritura, no solo de lectura:** el kernel rechaza
  `BPF_OBJ_GET` sobre un `bpf_link` a menos que el descriptor se abra con `O_RDWR`. Un lector sin
  privilegios de root ve, por tanto, todos los mapas y ninguna conexión, lo que se informa como
  `attach_unknown` (salida `1`) y no como "detached".

<Callout type="info" title="Nunca modifica aquello que diagnostica">
Por eso `dataplane status` es una ruta de solo lectura aparte, en vez de reutilizar el propio
código de arranque del demonio. Arrancar el plano de datos adopta un conjunto de pins existente o,
cuando el esquema no coincide, lo derriba y lo reconstruye, descartando todas las reglas de
mitigación dinámicas que hubiera en el kernel. Un diagnóstico capaz de hacer eso en mitad de un
ataque sería peor que no tener diagnóstico.
</Callout>

### `scrub`

```sh
kapkan scrub -config /etc/kapkan/scrub.yaml
```

Ejecuta el rol de [nodo de scrubbing](/docs/scrubbing#nodos-de-scrubbing-gestionados): el mismo
binario, otro trabajo. No hay detección, ni BGP, ni escucha de telemetría — la máquina recibe el
tráfico que el cerebro le desvió, hace long-poll de la tabla de reglas del cerebro y mantiene su
[plano de datos](/docs/dataplane) XDP local aplicando exactamente lo que el cerebro dice que hay que
descartar. El sondeo hace de paso las veces de señal de vitalidad del nodo.

Todo lo específico del rol vive en su propio `scrub.yaml`; el `config.yaml` del demonio **no** se
lee (`-config` aquí toma por defecto `/etc/kapkan/scrub.yaml`). Tiene tres partes: el controlador a
alcanzar, la identidad del nodo y el mismo bloque `dataplane:` que lleva un demonio.

```yaml
dry_run: true                     # the remote-role default — counts, drops nothing
controller:
  url: "https://kapkan.example.net:8443"   # the brain's API base (no path)
  token_env: KAPKAN_AGENT_TOKEN            # env var holding the agent token (required)
  name: scrub-fra1                         # must equal a scrubbing.nodes[] name on the brain
dataplane:
  interfaces: [eth0]              # the dirty side (diverted traffic arrives here)
  xdp_mode: auto
  pin_path: /sys/fs/bpf/kapkan
```

<Callout type="warning" title="Un nodo de scrubbing arranca en dry-run">
`dry_run` toma por defecto **true** para un rol remoto — el nodo instala las reglas y cuenta lo que
*descartaría*, pero no descarta nada, hasta que pongas `dry_run: false` explícitamente. Nunca aplica
una regla que el cerebro marcó como dry-run mientras está activa, y requiere un token agent real: sin
uno sus sondeos no llevan identidad y el cerebro lo contaría como muerto. Usa `https` fuera de un
laboratorio — un `controller.url` en texto plano envía el token en claro.
</Callout>

| Flag | Por defecto | Descripción |
| --- | --- | --- |
| `-config <path>` | `/etc/kapkan/scrub.yaml` | La configuración del nodo de scrubbing. |
| `-log-format <fmt>` | `json` | `json` o `text`. |
| `-log-level <lvl>` | `info` | `debug`, `info`, `warn` o `error`. |

Confirma que un nodo está en marcha con `kapkan dataplane status` en el propio nodo — informa
`ENFORCING` y el recuento de reglas instaladas — y la [vista de Nodos](/docs/dashboard) del cerebro
lo muestra vivo. Llevar el tráfico desviado hasta el nodo es la [guía de integración de red](/docs/network-integration).

### `edge`

```sh
kapkan edge -config /etc/kapkan/edge.yaml
```

Ejecuta el rol de [nodo edge](/docs/edge): el nginx o Angie de la máquina se convierte en un frontal
HTTPS gestionado para las zonas que sirve el cerebro. El rol hace long-poll del documento de zonas del
cerebro, renderiza la configuración del terminador y la instala tras pasar `nginx -t`, responde al
`auth_request` de nginx desde un servicio de decisión local, lee el access log y lo agrega por fuente,
emite y renueva los certificados de las zonas en la propia máquina, y se autoinforma. El sondeo hace
de paso las veces de señal de vitalidad del nodo. El paso a paso es la
[guía de instalación](/docs/edge-install).

Todo lo específico del rol vive en su propio `edge.yaml`; el `config.yaml` del demonio **no** se
lee (`-config` aquí toma por defecto `/etc/kapkan/edge.yaml`).

```yaml
dry_run: true                          # the remote-role default — marks, refuses nothing
controller:
  url: https://kapkan.example.net:8443 # the brain's API base (no path); https outside a lab
  token_env: KAPKAN_EDGE_TOKEN         # env var holding the agent token (required)
  name: edge-1                         # must equal an edge.nodes[] name on the brain
  report_interval_seconds: 10          # self-report cadence
state_dir: /var/lib/kapkan-edge        # document cache, generations, ACME keys and certificates
sockets_dir: /run/kapkan-edge          # edge-decide.sock, edge-challenge.sock, edge-log.sock
socket_group: nginx                    # the terminator's worker group (nginx | www-data | angie)
terminator:
  binary: nginx                        # nginx (default) | angie
  main_conf: /etc/nginx/nginx.conf     # -c for `nginx -t` and `nginx -s reload`; empty = compiled default
  reload: exec                         # exec (default) | signal | command
  pid_file: /run/nginx.pid             # liveness check; required for reload: signal
  # command: [systemctl, reload, nginx]
acme:
  directory: ""                        # default CA; empty = Let's Encrypt production
  fallback: ""                         # optional second CA after three consecutive failures
  contact: ["mailto:ops@example.net"]
  # eab:                               # External Account Binding for CAs that require one
  #   - directory: https://acme.zerossl.com/v2/DV90
  #     kid: your-kid
  #     hmac_key_env: KAPKAN_EDGE_ZEROSSL_HMAC
  # disabled: true                     # issue nothing (zones stay on :80 answering 503)
status_listen: 127.0.0.1:9102          # /healthz + /metrics; unauthenticated, keep it private
omit_catch_all: false                  # true when nginx.conf has its own default_server
disable_ipv6: false                    # true on hosts without an IPv6 stack
```

| Clave | Significado |
| --- | --- |
| `dry_run` | Ausente o `true`: las decisiones se cuentan y se marcan (`X-Kapkan-Mark: would-deny:<reason>` llega al origen), pero ninguna se aplica. Ponlo en `false` para rechazar. |
| `controller.url` / `token_env` / `name` | La base de la API del cerebro (sin ruta, sin credenciales en la URL), la variable de entorno que contiene el token **agent**, y el nombre de este nodo — debe coincidir con una entrada `edge.nodes[]` en el cerebro, o cada sondeo será un sonoro `404`. |
| `state_dir` / `sockets_dir` | Los directorios propios del rol (por defecto `/var/lib/kapkan-edge`, `/run/kapkan-edge`) — nunca los `/var/lib/kapkan` y `/run/kapkan` del cerebro, a los que systemd les cambiaría el propietario y que eliminaría bajo sus pies en un host compartido. Absolutos, sin caracteres que nginx pudiera malinterpretar. |
| `socket_group` | El grupo de los workers del terminador. Los sockets de decisión y de log son `0660` para él; el socket de challenge es `0666` (responde tokens públicos). Vacío deja los dos sockets restringidos por grupo accesibles solo para el propietario. |
| `terminator.binary` / `main_conf` | Qué ejecutar para `-t` y las recargas, y la configuración principal que pasar como `-c`. Ese archivo debe hacer `include /var/lib/kapkan-edge/conf/live/*.conf;` una sola vez, dentro de `http {}`. |
| `terminator.reload` | `exec` ejecuta `<binary> -s reload` (necesita enviar una señal al master de nginx — la unidad se ejecuta como root); `signal` envía `HUP` al pid de `pid_file`; `command` ejecuta `terminator.command`, p. ej. `[systemctl, reload, nginx]`. |
| `terminator.pid_file` | Cuando está definido, se lee en cada tick de reporte y se le envía la señal `0`: `/healthz` responde `503` y el reporte dice `alive: false` mientras ningún proceso tenga ese pid. |
| `acme.directory` / `fallback` / `contact` | La CA predeterminada del nodo (el bloque `acme` propio de una zona prevalece sobre directory y fallback), la CA de respaldo que se intenta tras tres fallos consecutivos (debe ser distinta de la primaria resuelta) y el contacto de la cuenta. |
| `acme.eab[]` | External Account Binding por URL de directorio (`directory`, `kid`, `hmac_key_env`) para las CA que lo exigen — ZeroSSL, Google Trust Services. La clave HMAC es un secreto y se lee de la variable de entorno indicada. |
| `acme.disabled` | No emitir nada: las zonas se quedan en `:80` respondiendo `503` (un laboratorio que ejercita todo salvo la emisión). Los certificados aportados por el operador aún no son una funcionalidad. |
| `status_listen` | Sirve `/healthz` y `/metrics` cuando está definido. Sin autenticación — loopback o una dirección privada. |
| `omit_catch_all` / `disable_ipv6` | Omite el `default_server` comodín de Kapkan (tu `nginx.conf` ya declara uno) / omite los listeners `[::]` (sin pila IPv6). |

<Callout type="warning" title="Un nodo edge arranca en dry-run">
`dry_run` toma por defecto **true** para un rol remoto — el nodo cuenta y marca lo que
*rechazaría*, pero no rechaza nada, hasta que pongas `dry_run: false` explícitamente. Requiere un
token agent real: sin uno sus sondeos no llevan identidad y el cerebro lo contaría como muerto. Usa
`https` fuera de un laboratorio — un `controller.url` en texto plano envía el token en claro.
</Callout>

| Flag | Por defecto | Descripción |
| --- | --- | --- |
| `-config <path>` | `/etc/kapkan/edge.yaml` | La configuración del nodo edge. |
| `-check` | desactivado | Valida el archivo y lo que nombra en esta máquina — el grupo del socket debe existir y cualquier clave EAB debe estar bien formada (problemas); un token, un binario del terminador o un `main_conf` ausentes son una advertencia — y termina. |
| `-log-format <fmt>` | `json` | `json` o `text`. |
| `-log-level <lvl>` | `info` | `debug`, `info`, `warn` o `error`. |

Confirma que un nodo está en marcha con `curl 127.0.0.1:9102/healthz` — `200` con `"converged":true`
una vez que el documento está renderizado y activo — y el inventario del cerebro
(`GET /api/v1/edge/nodes`, la vista de Nodos de la consola) lo muestra vivo. El esquema del archivo
de zonas del lado del cerebro es `kapkan -dump-zones-schema`.

### `nginx-exporter`

```sh
KAPKAN_API_TOKEN=... kapkan nginx-exporter -log /var/log/nginx/kapkan.json.log -api http://127.0.0.1:8080
```

Sigue un access log JSON de nginx, mide las tasas de peticiones por origen en cada ventana y
publica los veredictos en el
[canal de bloqueo de orígenes](/docs/api#el-canal-de-bloqueo-de-orígenes) del cerebro. El
`log_format` requerido, los umbrales y los límites operativos viven con la funcionalidad:
[el exportador de referencia](/docs/dataplane#el-exportador-de-referencia-kapkan-nginx-exporter).
Los flags globales del demonio no se leen; todos los suyos son propios:

| Flag | Por defecto | Descripción |
| --- | --- | --- |
| `-log <path>` | — (obligatorio) | El access log de nginx, en el `log_format` JSON documentado. |
| `-api <url>` | `http://127.0.0.1:8080` | La URL base de la API del cerebro. |
| `-token-env <name>` | `KAPKAN_API_TOKEN` | Variable de entorno que contiene un token de **operator**. |
| `-victim <ip>` | — | Víctima fija; prevalece sobre el campo `dst` del log. |
| `-window <dur>` | `10s` | Ventana de medición. |
| `-rps <n>` | `50` | Peticiones/segundo por origen que arman un bloqueo. |
| `-min-requests <n>` | `100` | Suelo por ventana antes de que se aplique la aritmética de tasas. |
| `-error-ratio <r>` | `0` | Exige además esta proporción de 4xx/5xx (`0` desactiva ese eje). |
| `-ttl <dur>` | `5m` | TTL del bloqueo; un origen aún caliente se refresca antes de caducar. Debe ser al menos `2×-window`. |
| `-observe` | desactivado | Registra los veredictos sin publicarlos. |
| `-log-format` / `-log-level` | `json` / `info` | El logging propio del exportador. |
