# API REST

Kapkan expone una pequeña API REST en JSON para observar la detección y accionar la mitigación manual.
Se sirve en la dirección indicada en `api.listen`, cuyo valor por defecto es `127.0.0.1:8080`. El mismo
listener también sirve el [panel](/docs/dashboard) integrado y el endpoint
[`/metrics`](/docs/metrics) de Prometheus.

La API es mayormente de lectura: el estado, los ataques activos y recientes, la instantánea de hosts
monitorizados y la tabla de baneos son todos `GET`. Tres endpoints `POST` modifican el estado: baneo manual,
desbaneo manual y recarga de configuración.

<Callout type="warning" title="Autentícala antes de exponerla">
El valor por defecto de `api.listen` enlaza con `127.0.0.1`, por lo que la API solo es segura sin autenticación en
localhost. Antes de enlazarla más allá del loopback, configura un token bearer. Consulta [Autenticación](/docs/authentication).
</Callout>

Todas las rutas `/api/v1` pasan por la comprobación del token cuando la autenticación está configurada; una vez configurada,
toda petición debe llevar `Authorization: Bearer <token>`. Los tokens llevan un **rol**: las rutas `GET`
necesitan el rol **viewer**, y las rutas que modifican el estado (`ban`, `unban`, `config/reload`)
necesitan el rol **operator**. `config/reload` va más allá: requiere un token **sin acotar (admin)**,
por lo que incluso un token operator que está acotado a un tenant se rechaza con `403`. El
[canal de nodos de scrubbing](#el-canal-de-nodos-de-scrubbing) toma el rol **agent** — la
credencial de un nodo de scrubbing que alcanza esas rutas y ninguna otra. Una lectura con un
token viewer funciona; una modificación con un token viewer devuelve `403`; un token desconocido devuelve
`401`. Los endpoints `POST` requieren además un tipo de contenido JSON: envía
`Content-Type: application/json`. Un `POST` sin esa cabecera se rechaza con
HTTP `415 Unsupported Media Type`, así que si un `ban` con `curl` falla con un 415, esa cabecera
ausente es casi siempre el motivo. Ten en cuenta que `/metrics` y el
armazón estático del panel se sirven sin token; los datos que el panel carga se obtienen
a través de la API protegida. Consulta [Autenticación](/docs/authentication) para conocer los roles de los tokens.

Un token también puede estar **acotado a un tenant**: en ese caso solo ve las filas de su tenant en cada endpoint
de lectura (`/status` se reconstruye con sus propios hostgroups y recuentos), y solo puede hacer `ban`/`unban`
dentro de su tenant — un objetivo fuera del tenant devuelve un `403` uniforme. Un token acotado a un tenant
no puede recargar la configuración en absoluto: `config/reload` está restringido a tokens sin acotar (admin) y
devuelve `403` en caso contrario. Consulta [Multi-tenencia](/docs/multi-tenancy).

## Endpoints

| Método | Ruta | Descripción |
| --- | --- | --- |
| GET | `/api/v1/status` | Modo, tiempo de actividad, redes protegidas, umbrales, hostgroups, recuento de ataques/baneos activos. |
| GET | `/api/v1/attacks` | Ataques activos más los últimos 100 que finalizaron, con muestras y clasificación. |
| GET | `/api/v1/hosts` | Instantánea de hosts monitorizados: tasas por dirección, baselines aprendidos, estado de ataque. |
| GET | `/api/v1/bans` | Todos los baneos, activos e históricos. |
| GET | `/api/v1/traffic` | Historial de tasas por host persistido (viewer); `{available:false, points:[]}` cuando el almacenamiento está desactivado. |
| GET | `/api/v1/audit` | Registro de auditoría de las modificaciones, atribuido al operador (quién baneó/recargó, cuándo, resultado). |
| POST | `/api/v1/ban` | Banear una dirección manualmente. |
| POST | `/api/v1/unban` | Retirar un baneo manualmente. |
| POST | `/api/v1/config/reload` | Releer el archivo de configuración (igual que `SIGHUP`). |
| POST | `/api/v1/dataplane/sources` | Descartar un origen en el [plano de datos](/docs/dataplane), acotado a una víctima, con un TTL obligatorio. |
| POST | `/api/v1/dataplane/sources/unblock` | Retirar de inmediato un bloqueo de origen. |
| GET | `/api/v1/dataplane/rules` | El feed de reglas del [nodo de scrubbing](/docs/scrubbing#nodos-de-scrubbing-gestionados) (`agent`/`operator` sin acotar); long-poll con ETag, retenido hasta 30 s. |
| POST | `/api/v1/dataplane/nodes/{name}/report` | El autoinforme orientativo de un nodo de scrubbing (`agent`/`operator` sin acotar). |
| GET | `/api/v1/dataplane/nodes` | Inventario de nodos gestionados: vitalidad, configuración, recuentos de baneos por nodo (`viewer` sin acotar o superior). |
| GET | `/metrics` | Métricas de Prometheus. |
| GET | `/healthz` | Sonda de vida/disponibilidad sin autenticación: `503` hasta que arranca por completo, luego `200`. |

Todas las respuestas son JSON. Los errores devuelven un objeto con la forma `{"error": "..."}` con el
estado HTTP apropiado.

### GET /api/v1/status

Devuelve el modo de operación actual y un resumen de lo que Kapkan está protegiendo. Para leerlo
(omite la cabecera `Authorization` si no hay ningún token configurado):

```sh
curl -fsS localhost:8080/api/v1/status \
  -H "Authorization: Bearer $TOKEN" | jq
```

```json
{
  "dry_run": true,
  "uptime_seconds": 8123,
  "version": "v1.2.0 · a1b2c3d",
  "update_available": false,
  "role": "operator",
  "unscoped": true,
  "networks": ["203.0.113.0/24", "198.51.100.0/24"],
  "active_attacks": 1,
  "active_bans": 1,
  "thresholds": {
    "pps": 80000,
    "mbps": 1000,
    "flows_per_sec": 20000
  },
  "hostgroups": [
    { "name": "web", "calculation": "per_host", "mitigation": "blackhole", "ban": true }
  ]
}
```

`dry_run` indica el modo global: cuando es `true`, no se anuncia ningún blackhole a tus routers.
`version` es el build en ejecución, siempre presente y sin tráfico de salida. `update_available` es `false`
salvo que el opt-in [`update_check`](/docs/configuration) esté habilitado y encuentre una versión más nueva:
entonces es `true` y `latest_version`, `latest_is_security` y `latest_url` se incluyen junto a él.
Consulta [Actualización](/docs/upgrading).
`thresholds` y `hostgroups` reflejan la configuración activa; consulta
[Detección](/docs/detection) y [Hostgroups](/docs/hostgroups) para conocer su forma completa.
`role` y `unscoped` siempre están presentes: le indican al panel qué token está
usando. Los campos `networks`, `thresholds`, `bgp`, `scrubbing` y `notify` son
configuración de todo el despliegue y solo se devuelven a un token sin acotar (admin); un
token acotado a un tenant recibe un objeto de estado sin ellos (solo `dry_run`, `version`,
`uptime_seconds`, `update_available`, `role`, `unscoped`, sus propios `hostgroups` y los recuentos). Un token admin obtiene además
objetos `bgp`, `scrubbing` y `notify`: `notify` expone únicamente qué canales están
habilitados, nunca tokens ni URLs. Así que si un campo parece "faltar", comprueba si tu token está
acotado a un tenant en lugar de asumir que Kapkan está roto.

### GET /api/v1/attacks

Devuelve los ataques actualmente activos más los últimos 100 que finalizaron (los más recientes primero). Ambos arrays
contienen objetos `Attack`.

| Campo | Tipo | Notas |
| --- | --- | --- |
| `scope` | string | `host` o `group`. Los ataques con alcance de grupo no llevan `target`. |
| `target` | string | La dirección atacada (alcance de host). |
| `group` | string | Nombre del hostgroup (alcance de grupo, o el grupo del host). |
| `tenant` | string | El tenant del grupo propietario, cuando hay uno etiquetado (consulta [Multi-tenencia](/docs/multi-tenancy)). |
| `direction` | string | `incoming` o `outgoing`. |
| `metric` | string | La métrica que se disparó, p. ej. `pps`, `mbps`, `tcp_syn_pps`. |
| `rate` | number | La tasa de la métrica que se disparó, en su unidad: la medición actual del motor mientras el ataque está activo, y la última antes de terminar después. |
| `threshold` | number | El umbral que se cruzó. |
| `rates` | object | Desglose completo de tasas por protocolo (ver más abajo), de la misma medición que `rate`. |
| `active` | bool | `true` mientras está en curso. |
| `ban_state` | string | `active`, `withdrawn` o `rejected`. Se omite cuando no hay baneo. |
| `method` | string | Método de mitigación: `blackhole`, `flowspec` o `divert`. Se omite cuando no hay baneo. |
| `route` | string | La cadena de ruta (`blackhole …` / `divert …`), o un resumen `flowspec: ...`, cuando existe un baneo. |
| `flowspec` | array | Las reglas [FlowSpec](/docs/flowspec) generadas, cuando `method` es `flowspec`. |
| `dry_run` | bool | Si el baneo fue virtual. |
| `started_at` | string | Marca de tiempo RFC 3339. |
| `ended_at` | string | Marca de tiempo RFC 3339; se omite mientras está activo. |
| `sample` | object | Muestra de flow capturada en la detección; se omite cuando el muestreo está desactivado. |
| `classification` | object | Vector de ataque inferido; se omite cuando no está clasificado. |
| `reason` | object | Por qué se disparó la detección: procedencia del umbral, calentamiento, proporciones por protocolo. Se adjunta al inicio. |

```json
{
  "active": [
    {
      "scope": "host",
      "target": "203.0.113.66",
      "group": "web",
      "direction": "incoming",
      "metric": "pps",
      "rate": 412000,
      "threshold": 80000,
      "rates": {
        "pps": 412000,
        "mbps": 3100,
        "flows_per_sec": 9800,
        "udp_pps": 405000,
        "udp_mbps": 3080
      },
      "active": true,
      "ban_state": "active",
      "route": "blackhole 203.0.113.66/32 next-hop 192.0.2.1 community 65000:666",
      "dry_run": false,
      "started_at": "2026-06-13T09:41:07Z",
      "sample": {
        "top_sources": [
          { "key": "198.51.100.23", "packets": 1240000, "bytes": 1612000000 }
        ],
        "top_src_ports": [
          { "key": "123", "packets": 1180000, "bytes": 1534000000 }
        ],
        "top_dst_ports": [
          { "key": "443", "packets": 1240000, "bytes": 1612000000 }
        ],
        "protocols": [
          { "key": "udp", "packets": 1240000, "bytes": 1612000000 }
        ],
        "total_packets": 1240000
      },
      "classification": {
        "type": "ntp_amplification",
        "confidence": 0.95,
        "src_port": 123
      }
    }
  ],
  "recent": []
}
```

Mientras un ataque está activo, `rate` y `rates` se releen del motor en cada solicitud, de
modo que siguen al ataque en lugar de informar el instante de su detección — cuando la
ventana deslizante contenía un solo segundo y subestimaba una inundación sostenida por un
factor de varias veces. `metric` y `threshold` se mantienen tal como se capturaron en la
detección: nombran lo que se disparó, y el motor juzga el final del ataque contra los
umbrales congelados en su inicio.

El objeto `rates` lleva el trío base (`pps`, `mbps`, `flows_per_sec`) más los
campos por protocolo que sean distintos de cero: `tcp_pps`, `tcp_mbps`, `udp_pps`, `udp_mbps`,
`icmp_pps`, `icmp_mbps`, `tcp_syn_pps`, `tcp_syn_mbps`, `frag_pps`, `frag_mbps`. El
objeto `sample` resume los flows almacenados en buffer detrás de la detección: `top_sources`,
`top_src_ports`, `top_dst_ports`, `protocols` (cada uno una lista de contadores `{key, packets, bytes}`),
una lista opcional de `flows` en bruto, y `total_packets`. El `type` de la
`classification` es uno de los vectores documentados en [Detección](/docs/detection); `confidence`
es la proporción (`0..1`) del tráfico de ataque que coincide con la firma ganadora, y `src_port`
es el puerto del servicio reflejado para los vectores de amplificación.

El objeto `reason` explica **por qué** se disparó la detección: se captura una vez al inicio, fuera
de la ruta crítica. `threshold_source` es `static` o `baseline`: si el límite cruzado provino
de la configuración estática o de un [baseline aprendido](/docs/baselines) ya calentado. Cuando es
`baseline`, un objeto `baseline` lleva el cálculo efectivo
(`min(ceiling, max(floor, normal × factor))`). `baseline_configured`, `warming_up` y
`warmup_remaining_seconds` explican un umbral estático que se aplicó solo porque el baseline
aún no se había calentado. `shares` es la fracción por protocolo del total de PPS que impulsó
la clasificación, y `dominant_share_gate` es la proporción que un protocolo necesita para ganar un vector
(en caso contrario el ataque es `mixed`). Consulta [Detección](/docs/detection) para
saber cómo leerlo.

```json
{
  "reason": {
    "threshold_source": "baseline",
    "baseline": { "normal": 1200, "factor": 8, "floor": 5000, "ceiling": 80000 },
    "baseline_configured": true,
    "shares": { "udp": 0.98, "syn": 0, "tcp": 0.01, "icmp": 0, "frag": 0 },
    "dominant_share_gate": 0.5
  }
}
```

### GET /api/v1/hosts

Devuelve una instantánea de cada host monitorizado: los datos de los top-talkers. Cada entrada es un `HostStat`.

| Campo | Tipo | Notas |
| --- | --- | --- |
| `target` | string | La dirección del host. |
| `group` | string | El nombre del hostgroup del host. |
| `rates` | object | Tasas entrantes actuales por ventana. |
| `rates_out` | object | Tasas salientes; solo distintas de cero cuando la detección de salida está activa. |
| `in_attack` | bool | Si el host está en algún ataque activo. |
| `metric` | string | La métrica del ataque activo; se omite cuando no está en ataque. |
| `direction` | string | La dirección del ataque activo; se omite cuando no está en ataque. |
| `baseline` | object | Baseline entrante aprendido; presente cuando hay baselines configurados. |
| `baseline_out` | object | Baseline saliente aprendido; presente cuando hay baselines configurados. |

```json
{
  "hosts": [
    {
      "target": "203.0.113.66",
      "group": "web",
      "rates": {
        "pps": 412000,
        "mbps": 3100,
        "flows_per_sec": 9800,
        "udp_pps": 405000
      },
      "rates_out": {
        "pps": 120,
        "mbps": 2
      },
      "in_attack": true,
      "metric": "pps",
      "direction": "incoming",
      "baseline": {
        "pps": 950,
        "mbps": 7,
        "flows_per_sec": 60
      },
      "baseline_out": {
        "pps": 110,
        "mbps": 2,
        "flows_per_sec": 14
      }
    }
  ]
}
```

Los objetos `baseline` y `baseline_out` llevan el trío base de normalidad aprendida (`pps`,
`mbps`, `flows_per_sec`) y aparecen solo mientras hay baselines EWMA configurados para el grupo del
host. Consulta [Baselines](/docs/baselines).

### GET /api/v1/bans

Devuelve la tabla completa de baneos: activos e históricos. Cada entrada es un `Ban`.

| Campo | Tipo | Notas |
| --- | --- | --- |
| `target` | string | La dirección baneada. |
| `prefix` | string | El prefijo blackhole (`/32` o `/128`). |
| `metric` | string | La métrica que disparó el baneo; se omite en baneos manuales. |
| `rate` | number | Tasa observada en el momento del baneo; se omite cuando es cero. |
| `threshold` | number | Umbral cruzado; se omite cuando es cero. |
| `next_hop` | string | El next-hop de descarte. |
| `community` | string | El conjunto de communities adjunto a la ruta — la community RTBH para un blackhole, la community de desvío (scrubbing) para un baneo de desvío — unidas por espacios cuando hay más de una. |
| `local_pref` | number | El `LOCAL_PREF` adjunto a la ruta; se omite cuando es cero. |
| `node` | string | El [nodo de scrubbing gestionado](/docs/scrubbing#nodos-de-scrubbing-gestionados) al que este baneo de divert queda congelado; se omite cuando el baneo no desvía a un nodo gestionado. |
| `route` | string | La cadena de ruta completa, o un resumen `flowspec: ...` para baneos FlowSpec. |
| `state` | string | `active`, `withdrawn` o `rejected`. |
| `dry_run` | bool | Si el baneo fue virtual. |
| `manual` | bool | `true` para baneos solicitados por el operador. |
| `started_at` | string | Marca de tiempo RFC 3339. |
| `expires_at` | string | Expiración del TTL; los baneos nunca son permanentes. |
| `withdrawn_at` | string | Cuándo se retiró la ruta; se omite mientras está activo. |
| `reason` | string | Por qué se rechazó o retiró un baneo; se omite en otro caso. |
| `method` | string | Método de mitigación: `blackhole`, `flowspec` o `divert`. |
| `flowspec` | array | Las reglas [FlowSpec](/docs/flowspec) generadas, cuando `method` es `flowspec`. |
| `escalation` | array | La [escalera de escalado](/docs/escalation) configurada, cuando hay una establecida. |
| `escalation_step` | number | Índice del peldaño actual de la escalera. |

```json
{
  "bans": [
    {
      "target": "203.0.113.66",
      "prefix": "203.0.113.66/32",
      "metric": "pps",
      "rate": 412000,
      "threshold": 80000,
      "next_hop": "192.0.2.1",
      "community": "65000:666",
      "route": "blackhole 203.0.113.66/32 next-hop 192.0.2.1 community 65000:666",
      "state": "active",
      "dry_run": false,
      "manual": false,
      "started_at": "2026-06-13T09:41:07Z",
      "expires_at": "2026-06-13T10:41:07Z"
    }
  ]
}
```

Consulta [Mitigación](/docs/mitigation) para ver cómo el TTL, la histéresis y el límite de baneos dan forma a este
ciclo de vida.

### GET /api/v1/audit

Devuelve el registro de auditoría atribuido al operador: quién emitió cada `ban`, `unban` o
`config_reload`, cuándo, y el resultado (incluidas las acciones **rechazadas**). Los registros van
de más reciente a más antiguo y el endpoint está acotado al tenant en el servidor. Acepta los parámetros de
consulta opcionales `from`/`to` (RFC 3339), `action`
(`ban`/`unban`/`config_reload`/`source_block`/`source_unblock`) y `target` (una IP), y
por defecto devuelve la última hora:

```json
{
  "available": true,
  "events": [
    {
      "event_time": "2026-06-22 03:14:09",
      "action": "ban",
      "result": "rejected",
      "operator": "alice",
      "role": "operator",
      "tenant": "customerA",
      "target": "203.0.113.66",
      "target_type": "host",
      "reason": "whitelisted",
      "source": "api",
      "ban_state": "rejected",
      "dry_run": 0
    }
  ]
}
```

Cuando el almacenamiento está desactivado, la respuesta es `{"available": false, "events": []}`. Ten en cuenta que
los registros de auditoría codifican `dry_run` como un entero (`0`/`1`), no como el booleano JSON usado en el resto
de esta página. Consulta la página dedicada de [Registro de auditoría](/docs/audit) para conocer la lista completa de
campos, las reglas de consulta y el modelo de identidad del operador y de acotamiento por tenant.

### POST /api/v1/ban

Aplica un blackhole a una dirección manualmente. El cuerpo es una sola IP:

```http
POST /api/v1/ban
Content-Type: application/json

{"ip": "203.0.113.66"}
```

Como comando ejecutable (omite la cabecera `Authorization` si aún no has configurado un token):

```sh
curl -fsS -X POST localhost:8080/api/v1/ban \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"ip":"203.0.113.66"}'
```

La respuesta es el objeto `Ban` resultante. Un baneo manual respeta todas las reglas de seguridad que respeta un
baneo automático:

- Un objetivo en la **lista blanca** se rechaza con HTTP `409 Conflict` y `reason: "whitelisted"`; nunca se anuncia.
- Un objetivo **fuera de las `networks` configuradas** se rechaza con HTTP `409` y `reason: "outside configured networks"`.
- Una petición que excedería **`max_active_bans`** se rechaza con HTTP `409` y `reason: "max_active_bans reached"`.

En cada caso de `409`, el cuerpo sigue siendo un objeto `Ban` con `state: "rejected"` y el
campo `reason` establecido. Una IP no válida o no analizable devuelve HTTP `400`.

<Callout type="warning" title="El dry-run sigue aplicándose">
Un baneo manual respeta el modo global. Mientras `dry_run` es `true`, el baneo se registra y
se devuelve con `dry_run: true` pero no se anuncia ninguna ruta. Consulta el [modelo de seguridad](/docs/safety).
</Callout>

### POST /api/v1/unban

Retira un baneo activo para la dirección dada. El cuerpo tiene la misma forma `{"ip": "..."}`
y se requiere el mismo tipo de contenido JSON:

```http
POST /api/v1/unban
Content-Type: application/json

{"ip": "203.0.113.66"}
```

Si tiene éxito, devuelve el `Ban` retirado. Si no hay un baneo activo para la dirección,
devuelve HTTP `404`.

### POST /api/v1/config/reload

Relee el archivo de configuración desde disco y lo aplica: el mismo efecto que enviar `SIGHUP`.
El cuerpo está vacío; el tipo de contenido JSON sigue siendo obligatorio. A diferencia de `ban`/`unban`, este
endpoint requiere un token **sin acotar (admin)**: una recarga intercambia toda la configuración, por lo que un
token acotado a un tenant se rechaza con `403` y `config reload is restricted to unscoped
(admin) tokens`.

```json
{
  "reloaded": true,
  "dry_run": false,
  "thresholds": {
    "pps": 80000,
    "mbps": 1000,
    "flows_per_sec": 20000
  }
}
```

Si la nueva configuración no se analiza o no se valida, la configuración en ejecución se mantiene intacta y el
endpoint devuelve HTTP `400` con el error. Consulta [Configuración](/docs/configuration).

### El canal de bloqueo de orígenes

Dos endpoints permiten que quien ya termina el tráfico de una víctima — un nginx delante, un
exportador de logs, un operador a las 3 de la mañana — entregue a Kapkan un **origen** para descartar
en el [plano de datos XDP](/docs/dataplane), acotado a esa víctima y con un TTL obligatorio. La
decisión se toma donde las peticiones son visibles; la aplicación ocurre en el kernel. Ambos exigen un
token `operator`; al rol `agent` se le deniega.

```sh
curl -fsS -X POST localhost:8080/api/v1/dataplane/sources \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"victim":"203.0.113.10","source":"198.51.100.7","ttl_seconds":600,"reason":"login flood"}'
```

| Campo | Obligatorio | Significado |
| --- | --- | --- |
| `victim` | sí | El destino protegido al que se acota el bloqueo. Es contra lo que se comprueba un token de tenant, y lo que evita que la evidencia de quien llama se convierta en un descarte global. |
| `source` | sí | La dirección a descartar. Debe ser de la misma familia de direcciones que `victim`. |
| `ttl_seconds` | sí para un bloqueo | Cuánto vive el bloqueo, de `1` a `86400` (24 h). No hay entradas permanentes. Bloquear de nuevo el mismo par conserva el `created_at` original y aplica el nuevo TTL: el refresco que necesita un exportador para mantener a un infractor persistente sin el vaivén de desbloquear y volver a bloquear. |
| `reason` | no | Una nota libre que se lleva al [rastro de auditoría](/docs/audit). |

La respuesta es el `SourceBlock` resultante:

```json
{
  "source": "198.51.100.7",
  "victim": "203.0.113.10",
  "created_at": "2026-08-17T21:04:11Z",
  "expires_at": "2026-08-17T21:14:11Z",
  "dry_run": false,
  "reason": "login flood"
}
```

`POST /api/v1/dataplane/sources/unblock` toma los mismos `victim` y `source` (cualquier `ttl_seconds`
se ignora) y retira de inmediato ese único par, para que nadie tenga que esperar un TTL que él mismo
escribió. Devuelve el `SourceBlock` retirado, o `404` si no hay un par así vivo.

#### Rechazos

Un error de entrada es `400`; una solicitud bien formada rechazada por política es `409`. Cada
llamada — incluido un rechazo — escribe un evento de auditoría atribuido, porque un bloqueo rechazado
es en sí una acción de operador.

| Estado | Causa |
| --- | --- |
| `400` | JSON o dirección no parseable, `victim` y `source` de familias de direcciones distintas, o `ttl_seconds` fuera de `[1, 86400]`. |
| `403` | `victim` está fuera de tu tenant. El mismo rechazo uniforme que dan los endpoints de baneo, para que este endpoint no sea un oráculo de existencia de los hosts de otros tenants. |
| `404` | Solo al desbloquear: no hay un bloqueo vivo para ese par. |
| `409` | El plano de datos está ausente o deshabilitado; `victim` está en `protected_whitelist`; `source` está en `dataplane.allowlist`; `source` está dentro de las `networks` protegidas; este origen ya tiene 8 víctimas; o no quedan huecos de política. |

Los dos rechazos por listas de permitidos son los interesantes, y son rechazos precisamente porque la
alternativa es el silencio: el plano de datos deja pasar un origen permitido en la precedencia 1 y el
tráfico a un destino protegido en la precedencia 2, ambos **antes** de evaluar una sola regla, así que
ese bloqueo se instalaría y luego nunca coincidiría con un paquete. Un `source` dentro de tus propias
`networks` también se rechaza: un host interno es un [baneo](/docs/mitigation), no un bloqueo de
origen.

<Callout type="warning" title="Un fallo de instalación retira todos los pares de ese origen">
Los pares de un origen comparten un único bloque de política del kernel, y el rollback del instalador
es todo-o-nada sobre ese bloque. Si una instalación falla, todos los pares de ese origen se retiran en
lugar de quedar registrados-pero-sin-aplicar, y el error lo dice: vuelve a añadir los que aún
necesites. La tabla nunca afirma estar aplicando algo que el kernel no aplica.
</Callout>

<Callout type="info" title="Las mismas garantías que un baneo">
Los TTL son obligatorios y acotados, cada par lleva su propia caducidad al kernel (así que deja de
aplicarse a su hora incluso si Kapkan muere), las instalaciones se contabilizan contra
`dataplane.limits.max_dynamic_rules`, los bloqueos sobreviven a un reinicio mediante el archivo de
estado, y se respeta `dry_run`: el par se registra, se devuelve con `dry_run: true`, y nada llega a un
mapa del kernel. Consulta
[Bloqueos de origen](/docs/dataplane#bloqueos-de-origen-desde-tu-propio-stack) para los límites y el
[Modelo de seguridad](/docs/safety).
</Callout>

### El canal de nodos de scrubbing

Estos tres endpoints existen para los [nodos de scrubbing gestionados](/docs/scrubbing#nodos-de-scrubbing-gestionados)
— máquinas que ejecutan [`kapkan scrub`](/docs/cli). Toman el rol `agent` (la credencial de un
nodo de scrubbing; ver [autenticación](/docs/authentication)) o un token `operator` sin acotar,
nunca un `viewer` ni un token acotado a un tenant: los documentos abarcan todos los tenants, así
que acotarlos es una cuestión de flota, no de cada petición.

#### GET /api/v1/dataplane/rules

La tabla de reglas que aplica un nodo: cada víctima [desviada](/docs/scrubbing) activa, con las
reglas [FlowSpec](/docs/flowspec) que descartar y el TTL que reflejar. Un `GET` simple devuelve el
documento actual con un `ETag` de hash de contenido; un `GET` cuyo `If-None-Match` nombra ese ETag
se **retiene** hasta que la tabla cambie o hasta 30 s, y luego se responde `304` — un long-poll que
ofrece actualizaciones de reglas por debajo del segundo sobre HTTP corriente. Un nodo se identifica
con `?node=<name>`, y **ese sondeo es la señal de vitalidad del nodo** — así que el nombre debe ser
un nodo configurado (un nombre desconocido es `404`) y, fuera del modo local sin token, la petición
debe llevar un token real.

```json
{
  "version": 1,
  "bans": [
    {
      "target": "203.0.113.10",
      "prefix": "203.0.113.10/32",
      "method": "divert",
      "expires_at": "2026-08-13T10:00:00Z",
      "flowspec": [ { "dst": "203.0.113.10/32", "proto": 17, "action": "discard" } ]
    }
  ]
}
```

#### POST /api/v1/dataplane/nodes/\{name\}/report

El autoinforme orientativo de un nodo — versión, modo XDP, dry-run del lado del nodo, carga y
totales de descartes — almacenado para la [consola](/docs/dashboard). **Nunca** es una señal de
vitalidad (el sondeo lo es): un reporte nunca puede mantener a un nodo muerto marcado como vivo. El
cuerpo está limitado a 64 KiB (`413` si se supera) y un `{name}` desconocido es `404`. El éxito es
`204 No Content`.

#### GET /api/v1/dataplane/nodes

El inventario de nodos que representa la vista de Nodos de la consola: cada nodo configurado con lo
que el cerebro sabe (configuración, vitalidad del sondeo, cuántos baneos desvían hacia él) unido con
su último reporte. Una lectura de rango `viewer`, pero solo tokens sin acotar — el inventario nombra
next-hops y hostgroups, que es topología de despliegue. El recuento por sí solo (`nodes_total`) viaja
en `/api/v1/status` para todos los roles, así que una consola puede decidir si mostrar las
funcionalidades de nodos sin esta llamada.

### El canal edge

Estos endpoints existen para los [nodos edge](/docs/edge) — máquinas que ejecutan
[`kapkan edge`](/docs/cli#edge). Como el canal de nodos de scrubbing, toman el rol `agent` o un
token `operator` sin acotar, nunca un `viewer` ni un token acotado a un tenant: el documento de zonas
abarca todos los tenants. **El cerebro distribuye política, nunca veredictos** — no existe ninguna
llamada por petición, ni aquí ni en ningún otro sitio; un nodo responde a las peticiones por sí solo.

#### GET /api/v1/edge/zones

El documento de zonas que un nodo renderiza y aplica: cada zona del [archivo de zonas](/docs/zones)
con sus orígenes, su versión mínima de TLS, sus directorios ACME y su política, más las concesiones
de emisión vivas y los challenges ACME propagados. Un `GET` simple devuelve el documento con un
`ETag` de hash de contenido; un `GET` cuyo `If-None-Match` nombra ese ETag se **retiene** hasta que
el documento cambie — una recarga exitosa del archivo de zonas, un challenge de certificado publicado
por un nodo — o hasta 25 s, y luego se responde `304`. Un nodo se identifica con `?node=<name>`, y
**ese sondeo es la señal de vitalidad del nodo**, así que el nombre debe ser una entrada
`edge.nodes[]` configurada (un nombre desconocido es `404`) y la petición debe llevar un token real.

```json
{
  "version": 1,
  "zones": [
    {
      "name": "shop.example.com",
      "origins": ["10.0.0.10:8080"],
      "tls": { "min_version": "1.2" },
      "acme_directory": "",
      "policy": { "mode": "decide", "failure_mode": "open", "challenge": "off", "rate": { "rps": 50, "concurrency": 20 } }
    }
  ],
  "acme_challenges": [],
  "issuance_grants": []
}
```

#### POST /api/v1/edge/nodes/\{name\}/report

El autoinforme orientativo de un nodo — versión, dry-run del lado del nodo, el ETag del documento
que ha **renderizado** (para que un operador pueda ver un nodo rezagado o que se niega), el tipo, la
versión y la vitalidad del terminador, la generación activa y su resultado de `nginx -t`, y los
certificados que posee (solo metadatos públicos, nunca una clave; una lista larga se recorta al
límite de 64 KiB del cuerpo con un recuento `certs_truncated`) — almacenado para la
[consola](/docs/dashboard). Nunca es una señal de vitalidad (el sondeo lo es). Un `{name}`
desconocido es `404`; el éxito es `204 No Content`.

#### GET /api/v1/edge/nodes

El inventario de nodos: cada nodo edge configurado con la vitalidad de su sondeo unida a su último
reporte. Una lectura de rango `viewer`, solo tokens sin acotar.

#### POST /api/v1/edge/nodes/\{name\}/acme/slot y …/acme/challenges

El **coordinador de emisión**, orientativo y en memoria. Un nodo pide un hueco por zona antes de
solicitar un certificado (`{"zone": "…"}` → `{"granted": true, "expires_at": …}` o
`{"granted": false, "holder": "…", "retry_after_seconds": …}`; `{"release": true}` lo devuelve), para
que una flota no agote en una tarde el límite de certificados duplicados de una CA; espera como
máximo 15 minutos y luego lo solicita de todos modos. Un nodo que posee el hueco publica su challenge
HTTP-01 pendiente (`{"zone", "token", "key_authorization"}`) y el cerebro lo propaga en el documento
de zonas durante diez minutos para que todos los nodos lo respondan — la validación de la CA puede
caer en cualquier nodo detrás de una dirección compartida. Un challenge vivo nunca se sobrescribe con
una autorización de clave distinta (`409`), un nodo puede tener 16 challenges vivos, y cada llamada
se registra con el nodo, la zona y el prefijo del token: un token agent es una credencial que emite
certificados; rótalo ante cualquier compromiso de un nodo.

### GET /metrics

Sirve las métricas de Prometheus en el formato de exposición de texto estándar. Este endpoint no está
bajo `/api/v1` y se sirve sin el token bearer para que un scraper pueda alcanzarlo. Consulta
[Métricas](/docs/metrics) para conocer la lista completa de métricas.

### GET /healthz

Una sonda de vida/disponibilidad, no bajo `/api/v1` y servida **sin** un token bearer (no
filtra nada) para que un supervisor o el script de actualización [`update.sh`](/docs/upgrading) puedan
confirmar que el daemon está activo tras un reinicio. Devuelve `503 starting` hasta que cada componente
ha arrancado, luego `200 ok`. Como el listener de la API solo empieza a aceptar peticiones una vez que el daemon
ha arrancado, cualquier `200` aquí significa que la configuración se analizó, los componentes están activos y Kapkan está
sirviendo.

```sh
curl -fsS localhost:8080/healthz   # exits non-zero (503) until ready, then prints "ok"
```
